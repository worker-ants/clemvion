이 페이지에서는 외부 서비스와의 통합(Integration, 연동)을 중앙에서 관리하는 방법을 설명해요. HTTP Request나 Send Email 같은 노드가 여기서 만든 연동을 재사용해요.

## 통합이란

통합은 외부 서비스에 접근하기 위한 자격 증명 묶음이에요. 한 번 만들어 두면 여러 워크플로우의 여러 노드가 같은 계정·키를 공유해서 쓸 수 있고, 키 회전이나 재인증도 한 곳에서 끝낼 수 있어요.

## 팀 워크스페이스에서 공유 사용

팀 워크스페이스에 Organization 범위로 만든 통합은 그 워크스페이스의 모든 멤버가 자동으로 함께 사용할 수 있어요. 반면 같은 팀 워크스페이스라도 Personal 범위로 만든 통합은 만든 사람에게만 보여요 — 다른 멤버는 목록에서도, 상세 페이지 주소로 직접 이동해도 찾을 수 없고, 이 규칙은 역할과 무관해서 Owner·Admin 도 다른 멤버의 Personal 통합을 볼 수 없어요. 사용자가 사이드바에서 워크스페이스를 전환하면 통합 목록도 해당 워크스페이스 기준으로 갱신돼요.

노드에서 쓸 수 있는 통합도 범위에 따라 갈려요.

- **Organization 통합**: 워크스페이스의 어느 워크플로우 노드에서나 쓸 수 있어요.
- **Personal 통합**: 그 통합을 만든 사람이 직접 만든 워크플로우의 노드에서만 쓸 수 있어요. 통합을 만든 사람이라도 다른 멤버가 만든 워크플로우에서는 쓸 수 없어요.

판정 기준은 실행을 시작한 사람이 아니라 **워크플로우를 만든 사람**이에요. 그래서 스케줄·웹훅으로 자동 실행될 때와 서브 워크플로우로 실행될 때도 같은 규칙을 따라요. 서브 워크플로우는 그 워크플로우를 만든 사람을 기준으로 해요. 통합 선택을 표현식(`{{ }}`)으로 정했을 때도 Personal 통합은 쓸 수 없고 Organization 통합만 쓸 수 있어요.

규칙에 맞지 않는 Personal 통합을 쓰는 노드는 실행할 때 존재하지 않는 통합을 참조했을 때와 똑같은 "통합을 찾을 수 없음" 오류로 실행이 실패해요. 오류만 봐서는 없는 통합인지 쓸 수 없는 통합인지 구분되지 않아요. AI Agent 노드의 MCP 서버 항목은 해당 서버만 건너뛰고 노드는 계속 실행돼요.

권한 정책은 다음과 같아요.

동작별로 보면 다음과 같아요. Personal 통합은 어떤 동작이든 만든 사람만 할 수 있고, 표의 역할은 그 사람에게 필요한 최소 역할이에요.

| 동작 | Personal 통합 | Organization 통합 |
| --- | --- | --- |
| 조회(목록·상세·사용처·활동) | 모든 역할 | 모든 멤버 |
| 저장된 통합의 `Test connection` | 모든 역할 | 모든 멤버 |
| 새 통합 추가 | Editor 이상 | Admin 이상 |
| 별칭 수정 · 재인증 · 자격 증명 교체 · scope 추가 요청 | Editor 이상 | Admin 이상 |
| Personal ↔ Organization 범위 전환 | Admin 이상 | Admin 이상 |
| 삭제 | 모든 역할 | Admin 이상 |

화면과 서버가 같은 규칙으로 막아요. 할 수 없는 동작의 버튼과 입력 영역은 화면에 보이지 않아서, 눌렀다가 거절당하는 일이 없어요.

<Callout type="tip">개인 워크스페이스의 통합은 본인만 보고 사용할 수 있어요. 팀과 공유하려면 팀 워크스페이스에서 새로 만들어요. 같은 외부 계정도 워크스페이스마다 별개의 통합 레코드를 포함해요.</Callout>

### 멤버가 나가거나 제거될 때

멤버가 워크스페이스를 나가거나 관리자가 멤버를 제거하면 그 멤버가 이 워크스페이스에 추가한 Personal 통합이 모두 함께 삭제돼요.

- **상태와 사용 여부를 가리지 않아요.** 연결됨 · 설치 대기 · 만료 · 오류 어느 상태든 삭제해요. 워크플로우 노드가 쓰고 있어도 삭제해요. 평소의 통합 삭제는 사용처가 있으면 막히지만 이 경우는 막히지 않아요.
- **남는 통합이 있어요.** 그 멤버가 만든 Organization 통합과 다른 멤버의 Personal 통합은 그대로 남아요.
- **감사 로그에 남아요.** 삭제된 통합마다 통합 삭제 기록이 감사 로그에 남아요.
- **노드는 실행이 실패해요.** 삭제된 Personal 통합을 쓰던 워크플로우 노드는 다른 통합을 고르기 전까지 실행이 실패해요.
- **아무것도 삭제되지 않는 경우도 있어요.** 유일한 Owner 는 나갈 수 없고 Owner 는 제거할 수 없어서 그때는 아무것도 삭제되지 않아요.

같은 사람이 다시 초대받아 들어와도 삭제된 통합은 돌아오지 않아요. 나가기와 멤버 제거 화면은 [워크스페이스와 멤버](/docs/07-workspace-and-team/workspaces-and-members)에서 확인해요.

### Organization 통합을 Personal 로 바꿀 때

통합 상세의 Danger zone 탭에서 Organization 통합을 Personal 로 바꾸면, 그 통합을 만든 사람이 아닌 사람이 만든 워크플로우는 이 통합을 노드에서 쓸 수 없게 돼요. 그래서 바꾸기 전에 이 통합의 사용처를 먼저 확인해요.

- 그런 워크플로우가 있으면 "개인으로 바꾸면 실행이 실패하는 워크플로우가 있어요" 경고 대화상자가 떠요. 해당 워크플로우와 노드 목록이 함께 나오고, `개인으로 바꾸기` 를 누르면 그대로 전환돼요. 전환을 막지는 않아요.
- 그런 워크플로우가 없으면 "개인으로 바꾸면 이 통합을 만든 사람만 이 통합을 보고 쓸 수 있어요. 계속할까요?" 라는 확인 창만 떠요.
- 사용처를 확인하지 못하면 범위를 바꾸지 않고 "사용처를 확인하지 못해 공개 범위를 바꾸지 않았어요" 오류 토스트가 떠요.

## 연동 추가하기

[통합 관리](/integrations) 목록의 우측 상단에서 `[+ Add Integration]` 을 눌러요. 추가 플로우는 목록 모달에서 서비스를 고르고, 인증 단계부터 전용 페이지(`/integrations/new?service=...&step=auth`)로 전환돼요.

통합 추가는 Editor 이상만 할 수 있어요. Viewer 에게는 `[+ Add Integration]` 버튼이 보이지 않고, 목록에서 `N` 키를 눌러도 서비스 선택 창이 열리지 않아요. Viewer 가 추가 화면 주소로 바로 들어오면 추가 화면 대신 "통합 추가는 편집자 이상만 할 수 있어요." 안내와 목록으로 돌아가는 링크만 보여요.

### 설치 기한이 지난 설치 대기 통합

Cafe24 Private 과 MakeShop 의 설치 대기 통합은 설치 토큰을 발급하고 24시간 안에 설치를 마치지 않으면 상태가 만료(설치 기한 초과)로 바뀌어요. 이때 통합이 쥐고 있던 상점 식별자(Cafe24 mall ID · MakeShop 상점) 자리도 놓아요.

- **같은 상점을 다시 등록할 수 있어요.** 만료된 통합을 지우지 않아도 같은 상점을 새로 등록할 수 있어요. 만료된 통합은 저절로 지워지지 않고 주의 필요 대상으로 남아요. 필요 없으면 직접 삭제해요.
- **옛 App URL(설치 링크)은 쓸 수 없어요.** 만료된 통합의 App URL 을 열면 유효하지 않은 설치 링크라는 오류가 나요.
- **통합 이름은 그대로예요.** 만료된 통합과 같은 이름으로 다시 등록하면 통합 추가 화면의 이름 칸 아래에 "같은 이름의 통합이 이미 있어요. 다른 이름을 입력해 주세요." 오류가 보이고 같은 문구의 토스트도 떠요. 이름을 고치면 이름 칸 오류가 사라져요. Cafe24 Private 은 기본 이름이 mall ID 로 만들어져서 이런 일이 흔해요.
- **설치 기한 초과가 아닌 만료·오류는 예외예요.** 토큰 만료처럼 다른 이유로 만료되거나 오류가 난 같은 상점의 통합은 상점 자리를 그대로 쥐고 있어요. Cafe24 는 등록 단계에서 같은 mall ID 가 이미 연결돼 있다는 안내로, MakeShop 은 설치 단계에서 같은 상점이 이미 연결돼 있다는 오류로 막혀요. 그 통합을 재인증하거나 삭제한 뒤 다시 등록해요. MakeShop 통합은 재인증할 수 없으니 삭제한 뒤 다시 등록해요.

<Callout type="note">
재인증과 권한 추가(권한 요청)가 동작하는 방식은 제공자마다 달라요.

- **Google · GitHub · Cafe24 Public 앱**: 팝업이 열리고 제공자의 동의 화면에서 다시 인증해요.
- **Cafe24 Private 앱**: 팝업이 열리지 않아요. 요청을 남기면 상세 화면 머리글 아래에 안내가 뜨고 Cafe24 Developers 에서 **테스트 실행** 을 눌러야 끝나요. 순서는 [Cafe24 통합](/docs/06-integrations-and-config/cafe24) 에서 확인해요. 설치 시간이 지나 만료된 통합은 재인증할 수 없어요. 같은 상점을 새로 등록하면 되고 그 통합을 먼저 지우지 않아도 돼요. App URL 이 없는 통합은 삭제한 뒤 다시 등록해요.
- **MakeShop**: 재인증과 권한 추가를 지원하지 않아요. 두 버튼이 비활성이고 통합을 삭제한 뒤 다시 등록해야 해요. 자세한 내용은 [MakeShop 통합](/docs/06-integrations-and-config/makeshop) 에서 확인해요.
</Callout>

<Callout type="note">
연결 테스트가 확인하는 범위는 서비스마다 달라요.

- **실제로 접속해서 확인**: Email(SMTP 로그인까지), MCP 서버, Database, HTTP/REST.
- **입력 형식만 확인**(외부 호출 없음): Google, GitHub, Webhook.
- **Cafe24 · MakeShop**: 연동을 추가하는 중(Step 3)에는 형식만 확인하고, 연결된 뒤 상세 페이지의 `Test connection` 은 실제로 호출해요.

Database는 연결을 열어 `SELECT 1`을 실행해요. 비밀번호가 틀렸거나 접근 권한이 없으면 테스트가 실패하고, 테스트용 연결은 확인이 끝나면 바로 닫혀요. HTTP/REST는 `base_url`로 노드와 같은 방식의 인증 정보를 붙여 요청을 보내요 — 서버가 401 · 403을 돌려줄 때만 인증 정보가 틀렸다는 것을 알 수 있어요. 그 밖의 4xx는 서버에는 닿았다는 뜻이라 통과로 표시되지만 인증 정보가 맞다는 확인은 아니고, 5xx는 실패로 표시돼요. `base_url`이 비어 있는 연동(노드에서 URL 전체를 적는 경우)은 요청을 보내지 않아요. Database는 연결과 `SELECT 1`을 각각 최대 10초, HTTP/REST는 리다이렉트를 포함한 요청 전체를 최대 10초 기다려요.

사설망·loopback·CGNAT(`100.64.0.0/10`) 같은 내부 주소로 향하는 Database · HTTP · Email(SMTP) 연동은 보안을 위해 테스트가 차단되고 실패로 표시돼요(운영자가 내부 주소를 허용한 설치는 예외). 워크플로에서 그 연동을 쓰는 노드도 같은 규칙으로 막혀요. 차단된 주소는 오류 메시지에 나오지 않아요.
</Callout>

<Callout type="tip">연동이 `expired` 또는 `error` 상태로 바뀌면 사이드바에 주의 필요 배지가 뜨고, 목록 상단에 `Need attention` 배너가 나타나요. 배너를 누르면 해당 상태 필터로 바로 이동해요. 주의 대상에는 토큰이 7일 이내 만료되는 만료 임박 `connected` 연동도 포함돼요. **단, refresh_token 자동 갱신을 지원하는 통합(Cafe24·MakeShop·Google)은 만료 임박이어도 `Need attention` 배너·사이드바 배지·`Expiring` 필터에 포함되지 않아요** — 시스템이 백그라운드에서 자동 갱신하므로 조치가 필요 없기 때문이에요(같은 이유로 access_token 이 만료돼도 passive `integration_expired` 알림을 보내지 않아요). 자동 갱신이 실패해 `error`/`expired` 로 바뀌면 그때 정상적으로 주의 대상에 포함되고 `integration_action_required` active 알림이 발송돼요.</Callout>

## 노드에서 연동 선택하기

워크플로우 에디터에서 HTTP Request, Send Email, Database Query 같은 노드를 추가하면, 설정 패널 상단에 `Integration` 드롭다운이 있어요. 드롭다운에는 해당 서비스 유형과 일치하는 연동만 나열돼요.

<Example title="HTTP Request 노드에서 연동 쓰기">
```ts
// 설정 패널에서 선택한 값은 노드 config에 저장돼요.
{
  "type": "httpRequest",
  "config": {
    "integrationId": "int_01H...",   // 통합 관리에서 만든 연동 ID
    "method": "POST",
    "path": "/v1/orders",            // base_url 뒤에 붙는 상대 경로
    "body": "{{ $run.input }}"
  }
}
```
</Example>

Send Email 노드도 같은 방식이에요. SMTP 연동의 `default_from` 값이 자동으로 기본 발신자가 되고, 필요하면 노드에서 개별적으로 덮어쓸 수 있어요.

내가 이 워크플로우를 만든 사람이 아니면 내 Personal 통합은 목록에 보이지만 고를 수 없게 비활성으로 표시되고, 이름 옆에 "이 워크플로우에서는 쓸 수 없음"이 붙어요. 드롭다운 아래에는 "이 워크플로우를 만든 사람이 아니어서 내 개인 통합은 고를 수 없어요. 노드에는 조직 통합과 워크플로우를 만든 사람의 개인 통합만 쓸 수 있어요." 안내가 나와요. 이럴 때는 Organization 통합을 고르거나, 워크플로우를 만든 사람이 자기 통합으로 설정하도록 부탁해요.

## 팁 & 참고

- 자격 증명은 AES-256-GCM으로 암호화돼 저장되고, API 응답에서는 `****4f2a` 처럼 마스킹된 프리뷰만 돌아와요.
- 비OAuth 연동의 `Rotate credentials` 는 새 값의 테스트가 통과해야 기존 값을 덮어써요. 실패하면 기존 자격 증명은 그대로 유지돼요.
- 하나의 서비스에 여러 계정을 등록하려면 별칭을 다르게 해서 반복 추가하면 돼요. 워크스페이스 내에서 별칭은 유일해야 해요.
- 사용처가 있는 연동은 삭제할 수 없어요. 다만 멤버가 나가거나 제거될 때 그 멤버의 Personal 통합이 함께 삭제되는 경우는 사용처가 있어도 막히지 않아요. `Delete integration` 을 누르면 먼저 사용처를 조회해서, 사용 중이면 삭제 차단 다이얼로그에 어떤 워크플로우·노드가 참조 중인지(AI Agent의 MCP 서버 참조는 `MCP` 배지로 구분) 보여줘요. 다이얼로그의 워크플로우 링크로 이동해 노드의 `integrationId` 를 다른 연동으로 바꾸거나 해당 노드를 제거한 뒤 다시 삭제해요.
- AI Agent에서 외부 도구·리소스를 LLM에게 노출하려면 MCP 서버 통합을 등록하고 AI Agent 노드의 `MCP Servers` 필드에 연결해요. 자세한 흐름은 [MCP 서버 통합](/docs/06-integrations-and-config/mcp-servers)에서 확인해요.
- 다른 사람이 만든 워크플로우에서 내 Personal 통합이 비활성으로 보인다면 [자주 묻는 질문](/docs/99-faq/faq)의 답을 참고해요.
