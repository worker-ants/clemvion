This page covers how to centrally manage your third-party integrations. Nodes like HTTP Request and Send Email reuse the integrations you create here.

## What an integration is

An integration is a bundle of credentials for reaching an external service. Create one, and multiple nodes across multiple workflows can share the same account/key. Key rotation and re-auth happen in one place.

## Sharing inside a team workspace

Integrations created with Organization scope in a team workspace are automatically usable by every member. Integrations created with Personal scope in the same team workspace, though, are visible only to the person who created them — other members can't find them in the list or even by navigating straight to the detail page, and the rule has no role exception: Owners and Admins can't see another member's Personal integrations either. Switching workspaces from the sidebar refreshes the integration list for the selected workspace.

Which integrations a node can use also depends on scope.

- **Organization integrations**: usable from the nodes of any workflow in the workspace.
- **Personal integrations**: usable only from the nodes of workflows created by the person who created the integration. Even that person can't use it in a workflow another member created.

The check is based on **the person who created the workflow**, not the person who started the run. Automatic runs from a schedule or webhook, and runs as a sub-workflow, follow the same rule; a sub-workflow is judged by the person who created that sub-workflow. A Personal integration also can't be used when the node picks the integration through an expression (`{{ }}`). Only Organization integrations work in that case.

A node that uses a Personal integration the rule doesn't allow fails at run time with the same "integration not found" error as a node that references an integration that doesn't exist. The error alone can't tell you whether the integration is missing or just not usable. For an AI Agent node, an MCP server entry like that is skipped and the node keeps running.

By action, it works out like this. A Personal integration can only be handled by the person who created it, and the role in the table is the minimum role that person needs.

| Action | Personal integration | Organization integration |
| --- | --- | --- |
| View (list, detail, usages, activity) | Any role | Every member |
| `Test connection` on a saved integration | Any role | Every member |
| Add a new integration | Editor or above | Admin or above |
| Rename, re-auth, rotate credentials, request scopes | Editor or above | Admin or above |
| Switch scope between Personal and Organization | Admin or above | Admin or above |
| Delete | Any role | Admin or above |

The screen and the server enforce the same rules. Buttons and input areas for actions you can't take are not shown, so you never press something only to be turned down.

<Callout type="tip">Integrations in a personal workspace are visible only to the owner. To share with a team, create the integration inside the team workspace. The same external account is a separate record per workspace.</Callout>

### When a member leaves or is removed

When a member leaves the workspace, or an admin removes a member, every Personal integration that member added to this workspace is deleted along with the membership.

- **Status and usage don't matter.** Connected, pending install, expired, and error integrations are all deleted, even when a workflow node uses them. A regular integration delete is blocked while the integration is in use, but this one isn't.
- **Some integrations stay.** Organization integrations the member created, and other members' Personal integrations, are kept.
- **It is recorded in the audit log.** Each deleted integration leaves an integration-deleted entry in the audit log.
- **Nodes fail at run time.** A workflow node that used a deleted Personal integration fails to run until you pick another integration for it.
- **Sometimes nothing is deleted.** The sole Owner can't leave and an Owner can't be removed, so in those cases nothing is deleted.

If the same person is invited again and rejoins, the deleted integrations do not come back. See [Workspaces and members](/docs/07-workspace-and-team/workspaces-and-members) for the leave and remove-member screens.

### Switching an Organization integration to Personal

On the integration's Danger zone tab, switching an Organization integration to Personal means workflows created by anyone other than the person who created the integration can no longer use it in their nodes. So the integration's usages are checked before the switch.

- If any such workflow exists, a warning dialog titled "Some workflows will fail after switching to Personal" appears. It lists those workflows and nodes, and clicking `Switch to Personal` goes ahead with the switch. The switch isn't blocked.
- If none exist, only a confirmation prompt appears: "After switching to Personal, only the person who created this integration can see and use it. Continue?"
- If the usages can't be checked, the scope isn't changed and an error toast appears: "Couldn't check where this integration is used, so the scope wasn't changed".

## Adding an integration

Click `[+ Add Integration]` in the top-right of [Integrations](/integrations). Pick a service in the modal; the flow then transitions into a dedicated page starting from the auth step (`/integrations/new?service=...&step=auth`).

Only Editors and above can add integrations. Viewers don't see the `[+ Add Integration]` button, and pressing `N` on the list doesn't open the service picker. If a Viewer goes straight to the add page's address, the page shows only the notice "Only Editors and above can add integrations." and a link back to the list.

### A pending install that passed its deadline

A Cafe24 Private or MakeShop integration that is waiting for install changes to expired (install deadline passed) if the install isn't finished within 24 hours of the install token being issued. At that moment it also lets go of the store identifier (Cafe24 mall ID, MakeShop store) it was holding.

- **You can register the same store again.** You don't have to delete the expired integration first. It isn't deleted automatically and stays flagged as `Need attention`, so delete it yourself if you don't need it.
- **The old App URL (install link) no longer works.** Opening the App URL of an expired integration shows an error saying the install link is not valid.
- **The integration name is kept.** If you register again with the same name as the expired integration, the add-integration screen shows "An integration with this name already exists. Enter a different name." under the name field, and a toast with the same message appears. Change the name and the field error goes away. Cafe24 Private builds its default name from the mall ID, so this happens often.
- **Expired or errored for another reason is an exception.** An integration for the same store that expired or errored for a reason other than the install deadline (a token expiry, for example) keeps holding the store. Cafe24 stops you at the registration step with a notice that the mall ID is already connected, and MakeShop stops you at the install step with an error that the store is already connected. Reauthorize that integration, or delete it and register again. A MakeShop integration can't be reauthorized, so delete it and register again.

<Callout type="note">
How reauthorizing and adding scopes (Request scopes) work depends on the provider.

- **Google, GitHub, and Cafe24 Public apps**: a popup opens and you authenticate again on the provider's consent screen.
- **Cafe24 Private apps**: no popup opens. After you submit the request, a notice appears below the detail page header and you finish by clicking **Test Run** in Cafe24 Developers. See the [Cafe24 integration guide](/docs/06-integrations-and-config/cafe24) for the steps. An integration that expired because the install timed out can't be reauthorized. Register the same store again; you don't need to delete that integration first. If the integration has no App URL, delete it and register it again.
- **MakeShop**: reauthorizing and adding scopes are not supported. Both buttons are disabled, so delete the integration and register it again. For an integration that expired because its install deadline passed, register the same store again; you don't need to delete that integration first. See the [MakeShop integration guide](/docs/06-integrations-and-config/makeshop).
</Callout>

<Callout type="note">
What a connection test checks depends on the service.

- **Actually connects**: Email (through SMTP login), MCP server, Database, HTTP/REST.
- **Checks input format only** (no external call): Google, GitHub, Webhook.
- **Cafe24 · MakeShop**: format-only while adding the integration (Step 3); once connected, `Test connection` on the detail page makes a real call.

Database opens a connection and runs `SELECT 1`. A wrong password or missing access privileges fail the test, and the test connection closes right after. HTTP/REST sends a request to `base_url` using the same credentials the node would use — only a 401 or 403 response confirms the credentials are wrong. Other 4xx responses count as a pass (the server was reachable) but don't confirm the credentials are correct, and a 5xx response fails. If `base_url` is empty (the node supplies the full URL instead), no request is sent. Database waits up to 10 seconds each for the connection and for `SELECT 1`; HTTP/REST waits up to 10 seconds for the whole request, redirects included.

Database, HTTP and Email (SMTP) connections aimed at private, loopback or CGNAT (`100.64.0.0/10`) addresses are blocked for security, and the test fails (unless the operator has allowed internal addresses for the installation). Nodes that use the integration in a workflow are blocked by the same rule. The blocked address is not shown in the error message.
</Callout>

<Callout type="tip">When an integration flips to `expired` or `error`, the sidebar shows an attention badge and the list displays a `Need attention` banner. Clicking it jumps to the matching status filter. Attention also includes `connected` integrations whose token expires soon (within 7 days). **Note: integrations that support refresh_token auto-renewal (Cafe24, MakeShop, Google) are NOT included in the `Need attention` banner, sidebar badge, or `Expiring` filter even when expiry is near** — the system renews them automatically in the background, so no action is needed (for the same reason, no passive `integration_expired` notification is sent when the access_token expires). If auto-renewal fails and the integration flips to `error`/`expired`, it then appears in attention as usual and an `integration_action_required` active alert is sent.</Callout>

## Choosing an integration from a node

In the workflow editor, adding an HTTP Request, Send Email, or Database Query node exposes an `Integration` dropdown at the top of the settings panel. The dropdown lists only integrations whose service type matches.

<Example title="Using an integration from an HTTP Request node">
```ts
// The values you pick in the settings panel are persisted in the node config.
{
  "type": "httpRequest",
  "config": {
    "integrationId": "int_01H...",   // integration id from integration management
    "method": "POST",
    "path": "/v1/orders",            // relative path joined to base_url
    "body": "{{ $run.input }}"
  }
}
```
</Example>

Send Email works the same way. The SMTP integration's `default_from` becomes the default sender; each node can still override it.

If you didn't create the workflow, your own Personal integrations still appear in the list but are disabled, with "can't be used in this workflow" next to the name. A hint appears under the dropdown: "You didn't create this workflow, so you can't pick your personal integrations. Nodes can use organization integrations and the workflow creator's personal integrations only." In that case, pick an Organization integration, or ask the person who created the workflow to set it up with their own integration.

When you save, the server checks only the integration choices that are new or changed. If creating or changing a node, or saving the canvas, brings in an integration that can't be used (one that doesn't exist, or a Personal integration you can't use), the save is rejected with an "integration not found" error. Choices that were already saved aren't re-checked. Duplicating a workflow, importing JSON, and restoring a version don't reject the save; they clear the choices that can't be used. See [Editing and arranging nodes](/docs/03-workflow-editor/editing-nodes), [Saving, autosave, and import/export](/docs/03-workflow-editor/saving-and-sharing), and [Version history](/docs/05-run-and-debug/version-history) for how that works.

## Tips & notes

- Credentials are stored encrypted with AES-256-GCM. API responses return only masked previews like `****4f2a`.
- For non-OAuth integrations, `Rotate credentials` only overwrites the existing secret after the new value passes the connection test. On failure, the existing credential is untouched.
- To register multiple accounts for the same service, add separate integrations with different aliases. Aliases must be unique within a workspace.
- An integration in use cannot be deleted. The exception is when a member leaves or is removed: that member's Personal integrations are deleted along with the membership even if they are in use. Clicking `Delete integration` first checks its usages; if it's still in use, a delete-blocked dialog shows which workflows and nodes reference it (AI Agent MCP-server references are marked with an `MCP` badge). Follow the workflow link in the dialog, switch the node's `integrationId` to another integration or remove the node, then delete again.
- To expose external tools and resources to the LLM from an AI Agent, register an MCP server integration and wire it into the AI Agent node's `MCP Servers` field. See [MCP server integration](/docs/06-integrations-and-config/mcp-servers).
- If your own Personal integration appears disabled in a workflow someone else created, see the answer in the [FAQ](/docs/99-faq/faq).
