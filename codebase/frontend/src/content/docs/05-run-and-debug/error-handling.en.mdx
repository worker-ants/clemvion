This page covers the **five error policies** that decide how a workflow continues when a node fails. Pick one from the `Error Handling` dropdown in the settings panel.

## The five policies at a glance

<FieldTable rows={[
  { name: "Stop Workflow", type: "Default", description: "Immediately stops the entire run and records it as failed." },
  { name: "Skip Node", type: "Skip", description: "Skips the failing node and passes `null` to the next node as input." },
  { name: "Use Default Output", type: "Default output", description: "Emits a preset default value as if the node succeeded." },
  { name: "Retry", type: "Retry", description: "Auto-retries up to a configurable number of times. If all fail, falls back to Stop Workflow." },
  { name: "Route to Error Port", type: "Error port", description: "Sends the error payload out through a dedicated error port so a recovery branch can take over." }
]} />

## Stop Workflow

The default policy. Execution halts the moment an error occurs.

- `Execution.status = "failed"` is recorded.
- The failing node is highlighted red on the canvas.
- Downstream nodes of the failure do not run.

**When to use it**: deterministic paths where bad data must never leak downstream — think payment approval flows when the auth node fails.

## Skip Node

The failing node is ignored; execution continues.

- `NodeExecution.status = "skipped"`; error info is preserved on `NodeExecution.error`.
- The output is `null`. The next node receives `null` as input.

<Callout type="warn">If the next node can't handle `null` input, you might chain a failure. Pair with null checks or `||` default values.</Callout>

**When to use it**: non-critical side steps like Slack/email notifications where the main flow must continue regardless.

## Use Default Output

Emits a **preset default value** in place of the failed output.

Changing `Error Handling` to `Use Default Output` exposes a JSON editor.

<Example title="Default Output value">
```json
{
  "result": null,
  "status": "fallback"
}
```
</Example>

- If you don't provide a default, a type-aware auto default is used.

<FieldTable rows={[
  { name: "Object", type: "Default", description: "`{}`" },
  { name: "Array", type: "Default", description: "`[]`" },
  { name: "String", type: "Default", description: "`\"\"`" },
  { name: "Number", type: "Default", description: "`0`" },
  { name: "Boolean", type: "Default", description: "`false`" },
  { name: "Null/Unknown", type: "Default", description: "`null`" }
]} />

- `NodeExecution.status` is `completed`, but a warning is recorded alongside.

**When to use it**: when an external API occasionally fails and a **safe fallback** keeps the flow healthy — e.g. returning an empty object when a cache lookup fails.

## Retry

Automatically retries the node a configurable number of times.

<FieldTable rows={[
  { name: "maxRetries", type: "Integer", description: "Max retry count. Default 3." },
  { name: "retryInterval", type: "Integer (ms)", description: "Initial retry interval. Default 1000ms." },
  { name: "backoffMultiplier", type: "Float", description: "Exponential backoff multiplier. Default 2.0." },
  { name: "maxInterval", type: "Integer (ms)", description: "Cap on the retry interval. Default 30000ms." }
]} />

Intervals are computed with:

<Example title="Retry interval formula">
```ts
interval = min(retryInterval * backoffMultiplier ^ attempt, maxInterval)
```
</Example>

If every retry fails, falls back to **Stop Workflow**.

**When to use it**: external calls that fail **transiently** — network blips, LLM rate limits, etc.

## Route to Error Port

Sends the error payload out the node's **error port**, letting a connected downstream node pick up recovery from there.

- On a node that has no error port of its own, selecting this policy adds a red **error port** at the bottom right of the node. Connect the error branch there.
- If you switch such a node to another policy and save, the error port goes away and its edges are removed too. A notification shows how many were removed, and a single **Ctrl+Z** brings back both the policy and the edges.
- Nodes that **already have an error port**, such as HTTP Request, Database Query, and Send Email, get no extra port and use the one they have.
- When a node throws a failure, **only the edge on the error port** opens. Edges on other output ports such as `out` stay closed, so only the error branch runs.
- When the node succeeds, the edge on the error port stays closed. Only edges on the other output ports open.
- With nothing connected to the error port, the run logs `ERROR_PORT_FALLBACK` and falls back to Stop Workflow.
- `NodeExecution.status` is `failed`, but when an error edge exists **the Execution as a whole keeps going**.

<Callout type="warn">Behavior has changed. Previously, when a node threw a failure, every outgoing edge opened regardless of port. The next node on the normal path also ran with `{ error }` as its input, and the next node ran even with no error edge. Now only the error branch runs, and the workflow stops if there is no error edge. For such workflows, connect an edge to the error port, or pick another policy such as Stop Workflow or Skip Node.</Callout>

When a node throws a failure, this policy builds the payload below and passes it to the next node.

<Example title="Error-port payload">
```json
{
  "error": {
    "code": "UNKNOWN_ERROR",
    "message": "Cannot read properties of undefined (reading 'id')"
  }
}
```
</Example>

- `code` holds a registered error code. If the node fails with a registered code (e.g. `INTEGRATION_NOT_CONNECTED`, `CAFE24_RATE_LIMITED`), you get that code; every other failure becomes `UNKNOWN_ERROR`.
- `message` holds the failure message.
- The failed node's ID and its original input are not included. If you need the original input, read the upstream node's output with `$node["Node name"]`.
- Nodes that already have an error port, such as HTTP Request, may send a failure to it themselves. In that case `details` carries extra information such as the status code.

<Callout type="warn">The `code` value has changed. It used to hold error names such as `Error`, `TypeError`, or `IntegrationError`. Update conditions that compared against an error name, such as `$node["X"].output.error.code == "Error"`, to compare against `"UNKNOWN_ERROR"` or the specific error code (e.g. `INTEGRATION_NOT_CONNECTED`) instead.</Callout>

**When to use it**: when failures should trigger a **separate recovery path** — admin alert, alternative LLM call, archiving the original input, etc.

## Execution time limit exceeded (`EXECUTION_TIME_LIMIT_EXCEEDED`)

When a workflow's **accumulated active execution time** exceeds the limit (default **30 minutes**), the execution is automatically terminated with status `failed`. The error code is `EXECUTION_TIME_LIMIT_EXCEEDED`.

**What is "active execution time"?**

- Only the time nodes spend actively processing is counted.
- **`waiting_for_input` wait time** — e.g. waiting for form submission or AI Agent conversation input — is excluded.
- A workflow that spans multiple days waiting for user input will work fine as long as the accumulated active execution time stays under 30 minutes.

<Callout type="info">
This is separate from `EXECUTION_TIMEOUT` (Code node script timeout, per-node). `EXECUTION_TIME_LIMIT_EXCEEDED` measures the entire workflow's accumulated active execution time.
</Callout>

**Adjusting the limit**: set the server environment variable `EXECUTION_MAX_ACTIVE_RUNNING_MS` (in milliseconds). Set to `0` to disable the limit. A server restart is required after changing this value.

```bash
# Increase to 60 minutes
EXECUTION_MAX_ACTIVE_RUNNING_MS=3600000
```

## The cancelled status and error policies

When a node is stopped by an **external abort** — a parallel branch failure with `cancel-others-on-fail`, or the user clicking Stop — the node records `NodeExecution.status = "cancelled"` instead of `"failed"`.

- Error policies do **not** apply to cancelled nodes. Retry, Skip, Default Output, and Error Port branches are all bypassed; the node stops immediately.
- The timeline shows a distinct `cancelled` badge so you can tell cancellation from failure at a glance.
- Even if a node has the Retry policy set, receiving an abort signal terminates it as `cancelled` with no retries.

<Callout type="tip">Retry and Route to Error Port can't be used together. If you need an alternative path when retries fail, pick the error-port flow instead of retries.</Callout>

## Interaction errors during execution (AI conversation · form · button response failures)

When an error occurs while interacting with a node waiting for user input (AI Agent conversation, Form node, Button node), a toast notification appears in the bottom-right of the screen. One of the messages below will be shown depending on the error type.

<FieldTable rows={[
  { name: "INVALID_EXECUTION_STATE", type: "Error code", description: "The execution is not currently waiting for input — it may have already progressed or been cancelled." },
  { name: "EXECUTION_MESSAGE_TOO_LONG", type: "Error code", description: "The message exceeds the maximum allowed length. Shorten your input and try again." },
  { name: "EXECUTION_INTERNAL_ERROR", type: "Error code", description: "An internal error occurred. Try again in a moment or contact your workspace admin." }
]} />

<Callout type="info">For security, internal server error details are never exposed to the user. Admins can check the server logs for the root cause.</Callout>
