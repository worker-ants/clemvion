# `.claude/tests/` — harness self-tests

Unit tests for the **harness's own Python** (hooks, skill libs, config) — not
the product code under `codebase/`. These guard the automation layer that has
no other coverage: branch guards, branch normalization, and the multi-place
agent registry.

## Run

```bash
python3 -m unittest discover -s .claude/tests -p 'test_*.py'
```

The suite uses the **standard library** (`unittest`, `unittest.mock`), matching
the harness convention that its Python carries zero third-party dependencies —
hooks must run on a bare `python3`. Do not introduce `pytest`/`requirements.txt`
here without revisiting that convention.

**One exception, added 2026-08-01: PyYAML.** `test_override_floors.py` execs
`scripts/check-override-floors.py`, which parses `pnpm-workspace.yaml` at import
time; `test_workflow_yaml_structure.py` parses `.github/workflows/*.yml` to
catch duplicate keys — something no stdlib parser does; and
`test_review_gate_ci.py` reads `review-gate.yml` structurally, because the
substring version of that test passed while the wiring it named was deleted.
Each guards YAML the repo depends on, so hand-rolling a parser would put the
guard's own correctness in question. (Deliberately not "two files" or "three" —
a count in prose goes stale the next time one is added, which is how this
paragraph was wrong.) CI installs it (`pip install "pyyaml>=6,<7"`, the same pin
`deps-security-checks.yml` already uses); locally it is normally present. **The
exception is PyYAML and nothing else** — the no-dependency rule still holds for
anything a *hook* imports, since hooks get no install step.

| `test_override_floors.py` | `scripts/check-override-floors.py` — the guard that fails a PR when a package we already pinned via `overrides` shows up vulnerable again (floor erosion). | `test_workflow_yaml_structure.py` | Structural validity of every `.github/workflows/*.yml`: no duplicate mapping keys, and every step carries exactly one of `run`/`uses`. | `test_changed_paths_reusable.py` | `_changed-paths.yml` — the `changes` job the converted workflows share. `workflow_call` inputs are scalars only, so the pathspec list crosses as a **multi-line string** and has to be turned back into an argument array on the other side. That conversion is the quietest failure surface in the whole pattern: pass it unquoted and the shell either hands the judge **one** argument containing everything or expands the globs against the runner's cwd; either way the judge answers "nothing relevant changed" and every check in all converted workflows silently no-ops while the required checks stay green. This repo has already paid for that exact class once — an argument list arriving as a single blob made an entire round of "explicit file" work vacuous — and the rule it left behind is **verify what the receiving side actually got**. So these tests do not grep the YAML for `read`/`mapfile`; they pull the real `run:` block out of the workflow, execute it under bash with a stub at `scripts/ci-paths-changed.sh` that prints `$#` and each argument, and assert on that. Also pinned: globs surviving unexpanded, blank/whitespace-only lines dropped (an empty pathspec means **every** path to git, which pins the verdict to true and removes the gate), `#`-initial lines dropped as comments while a `#` mid-path survives, a list of only comments failing closed like an empty one, and an empty input exiting non-zero rather than passing quietly. | `test_required_check_skip_jobs.py` | The skip-job contract that lets a workflow be registered as a **required status check** without deadlocking merges. A workflow with `on.pull_request.paths` simply does not run on an unrelated PR, and a check that never runs is not *failed* — it stays `Expected — Waiting for status to be reported`, blocking the merge forever. So the converted workflows drop `paths:` (always run) and a `changes` job decides relevance, gating each job's **steps**. Gating the *job* instead was rejected: a skipped job's conclusion is `skipped`, and whether that satisfies a required check is documented ambiguously — betting on it reintroduces the very deadlock. Three regressions are pinned: restoring `paths:` (deadlock returns); adding a step without `if:` (it then really executes on unrelated PRs); and **dropping `needs: changes`**, after which `needs.changes.outputs.relevant` evaluates to the empty string and the gating is no longer a decision at all. Which way that empty string falls is the whole design: steps are gated `!= 'false'`, **not** `== 'true'`, so an empty value runs the real checks (wasteful, safe) instead of skipping them (green, silent) — the same fail-safe direction the judge script takes. The dangerous regression is therefore inverting those conditions back, which is why the two standard strings are matched exactly and a mutation flipping either one turns six tests red; this repo's recurring failure is "the gate silently stopped running", never "the gate ran when it needn't have". A fourth test requires each job to keep a no-op announcement step so a skipped run is distinguishable from a real one in the log, and a fifth requires each workflow to list `scripts/ci-paths-changed.sh` among its own globs, so a change to the judge re-triggers the workflows that depend on it (the `paths` coverage gap `harness-checks.yml` hit six times). Since the `changes` wiring moved into the shared `_changed-paths.yml`, these checks follow the `uses:` indirection rather than stopping at the caller — a caller now only has to name the reusable workflow and hand it pathspecs, so verifying just that would let the one file every workflow depends on lose its output wiring while all three suites stayed green. The pathspec assertions parse the YAML instead of grepping the file, which also closes the older hole where a path mentioned in a **comment** satisfied a substring check. Each caller must additionally list `_changed-paths.yml` among its own pathspecs — a dependency the extraction created, and exactly the coverage-gap shape this repo has hit six times. As of 2026-08-09 the registry covers **eight** workflows — every `pull_request`-triggered one except `review-gate.yml` (converting it makes the gate run on doc-only PRs, which needs its pass behaviour checked there first) and `e2e.yml` (a `paths-ignore` shape, and the most expensive). `pathspecs_of` normalises the block scalar with the **same three cuts as the runtime** — strip, drop blank, drop `#`-initial — because a guard that reads a different list than the runner is how a pathspec passes review and is silently inert on CI. Pairs with `test_workflow_yaml_structure.py`, whose `_PULL_REQUEST_KEYS` registry permits the bare `pull_request:` shape **only** for the workflows listed here — that registry's own comment calls bare `pull_request:` the most dangerous shape (it can produce an always-green workflow), and this file is the compensating control that makes it safe. |

The race is reproduced **deterministically by re-entrancy** — one writer is interrupted between its read and its write and the other runs to completion inside that window — so there are no threads or sleeps and both writers still go through the real function. ## Conventions for new tests

- Patch the git-backed helpers (`_repo_root`, `_run_git`, …), not git itself, so
  tests stay hermetic and fast. **Deliberate exception:** when the behaviour
  under test *is* a git semantic — e.g. that `git rebase` rewrites committer date
  but preserves author date, which `review_guard._newest_commit_time` relies on —
  build a real temp repo (`git init` in a `tempfile.mkdtemp()`, isolated via
  `GIT_CONFIG_GLOBAL=/dev/null`) and set `GIT_AUTHOR_DATE`/`GIT_COMMITTER_DATE`
  explicitly. Mocking would assert our model of git, not git. Keep these few and
  fast.
- Load harness modules via `_harness.load_module_by_path` when they would
  collide on the shared `_lib` package name (the two `_lib` packages under
  `hooks/` and `skills/`). See `_harness.py`.
- Assert **structural / behavioral invariants**, not prose. The `.md` agent
  definitions and docs are allowed to read differently from their SSOT.
  **Deliberate exception:** where the document *is* the runtime spec rather than a
  rendering of one — a sub-agent definition is the system prompt the model executes —
  its wording is behaviour, and `test_summary_agent_contract.py` pins the load-bearing
  phrases. That exception earned itself: a refuted explanation ("your write is blocked
  because you are the terminal sub-agent") sat in 7 such files while the workflows had
  begun asking those very agents to write per-agent files, and nothing caught the
  contradiction. Keep such checks to phrases that change what the agent *does*.
