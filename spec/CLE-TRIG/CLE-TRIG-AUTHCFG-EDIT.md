## 개요

이 문서는 [외부 호출 인증 설정](CLE-TRIG-AUTHCFG.md) 의 하위 문서로 인증 방식별 입력 항목, 편집, 재생성을 정한다. 복호화 불가 표식으로 읽히는 설정의 편집 · 재생성도 여기서 정한다. 마스킹과 평문 보기는 [마스킹과 평문 보기](CLE-TRIG-AUTHCFG-REVEAL.md), API 목록과 권한은 부모 문서가 정한다.

## 인증 방식별 입력 항목

유형별 `config` 스키마와 자동 발급 규칙의 단일 기준은 [트리거 데이터와 흐름](CLE-TRIG-DATA.md) 이다. IP Whitelist 는 모든 유형에 공통인 선택 필드다. 생성 폼은 IP Whitelist 입력(한 줄에 IP 나 CIDR 하나)과 유형별 추가 입력을 모두 보여 준다.

### API Key

| 필드 | 설명 |
|------|------|
| 이름 | 인증 설정 이름 |
| API Key | 자동 생성(`wfk_<hex24>`), 표시는 마스킹. 복사 버튼은 마스킹 문자열을 복사한다. 평문은 생성 직후 한 번 또는 평문 보기로만 복사한다 |
| Header 이름 | 검증에 쓸 헤더 이름(기본 `X-API-Key`) |
| Key 재생성 | 기존 키를 폐기하고 새 키를 만든다(확인 필요) |
| IP Whitelist | 허용 IP 목록(선택) |

### Bearer Token

| 필드 | 설명 |
|------|------|
| 이름 | 인증 설정 이름 |
| Token | 자동 생성(`wft_<hex32>`), 표시는 마스킹. 사용자 입력은 받지 않는다 |
| Token 재생성 | 기존 토큰을 폐기하고 새 토큰을 만든다(확인 필요) |
| IP Whitelist | 허용 IP 목록(선택) |

### Basic Auth

| 필드 | 설명 |
|------|------|
| 이름 | 인증 설정 이름 |
| Username | 사용자 이름(사용자 입력). 식별을 돕는 값이라 응답에 평문으로 나간다 |
| Password | 비밀번호(사용자 입력, 가린 입력창). 저장 뒤 응답은 `***<last4>` 로 가린다. 평문 재확인은 평문 보기로만 한다 |
| IP Whitelist | 허용 IP 목록(선택) |

사용자 이름과 비밀번호는 필수다. 생성 요청에서 둘 중 하나라도 없거나 문자열이 아니거나 빈 문자열이면 400 `VALIDATION_ERROR` 로 거부한다. 편집에서 사용자 이름을 비우는 요청도 400 이다([편집](#편집)). 공백만 있는 값은 거부하지 않는다. 화면의 생성·편집 폼은 사용자 이름의 앞뒤 공백을 지워 보내고 사용자 이름이나 생성 때의 비밀번호가 비면 저장하지 않는다.

생성 · 편집 요청을 저장 때 검증하는 요구([외부 호출 인증 설정 「요구사항」](CLE-TRIG-AUTHCFG.md#요구사항)의 Basic Auth 생성 · 편집 거부 요구)가 들어오기 전에 빈 값으로 저장된 설정은 그대로 남는다. 사용자 이름이나 비밀번호가 비어 있는 설정으로 받은 웹훅 요청은 인증 단계에서 늘 401 `AUTH_FAILED` 로 거부된다. 이 요구는 [웹훅 「인증」](CLE-TRIG-WEBHOOK.md#인증) 이 정한다.

Basic Auth 에는 재생성이 없다. 사용자 이름과 비밀번호는 제품이 발급하는 값이 아니라 사용자가 입력한 값이기 때문이다. 재생성 요청은 400 `AUTH_CONFIG_REGENERATE_UNSUPPORTED` 로 거부한다([재생성](#재생성)). 비밀번호를 바꾸려면 설정을 지우고 다시 만든다.

### HMAC

| 필드 | 설명 |
|------|------|
| 이름 | 인증 설정 이름 |
| Secret | 자동 생성(`whs_<hex32>`), 표시는 마스킹, 재생성 가능 |
| Header | 서명을 담는 헤더 이름(기본 `X-Hub-Signature-256`). 외부 provider 에 맞춘다(GitHub `X-Hub-Signature-256`, Stripe `Stripe-Signature` 등) |
| Algorithm | 선택: `sha256` / `sha512`. 다른 값은 보안상 지원하지 않는다 |
| IP Whitelist | 허용 IP 목록(선택) |

### IP Whitelist

각 항목은 단일 IP 나 CIDR 이다(예: `10.0.0.0/8`, `2001:db8::/32`). 단일 IP 는 `/32`·`/128` 호스트로 취급한다. 생성·수정 때 항목마다 형식을 검증하고 단일 IP·CIDR(IPv4·IPv6)이 아니면 400 으로 거부한다. 웹훅 수신 때 이 목록을 시행하는 규칙은 [웹훅](CLE-TRIG-WEBHOOK.md) 이 정한다.

## 편집

같은 화면에서 행별 편집 버튼을 누르면 `PATCH /api/auth-configs/:id` 로 다음 값을 고친다.

- 이름
- IP Whitelist
- 비밀이 아닌 config: API Key 의 `headerName`, HMAC 의 `header`·`algorithm`, Basic Auth 의 `username`

유형과 비밀 값은 편집할 수 없다. 제품이 발급하는 비밀(API Key·Bearer Token·HMAC)을 바꾸는 것은 재생성 하나로 모은다. 사용자가 입력한 Basic Auth 비밀번호는 재생성이 없으므로 설정을 지우고 다시 만들어 바꾼다. 편집 PATCH 는 config 를 통째로 바꾸지 않고 shallow-merge 해 암호화된 비밀 값을 보존한다. 마스킹 값(`***<last4>`)이 되돌아와도 무시한다.

Basic Auth 설정에 `config.username` 을 빈 문자열이나 문자열이 아닌 값으로 보내면 400 `VALIDATION_ERROR` 로 거부한다. `password` 는 편집 PATCH 가 무시하므로 이 검증 대상이 아니다. `config.username` 을 싣지 않은 요청은 저장된 사용자 이름을 검사하지 않는다. 그래서 빈 값으로 저장된 옛 설정도 이름·IP Whitelist·활성 상태를 고칠 수 있다.

생성 요청과 편집 PATCH 의 `config` 최상위 키 중 `__` 로 시작하는 키가 있으면 400 `VALIDATION_ERROR` 로 거부한다. `__` 로 시작하는 키는 복호화 불가 표식이 쓰는 자리다. 표식 판정이 최상위 키만 보므로 중첩된 객체 안의 키는 검사하지 않는다. 이 키를 받아 저장하면 저장 때 암호화를 건너뛸 수 있다. 사용자 이름 검증과 이 검증은 함께 돌고, 틀린 필드를 한 응답에 모두 싣는다.

복호화 불가 표식으로 읽히는 설정에 편집 PATCH 를 보내면 `config` 를 병합하지 않는다. 이름·IP Whitelist·활성 상태는 바뀐다. 응답 `config` 에는 표식만 남는다. 표식에 비밀이 아닌 config 를 병합해도 다시 저장할 때 원래 저장값이 그대로 저장되므로 그 값은 남지 않기 때문이다. 이런 설정을 다시 쓰려면 원래 키를 되돌리거나 재생성한다([재생성](#재생성)). 위의 입력 검증(사용자 이름, `__` 키)은 표식 여부와 상관없이 먼저 돈다. 그래서 화면은 이런 설정을 편집할 때 `config` 를 싣지 않는다. 실으면 편집 폼이 채운 빈 사용자 이름이 검증에 걸려 이름 · IP Whitelist 편집도 400 이 된다.

## 재생성

`POST /api/auth-configs/:id/regenerate` 는 제품이 발급하는 비밀을 새로 발급한다. 재생성할 수 있는 유형은 API Key·Bearer Token·HMAC 이다.

| 유형 | 정상 설정 | 복호화 불가 표식으로 읽히는 설정 |
|------|-----------|-----------------------------------|
| API Key | `key` 만 새 값(`wfk_<hex24>`)으로 바꾼다. `headerName` 은 그대로다 | 표식을 버리고 `{ key }` 로 새로 만든다. 헤더 이름은 기본값 `X-API-Key` 로 돌아간다 |
| Bearer Token | `token` 만 새 값(`wft_<hex32>`)으로 바꾼다 | 표식을 버리고 `{ token }` 으로 새로 만든다 |
| HMAC | `secret` 만 새 값(`whs_<hex32>`)으로 바꾼다. `header`·`algorithm` 은 그대로다 | 표식을 버리고 `{ secret, header: 'X-Hub-Signature-256', algorithm: 'sha256' }` 으로 새로 만든다 |
| Basic Auth | 400 `AUTH_CONFIG_REGENERATE_UNSUPPORTED` | 400 `AUTH_CONFIG_REGENERATE_UNSUPPORTED` |

- 재생성은 기존 값을 폐기하고 새 값을 저장한 뒤 그 값을 한 번 평문으로 응답한다. 감사 로그에 `auth_config.regenerate` 를 남긴다.
- 복호화 불가 표식으로 읽히는 설정은 생성 때와 같은 기본값으로 새 config 를 만든다. 표식이 가진 원래 저장값은 이때 버린다. 그래서 원래 키를 되돌려도 재생성 전의 값으로는 돌아가지 않는다. 이 설정을 쓰는 트리거는 그대로 연결되어 있으므로 외부 호출자에게 새 값만 알리면 된다. 비밀이 아닌 메타(`headerName`·`header`·`algorithm`)는 기본값으로 돌아가므로 필요하면 편집으로 다시 맞춘다.
- Basic Auth 재생성은 저장과 감사 기록 전에 거부한다. 화면은 Basic Auth 행에 Regenerate 를 보이지 않는다.
- 화면의 재생성 확인 대화상자는 복호화 불가 표식으로 읽히는 행이면 새 값과 기본 헤더·알고리즘으로 다시 만든다고 안내한다.

## Rationale

### Bearer Token 을 자동 발급만 허용하는 이유

예전에는 Bearer Token 을 "자동 생성 또는 사용자 입력" 으로 받았다. 사용자 입력을 없애고 자동 발급(`wft_<hex32>`)만 허용한다. 외부 호출자에게 발급하는 토큰은 제품이 충분한 엔트로피로 만드는 편이 일관되고 사용자 입력 토큰의 형식·엔트로피를 검증할 부담도 사라진다.

### 편집 폼에서 비밀을 다시 입력받지 않는 이유

편집(`PATCH`)은 이름·IP·비밀이 아닌 config 만 바꾸고 비밀 값을 다시 입력받지 않는다. 제품이 발급하는 비밀의 변경은 재생성 하나로 모은다. 사용자가 입력한 Basic Auth 비밀번호는 재생성이 없어 지우고 다시 만든다([Basic Auth 재생성을 거부한다](#basic-auth-재생성을-거부한다-2026-11-05)). 백엔드 `update` 는 `config` 를 통째로 바꾸지 않고 shallow-merge 하며 마스킹된 비밀 값(`***<last4>`)이 되돌아와도 무시해 실제 비밀이 망가지지 않게 한다. 유형 변경도 편집 폼에서 막는다. 유형을 바꾸면 비밀을 다시 발급해야 하므로 지우고 다시 만든다.

### Basic Auth 의 빈 값은 인증 때 거부한다 (2026-10-31)

Basic Auth 의 사용자 이름과 비밀번호는 사용자가 입력하는 값이다. 이 절을 쓴 때(v2~v4)는 생성 API 가 빈 값을 막지 않았고 API 설명(`create-auth-config.dto.ts`)에 «사용자 입력 필수» 라고만 적혀 있었다. 빈 값을 막는 곳은 웹훅 인증이다. 사용자 이름이나 비밀번호가 비어 있는 설정으로 받은 요청은 인증 단계에서 늘 401 `AUTH_FAILED` 다. 전에는 빈 기대값끼리 비교해서 `Authorization: Basic Og==` 가 통과했다.

인증 시점 거부는 빈 기대값이 생기는 경로를 모두 막는다. 생성 때 들어온 빈 입력, 편집(`PATCH`)으로 `username` 을 비운 설정, 이미 빈 값으로 저장된 옛 행, 키를 바꾼 뒤 복호화하지 못해 표식이 담긴 설정 등이 그런 경로다. 지금은 앞의 두 경로를 저장 때 400 으로 막는다([아래 절](#basic-auth-의-빈-값은-생성과-편집에서도-거부한다-2026-10-31)). 뒤의 두 경로는 여전히 인증 단계 거부만 막는다.

인증 시점 거부를 넣은 동기는 키 교체다. 키를 바꾸면 `auth_config.config` 가 복호화 불가 표식으로 읽히고 Basic Auth 와 HMAC 이 빈 기대값으로 비교돼 열린다. 빈 기대값을 받아들이던 결함도 함께 막았다. 같은 때 HMAC 의 빈 secret 도 거부하게 됐다. API Key 와 Bearer Token 은 그 전부터 빈 기대값을 거부했다.

빈 값을 인증 때 거부하는 요구는 웹훅 문서 한 곳에 두고 이 문서 본문은 그 요구를 가리킨다. 한 동작을 두 요구에 적으면 한쪽만 고쳤을 때 어긋나기 때문이다. 웹훅 인증의 요구사항은 [웹훅 「인증」](CLE-TRIG-WEBHOOK.md#인증) 이 정한다.

### Basic Auth 의 빈 값은 생성과 편집에서도 거부한다 (2026-10-31)

생성 요청의 빈 사용자 이름·비밀번호와 편집 `PATCH` 의 빈 사용자 이름을 400 `VALIDATION_ERROR` 로 거부한다. 인증 단계 거부([웹훅 「인증」](CLE-TRIG-WEBHOOK.md#인증))는 그대로 둔다. 이미 빈 값으로 저장된 설정과 키를 바꿔 복호화하지 못한 설정은 저장 때 검사로 막을 수 없기 때문이다. 그래서 [외부 호출 인증 설정 「요구사항」](CLE-TRIG-AUTHCFG.md#요구사항)의 Basic Auth 입력 요구(Basic Auth 유형을 만들 때 사용자 이름과 비밀번호를 받는 요구)에 «필수» 를 넣었다. 그 입력 요구는 두 입력이 필수라는 것을 정한다. 같은 절의 생성 거부 요구(빈 사용자 이름·비밀번호로 만드는 요청을 400 으로 거부)와 편집 거부 요구(빈 사용자 이름을 싣는 편집 PATCH 를 400 으로 거부)는 그 규칙을 어긴 요청을 어떻게 거부하는지 정한다.

빈 값 설정은 어느 웹훅 요청도 통과시키지 못한다. 저장을 받아 주면 잘못된 설정이 웹훅을 부를 때의 401 로만 드러난다. 그 401 은 자격 증명이 틀린 요청과 구분되지 않아서 원인을 찾기 어렵다. 저장 때 거부하면 설정을 만드는 관리자가 바로 알 수 있다. 화면의 폼은 빈 값을 저장하지 않았으므로 빈 값은 API 를 직접 부른 경우에만 들어갔다. 같은 생성·수정 API 는 IP Whitelist 형식도 저장 때 400 으로 거부한다. 잘못된 값이 웹훅을 부를 때에야 드러나 원인을 찾기 어렵다는 같은 이유다([트리거 데이터와 흐름 「인증 설정 도메인 결정」](CLE-TRIG-DATA.md#인증-설정-도메인-결정)).

값이 없거나 빈 문자열이면 비었다고 본다. 인증 단계가 빈 기대값을 401 로 거부하는 기준과 같다. 저장 때는 여기에 더해 문자열이 아닌 값도 거부한다. 인증 단계는 기대값을 문자열로 비교하므로 그런 값으로는 어떤 요청도 인증되지 않는다. 이미 저장된 그런 기대값은 인증 단계가 빈 기대값과 같이 401 `AUTH_FAILED` 로 거부한다([웹훅 「인증」](CLE-TRIG-WEBHOOK.md#인증)). 공백만 있는 값은 받는다. 인증 단계가 같은 공백 값을 보낸 요청을 통과시키므로 동작하는 설정이다. 화면이 사용자 이름의 앞뒤 공백을 지우는 것은 입력 실수를 막는 폼의 처리이고 API 계약과는 따로다.

편집에서는 `password` 를 검사하지 않는다. 편집 `PATCH` 는 비밀 값을 무시하므로 편집으로 비밀번호가 비는 경로가 없다. `config.username` 을 싣지 않은 편집도 저장된 값을 검사하지 않는다. 빈 값으로 저장된 옛 설정의 이름·IP Whitelist·활성 상태를 고치는 요청까지 막지 않으려는 것이다. 옛 설정을 고치는 데이터 이전은 하지 않는다. 그런 설정은 인증 단계에서 이미 401 로 막혀 있고 빈 값을 무엇으로 채울지는 설정을 만든 관리자만 정할 수 있다.

편집 PATCH 가 유형 · 비밀 값을 다루는 요구의 동사는 «허용하지 않는다» 에서 «무시하고 그대로 둔다» 로 바꿨다. 편집 `PATCH` 는 유효한 유형 값과 비밀 값을 거부하지 않고 무시해 왔다. 마스킹 값이 되돌아와도 실제 비밀을 지키는 규칙([편집 폼에서 비밀을 다시 입력받지 않는 이유](#편집-폼에서-비밀을-다시-입력받지-않는-이유))과 같은 방향이라 문서를 코드에 맞췄다. 유형 목록에 없는 `type` 값과 요청 본문에 정의되지 않은 최상위 키는 이와 따로 요청 형식 검증에서 400 이다.

검사는 서비스(`AuthConfigsService` 의 생성·수정)가 한다. 편집은 저장된 유형을 읽어야 Basic Auth 인지 알 수 있다. 거부 응답은 요청 형식 검증과 같은 `details` 배열이다. 한 요청에서 두 필드가 함께 틀릴 수 있고 같은 API 의 다른 400 과 같은 방식으로 읽힌다.

접은 선택지는 빈 값을 계속 받고 API 설명만 고치는 것이다. 빈 값 설정을 받아 둘 쓸모가 없어서 접었다.

### 복호화 불가 인증 설정은 재생성으로 새로 만든다 (2026-11-05)

키를 바꿔 복호화하지 못한 API Key·Bearer Token·HMAC 설정에 재생성을 요청하면 표식을 버리고 생성 때와 같은 기본값으로 새 config 를 만들어 저장한다. 정상 설정의 재생성은 바꾸지 않는다. 비밀 값 하나만 새 값으로 바꾸고 `headerName`·`header`·`algorithm` 은 그대로 둔다.

전에는 재생성이 표식 객체에 새 값을 넣어 저장했다. 키를 바꿔 생긴 표식에는 원래 저장값이 담겨 있고, 표식을 저장하면 원래 저장값이 그대로 다시 저장된다. 그래서 응답에는 새 값이 실렸지만 저장되지 않았고 사용자는 동작하지 않는 키를 받았다.

재생성은 원래 저장값을 버린다. 그래서 원래 키를 되돌려도 재생성 전의 값으로는 돌아가지 않는다. 재생성은 정의상 옛 비밀을 폐기하는 동작이므로 정상 설정과 같은 결과다. 표식에서는 비밀이 아닌 메타(`headerName`·`header`·`algorithm`)를 읽을 수 없어서 생성 때의 기본값으로 돌아간다. 응답에 새 config 가 그대로 실리므로 관리자가 바로 확인하고 편집으로 다시 맞출 수 있다. 화면의 재생성 확인 대화상자도 이 점을 알린다.

transformer 는 바꾸지 않는다. 재생성이 표식 객체를 고치지 않고 새 객체로 바꾸므로 저장할 때 평소처럼 암호화된다. 원래 저장값을 지키는 transformer 의 동작은 이름 변경 같은 무관한 재저장을 위한 것이고 그대로 둔다([마스킹과 평문 보기 「복호화 불가 인증 설정의 응답에서 원래 저장값을 뺀다」](CLE-TRIG-AUTHCFG-REVEAL.md#복호화-불가-인증-설정의-응답에서-원래-저장값을-뺀다-2026-10-31)).

접은 선택지는 재생성을 거부하고 «설정을 새로 만들라» 는 오류를 내는 것이다. 그러면 그 설정을 쓰는 트리거를 모두 새 설정에 다시 연결해야 한다. 키 교체 사고는 워크스페이스의 모든 설정을 한꺼번에 읽지 못하게 만들므로 다시 연결할 트리거도 많다. 통합도 읽지 못한 자격 증명을 다시 연결해 같은 행에서 복구한다([통합 데이터와 흐름 「암호화」](../CLE-INT/CLE-INT-DATA.md#암호화)). 거부하면 재생성 요구에 «복호화 불가 설정은 빼고» 라는 예외도 붙는다.

Basic Auth 는 표식 여부와 상관없이 재생성을 거부한다([아래 절](#basic-auth-재생성을-거부한다-2026-11-05)). 표식으로 읽히는 Basic Auth 설정은 지우고 다시 만든다.

### Basic Auth 재생성을 거부한다 (2026-11-05)

Basic Auth 설정에 재생성을 요청하면 저장과 감사 기록 전에 400 `AUTH_CONFIG_REGENERATE_UNSUPPORTED` 로 거부한다. 화면은 Basic Auth 행에 Regenerate 를 보이지 않는다.

전에는 재생성이 Basic Auth 에 발급할 값이 없는데도 설정을 그대로 저장하고 감사 로그 `auth_config.regenerate` 를 남긴 뒤 저장된 사용자 이름과 비밀번호를 평문으로 응답했다. 관리자는 같은 비밀번호를 평문 보기의 비밀번호 재확인과 `auth_config.reveal` 감사 없이 읽을 수 있었다. 화면도 이 비밀번호를 «새로 발급한 값» 으로 보여 주었다.

이 결정으로 원칙 하나를 세운다. 사용자가 입력해 저장한 비밀을 다시 읽는 길은 평문 보기 하나다([마스킹 규칙](CLE-TRIG-AUTHCFG-REVEAL.md#마스킹-규칙)). 생성 응답에 실리는 비밀번호는 같은 요청이 보낸 입력이라 이 원칙에 어긋나지 않는다.

재생성 가능한 유형을 API Key·Bearer Token·HMAC 으로 명시하고 나머지는 거부한다. 유형이 늘어도 발급 규칙을 정하기 전에는 재생성이 저장된 값을 그대로 응답하지 않는다.

거부 코드는 새로 둔다. 요청 본문에 틀린 필드가 없으므로 `details` 로 필드를 가리키는 `VALIDATION_ERROR` 와 뜻이 다르다. 유형은 바꿀 수 없으므로 상태가 바뀌면 풀리는 409 와도 다르다. 400 을 고른 것은 같은 요청을 다시 보내도 결과가 같은 클라이언트 오류이기 때문이다. 코드 카탈로그는 [에러 코드 규약과 카탈로그](../CLE-API/CLE-API-ERRCODES.md) 가 정한다.

접은 선택지는 재생성 응답의 비밀번호를 가리는 것이다. 평문 노출은 막지만 저장할 것이 없는 요청이 성공 응답과 `auth_config.regenerate` 감사를 남긴다. 화면도 «재생성됨» 을 알리게 되어 관리자가 비밀번호가 바뀌었다고 오해할 수 있다.

### 복호화 불가 인증 설정의 편집은 config 를 병합하지 않는다 (2026-11-05)

복호화 불가 표식으로 읽히는 설정에 편집 PATCH 를 보내면 `config` 를 병합하지 않고 이름·IP Whitelist·활성 상태만 바꾼다. 전에는 비밀이 아닌 config 를 표식에 병합했다. 원래 저장값을 담은 표식이면 다시 저장할 때 원래 저장값이 그대로 저장되므로 병합한 값은 응답에만 보이고 저장되지 않았다. 원래 저장값이 없는 표식이면 병합한 값이 든 표식 자체가 저장됐다. 어느 쪽이든 관리자가 고친 값은 동작하지 않는다.

병합하지 않으면 응답과 저장이 어긋나지 않는다. 편집 PATCH 가 비밀 값과 유형을 무시하는 규칙과 같은 방식이다. 이런 설정을 다시 쓰려면 원래 키를 되돌리거나 재생성한다.

접은 선택지는 표식 설정의 편집 PATCH 를 409 로 거부하는 것이다. 화면의 편집 폼은 이름만 고쳐도 늘 `config` 를 싣는다. 그래서 거부하면 표식 설정의 이름·IP Whitelist·활성 상태도 고칠 수 없다. 새 에러 코드도 필요하다.

### `__` 로 시작하는 config 키를 거부한다 (2026-11-05)

생성 요청과 편집 PATCH 의 `config` 최상위 키 중 `__` 로 시작하는 키가 있으면 400 `VALIDATION_ERROR` 로 거부한다. 복호화 불가 표식은 `__unreadable` 과 원래 저장값 키를 쓴다. 이 키를 요청으로 받아 저장하면 저장 때 transformer 가 표식으로 보고 원래 저장값 자리의 문자열을 암호화하지 않고 그대로 쓴다. 관리자 이상만 부를 수 있어 권한이 넘어가지는 않지만 저장 때 암호화를 건너뛸 수 있다.

조용히 버리지 않고 거부한다. 같은 API 가 틀린 입력(IP Whitelist 형식, Basic Auth 빈 값)을 400 으로 알리는 방식과 맞춘다. 화면의 폼은 이런 키를 보내지 않으므로 API 를 직접 부른 경우에만 걸린다. 표식 키 두 개만 막지 않고 `__` 접두사 전체를 막는 것은 표식이 나중에 키를 더해도 같은 구멍이 생기지 않게 하려는 것이다.
