## 개요

이 문서는 [EIA 수신 API와 SSE](CLE-EIA-INBOUND.md) 의 하위 문서로 SSE 이벤트 스트림의 형식, 이벤트 종류, 재전송과 `execution.replay_unavailable`, 서버 인스턴스 사이의 전달, 스트림 닫기와 연결 오류를 정한다.

## SSE 이벤트 스트림

```
GET /api/external/executions/{executionId}/stream
Authorization: Bearer <iext_jwt | itk_token>   # 브라우저 EventSource 는 ?token=<jwt> 허용
Accept: text/event-stream
Last-Event-Id: 42                              # 다시 연결할 때(선택)
```

스트림 형식 예시:

```text
event: execution.started
id: 1
data: {"executionId":"550e8400-...","workflowId":"...","mode":"production","startedAt":"..."}

event: execution.node.started
id: 2
data: {"executionId":"...","nodeId":"...","nodeType":"manual_trigger"}

event: execution.waiting_for_input
id: 3
data: { ... 알림 웹훅과 같은 안쪽 객체 ... }

: heartbeat

event: execution.resumed
id: 4
data: {"executionId":"...","nodeId":"..."}

event: execution.completed
id: 99
data: { ... 알림 웹훅과 같은 안쪽 객체 ... }
```

`: heartbeat` 는 15초마다 보내는 주석 줄이다. 이벤트가 아니며, 프록시의 유휴 연결 끊김을 막는다.

### 이벤트 종류

SSE 는 알림 웹훅 이벤트(`execution.waiting_for_input`·`completed`·`failed`·`cancelled`·`ai_message`)에 더해 다음 이벤트도 보낸다.

- 노드 이벤트: `execution.node.started`·`execution.node.completed`·`execution.node.failed`·`execution.node.cancelled`·`execution.node.skipped`
- 대화·진행 이벤트: `execution.message`·`execution.user_message`·`execution.tool_call_started`·`execution.tool_call_completed`·`execution.resumed`
- 실행 시작 `execution.started`, 제어 프레임 `execution.replay_unavailable`

각 이벤트의 필드는 [WebSocket 이벤트와 명령](../CLE-API/CLE-API-WS-EVENTS.md) 과 같다. SSE 는 봉투 차원에서 WS 와 같은 평면 객체에 `triggerId`·`workflowId` 를 더하고, 알림 웹훅의 `payload` 래퍼는 없다. 채널별 봉투 차이와 종결 이벤트 필드 집합, `waiting_for_input` 의 실제 필드 이름은 [EIA 알림 웹훅](CLE-EIA-NOTIFY.md) 이 정한다.

디버그 전용 필드(`nodeOutput.meta.turnDebug[].llmCalls` 같은 원본 LLM 요청·응답)는 필드 이름 기준으로 깊이와 관계없이 빠진다. 인증된 내부 WS(에디터)에만 남는다. 노드 출력 키 허용 목록과 자격 증명 값 가리기의 적용 범위는 [응답 자격 증명 마스킹](../CLE-API/CLE-API-EGRESS.md) 이 정한다.

### 표시 메시지 이벤트

표시 메시지 이벤트(`execution.message`)는 버튼 없이 자동으로 진행하는(non-blocking) Presentation 노드(`carousel`·`table`·`chart`·`template`)가 완료될 때 보내는 실행 수준 이벤트다. AI 가 만든 `execution.ai_message` 와 뜻이 다른 정적 표시 메시지다.

```json
{
  "executionId": "550e8400-...",
  "nodeId": "<graph uuid>",
  "nodeType": "template",
  "presentations": [{ "config": { "outputFormat": "markdown" }, "output": { "rendered": "..." } }],
  "seq": 12,
  "timestamp": "..."
}
```

- `presentations[i]` 는 `{ config, output }` 평면 객체다. AI Agent `render_*` 의 표시물 페이로드(`PresentationPayload`, [AI 에이전트 노드 출력과 디버그](../CLE-NODE-AI/CLE-NODE-AGENT-OUTPUT.md))와 같은 위젯 렌더 경로(`classifyPresentation`)를 탄다. 다만 `PresentationPayload` 의 `{ type, toolCallId, renderedAt, payload }` 래핑 없이 핸들러 구조 출력(`adaptHandlerReturn` 의 config·output)을 그대로 싣는다.
- 5분 재전송 대상이다(`id`=순번). 노드 수준 `execution.node.completed` 와 별개다. 후자는 모든 비차단 노드의 디버깅용 전체 이벤트이고, `execution.message` 는 Presentation 네 종류만 싣는 EIA 표시 이벤트다. EIA 클라이언트가 전체 이벤트를 직접 구독하지 않게 하려는 것이다.
- 불변식: 위젯·EIA 클라이언트는 비차단 Presentation 노드의 렌더를 `execution.message` 에서만 받고 `execution.node.completed` 는 무시한다. 반대로 채팅 채널 어댑터는 계속 `execution.node.completed` 를 받는다([채팅 채널](../CLE-CHAT/CLE-CHAT-CORE.md)). 그래서 두 경로가 같은 내용을 두 번 보내지 않는다.
- 이 이벤트는 SSE 에만 더한 것이다. 서버 간 알림 웹훅 화이트리스트에는 없다.
- 참조 구현: `codebase/channel-web-chat/src/lib/eia-events.ts` 의 `parseMessage`.

### 스트림 규칙

- `id` 필드는 그 실행의 이벤트 순번(`seq`)이다. WebSocket 이벤트 래퍼의 순번, 알림 웹훅의 `seq` 와 같은 값이다.
- `Last-Event-Id` 헤더나 `?lastEventId=` 쿼리로 다시 연결하면 5분 재전송 버퍼(SSE replay buffer)에서 놓친 이벤트를 다시 보낸다.
- 첫 연결에서 `?lastEventId=0` 을 명시하면 버퍼의 순번 1 이상 이벤트를 모두 다시 보낸다. 구독 전에 지나간 이벤트를 채울 수 있고, 상태 조회 시드와 함께 쓴다.
- 서버는 다음 가운데 하나에 해당할 때마다 `execution.replay_unavailable` 을 한 번 보낸다. 클라이언트는 상태 조회로 현재 상태를 다시 읽는다. payload 는 `{ executionId, lastEventId, message }` 이고 `lastEventId` 는 클라이언트가 마지막으로 받은 순번이다. 연결한 뒤 받은 이벤트가 없으면 연결할 때 보낸 `Last-Event-Id` 이고 그것도 없으면 `0` 이다.
  1. 버퍼가 요청 범위를 다 채우지 못한다(만료나 개수 상한으로 중간 순번 유실). 다시 보낼 수 있는 가장 이른 순번이 `Last-Event-Id + 1` 이 아니면 부분 재전송 대신 이 신호를 보낸다. 구현은 `sse-adapter.service.ts` 의 `replayOrSignalUnavailable` 이다. 버퍼 안의 연속 구간 재전송은 손실 없이 동작한다.
  2. 버퍼에 `Last-Event-Id` 뒤의 이벤트가 없는데 버퍼가 비었거나 Redis 에서 읽지 못해 버퍼만으로 판정할 수 없다. 버퍼 키는 그 실행의 마지막 이벤트 뒤 5분이 지나면 사라진다. 그때 서버는 실행의 순번 카운터와 견준다. 카운터가 `Last-Event-Id` 보다 크면 그 사이 순번 가운데 연결을 준비하며 모은 실시간 이벤트에 없는 것이 있을 때 신호를 보낸다. 카운터를 읽지 못하면(키가 없음 · Redis 장애 · 메모리 모드) 놓쳤을 수 있다고 보고 신호를 보낸다. 견주는 방법과 카운터의 수명은 [EIA 데이터와 흐름 「SSE 스트림」](CLE-EIA-DATA.md#sse-스트림) 이 정한다.
  3. 연결을 준비하는 동안(연결 자리 얻기 · 토큰 다시 확인 · 재전송) 모은 실시간 이벤트가 재전송 버퍼의 개수 상한과 같은 상한을 넘었다. 서버는 가장 오래된 것부터 버린다. 실시간 전달로 바꾸기 전에 이 신호를 먼저 보내고 남은 이벤트를 보낸다.
  4. 서버의 실시간 구독 연결이 끊겼다 복구되거나 실행 채널 구독 확인이 늦게 왔다. 서버는 그 사이 놓친 구간을 재전송 버퍼로 채운다. 1 · 2 번과 같은 판정으로 채울 수 없으면 신호를 보낸다. `Last-Event-Id` 없이 연결했고 순번이 1 이상인 이벤트를 아직 받지 않은 스트림은 기준 순번이 없어서 이때 늘 신호를 받는다. 그 신호의 `lastEventId` 는 `0` 이다. 자세한 규칙은 [EIA 데이터와 흐름 「SSE 스트림」](CLE-EIA-DATA.md#sse-스트림) 이 정한다.
  5. 다른 서버 인스턴스가 낸 이벤트가 크기 상한을 넘어 그 서버 인스턴스 밖으로는 생략 표시(실행 id · 순번 · 이벤트 이름만 담은 표시)만 전달됐다. 실시간 전달에서는 그 순번 자리에서 신호를 보낸다. 재전송 범위에 그런 순번이 있으면 1 번처럼 구간이 끊긴 것으로 보고 신호를 보낸다. 빠진 순번은 받은 순번으로 세지 않으므로 `lastEventId` 를 바꾸지 않는다. 상한과 예외(종료 이벤트)는 [EIA 데이터와 흐름 「SSE 스트림」](CLE-EIA-DATA.md#sse-스트림) 이 정한다.
- 2번 조건은 놓친 이벤트가 없어도 신호를 보낼 수 있다. 이벤트를 아직 하나도 내지 않은 새 실행에 `lastEventId=0` 으로 연결하면 카운터가 없어 신호가 간다. 카운터가 만료됐거나 지워진 경우와 구별할 수 없기 때문이다. 클라이언트는 상태 조회를 한 번 더 할 뿐이고 스트림은 그대로 이어진다. 위젯은 시작할 때 이미 상태 조회로 현재 대기 표면을 시드한다([단발 상태 조회](CLE-EIA-INBOUND-STATUS.md#단발-상태-조회)).
- `execution.replay_unavailable` 은 내부 WS 의 `replay.unavailable` 과 뜻이 같다. SSE 이벤트 이름 규칙(`execution.*`)에 맞추려고 이름만 다르게 했다.
- `execution.replay_unavailable` 은 실행 순번을 배정받지 않는 제어 프레임이다. SSE 연결을 시작할 때 보내고 위 4 · 5 번 경우에는 스트림 도중에도 보낸다. 순번 자리에 `0` 을 쓰고 SSE `id:` 줄을 생략한다(`writeSseFrame` 은 순번이 0 이하면 쓰지 않는다). 브라우저 `EventSource` 의 Last-Event-Id 가 `0` 으로 바뀌어 다음 자동 재연결이 전체 재전송을 일으키는 것을 막는다.
- 신호를 보낸 뒤에도 스트림은 닫지 않는다. 위젯은 이 신호를 받으면 상태 조회 스냅샷으로 다시 맞춘다. 스냅샷이 이미 종료 상태면 공백 사이에 종료 이벤트까지 잃은 것이므로 종료를 확정한다. 소비 규칙은 [웹채팅 위젯](../CLE-WEBCHAT/CLE-WEBCHAT-WIDGET.md) 이 정한다.
- 종료 이벤트(`execution.completed`·`failed`·`cancelled`)를 보낸 뒤 서버가 연결을 닫는다.
- 트리거 단위 토큰(`itk_*`)으로 연 스트림은 종료 이벤트 전이라도 서버가 닫을 수 있다. 그 토큰을 재발급할 때, PATCH 가 전략을 `per_trigger` 에서 다른 값으로 바꿔 토큰을 지울 때, PATCH 가 인터랙션을 끌 때, 트리거를 지울 때다. 어느 서버 인스턴스에 붙은 스트림이든 닫는다. 가드를 통과한 뒤 무효가 된 토큰을 놓치지 않도록 서버는 구독을 등록하고 연결 자리를 얻은 뒤 SSE 헤더를 보내기 전에 토큰을 다시 확인한다. 토큰이 무효면 `401 TOKEN_INVALID` 로 거부한다. 그 사이 그 토큰의 닫기 신호가 와도 같은 401 이다([스트림 연결 오류](#스트림-연결-오류)). 스트림이 열려 있는 동안 서버는 60초마다 토큰을 다시 확인한다. 그래서 닫기 신호가 서버 인스턴스 사이에서 유실돼도 무효가 된 토큰의 스트림은 이 간격 안에 닫힌다. 다시 확인하다 조회가 실패하면 스트림을 유지하고 다음 재확인에서 다시 본다.
- SSE 헤더를 보낸 뒤에 닫으면 따로 보내는 이벤트 없이 200 응답이 끝난다. 클라이언트가 옛 토큰으로 다시 연결하면 가드가 401 로 거부한다. 재발급 · 전략 변경 · 인터랙션 끄기 뒤에는 `TOKEN_INVALID` 이고 트리거를 지운 뒤에는 `EXECUTION_NOT_FOUND` 다. 브라우저 `EventSource` 는 200 이 아닌 응답을 받으면 자동 재연결을 멈춘다. `itk_*` 를 쓰는 서버 간 자동화는 이 401 을 받으면 같은 토큰으로 다시 연결하지 않는다.
- 실행 단위 토큰(`iext_*`)으로 연 스트림은 토큰이 만료되거나 갱신돼도 닫지 않는다. 그 실행의 종료 이벤트까지 이어진다([EIA 데이터와 흐름 「실행 단위 토큰」](CLE-EIA-DATA.md#실행-단위-토큰)).
- 동시 연결 한도는 모든 서버 인스턴스의 연결을 합해 센다. 한도를 넘으면 `429 TOO_MANY_CONNECTIONS` 다. 연결마다 15초 heartbeat 가 그 연결 자리의 시각도 갱신한다. 서버 인스턴스가 죽어 연결 종료를 기록하지 못해도 그 자리는 마지막 heartbeat 뒤 45초(heartbeat 간격의 세 배)가 지나면 빠진다.
- 서버 인스턴스가 여럿이어도 sticky-session 이 필요 없다. SSE fan-out(`SseFanoutService`)이 실행 이벤트, 5분 재전송 버퍼, 스트림 닫기 신호, 동시 연결 수를 Redis 로 서버 인스턴스끼리 나눈다. 그래서 클라이언트는 어느 서버 인스턴스에 연결해도 그 실행의 이벤트를 모두 받고 다른 서버 인스턴스로 다시 연결해도 재전송을 받는다. 재전송과 실시간 전달이 겹치면 그 스트림에 이미 보낸 순번 이하의 이벤트는 다시 보내지 않는다. 순번이 0 이하인 제어 프레임은 이 규칙에서 빠진다. 키와 TTL 은 [EIA 데이터와 흐름 「SSE 스트림」](CLE-EIA-DATA.md#sse-스트림) 이 정한다.
- Redis 를 쓸 수 없으면 서버 인스턴스 메모리로 이어 간다. 이때 클라이언트는 연결한 서버 인스턴스가 낸 이벤트만 받는다. 재전송도 그 서버 인스턴스의 버퍼에서만 한다. 동시 연결 수도 서버 인스턴스마다 따로 센다. 서버는 경고 로그를 남긴다.
- 알려진 한계: 구독 공백(위 4 번) 말고 남는 한계는 서버 인스턴스 사이에서 이벤트 도착 순서가 뒤집힌 경우와 크기 상한을 넘은 이벤트(위 5 번)다. 서버가 그 실행의 이벤트를 Redis 에 쓸지 정하는 동안에는 다른 서버 인스턴스에 연결한 클라이언트가 이벤트를 최대 2초 늦게 받을 수 있다. 목록과 영향은 [EIA 데이터와 흐름 「SSE 버퍼와 실시간 전달을 Redis 에 둔다」](CLE-EIA-DATA.md#sse-버퍼와-실시간-전달을-redis-에-둔다-2026-10-17) 의 남은 위험에 있다. 버퍼 크기(5분·최대 1000건)는 [EIA 데이터와 흐름](CLE-EIA-DATA.md) 에 있다.

### 스트림 연결 오류

SSE 연결은 SSE 헤더를 보내기 전에만 오류 상태 코드로 거부할 수 있다. 서버는 다음 순서로 확인한다.

1. 가드가 토큰을 확인한다.
2. 구독을 등록하고 동시 연결 자리를 얻는다.
3. 트리거 단위 토큰이면 토큰을 다시 확인한다.
4. SSE 헤더를 보내고 재전송을 시작한다.

| 상태 | 코드 | 조건 |
|---|---|---|
| `401` | `TOKEN_*` | 1단계 가드의 토큰 검증 실패. 코드와 뜻은 [명령 에러](CLE-EIA-INBOUND-COMMAND.md#명령-에러) 와 같다. `X-Refresh-Token-Url` 헤더가 붙는다 |
| `401` | `EXECUTION_NOT_FOUND` | 1단계. 트리거 단위 토큰으로 열 때 실행이 없거나 그 실행의 트리거가 지워졌다([에러 코드 규약과 카탈로그 §6.9](../CLE-API/CLE-API-ERRCODES.md#69-eia-rest-외부-표면-도메인-문서-참조)). `X-Refresh-Token-Url` 헤더가 붙는다 |
| `401` | `TOKEN_INVALID` | 2 · 3단계. 트리거 단위 토큰으로 열 때 다시 확인한 토큰이 무효다. 인터랙션을 껐거나 전략을 바꿨거나 트리거를 지워 쓸 수 있는 토큰이 없으면 `message` 는 `Trigger has no per-trigger token` 이다. 저장된 토큰과 다르면 `Token rejected` 다. 연결 자리를 얻거나 토큰을 다시 확인하는 동안 그 토큰의 닫기 신호가 와도 이 코드이고 `message` 는 `Token rejected` 다. `X-Refresh-Token-Url` 헤더가 붙는다 |
| `429` | `TOO_MANY_CONNECTIONS` | 2단계. 그 실행의 SSE 연결이 모든 서버 인스턴스를 합해 이미 3개다. 연결 자리를 얻는 동안 닫기 신호가 왔으면 이 코드 대신 위의 `401 TOKEN_INVALID` 다 |
| `500` | `INTERNAL_ERROR` | 3단계. 트리거 단위 토큰을 다시 확인하다 데이터베이스 오류가 났다 |

다시 확인에 실패한 응답의 예시다.

```text
401 Unauthorized
X-Refresh-Token-Url: /api/external/executions/{executionId}/refresh-token

{"error":{"code":"TOKEN_INVALID","message":"Token rejected"}}
```

SSE 헤더를 보낸 뒤 트리거 단위 토큰이 무효가 되면 서버는 따로 보내는 이벤트 없이 200 응답을 끝낸다([스트림 규칙](#스트림-규칙)).

## Rationale

### SSE 를 이벤트 채널로 고른다

외부 인바운드 이벤트 스트림의 1차 채널로 SSE 를 쓴다. 고른 기준은 다음과 같다.

- HTTP/1.1 호환이라 CDN·리버스 프록시·모바일 환경에 잘 맞는다.
- 브라우저 표준 `EventSource` API 가 있다.
- 자동 재연결과 `Last-Event-Id` 기반 누락 복구가 표준에 들어 있다.
- 서버리스·에지 환경에서도 구현할 수 있다.

Long-polling 은 실시간 채팅·멀티턴에서 지연이 커 사용 경험이 나빠지므로 뺐다. 외부 WebSocket 은 아래 결정에 따라 보류했다.

### 외부 WebSocket 채널은 보류한다

v1 에서 외부 WebSocket 채널을 새로 만들지 않는다. SSE 와 REST 조합으로 충분하다.

1. 구현이 둘로 갈린다: 이미 내부 `/ws` 게이트웨이가 있다. 외부 WS 를 따로 만들면 인증 흐름·이벤트 발행 경로·재연결 정책이 두 곳에 생겨 백엔드 유지 부담이 두 배가 된다.
2. 양방향 이점이 작다: 외부 WS 의 저지연 양방향 이점은 인바운드 REST POST 로 충분히 대신한다. 멀티턴 AI 채팅도 SSE 수신과 REST 제출로 동작한다(실측 지연 100ms 대로 사람이 느끼는 임계 아래).
3. 인프라 제약: WS 는 CDN·서버리스·모바일에서 까다롭고 일부 기업 방화벽이 막기도 한다. SSE 는 표준 HTTP 응답이라 막힐 일이 사실상 없다.
4. 호환성 모델 단순화: 외부 클라이언트가 SSE 와 WS 중 고를 수 있으면 SDK·문서·테스트 매트릭스가 두 배로 는다. v1 은 SSE+REST 하나로 맞춰 학습 부담을 낮춘다.

다시 검토할 계기는 다음 중 하나다.

- SSE 동시 연결 한계(브라우저당 HTTP/1.1 연결 6개)가 실제 병목으로 측정된다.
- 인바운드 REST 왕복 지연이 사용 경험을 해치는 수준(평균 300ms 초과)으로 측정된다.
- 요청 빈도가 높아(분당 60 이상) 실행별 REST 부하가 SSE 대비 비효율임이 입증된다.
- 외부 WS 를 명시적으로 요구하는 대형 통합 파트너가 생긴다.

다시 도입한다면 기존 `/ws` 게이트웨이를 그대로 쓰고 인증 단계에서 `iext_*`·`itk_*` 도 받게 넓힌다. 새 URL 은 만들지 않는다. 명령·이벤트 형식은 [WebSocket 이벤트와 명령](../CLE-API/CLE-API-WS-EVENTS.md) 과 완전히 같게 해 구현이 갈라지지 않게 한다.

### 표시 메시지 이벤트를 새로 둔다

버튼 없이 자동으로 진행하는 Presentation 노드(캐러셀·표·차트·템플릿)는 핸들러가 `status` 없이 `{ config, output }` 만 돌려주고, 엔진은 노드 수준 `execution.node.completed` 만 냈다. 이 이벤트는 SSE 까지 가지만 웹채팅 위젯에는 노드 수준 핸들러가 없어 무시했다. 그 결과 노드 사이의 표시 메시지(예: 캐러셀 다음 템플릿 메시지)가 미리보기에서 빠졌다(2026-06-25). 입력 대기(차단)와 `ai_message`(AI 생성)는 보였지만, 자동 진행 표시 노드의 출력을 싣는 실행 수준 이벤트가 없었다.

그래서 Presentation 네 종류가 차단 없이 완료되면 실행 수준 `execution.message` 를 새로 낸다. `presentations` 는 `{ config, output }` 평면 객체라 위젯의 기존 렌더 경로(`classifyPresentation`)를 그대로 쓴다. 위젯은 이 이벤트를 기존 `AI_MESSAGE` reducer 로 보내되 텍스트를 비워 표시물만 그린다. 텍스트와 표시물이 겹쳐 말풍선이 두 번 생기는 것을 막기 위해서다.

기각한 대안:

- 위젯이 `execution.node.completed` 를 직접 구독하는 안: 모든 비차단 노드(code·llm·logic 등)의 전체 이벤트라 내부 라이프사이클 필드가 EIA 로 새고 걸러 내기가 약하다. Presentation 전용 이벤트가 경계를 분명히 한다.
- `execution.ai_message` 를 다시 쓰는 안: 정적 표시 노드 출력을 "AI 생성 메시지" 로 부르면 뜻이 헷갈리고, AI 턴 전용 불변식(`turnCount`·`messages` 스냅샷 등)과 부딪친다.

이 변경은 SSE·서버 안 fan-out 에만 이벤트를 더한다. 채팅 채널이 기각한 대상(외부 HTTP 알림 웹훅 화이트리스트 확장)과는 별개이고, 알림 웹훅 다섯 종은 그대로다. 엔진은 여전히 단일 싱크로만 내므로 단일 싱크 원칙도 유지된다.

### 버퍼 만료를 명시 신호로 알린다

SSE 재연결 재전송(`Last-Event-Id`) 때 5분 버퍼가 요청 범위를 다 채우지 못하면(만료나 `SSE_BUFFER_MAX_EVENTS` 상한 초과로 중간 순번 유실) 부분 재전송 대신 `execution.replay_unavailable` 을 한 번 보낸다. `SSE_BUFFER_MAX_EVENTS`(1000)는 코드 상수라 설정으로 바꿀 수 없다. 이전의 "만료분을 조용히 버림" 을 명시 신호로 바꿨다.

- **공백 판정**: 순번은 단조 증가라 만료·폐기는 늘 앞쪽부터 일어난다. 다시 보낼 수 있는 가장 이른 순번이 `Last-Event-Id + 1` 이 아니면 그 사이가 유실된 것이다. 다시 보낼 수 있는 구간 안에 구멍이 있어도(상류 순번 유실·중복 같은 비정상) 공백으로 본다. 이 기능이 없애려는 조용한 누락을 놓치지 않으려는 전 구간 연속성 방어다(`replayable.every`). 버퍼를 다 읽었고 버퍼가 비어 있지 않은데 `seq > Last-Event-Id` 인 이벤트가 없을 때만 클라이언트가 최신까지 받은 것으로 본다. 그때는 신호를 보내지 않고 실시간 스트림으로 이어 간다.
- **`id: 0` 을 싣는 안은 기각했다**: WHATWG `EventSource` 는 `id:` 를 받으면 내부 Last-Event-Id 를 바꾼다. 그러면 다음 브라우저 자동 재연결이 `Last-Event-Id: 0` 을 보내 전체 재전송을 뜻하지 않게 일으킨다. `id:` 를 생략하면 클라이언트의 실제 위치가 보존된다. 순번 자리의 `0` 은 상태 조회의 `SSE_SEQ_PLACEHOLDER` 관례와 같은 영역이다.
- **내부 WS 에는 두지 않는다**: 내부 WS 는 순번 버퍼 없이 재구독 때 실행 스냅샷 이벤트(`execution.snapshot`) 한 번으로 복구하므로 만료 신호가 구조상 필요 없다([WebSocket 연결과 채널 구독](../CLE-API/CLE-API-WS.md)). 그래서 이 신호는 SSE 에만 있다.
- **신호 뒤에도 연결을 유지한다**: 신호를 보낸 뒤에도 구독자를 활성 목록에 둔다. 클라이언트는 상태 조회로 현재 상태만 함께 보정하고 이후 이벤트는 열린 스트림으로 계속 받는다. 상태 조회의 순번은 늘 `0` 이라 재연결 근거가 없다. 그래서 다시 연결하지 않고 함께 보정하는 것이 유일하게 맞는 흐름이다.
- **버퍼가 비면 순번 카운터와 견준다 (2026-10-17)**: 처음에는 버퍼에 `seq > Last-Event-Id` 인 이벤트가 없으면 최신으로 봐서, 버퍼가 통째로 사라진 뒤 다시 연결하면 놓친 이벤트가 있어도 신호를 보내지 못했다. Redis 로 옮긴 버퍼는 마지막 이벤트 뒤 5분이 지나면 키가 사라진다. Redis 장애로 버퍼를 읽지 못하는 경우도 생긴다. 그래서 2026-10-17 에 버퍼가 비었거나 읽지 못했을 때 실행의 순번 카운터와 견주도록 바꿨다. 카운터를 읽지 못하면 신호를 보낸다. 상태 조회를 한 번 더 하게 하는 편이 이벤트를 조용히 잃는 것보다 낫다. 기각한 대안은 옛 판정을 그대로 두는 안이다. 버퍼 키가 사라진 뒤 다시 연결한 클라이언트는 놓친 이벤트를 모른 채 실시간 스트림만 받는다. 새 실행의 거짓 신호(스트림 규칙의 2번 조건 설명)는 받아들인다. 거짓 신호의 비용은 상태 조회 한 번이다.
- **연결을 준비하는 동안 모은 이벤트에도 상한을 둔다 (2026-10-17)**: 서버는 구독을 등록한 때부터 실시간 전달로 바꿀 때까지 온 실시간 이벤트를 모아 둔다. 실시간 채널 구독이 확정되기 전에 낸 이벤트가 재전송과 실시간 전달 사이로 빠지지 않게 하려는 것이다([EIA 데이터와 흐름 「SSE 스트림」](CLE-EIA-DATA.md#sse-스트림)). 재전송이 오래 걸리면 모은 이벤트가 끝없이 늘 수 있다. 그래서 재전송 버퍼와 같은 개수 상한을 두고 넘으면 가장 오래된 것부터 버린다. 버린 것이 있으면 `execution.replay_unavailable` 을 보낸다. 기각한 대안은 둘이다. 상한 없이 모으는 안은 연결 하나가 메모리를 끝없이 쓸 수 있다. 상한을 넘으면 알리지 않고 버리는 안은 이 신호가 없애려는 조용한 누락을 다시 만든다.

### SSE 를 여러 서버 인스턴스에서 받는다 (2026-10-17)

스트림 규칙은 처음에 서버 인스턴스 하나를 전제로 했다(버퍼가 서버 인스턴스 메모리에 있었다). 그런데 쿠버네티스 배포는 이미 서버 인스턴스를 둘 이상 띄우고 sticky-session 을 쓰지 않는다. 실행 세그먼트와 재개도 아무 서버 인스턴스의 워커에서나 돈다. 그래서 2026-10-17 에 Redis 로 서버 인스턴스끼리 나누는 구조를 구현하기로 정했다.

나누는 대상과 메모리 폴백은 [스트림 규칙](#스트림-규칙) 에 있다. 순번은 이미 Redis `INCR` 로 실행마다 단조 증가하므로 재전송과 실시간 전달이 겹쳐도 순번으로 걸러 한 번만 보낸다. 키 · TTL · 장애 정책과 설계의 자세한 근거는 [EIA 데이터와 흐름](CLE-EIA-DATA.md) 이 정한다.

기각한 대안:

- 서버 인스턴스 하나로 제한하는 안(지금까지의 전제): 배포가 이미 서버 인스턴스를 여럿 띄운다. 이 전제를 지키려면 SSE 때문에 수평 확장을 포기해야 한다.
- sticky-session 로드밸런서: 클라이언트를 서버 인스턴스 하나에 묶을 뿐 실행을 묶지 않는다. 이벤트를 낸 서버 인스턴스와 SSE 연결을 받은 서버 인스턴스는 여전히 다를 수 있다.

### 트리거 단위 토큰이 무효가 되면 알리지 않고 닫는다 (2026-10-17)

트리거 단위 토큰이 무효가 되면 그 토큰으로 연 스트림을 닫는다는 결정은 2026-10-09 에 했다. 근거는 [EIA 데이터와 흐름 「재검토에서 갈린 EIA 동작을 정한다」](CLE-EIA-DATA.md#재검토에서-갈린-eia-동작을-정한다-2026-10-09) 에 있다. 2026-10-17 에 그 결정을 스트림 규칙으로 옮기고 클라이언트가 받는 신호를 적었다. 인터랙션을 끄는 PATCH 도 같은 이유로 스트림을 닫는다. 가드가 인터랙션이 꺼진 트리거의 토큰을 거부하므로 열린 스트림만 남겨 두면 같은 인가 틈이 생긴다.

닫기 전에 알리지 않는다. 서버는 SSE 응답을 끝내고 클라이언트는 다시 연결할 때 401 을 받는다. 내부 WebSocket 은 토큰 만료 60초 전에 알린다([WebSocket 연결과 채널 구독](../CLE-API/CLE-API-WS.md#소켓-수명을-토큰-수명에-묶는다-2026-09-02)). 그 만료 시각은 미리 알 수 있고 클라이언트는 그 사이 토큰을 새로 받아 다시 연결할 수 있다. 트리거 단위 토큰이 무효가 되는 것은 관리자의 조작이라 미리 알 수 없다. 스트림 안에서 새 토큰을 건넬 방법도 없다. 그래서 미리 알려도 클라이언트가 할 수 있는 일이 없다. `execution.replay_unavailable` 과도 경우가 다르다. 그 신호는 연결을 유지한 채 상태를 다시 맞추라고 알린다. 토큰이 무효가 된 스트림은 더 이을 수 없으므로 연결을 끝내는 것 자체가 신호다.

구독을 등록한 뒤 SSE 헤더를 보내기 전에 토큰을 다시 확인하는 것은 2026-10-17 에 더했다. 가드를 통과한 뒤 구독을 등록하기 전에 토큰이 무효가 되면 닫기 신호는 아직 등록되지 않은 구독자를 지나친다. 그러면 무효인 토큰의 스트림이 남는다. 닫기 신호는 토큰을 무효로 만든 트랜잭션이 커밋된 뒤에 나간다. 그래서 등록 앞에 신호가 지나갔다면 등록 뒤에 다시 읽은 값은 커밋 뒤의 값이다. 등록 뒤에 온 신호는 등록된 구독자를 닫는다. 이 시점에는 아직 SSE 헤더를 보내지 않았으므로 서버는 200 을 끝내지 않고 바로 401 로 답한다. 클라이언트는 다시 연결해 볼 필요 없이 첫 응답에서 토큰을 더 쓸 수 없다는 것을 안다. 기각한 대안은 다시 확인하지 않고 닫기 신호만 기다리는 안이다. 등록 앞에 지나간 신호는 그 구독자를 닫지 못한다.

기각한 대안:

- 닫기 전에 새 닫힘 이벤트를 보내는 안: 클라이언트가 그 이벤트를 받고 할 수 있는 일은 다시 연결해 401 을 받는 것과 같다. SSE 이벤트 목록과 WebSocket 대응표만 늘어난다.

### 스트림 도중에도 재전송 불가 신호를 보낸다 (2026-11-05)

`execution.replay_unavailable` 은 이전에는 연결을 시작할 때만 보냈다. 서버의 구독 공백과 크기 상한 때문에 빠진 이벤트를 알리지 않으면 그 스트림에서 조용히 빠진다. 그래서 두 경우에는 스트림 도중에도 보낸다([스트림 규칙](#스트림-규칙) 의 4 · 5 번). 위젯은 이미 스트림 도중의 신호도 같은 방법으로 처리한다. 상태 조회 스냅샷으로 다시 맞추는 것이다([웹채팅 위젯](../CLE-WEBCHAT/CLE-WEBCHAT-WIDGET.md)). 자세한 근거는 [EIA 데이터와 흐름 「SSE 의 Redis 쓰기를 줄이고 구독 공백을 메운다」](CLE-EIA-DATA.md#sse-의-redis-쓰기를-줄이고-구독-공백을-메운다-2026-11-05) 에 있다.

기각한 대안:

- 실시간 전달에서 `seq` 공백을 보고 신호를 보내는 안: 서버 인스턴스 사이에서 도착 순서가 뒤집히면 잠깐 공백이 생겨 거짓 신호가 난다. 공백을 얼마나 기다릴지 정할 근거도 없다. EIA 데이터와 흐름이 같은 이유로 기각했다.

같은 작업에서 트리거 단위 토큰으로 연 스트림은 열려 있는 동안 60초마다 토큰을 다시 확인하게 했다. 이 주기 재확인은 닫기 신호가 유실됐을 때의 보완이다. 닫기 신호는 그대로 스트림을 바로 닫는다. 2026-10-17 에 «다시 확인하지 않고 닫기 신호만 기다리는 안» 을 기각하고 둔 연결할 때의 재확인도 그대로다([트리거 단위 토큰이 무효가 되면 알리지 않고 닫는다](#트리거-단위-토큰이-무효가-되면-알리지-않고-닫는다-2026-10-17)). 주기 재확인은 그 재확인을 대신하지 않는다. 재확인 조회가 실패할 때 스트림을 유지하는 위험은 [EIA 데이터와 흐름 「인프라 장애에는 fail-open 한다」](CLE-EIA-DATA.md#인프라-장애에는-fail-open-한다) 에 있다.
