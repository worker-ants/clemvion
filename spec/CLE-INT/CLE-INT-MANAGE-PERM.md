## 개요

이 문서는 [통합 관리](CLE-INT-MANAGE.md) 의 하위 문서로 통합 동작별 권한, 역할 거부 코드, 삭제 판정 순서, 개인 통합 행을 쓰는 트랜잭션의 잠금과 멤버가 나가거나 제거될 때의 개인 통합 삭제를 정한다. 노드가 개인 통합을 쓸 수 있는지는 [통합 관리 — 개인 통합 사용 판정](CLE-INT-MANAGE-USE.md) 이 정한다.

## 권한

| 동작 | 개인 통합 | 조직 통합 |
| --- | --- | --- |
| 생성 | 편집자 이상 | 관리자 이상 |
| 저장 전 연결 테스트 | 편집자 이상 | 편집자 이상 |
| 조회 | 통합 소유자만(뷰어 포함) | 모든 멤버 |
| 수정(별칭) | 통합 소유자만(편집자 이상) | 관리자 이상 |
| 통합 재인증 | 통합 소유자만(편집자 이상) | 관리자 이상 |
| 자격 증명 교체 | 통합 소유자만(편집자 이상) | 관리자 이상 |
| 추가 권한 요청 | 통합 소유자만(편집자 이상) | 관리자 이상 |
| 공개 범위 전환 | 통합 소유자만(관리자 이상) | 관리자 이상 |
| 삭제 | 통합 소유자만(뷰어 포함, 사용처 없을 때) | 관리자 이상(사용처 없을 때) |
| 워크플로우 노드에서 사용 | [개인 통합 사용 판정](CLE-INT-MANAGE-USE.md#개인-통합-사용-판정)을 통과할 때만 | 모든 멤버 |

역할 매트릭스 전체는 [워크스페이스와 멤버](../CLE-ACCT/CLE-ACCT-WS.md) 가 기준이다. 판정 규칙(2026-09-25 부터 강제):

- **통합 소유자는 `created_by` 다.** 개인 통합에는 역할 우위가 없다. 소유자·관리자 역할도 남의 개인 통합을 보거나 바꾸지 못한다. 예외는 멤버 제거 하나다. 관리자가 멤버를 제거하면 그 멤버의 개인 통합도 함께 지워진다([멤버가 나가거나 제거될 때](#멤버가-나가거나-제거될-때)). 관리자가 그 통합을 보거나 고르게 되지는 않는다.
- **남의 개인 통합은 없는 통합과 같다.** 목록(`GET /api/integrations`)에서 빠지고 `:id` 경로 전부(상세, 사용처, 활동, 연결 테스트, 별칭 수정, 삭제, 자격 증명 교체, 통합 재인증, 추가 권한 요청, 공개 범위 전환)가 없는 ID 와 같은 `404 RESOURCE_NOT_FOUND` 를 낸다. `POST /api/integrations/oauth/begin` 의 `reauthorize`·`request_scopes` 모드(`integrationId` 지정)도 같은 판정을 받는다. 라우트 가드가 있는 경로(편집자 이상 쓰기, 관리자 이상 공개 범위 전환)는 가드의 거부 코드가 먼저 나간다. 가드는 요청 대상을 보기 전에 돌아서 남의 개인 통합이 있는지 드러나지 않는다.
- **표에 없는 조회성 경로는 «조회» 행을 따른다.** 저장된 통합의 연결 테스트(`:id/test`), 사용처, 활동, 그리고 워크플로우 어시스턴트의 통합 목록 도구와 노드 후보 제시가 해당한다. 어시스턴트의 두 경로는 여기에 노드 사용 기준을 더해 그 워크플로우에서 쓸 수 있는 통합만 고른다.
- **조직 통합의 변경은 관리자 이상이다.** 생성, 별칭 수정, 삭제, 통합 재인증, 자격 증명 교체, 추가 권한 요청, 공개 범위 전환이 해당한다. 거부는 `403 ADMIN_REQUIRED` 다. 라우트 가드의 역할 거부와 같은 코드에 동작별 문구를 싣는다. 라우트 가드(대부분 `@Roles('editor')`, 삭제는 `@Roles('viewer')`, 공개 범위 전환은 `@Roles('admin')`)는 그 아래의 첫 번째 선일 뿐이다.
- **공개 범위 전환은 관리자가 볼 수 있는 통합에만 된다.** 자기 개인 통합을 조직으로, 조직 통합을 개인으로 바꾼다. 전환해도 `created_by` 는 바뀌지 않으므로 조직에서 개인으로 바꾸면 그 통합을 만든 사람이 통합 소유자가 된다. 그러면 워크플로우 작성자가 통합 소유자가 아닌 워크플로우는 이 통합을 노드에서 쓰지 못한다. 전환은 막지 않고 다이얼로그에서 그런 워크플로우를 알린다([위험 영역 탭](CLE-INT-MANAGE-DETAIL.md#위험-영역-탭)). 그 통합을 만든 사람이 이미 워크스페이스를 나갔으면 조직에서 개인으로 바꾸지 못한다. 바꾸면 아무도 보거나 지울 수 없는 개인 통합이 다시 생긴다. 판정 순서는 관리자 미만 403 `ADMIN_REQUIRED`, 볼 수 없는 통합 404, 같은 공개 범위면 바꾸지 않고 그대로 돌려준다, 409 `INTEGRATION_OWNER_NOT_MEMBER` 다.
- **중복 사전 감지는 공개 범위를 가리지 않는다.** 상점 식별자 유일성이 워크스페이스 단위라서다. 충돌 행이 남의 개인 통합이면 `existingIntegrationId`·`existingName` 을 싣지 않고 `conflict`·`status` 만 싣는다. 설치 흐름의 409 `*_ALREADY_CONNECTED` 는 공개 범위와 상관없이 `integrationId` 를 싣지 않는다([OAuth 연결과 토큰 갱신](CLE-INT-OAUTH.md#oauthbegin-요청과-응답)).

2026-10-24 에 정한 판정 규칙([Rationale](CLE-INT-MANAGE-USE.md#개인-통합의-역할-하한과-노드-사용-기준을-정한다-2026-10-24)):

- **역할 거부 코드는 라우트 가드가 먼저 정한다.** 편집자 이상 라우트 가드가 붙는 라우트는 생성, 별칭 수정, 자격 증명 교체, 통합 재인증, 추가 권한 요청, 저장 전 연결 테스트, `oauth/begin` 이다. 뷰어가 부르면 대상의 공개 범위와 상관없이 `403 EDITOR_REQUIRED` 다. 관리자 미만 가운데 뷰어가 받는 코드는 이 규칙이 정한다.
- **공개 범위 전환은 라우트 가드가 관리자 이상으로 막는다.** 관리자 미만이 `PATCH /api/integrations/:id/scope` 를 부르면 뷰어도 `403 ADMIN_REQUIRED` 다.
- **저장 전 연결 테스트(`POST /api/integrations/preview-test`)는 편집자 이상이다.** 추가 화면에서만 쓰고 저장하지 않은 자격 증명으로 사용자가 적은 host 를 부른다. 저장된 통합의 연결 테스트(`:id/test`)는 «조회» 행을 따른다.
- **개인 통합의 쓰기는 편집자 이상이다.** 생성, 별칭 수정, 자격 증명 교체, 통합 재인증, 추가 권한 요청이 해당한다. 뷰어가 하면 라우트 가드가 `403 EDITOR_REQUIRED` 로 거절한다. `POST /api/integrations/oauth/begin` 의 `new` 모드(설치 대기 행을 만드는 Cafe24 Private·MakeShop 포함)도 생성으로 본다. 뷰어가 부르면 `403 EDITOR_REQUIRED` 다. 관리자 미만이 조직 공개 범위를 고르면 `403 ADMIN_REQUIRED` 다. OAuth 콜백이 커밋 직전에 하는 재판정도 같은 하한을 본다([OAuth 연결과 토큰 갱신](CLE-INT-OAUTH.md#처리-순서)).
- **뷰어는 자기 개인 통합을 보고 지울 수 있다.** 그래서 삭제 라우트의 역할 가드는 뷰어 이상이다. 라우트 가드는 대상 통합을 읽기 전에 돌아 공개 범위를 볼 수 없으므로 조직 통합 삭제의 관리자 검사는 서비스 계층이 대상을 읽은 뒤에 한다. 사용처가 남아 있으면 다른 역할과 같이 `409 INTEGRATION_IN_USE` 다.
- **삭제는 404, 403, 409 순으로 판정한다.** 먼저 없는 통합과 남의 개인 통합을 `404 RESOURCE_NOT_FOUND` 로 거른다. 다음으로 관리자 미만의 조직 통합 삭제를 `403 ADMIN_REQUIRED` 로 거른다. 마지막으로 사용처가 남았으면 `409 INTEGRATION_IN_USE` 다. 캐시 무효화와 감사 로그는 셋을 모두 통과한 뒤에만 남긴다. 뷰어가 조직 통합을 지우려 하면 403 만 받고 아무것도 바뀌지 않는다.
- **개인 통합을 만들거나 개인으로 바꿀 때 통합 소유자가 될 사람의 멤버십을 잠가 다시 읽는다.** 라우트 가드가 멤버십을 확인한 뒤 행을 쓰기 전에 그 멤버가 나가거나 제거될 수 있다. 그래서 개인 통합 행을 만드는 트랜잭션은 워크스페이스, 멤버십, 통합 순으로 잠그고 멤버십이 없으면 403 `NOT_A_MEMBER` 로 거절한다. 조직 통합을 개인으로 바꾸는 트랜잭션도 같은 순서로 통합을 만든 사람의 멤버십을 읽고 없으면 409 `INTEGRATION_OWNER_NOT_MEMBER` 로 거절한다. 멤버십이 있는지만 보고 역할은 보지 않는다. 잠금 순서는 [통합 쓰기의 잠금 순서](#통합-쓰기의-잠금-순서) 가 정한다.
- **노드에서 개인 통합을 쓸 수 있는지는 [개인 통합 사용 판정](CLE-INT-MANAGE-USE.md#개인-통합-사용-판정) 하나로 정한다.** 실행 시점 조회, 노드 설정 저장 검사, 참조 비우기, 고르는 화면이 모두 이 판정을 쓴다.
- **노드 설정을 저장할 때는 새로 넣거나 바꾼 참조만 검사한다.** 검사할 참조의 위치는 [플랫폼 데이터 모델 「참조의 소속」](../CLE-PLAT/CLE-PLAT-DATA.md#참조의-소속) 의 목록 하나를 따른다. 개인 통합이면 저장자와 워크플로우 작성자가 둘 다 통합 소유자여야 한다. 경로마다의 규칙과 복제·가져오기·버전 복원에서 참조를 비우는 규칙도 같은 절이 정한다.
- **설치 대기 행은 그 행을 바꿀 수 있는 사람만 다시 쓴다.** 개인 행은 통합 소유자, 조직 행은 관리자 이상이다. 남의 개인 설치 대기 행과 부딪히면 409, 조직 설치 대기 행에 관리자 미만이 오면 `403 ADMIN_REQUIRED` 다. 코드와 응답, 그 근거는 [OAuth 연결과 토큰 갱신](CLE-INT-OAUTH.md#설치-대기-행-재사용의-권한) 이 정한다.
- **설치 대기 행 재사용은 공개 범위를 넓힐 수 있다.** 개인 공개 범위로 시작한 `oauth/begin` 이 같은 상점(MakeShop 은 같은 `client_id`)의 조직 설치 대기 행을 다시 쓰면 결과 통합은 조직 공개 범위가 된다. 행의 공개 범위는 바뀌지 않고 요청과 달라질 뿐이다. 그래서 `integration.scope_changed` 감사 로그를 남기지 않는다. 이것은 [위험 영역 탭](CLE-INT-MANAGE-DETAIL.md#위험-영역-탭) 의 공개 범위 전환 확인 규칙 밖의 명시적 예외다. 그 행은 관리자 이상만 다시 쓸 수 있고 응답의 `scope` 와 [추가 흐름 안내](CLE-INT-MANAGE-LIST.md#인증-단계)로 알린다.
- **고르는 화면은 저장 검사를 통과할 통합만 고르게 한다.** 노드 설정 패널의 통합 선택기는 지금 사용자가 워크플로우 작성자가 아니면 그 사용자의 개인 통합을 고를 수 없는 항목으로 보인다. 어시스턴트의 통합 목록 도구와 노드 후보는 그 통합을 아예 뺀다. 붙여넣거나 복제한 노드는 지금 사용자가 고를 수 없는 참조를 비우고 경고한다. 화면 규칙은 [워크플로우 에디터](CLE-INT-MANAGE-RUN.md#워크플로우-에디터), [AI 어시스턴트 도구](../CLE-WF/CLE-WF-ASSIST-TOOLS.md#위젯별-후보-조회-범위), [에디터](../CLE-WF/CLE-WF-EDITOR.md#노드-조작) 가 정한다.

MCP 서버 통합을 개인 공개 범위로 등록할 수 있는지는 [미결 사항](CLE-INT-MANAGE.md#미결-사항) 에 있다.

## 멤버가 나가거나 제거될 때

멤버십을 지우는 트랜잭션 안에서 그 멤버가 통합 소유자인 그 워크스페이스의 개인 통합을 상태와 사용처에 관계없이 모두 지운다. 나가기와 제거가 같다. 조직 통합은 지우지 않는다. 커밋 뒤 지운 통합마다 캐시를 무효화하고 `integration.deleted` 감사 로그를 남긴다([감사 로그](CLE-INT-MANAGE-RUN.md#감사-로그)). 캐시 무효화의 채널과 실패 처리는 [통합 데이터와 흐름 「멤버가 나가거나 제거될 때」](CLE-INT-DATA.md#멤버가-나가거나-제거될-때) 가 정한다. 이 삭제는 사용처 삭제 차단을 거치지 않는다([사용처 추적과 삭제 차단](CLE-INT-MANAGE-RUN.md#사용처-추적과-삭제-차단)). 근거는 [나간 멤버의 개인 통합은 나갈 때 지운다](#나간-멤버의-개인-통합은-나갈-때-지운다-2026-10-29) 에 있다.

### 통합 쓰기의 잠금 순서

통합 쓰기의 잠금 순서는 이 절이 정한다. 다른 문서는 이 절이나 아래 Rationale 을 링크한다. 순서는 워크스페이스, 멤버십, 통합이다. 워크스페이스 삭제와 소유자 이양이 워크스페이스, 멤버십 순으로 잠그므로([계정과 워크스페이스 데이터 흐름](../CLE-ACCT/CLE-ACCT-DATA.md#워크스페이스-삭제와-나가기)) 그 뒤에 통합을 붙였다.

- 통합 행을 INSERT 할 수 있는 쓰기는 공개 범위와 상관없이 트랜잭션에서 맨 먼저 워크스페이스 행을 `FOR KEY SHARE` 로 잡는다. 통합 생성과 Cafe24 Private·MakeShop `oauth/begin`(조직 · 개인 공개 범위 모두)이 해당한다. begin 은 다시 쓸 후보 행을 잠근 뒤 그 행을 고치거나 새 행을 INSERT 한다. 통합 INSERT 의 외래 키 확인도 워크스페이스 행에 `FOR KEY SHARE` 를 잡는다. 이 잠금이 멤버십이나 통합 행의 잠금 뒤에 오면 워크스페이스 삭제·소유자 이양과 순서가 엇갈리고 교착(`40P01`)이 날 수 있다. 그래서 워크스페이스를 먼저 명시적으로 잠근다. 이 적용 범위는 2026-10-30 에 사용자가 정했다.
- 워크스페이스가 그 사이 지워져 잠글 행이 없으면 통합 생성과 begin 은 공개 범위와 관계없이 403 `NOT_A_MEMBER` 로 끝낸다. 통합을 만드는 경로는 트랜잭션 안의 재확인에도 라우트 가드와 같은 거부 코드를 쓴다. 가드는 없는 워크스페이스와 비멤버를 구분하지 않고 `NOT_A_MEMBER` 로 답한다([워크스페이스와 멤버 「가드 거부 에러 코드」](../CLE-ACCT/CLE-ACCT-WS.md#가드-거부-에러-코드)). 워크스페이스를 지우면 멤버십도 함께 지워지므로 그 뒤에 가드를 다시 거쳐도 같은 코드가 나온다. 같은 경쟁에서 다른 응답을 내는 경로가 둘 있다. 워크스페이스 관리 경로는 대상 워크스페이스 자체를 다루는 요청이라 404 `WORKSPACE_NOT_FOUND` 를 낸다([워크스페이스와 멤버 「워크스페이스를 찾지 못할 때」](../CLE-ACCT/CLE-ACCT-WS.md#워크스페이스를-찾지-못할-때)). 조직에서 개인으로 바꾸는 전환은 이미 있는 통합을 바꾸는 요청이다. 워크스페이스와 함께 그 통합도 지워졌으므로 없는 통합과 같은 404 `RESOURCE_NOT_FOUND` 로 끝낸다.
- 개인 통합 행을 만드는 트랜잭션은 그다음 통합 소유자의 멤버십 행을 `FOR SHARE` 로 읽는다. 멤버십 잠금은 개인 공개 범위에만 더한다. 조직 통합은 만든 사람이 나가도 지우지 않으므로 멤버십을 잡지 않는다.
- 설치 대기 행을 다시 쓰는 begin 은 요청 공개 범위가 개인일 때만 멤버십을 잡는다. 요청이 조직인데 개인 설치 대기 행을 다시 쓰는 사람은 그 행의 통합 소유자다. 그래서 새 개인 행이 생기지 않는다. 그 기존 행은 나가기·제거의 통합 DELETE 가 행 잠금을 기다렸다가 지운다.
- MakeShop begin 은 이 잠금 다음에 `(workspace_id, client_id)` advisory lock 을 잡고 그다음 다시 쓸 후보 행을 `FOR UPDATE` 로 잠근다.
- 조직 통합을 개인으로 바꾸는 트랜잭션도 같은 순서로 잠근 뒤 통합 행을 바꾼다. 이 UPDATE 는 외래 키 컬럼을 바꾸지 않아 워크스페이스 행을 저절로 잠그지 않는다. 그래도 순서를 하나로 두려고 같게 잠근다.
- 나가기·제거는 멤버십을 지운 다음 통합을 지운다. 워크스페이스 행은 잠그지 않으므로 이 순서를 어기지 않는다.
- 생성이 먼저 잠그면 멤버십 삭제가 생성의 커밋을 기다린다. 그 뒤의 통합 삭제는 새 문장이라 생성이 만든 행까지 보고 지운다. 격리 수준은 READ COMMITTED 를 전제한다. 문장마다 새 스냅샷을 받아서 이렇게 된다.
- 삭제가 먼저 잠그면 생성의 `FOR SHARE` 가 삭제의 커밋을 기다린다. 그 뒤에는 멤버십 행이 없으므로 생성은 403 `NOT_A_MEMBER` 로, 전환은 409 `INTEGRATION_OWNER_NOT_MEMBER` 로 끝난다.
- `user` 행의 외래 키 잠금(`created_by`)은 이 순서 밖이다. 사용자 hard delete 가 생기면 다시 본다.
- 잠금을 쥔 동안 외부 호출(OAuth 토큰 교환, 연결 테스트, 제공자 API)을 하지 않는다. 외부 호출은 트랜잭션 앞에서 끝낸다. 잠금을 오래 쥐면 같은 멤버의 나가기·제거와 워크스페이스 삭제가 그만큼 기다린다.
- 통합 행을 만들거나 개인으로 바꾸는 쓰기는 모두 통합 도메인의 쓰기 도우미 `lockForIntegrationWrite` 를 트랜잭션 첫 문장으로 부른다. 잠금과 재확인은 그 도우미에만 둔다. 새 경로가 도우미를 건너뛰지 않는지는 그런 쓰기 경로를 열거하는 AST 가드(`integration-owner-write.spec.ts`)가 본다.
- 재확인은 멤버십이 있는지만 본다([재확인은 멤버십만 본다](#재확인은-멤버십만-본다-2026-10-29)).

## Rationale

### 나간 멤버의 개인 통합은 나갈 때 지운다 (2026-10-29)

개인 통합은 통합 소유자에게만 보인다. 그래서 통합 소유자가 워크스페이스를 나가거나 제거되면 그 통합은 아무도 보거나 지울 수 없었다. 2026-10-24 에 그런 통합을 노드 실행에서 거절하기로 했지만 행은 남았다. 남은 행은 암호화한 자격 증명과 워크스페이스 이름 UNIQUE 의 별칭, 상점 식별자 UNIQUE 의 상점 자리를 계속 잡는다. 만료 알림과 Cafe24 백그라운드 갱신도 그 행을 계속 다룬다. 2026-10-29 에 사용자가 정했다.

결정:

- 멤버십을 지울 때 그 사람의 개인 통합을 같은 트랜잭션에서 지운다. 멤버십만 지워지고 통합은 남는 중간 상태를 만들지 않는다.
- 상태와 사용처를 보지 않는다. 사용처가 남은 통합을 지우면 그 노드는 삭제된 통합과 같이 실패한다. 그런데 그 노드는 통합 소유자가 멤버가 아니라는 이유로 이미 실행에서 실패한다. 지워도 실행 결과는 같다. 사용처 때문에 남기면 그 행을 정리할 사람이 다시 없어진다.
- 조직 통합은 지우지 않는다. 조직 통합은 통합 소유자와 상관없이 관리자 이상이 관리한다.
- 제거는 멤버십을 끝내는 동작이고 개인 통합 삭제는 통합 소유자가 이 워크스페이스에서 사라진 결과다. 관리자가 남의 개인 통합을 보거나 고르는 권한을 얻는 것은 아니다.
- 일반 삭제와 같이 캐시를 무효화하고 통합마다 `integration.deleted` 를 남긴다. 일반 삭제와는 `details.mode` 로 구분한다. 키 이름과 값을 `member.removed` 와 같게 둬서 두 기록을 `mode`·`memberUserId` 로 이을 수 있다. 감사 액션을 따로 두지 않는다. 제공자 쪽 앱 해지는 하지 않는다. 일반 삭제도 하지 않는다.
- 나가기와 제거 확인 다이얼로그에서 개인 통합도 지워진다고 알린다. 안내 규칙과 근거는 [워크스페이스와 멤버](../CLE-ACCT/CLE-ACCT-WS.md#나가기와-제거는-개인-통합도-지운다-2026-10-29) 가 정한다.
- 다시 초대해도 지운 통합은 돌아오지 않는다. 다시 들어온 멤버는 새로 등록한다.
- 만료 알림과 Cafe24 백그라운드 갱신은 따로 막지 않는다. 행이 지워지면 둘 다 그 행을 다루지 않는다.

나간 멤버의 개인 통합을 노드 실행에서 거절하는 규칙은 두 번째 방어로 남긴다. 배포 중 옛 인스턴스가 처리한 나가기처럼 행이 남는 경우에도 그 통합을 노드에서 쓰지 못하게 한다.

나가기·제거와 개인 통합 생성이 겹치는 경쟁은 잠금으로 막는다. 라우트 가드는 트랜잭션 밖에서 멤버십을 확인하므로 그 뒤에 멤버십이 지워지고 통합 행이 만들어질 수 있다. 그러면 삭제 트랜잭션이 보지 못한 행이 남는다. 조직 통합을 개인으로 바꾸는 전환도 같다. 잠금 규칙은 [통합 쓰기의 잠금 순서](#통합-쓰기의-잠금-순서) 에 있다. 2026-10-25 에 설치 대기 행 재사용의 판정과 쓰기 사이를 잠금으로 묶은 것과 같은 방식이다([OAuth 연결과 토큰 갱신](CLE-INT-OAUTH.md#남의-개인-설치-대기-행은-409-로-거절한다-2026-10-24)).

이행: 이 규칙을 배포하기 전에 나간 멤버의 개인 통합은 배포 때 마이그레이션(V153)이 한 번 지우고 감사 로그를 남기지 않는다. 지우는 행은 그때까지 아무에게도 보이지 않던 행이다. 배포 전에 읽기 전용 조회로 건수를 재서 구현 PR 본문에 남기고, 배포 중에 옛 인스턴스가 처리한 나가기가 행을 남길 수 있으므로 배포 뒤 같은 조회로 0건인지 확인한다.

기각한 안:

- 관리자가 남은 개인 통합을 보고 지우게 하는 안: 관리자에게 남의 개인 통합을 보여야 한다. 2026-09-25 에 정한 대로 남의 개인 통합은 없는 것처럼 404 로 숨긴다. 정리할 행을 사람이 찾아야 하는 것도 그대로다.
- 그대로 두는 안: 자격 증명이 남고 이름과 상점 자리가 계속 잡힌다. 그 상점을 다시 등록하려는 멤버는 보이지 않는 행 때문에 막힌다.
- 조직 통합으로 옮기는 안: 개인으로 등록한 자격 증명을 본인 동의 없이 워크스페이스 전체가 쓰게 된다. 공개 범위 전환은 관리자 이상이 확인 다이얼로그를 거쳐 하는 일이다.
- 나가기 전에 개인 통합을 먼저 지우게 하는 안: 제거는 관리자가 하는 일이라 그 멤버에게 먼저 지우라고 할 수 없다. 나가기만 막으면 두 경로의 결과가 달라진다.
- 경쟁을 DB 트리거로 막는 안: 트리거도 멤버십을 잠가야 경쟁을 막으므로 잠금 순서 문제는 그대로다. 트리거의 예외를 403·409 응답으로 바꾸는 층이 따로 생기고 규칙이 애플리케이션과 DB 두 곳에 나뉜다.
- 복합 외래 키 `(workspace_id, created_by)` → `workspace_member(workspace_id, user_id)` 로 막는 안: 공개 범위에 따라 걸 수 없다. Postgres 에는 조건을 붙인 외래 키가 없다. 조직 통합에도 걸리면 만든 사람이 나갈 때 나가기가 막히거나(NO ACTION) 조직 통합까지 지워진다(CASCADE).
- 잠금 규칙을 개인 통합 쓰기에만 거는 안(2026-10-30): 조직 공개 범위의 begin 이 다시 쓸 후보 행을 `FOR UPDATE` 로 잠근 채 기다리는 사이 그 행이 설치 완료나 만료로 후보에서 빠지면 새 행을 INSERT 한다. 그때 외래 키 확인이 워크스페이스 행을 늦게 잡아 워크스페이스 삭제(워크스페이스를 잡고 CASCADE 로 그 후보 행을 기다린다)와 교착(`40P01`)할 수 있다. 워크스페이스 삭제가 희생되면 트리거의 외부 자원은 이미 놓인 채 워크스페이스가 남는다. 범위를 넓히는 비용은 조직 begin 의 SELECT 한 번이라 사용자가 넓히는 쪽을 골랐다.

받아들인 잔여:

- 사용처가 남은 개인 통합도 지우므로 그 노드에는 삭제된 통합과 같이 `(missing)` 옵션과 [삭제된 통합 표시](../CLE-NODE-INT/CLE-NODE-INT-COMMON.md#삭제된-통합-표시) 배지가 보인다. 이미 실행에서 실패하던 노드라 실행 결과는 바뀌지 않는다.
- 뷰어는 사용처가 남은 자기 개인 통합을 지우지 못한다. 그런데 나가면 그 통합도 지워진다. 그 노드는 이미 실행에서 실패하던 노드라 결과는 같다.
- 실수로 제거한 멤버를 다시 초대해도 개인 통합은 돌아오지 않는다. 다이얼로그가 미리 알린다.
- 다이얼로그는 개인 통합의 개수와 이름을 보이지 않지만 `integration.deleted` 감사 로그의 `details.name` 에는 이름이 남는다. 감사 로그를 볼 수 있는 사람은 지워진 개인 통합의 이름을 본다. 일반 삭제의 감사 로그와 같은 정도다.

### 나간 멤버의 개인 통합으로 바꾸는 전환은 거절한다 (2026-10-29)

공개 범위 전환은 `created_by` 를 바꾸지 않는다. 그래서 통합을 만든 사람이 이미 나간 조직 통합을 개인으로 바꾸면 아무도 보거나 지울 수 없는 개인 통합이 다시 생긴다. 그 사람을 다시 초대하면 그 통합이 돌아와서 «다시 초대해도 지운 통합은 돌아오지 않는다» 와도 어긋난다. 나가기와 전환이 겹쳐도 결과가 같다. 2026-10-29 에 사용자가 정했다.

- 통합을 만든 사람이 워크스페이스 멤버가 아니면 조직에서 개인으로 바꾸는 전환을 409 `INTEGRATION_OWNER_NOT_MEMBER` 로 거절한다. 개인 통합 생성의 재확인과 같은 순서로 잠근다. «나간 멤버의 개인 통합은 없다» 를 규칙 하나로 지킨다. 관리자는 그 통합을 조직 통합으로 두거나 지운다.
- `NOT_A_MEMBER` 를 쓰지 않는다. 요청자는 멤버이고 문제는 통합을 만든 사람이다. 클라이언트는 `NOT_A_MEMBER` 를 «이 워크스페이스에 더는 속하지 않는다» 로 읽는다([워크스페이스와 멤버](../CLE-ACCT/CLE-ACCT-WS.md#가드-거부에-에러-코드를-붙인다)). 대상 상태와 부딪힌 요청이라 409 다. 사용처가 남은 통합의 삭제를 막는 `INTEGRATION_IN_USE`(409)와 같은 부류다.
- 거절한 전환은 `integration.scope_changed` 를 남기지 않는다. 바뀐 것이 없다.
- 사용처가 있어도 전환을 막지 않고 다이얼로그로 알리는 규칙은 그대로다. 이 거절은 사용처를 보지 않고 통합을 만든 사람의 멤버십만 보며 에러로 알린다.

기각한 안: 전환할 때 통합을 지우는 안은 전환 요청이 삭제가 되어 관리자가 예상하지 못하고, 사용처가 있으면 409 로 막히는 일반 삭제 규칙과도 부딪힌다. 받아들인 잔여로 두는 안은 실행 거절과 배포 때의 정리 조회로 결과를 막을 수 있지만 없애려던 행이 다시 생긴다.

### 재확인은 멤버십만 본다 (2026-10-29)

개인 통합 행 쓰기와 개인 전환의 재확인은 멤버십이 있는지만 보고 역할은 보지 않는다. 2026-10-29 에 사용자가 정했다.

- 이 재확인은 나가기·제거와의 경쟁을 막으려는 것이다. 막을 것은 «나간 멤버의 개인 통합» 하나이고 멤버십이 있는지로 충분하다.
- 역할 하한은 라우트 가드가 본다(생성은 편집자 이상, 전환은 관리자 이상). 가드와 쓰기 사이에 역할이 낮아지는 경쟁은 남는다. 그래도 뷰어로 강등된 사람은 이미 자기 개인 통합을 갖고 있고 지울 수 있다. 그 틈으로 생긴 행도 아무도 보지 못하는 행이 아니다.
- 전환에서 역할까지 보면 만든 사람이 뷰어인 조직 통합을 개인으로 바꾸지 못한다. 뷰어도 개인 통합을 가질 수 있으므로 막을 이유가 없다.
- 요청자의 역할을 잠그지 않고 읽는 결정([워크스페이스와 멤버](../CLE-ACCT/CLE-ACCT-WS.md#관리자-역할-판정의-요청자-역할은-잠그지-않고-읽는다))과 부딪히지 않는다. 여기서 잠그는 것은 통합 소유자가 될 사람의 멤버십 행 하나이고 그 역할 값으로 판정하지 않는다.

### 개인 통합 소유자를 강제한다: 404 로 숨기고 역할 우위를 두지 않으며 노드 실행은 후속으로 둔다 (2026-09-25)

권한 표의 개인 열(«통합 소유자만»)은 표로만 있었고 코드는 어디서도 `created_by` 를 보지 않았다. 멤버면 남의 개인 통합을 목록·상세로 봤고 편집자면 별칭 수정·삭제까지 했다. 조직 통합도 별칭 수정·삭제가 관리자 대신 편집자에게 열려 있었고 통합 재인증은 역할 검사가 아예 없었다. 통합 재인증의 OAuth 콜백은 자격 증명을 통째로 바꾸므로 뷰어가 조직 통합을 자기 외부 계정으로 바꿔치기할 수 있었다. `oauth/begin` 의 `reauthorize` 모드는 `integrationId` 를 받기만 하고 검사하지 않아 두 번째 입구였다.

결정(2026-09-25 사용자 결정, 선택지 셋을 제시했다):

1. **쓰기와 읽기를 함께 닫고 노드 실행 시점 검사는 후속으로 둔다.** 실행 시점에는 «통합 소유자» 를 누구로 볼지(스케줄 실행에는 요청자가 없다)부터 정해야 하고 기존 워크플로우가 동료의 개인 통합을 쓰고 있으면 실행이 깨지므로 영향 조사가 필요하다.
2. **남의 개인 통합은 404 다.** 없는 통합과 같은 `RESOURCE_NOT_FOUND` 다. 목록에서 빠진 것과 일관되고 이 도메인이 워크스페이스 밖이나 없는 ID 에 이미 쓰는 응답이라 새 에러 코드가 필요 없다. «권한 없음과 부재를 같은 응답으로 묶는다» 는 원칙은 경로 파라미터 워크스페이스 가드와 같다([계정과 워크스페이스 데이터 흐름](../CLE-ACCT/CLE-ACCT-DATA.md)). 다만 그쪽 응답은 `403 NOT_A_MEMBER` 다. 원칙은 같고 상태 코드는 도메인마다 다르다.
3. **조직 통합의 별칭 수정·삭제는 관리자 이상이다.** 권한 표, 역할 매트릭스, 사용자 가이드(위험 영역 «Admin»)가 모두 그렇게 적는데 코드만 편집자였다. 표를 코드에 맞추지 않고 코드를 표에 맞췄다.

거부 코드는 `ADMIN_REQUIRED` 로 올렸다. 라우트 가드가 역할 거부에 전용 코드를 싣고 서비스 계층의 두 번째 선(`WorkspacesService.assertAdmin`)도 같은 코드를 쓴다. 이 모듈의 기존 관리자 판정 네 곳(생성, 교체, 추가 권한 요청, 공개 범위 전환)만 `FORBIDDEN` 이었고 클라이언트는 그 코드로 분기하지 않았다(프런트엔드 `FORBIDDEN` 참조 0곳, 2026-09-25 실측). 같은 변경이 그 자리를 모두 손보므로 함께 올렸다.

기각한 안(모두 같은 날 선택지로 제시했고 사용자가 고르지 않았다):

- 쓰기 경로만 먼저: 목록에 보이는 통합을 눌렀을 때 거부되는 어색한 중간 상태가 남는다.
- 노드 실행까지 한 번에: 기존 워크플로우 영향 조사와 실행 시점 «통합 소유자» 기준 결정이 먼저라 범위가 커진다.
- 403 과 새 에러 코드(예: `INTEGRATION_OWNER_REQUIRED`): 목록에서는 빠지는데 `:id` 가 존재를 확인해 주는 비대칭이 생기고 카탈로그와 클라이언트 분기가 늘어난다.
- 조직 별칭 수정·삭제를 편집자로 두고 스펙을 정정: 스펙 두 곳과 가이드가 이미 관리자다.

받아들인 잔여: 통합 이름(`integration_workspace_name_unique`)과 상점 식별자(`(workspace_id, service_type, mall_id)`)의 유일성은 워크스페이스 단위다. 그래서 생성·이름 변경의 `INTEGRATION_NAME_TAKEN` 과 begin·precheck 의 충돌 응답은 남의 개인 통합이 **있다는 사실**을 드러낸다. 유일성을 통합 소유자 단위로 바꾸면 같은 상점을 두 통합이 붙잡는 상태를 허용하는데 상점 식별자 유일성은 토큰과 설치 흐름의 전제다. 그래서 존재 신호는 남기고 precheck 가 식별자(ID, 이름)를 싣지 않는 데서 멈춘다.

후속으로 둔 노드 실행 시점 검사와 미결로 둔 뷰어의 개인 통합 쓰기는 2026-10-24 에 정했다([개인 통합의 역할 하한과 노드 사용 기준을 정한다](CLE-INT-MANAGE-USE.md#개인-통합의-역할-하한과-노드-사용-기준을-정한다-2026-10-24)).
