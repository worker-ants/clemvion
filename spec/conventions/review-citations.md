# Convention: 코드 주석의 리뷰 산출물 인용

## Overview (제품 정의)

이 저장소의 코드·테스트 주석은 **왜 이 자리가 이렇게 생겼는지**를 리뷰 산출물로 가리킨다.
`origin/main` 의 `codebase/` 안에 **107개 파일·514회** 쌓여 있다 (2026-09-05 09시 측정).
날짜를 확인할 수 있는 인용 중 가장 이른 것은 **2026-05-26** 세션이다 — bare 형태는 날짜가
없어 그보다 이른 것이 있는지 알 수 없고, 그 점이 §2 의 근거이기도 하다.

본 문서는 그 관례를 성문화하고 **인용 형태**를 정한다.

---

## 1. 인용은 유지한다

`review/**` 는 커밋된다. `.gitignore` 가 무시하는 것은 `review/**/_prompts/` **한 줄뿐**이고
`SUMMARY.md`·`<role>.md`·`meta.json`·`RESOLUTION.md` 는 저장소에 남는다 (`git check-ignore`
실측).

**다만 "영구" 라고까지는 말하지 않는다.** 옛 산출물이 정리된 적이 있다 — `f7c56bf0a`
(`refactor(plan,review): delete`). 실측(2026-09-05): 전체 경로 인용 중 **1건**
(`review/code/2026/05/26/12_10_38`) 이 워킹트리에 없다. 그래도 **git 이력에는 남아 있어**
`git log -- <경로>` 로 되짚을 수 있다.

이것이 §2 의 진짜 근거다 — 경로 인용은 정리돼도 **이력으로 해소되지만**, bare `hh_mm_ss` 는
**이력으로도 해소되지 않는다.** 어느 날짜인지가 어디에도 없기 때문이다.

## 2. 날짜를 포함한다

**bare `hh_mm_ss` 는 쓰지 않는다.** 세션 시각은 날짜를 넘어 충돌한다 — 실측(2026-09-05):

| | 값 | 성격 |
|---|---|---|
| 둘 이상의 날짜에 같은 시각이 존재 | **46개** | 라운드가 늘수록 커진다 |
| `codebase/**` 가 인용한 서로 다른 시각 (`origin/main`) | 197개 | |
| **그중 여러 날짜에 걸려 해소 불가** | **8개** | **이 규약의 근거** |

> **세션 디렉터리 총수는 적지 않는다.** 리뷰를 한 바퀴 돌 때마다 늘어서 어떤 값을 적어도
> 곧 낡는다 — 실제로 이 규약을 쓰는 동안에도 움직였다. 위 세 줄은 `origin/main` 기준이라
> 머지 전까지 고정이고, 판단에 쓰이는 것은 마지막 줄이다.

| 형태 | 예 | 판정 |
| --- | --- | --- |
| 전체 경로 | `review/code/2026/09/04/23_02_51` | **권장** |
| 날짜 + 시각 | `2026-09-04 23_02_51` | 허용 |
| bare 시각 | `23_02_51` | **금지** — 날짜가 없으면 해소 불가 |

지적 번호를 함께 적으면 더 좁혀진다: `review/code/2026/09/04/23_02_51 W1`.

## 3. 적용 범위 — 맥락 없이 읽히는 자리

가르는 기준은 **그 인용이 나중에 어떤 맥락에서 읽히는가** 다.

| 대상 | 규약 적용 | 이유 |
| --- | --- | --- |
| `codebase/**` 의 코드·테스트 주석 | **적용** | 몇 달 뒤 아무 맥락 없이 읽힌다 — 인용이 스스로 해소돼야 한다 |
| `scripts/**` · `.github/**` | **적용** | 같은 이유. 저장소 가드·CI 정의도 맥락 없이 읽힌다 (실측 2026-09-05: 인용 8건 중 **6건이 bare** — 이미 이 규약이 필요한 상태다) |
| **DTO·컨트롤러의 `/** */` JSDoc** | **대상 아님** | 그 JSDoc 은 **공개 OpenAPI `description` 으로 나간다.** 리뷰 인용은 소비자가 읽을 문장이 아니므로 애초에 거기 쓰지 않는다 — [`swagger.md` §3](./swagger.md) 이 정한 대로 **바로 위 `//` 주석**에 적고, 그 `//` 주석은 위 첫 행에 따라 이 규약을 따른다 |
| `spec/**` 문서 | **적용** | `codebase/**` 와 같은 논리 — 살아 있는 문서라 오래 읽힌다. **기존 bare 인용이 이미 많다** (실측 2026-09-05: 18개 파일·45건 중 **36건이 bare**) — §4 가 덮는다 |
| `plan/**` 문서 | 대상 아님 | 인용하는 라운드와 **같은 세션**에서 쓰이고, 문서 자체가 그 맥락을 담는다 |
| `review/**` 산출물 | 대상 아님 | **시점 기록**이다 — [`plan-lifecycle.md`](../../.claude/docs/plan-lifecycle.md) 이 *"`review/**` 같은 시점 기록 문서는 옛 경로 유지"* 라 적어 사후 편집 대상이 아님을 전제한다 |

> **DTO JSDoc 행이 왜 필요한가**: 이 규약과 `swagger.md` §3 이 같은 날 등재되면서 표면이
> 겹쳤다 — JSDoc 에 리뷰 인용을 넣으면 이 규약은 만족하고 저쪽은 위반하게 된다
> (`review/consistency/2026/09/05/09_53_09` W1). 실제 위반 사례는 없지만 두 규약이 서로를
> 모르는 상태를 남기지 않는다.
>
> `plan/**` 제외는 `review/code/2026/09/05/09_27_04` INFO#3 이 *"같은 PR 이 `plan/**` 에는
> bare 인용을 계속 넣는다"* 고 물어 명시하게 됐다. 의도적 제외다.

## 4. 기존 인용은 소급 정리 대상이 아니다

기존 bare 인용(`codebase/**` 499건 + `spec/**` 36건 + `scripts/**`·`.github/**` 6건)은 그 자리를 **다음에 건드릴 때** 함께 맞춘다. 일괄 치환은 하지 않는다 —
날짜를 코드 컨텍스트로 하나씩 특정해야 하는 일이라 기계적 변환이 안 된다.
(`swagger.md` §1-4·§3 가 새 DTO 규칙을 들일 때 세운 것과 같은 원칙.)

## Rationale

### `code:` 가 "구현 경로" 가 아니라 "준수 예시" 를 가리키는 이유

`spec-impl-evidence.md` 는 `code:` 를 *"본 spec 이 약속한 surface 의 구현 경로"* 로 정의한다.
이 규약에는 **시행하는 코드가 없다** — 주석 형태를 강제하는 가드가 없기 때문이다. 그래서
`code:` 에 **이 규약이 처방하는 형태를 실제로 쓰는 파일**을 적었다 (저장소에 10개 있고
backend·frontend 에서 하나씩).

이 예외는 `spec-impl-evidence.md` §2.1 `code:` 필드 정의에도 각주로 등재했다 — 한쪽만 재해석하면 SoT 가 그 사실을 모른다.

기각한 대안 — `codebase/backend/src/**` 처럼 넓은 트리를 적기: 가드는 통과하지만 이 저장소의
다른 규약 문서가 `code:` 를 좁고 구체적인 파일로 적는 관행과 어긋나고, 무엇보다 **아무것도
가리키지 않는 것과 같다.**

### 왜 PR 번호로 전환하지 않았나

`review/code/2026/09/05/00_06_38` W2 는 *"영구 코드 주석에 일시적 프로세스 식별자"* 라며
PR 번호·커밋 SHA 로의 전환을 제안했다. 두 가지 이유로 택하지 않았다.

**전제가 틀렸다** — 세션 ID 는 일시적이지 않다. `review/**` 가 커밋되므로 경로는 정리된
뒤에도 **git 이력으로 해소된다**(§1). 문제는 **날짜가 빠진 인용 형태**였지 인용 대상이
아니었다.

**전환 비용이 손실이다** — 514회의 기존 인용이 전부 고아가 된다. 그리고 PR 번호는 입도를
잃는다: PR 은 라운드별 산출물을 담지 않아 *"어느 라운드의 어느 지적"* 을 가리키지 못하는데,
세션 경로는 그것을 그대로 준다.

### 왜 소급 정리를 하지 않나

bare 인용의 날짜는 커밋 시각으로 근사할 수 있지만 **근사는 틀릴 수 있다** — 한 파일이 여러
날의 라운드를 인용하는 경우가 흔하다. 잘못 채운 경로는 bare 인용보다 나쁘다: 존재하는
**다른** 세션을 가리켜, 읽는 사람이 엉뚱한 근거를 읽게 된다. 그 자리를 아는 사람이 손볼 때
맞추는 편이 옳다.

### `spec/**` 을 "위반 0건" 이라 적었다가 반증됐다

`spec/**` 행을 처음 넣을 때 *"현재 위반 사례 0건"* 이라고 적었다 — **재지 않고 썼다.**
`review/code/2026/09/05/10_39_00` W1 이 반증했고, 직접 세어 보니 **18개 파일·45건 중 36건이
bare** 였다. 리뷰어가 센 값(12파일·22곳)보다도 많았다.

같은 문서 안에서 다른 범위(`codebase/**`, `scripts/**`)는 전부 실측해 놓고 이 행만 짐작으로
채운 것이다. **범위를 넓히는 편집은 그 범위를 재는 일까지 포함한다.**

### 이 수치를 처음 셀 때 거짓 0 을 냈다

`review/code/2026/09/05/00_06_38` 라운드에서 이 관례의 규모를 처음 셀 때 `-E "\b[0-9]{2}_…"`
정규식이 물지 않아 **"0건"** 이 나왔고, 하마터면 *"선례 없음 → 이 PR 의 일탈"* 이라는
**정반대 결론**을 낼 뻔했다. 존재가 확실한 문자열로 명령 자체를 먼저 검증해서 잡았다.
이 문서의 모든 수치는 그 절차를 거쳤다 — **0 은 언제나 "없다" 와 "못 찾았다" 두 가지다.**
