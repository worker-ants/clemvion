# spec draft — `updateExecutionStatus` else 분기 트랜잭션화 반영

ai-review `17_36_15` 의 **SPEC-DRIFT 1건**. 같은 PR 의 코드 변경이 spec 서술을 앞질렀다.

## 무엇이 어긋났나

`updateExecutionStatus` 의 else 분기(직접 마감 — RUNNING/COMPLETED/FAILED/CANCELLED)
guarded UPDATE 를 `dataSource.transaction` 안으로 옮겼다. 그런데 §1.1 의 **원자성 보장**
인용 블록은 `linkedNodeExec` 짝 전이와 §7.5 재개 claim 의 트랜잭션만 서술하고, else
분기는 언급이 없다.

## 두 곳을 고친다

### (1) §1.1 「원자성 보장」 블록 — 문장 추가

else 분기도 트랜잭션 안에서 돈다는 사실과 **그 이유**를 적는다. 이유가 짝 전이와 다르다:
짝 전이는 *두 save 의 원자성* 때문이고, else 분기는 **shape 가드의 throw 가 UPDATE 를
롤백하게** 하기 위해서다. 같은 수단(트랜잭션)이지만 목적이 달라 한 문장에 뭉치면 안 된다.

### (2) 2026-08-30 소급 각주 — 후속 각주 추가

`#1242` 에서 내가 쓴 각주가 **불완전하다.** 그 각주는 `8332d9a20` 이 고쳤다고 적고
"DB 는 안 깨졌다" 로 마무리하는데, 그 수정이 얹은 throw 는 **트랜잭션 밖 단발 UPDATE**
위에 있어 롤백을 부르지 못했다. 그래서 가드가 발동하면 원래 결함보다 나쁜 상태가 남았다:

| | 상태 |
|---|---|
| DB | terminal 로 **커밋됨** |
| 종결 이벤트 | 발행 안 됨(예외로 이탈) |
| stuck recovery | **안 잡힘** — non-terminal 만 스캔한다 |

즉 **가드가 막으려던 무기한 대기가 가드가 발동한 순간에 생긴다.**

노출 창은 `8332d9a20`(2026-08-13) ~ 이 PR 까지 약 **17일**. shape 위반은 드라이버 계약이
바뀌어야 나는 이벤트라 실제 발동 여부는 확인되지 않았다 — **"창이 있었다" 와 "발동했다"
를 구분해 적는다.**

## 왜 planner 턴인가

`developer` 의 자기-반증형 소정정 예외는 **예고·트리거 문장**에만 열린다. 여기 대상은
소급 각주(이력 서술)라 조건 2를 충족하지 못한다. 그래서 우회하지 않고 `--spec` 을 거친다.

## Rationale

### 왜 이 PR 에 함께 넣나

각주를 불완전한 채로 두면, 다음 사람이 "`8332d9a20` 이 이 결함을 닫았다" 로 읽는다.
실제로는 그 커밋이 **관측만** 하고 롤백은 이 PR 이 했다. 두 단계를 한 커밋으로 뭉뚱그리면
"throw 를 넣었으니 안전하다" 는 잘못된 일반화가 남는다 — 이 저장소가 반복해 겪은
"문서한 보장이 구현보다 넓다" 의 전형이다.

### 기각한 대안 — 별도 planner PR

각주의 부정확성이 **이 PR 의 코드 변경 때문에** 생긴 것이라, 나눠 내면 main 이 그 사이
"이미 닫혔다" 로 읽히는 서술을 갖는다. 창이 닫힌 시점과 그 사실이 기록되는 시점이
갈리지 않게 한다.
