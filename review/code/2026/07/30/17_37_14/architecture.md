## 요약

이번 diff(HEAD `3c306d593`, 10R CRITICAL 수정)는 `execution.retry_last_turn` 재진입이 turn 계속 시(`FAILED → WAITING_FOR_INPUT` re-park) 요구하는 opts→DB가드 번역이 전 계층에서 무검증이었다는 문제를 좁고 정확하게 고쳤다 — `reparkAiResumeTurn`에 mutation-검증된 회귀 테스트 1건을 추가해 그 특정 배선을 잠갔고, 부수 조치(JSDoc 보강, 사용자 가이드, CHANGELOG)도 적절한 범위였다. 설계 관점에서는 (1) 새 전이를 `ALLOWED_TRANSITIONS` 표 자체를 바꾸지 않고 opt-in 플래그로 확장한 점(OCP 존중), (2) `EngineDriver`가 소비자별 ISP 슬라이스(`CoreEngineDriver`/`AiTurnEngineDriver`/`RetryEngineDriver`)로 이미 잘 분리돼 있어 이번 시그니처 확장이 하위 호환(optional param)으로 처리된 점, (3) `RETRY_STATE_KEY` 상수 추출로 `_retryState` 리터럴 중복(raw SQL + TS 프로퍼티 접근)을 단일 출처로 통합한 점은 긍정적이다. 다만 독립적으로 코드를 추적한 결과, 이번 PR 이 고친 CRITICAL 의 근본 원인 — (a) 상태 전이 정당성이 `state-machine.ts`(TS 규칙)와 `execution-engine.service.ts`(손으로 나열한 SQL 상태 리스트) 두 곳에 이중 인코딩되어 수동 동기화에 의존하는 구조, (b) opt-in 플래그가 계층마다 이름을 바꿔가며(`allowRetryReentry`↔`retryReentry`) 인라인 구조적 타입으로 5곳 이상 재선언되는 구조 — 는 이번 수정 이후에도 그대로 남아 있으며 오히려 SQL 상수/3항 선택 로직이 1곳에서 2곳으로 늘었다. 이 두 지점과 세 번째(미검증 opts 소비 지점)는 모두 직전 라운드(`review/code/2026/07/30/16_42_36`, 10R) 아키텍처 리뷰가 이미 발견해 `plan/in-progress/retry-turn-terminal-guard.md` #21~#24 로 P2/P3 defer 처리한 항목과 정확히 일치한다 — 본 리뷰는 독립 교차검증 결과로 그 판단에 동의하며, 이번 diff 의 좁은 스코프(버그 수정 + 회귀 테스트)를 벗어나는 구조 리팩터를 이번 턴에 새로 요구하지 않는다(그래서 WARNING 이 아닌 INFO 로 기록). 순환 의존성·레이어 책임 측면에서 이번 diff 가 새로 도입한 문제는 없다(기존 forwardRef 기반 DI 순환은 불변, 문서화됨).
