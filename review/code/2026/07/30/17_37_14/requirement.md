### 발견사항

- **[WARNING]** `retryLastTurn`의 사전 검증 2곳이 재사용하는 `InvalidExecutionStateError`의 고정 client-safe 메시지가 retry_last_turn 컨텍스트와 의미상 맞지 않는다.
  - 위치: `codebase/backend/src/modules/execution-engine/retry-turn.service.ts:138-142`(NodeExecution 미존재/executionId 불일치), `:144-148`(`nodeExec.status !== FAILED`). 근본 원인은 범위 밖 파일 `codebase/backend/src/modules/execution-engine/workflow-errors.ts:113-118`의 `InvalidExecutionStateError` 생성자(`super('Execution is not waiting for input.', detail)`).
  - 상세: `ExecutionError` 계약(`workflow-errors.ts:20-30`)상 `message`는 "고정 client-safe 문자열"이고 `detail`(→ `serverDetail`)은 서버 로그 전용이라 client(WS ack)에 **절대 노출되지 않는다** — `websocket.gateway.ts:902-908`의 catch 블록이 이를 그대로 확인해 준다(`err.message`를 그대로 ack `error.message`로 전달). 그런데 `InvalidExecutionStateError`의 고정 문구는 "Execution is not waiting for input."이며, 이는 원래 4개 continuation 명령(`submit_form`/`click_button`/`submit_message`/`end_conversation`, `waiting_for_input` 기대)을 위해 설계된 문구다. `retryLastTurn`이 같은 클래스를 "NodeExecution이 존재하지 않음" 및 "NodeExecution이 FAILED가 아님"(즉 기대 상태는 `waiting_for_input`이 아니라 `failed`) 검증에도 그대로 재사용하면서, 사용자가 실제로 보게 되는 toast/ack 메시지가 실제 실패 사유와 무관한 문구가 된다. 같은 파일의 `RetryLastTurnError`는 정확히 이 문제를 피하기 위해 `notFound`/`notRetryable`/`tooEarly` 정적 팩토리로 상황별 고정 메시지를 이미 분리해 두었는데(`workflow-errors.ts:162-186`), `InvalidExecutionStateError` 재사용 2곳만 그 패턴을 따르지 않는다. `retry-turn.service.spec.ts:282-296`의 관련 테스트도 `code`(`INVALID_EXECUTION_STATE`)만 검증하고 `message`는 어디서도 단언하지 않아(전체 파일 grep 결과 `InvalidExecutionStateError`의 message 문자열 자체를 검증하는 테스트 없음) 이 drift가 회귀 테스트로 잡히지 않는다. spec(`5-system/6-websocket-protocol.md` §4.2)은 `code` 값만 규정하고 메시지 원문은 예시(`"..."`)로 남겨 두므로 스펙 위반은 아니지만, "의도(에러 사유를 사용자에게 정확히 전달)"와 "구현(다른 명령군을 위해 설계된 고정 문구 재사용)" 사이에 괴리가 있다.
  - 제안: `InvalidExecutionStateError`에도 `RetryLastTurnError`와 동일한 정적 팩토리 패턴(예: `InvalidExecutionStateError.notFailed(detail)` / 기존 생성자는 waiting_for_input 전용으로 유지)을 추가해 retry_last_turn 전용 고정 문구를 분리하거나, 최소한 `retryLastTurn`의 두 호출부에서 이 클래스 재사용 시 메시지가 부정확함을 JSDoc에 명시. 회귀 테스트에 `message` 단언도 추가해 향후 drift를 검출.

- **[WARNING]** (기존 추적 항목 재확인 — `plan/in-progress/retry-turn-terminal-guard.md` #20, P2, 10R 신규 등재) `retryLastTurn`이 `Execution.status === FAILED`를 검증하지 않아, Execution이 실제로는 `cancelled`(예: NodeExecution은 FAILED로 남아 있지만 그 사이 사용자가 Stop을 누른 경우)인데도 재진입이 성립해 spawn된 NodeExecution row가 영구 RUNNING 고아로 남을 수 있다.
  - 위치: `codebase/backend/src/modules/execution-engine/retry-turn.service.ts`의 `retryLastTurn`(130-252줄, Execution 자체 상태 검증 없음) 및 `applyRetryLastTurn`이 위임하는 `ai-turn-orchestrator.service.ts`의 `reparkAiResumeTurn`(`updateExecutionStatus` 호출, 453-458줄) / `finalizeAiNode`(1615-1620줄).
  - 상세: 독립적으로 코드를 추적해 plan의 진단을 재확인했다 — `retryLastTurn`은 `nodeExec.status !== FAILED`만 검사하고 `Execution.status`는 전혀 조회하지 않는다. 이후 `applyRetryLastTurn`이 turn을 재개하다 종료/re-park 시점에 `updateExecutionStatus(execution, ...)`를 호출하는데, 이때 in-memory `execution.status`가 실제로는 DB의 `cancelled`인 경우 `assertTransition('cancelled', 'running'|'waiting_for_input', opts)`가 **DB 가드 진입 전에 동기 throw**한다(`canTransition`의 `allowRetryReentry` 특례는 `from === FAILED`일 때만 적용되고 `cancelled`에는 적용 안 됨 — `state-machine.ts:72-79`). 이 throw는 `updateExecutionStatus`가 `false`를 반환하는 정상 경로(→ `assertLinkedTransitionApplied`가 짝 NodeExecution을 CANCELLED로 마킹)를 거치지 않고 곧장 `applyRetryLastTurn`의 catch로 전파되며, `failRetryExecution`은 Execution만 상태 재조회로 안전하게 no-op 처리할 뿐(정상 동작) spawn된 NodeExecution row는 아무도 terminal로 마킹하지 않아 RUNNING으로 영구 잔류한다.
  - 제안: 이미 plan에 P2로 등재되어 있고 이번 라운드의 신규 정보는 아니다 — 근본 조치(spawn 이전 `Execution.status === FAILED` 명시 검증) 또는 방어(`updateExecutionStatus`/`reparkAiResumeTurn` 호출을 try/catch로 감싸 동기 throw까지 흡수)가 plan에 이미 제안되어 있으므로 중복 지시는 생략하고, 이번 라운드에도 여전히 미해소 상태임만 확인차 재기록한다.

- **[INFO]** 8R~10R에 걸친 `allowRetryReentry` opt-in 배선(state-machine.ts → execution-engine.service.ts의 `lockNonTerminalExecutionRow`/`updateExecutionStatus`(8354-8496)/`tryLockActiveExecutionAndSaveNodeExec`(8224-8253) → ai-turn-orchestrator.service.ts의 `reparkAiResumeTurn`(453-458)/`finalizeAiNode`(1508, 1600, 1619))를 라인 단위로 직접 대조 확인했다. 모든 소비처가 opts를 누락 없이 전파하며(고아 호출부 없음), 회귀 테스트(`ai-turn-orchestrator.service.spec.ts:140-163`, `execution-engine.service.spec.ts:5115-5202`)가 실제 SQL 문자열(`sql.includes("'failed'")`)과 `dbExecutionStatus` 대조 mock으로 shape-preserving mutation까지 검증해 vacuous하지 않음을 확인했다. spec(`spec/5-system/4-execution-engine.md` §1.1 전이표 77-80줄, §1.3, spec/5-system/6-websocket-protocol.md §4.2 에러 코드 표, spec/4-nodes/3-ai/1-ai-agent.md §7.9/§12.8)과도 line-level로 일치 — 이번 라운드에서 새로 발견된 spec-코드 불일치는 없음.
  - 위치: 해당 없음(교차 검증 확인 사항, 발견 아님).

- **[INFO]** `plan/in-progress/retry-turn-terminal-guard.md`에 이미 등재된 다수 defer 항목(#1~#25 — 특히 backstop gap #15, 이중 SoT #21, claim↔in-memory sync 프로즈 의존 #18, `applyRetryLastTurn` 길이 누적 #19)은 코드에서 그대로 재확인되나 이번 라운드에서 우선순위·처분을 바꿀 새로운 근거는 찾지 못해 중복 등재하지 않는다.

### 요약

이 변경(retry_last_turn 재진입의 종결 2경로 guarded 전환 + 원자 claim + FAILED↔RUNNING/WAITING_FOR_INPUT opt-in 짝 전이)은 10라운드에 걸친 반복 리뷰로 이미 매우 성숙한 상태이며, 이번 독립 재검토에서 8R/9R/10R이 고친 "opts→DB가드 번역" 배선을 라인 단위로 전부 대조한 결과 빠짐없이 정확하고 spec(§1.1/§1.3/§4.2/§7.9/§12.8)과 line-level로 일치함을 확인했다 — 회귀 테스트도 vacuous하지 않다. 신규로 발견한 것은 `retryLastTurn`의 두 검증 실패 경로가 원래 다른 명령군(waiting_for_input 계열)을 위해 설계된 `InvalidExecutionStateError`의 고정 메시지를 그대로 재사용해 사용자에게 부정확한 실패 사유 문구가 노출될 수 있다는 점(신규, WARNING)뿐이며, 그 외에는 기존에 P2로 추적 중인 "Execution.status===FAILED 미검증 → 고아 RUNNING row" 엣지 케이스가 여전히 열려 있음을 독립적으로 재확인했다(신규 아님, 이미 등재). 두 항목 모두 프로그램적 계약(에러 `code`, Execution 최종 상태)은 올바르게 유지되고 블라스트 반경이 좁아(메시지 문구 부정확 / 진행률 표시용 고아 NodeExecution row 잔류) 기능 완전성에 대한 근본적 위협은 아니다.
