### 발견사항

- **[WARNING]** `retryLastTurn`이 `Execution.status === FAILED`를 검증하지 않는다 (`plan/in-progress/retry-turn-terminal-guard.md` #20, P2 — 기존 추적 항목 독립 재확인, 이번 라운드 신규 아님).
  - 위치: `codebase/backend/src/modules/execution-engine/retry-turn.service.ts:130`(`retryLastTurn` 함수 전체, 130-252줄에 걸쳐 `Execution` 자체 상태 검증 없음 — `nodeExec.status`만 확인).
  - 상세: `retryLastTurn`은 대상 `NodeExecution.status !== FAILED`만 검사하고 그 `NodeExecution`이 속한 `Execution.status`는 조회하지 않는다. `Execution`이 실제로는 `cancelled`(예: 해당 노드는 FAILED로 종결됐으나 그 직후 사용자가 Stop을 눌러 Execution만 취소된 경우)여도 spawn이 그대로 진행된다. 이후 `applyRetryLastTurn`이 turn을 재개하다 종료/re-park 시점에 `this.driver.updateExecutionStatus`를 호출하면, in-memory `execution.status`가 실제로는 DB의 `cancelled`인 상태에서 상태머신 opt-in(`allowRetryReentry`)이 `from === FAILED`일 때만 적용되므로(`state-machine.ts:72-79`, `from === CANCELLED`는 미적용) `assertTransition('cancelled', 'running'|'waiting_for_input', opts)`가 DB 가드 진입 전에 동기 throw한다. 이 throw는 `updateExecutionStatus`가 `false`를 반환하는 정상 경로(→ 짝 `NodeExecution`을 CANCELLED로 정리)를 우회해 곧장 `applyRetryLastTurn`의 catch로 전파되고, `failRetryExecution`은 `Execution`만 상태 재조회로 안전하게 no-op 처리할 뿐 spawn된 `NodeExecution` row는 아무도 terminal로 마킹하지 않아 RUNNING으로 영구 잔류할 수 있다(타임라인/진행률 집계 오염). Execution 전체의 최종 상태(cancelled 유지)는 올바르므로 사용자에게 잘못된 결과가 보고되지는 않는다 — blast radius는 고아 `NodeExecution` row에 한정된다.
  - 제안: 이미 plan에 P2로 등재돼 있어 중복 지시는 생략한다 — 근본 조치(spawn 이전 `Execution.status === FAILED` 명시 검증) 또는 방어(`updateExecutionStatus` 호출을 try/catch로 감싸 동기 throw까지 흡수해 짝 `NodeExecution` 정리 경로로 유도)가 이미 plan에 제안돼 있다.

- **[WARNING]** `retryLastTurn`의 사전 검증 2곳이 재사용하는 `InvalidExecutionStateError`의 고정 문구가 retry_last_turn 실패 사유와 의미상 맞지 않는다 (`plan/in-progress/retry-turn-terminal-guard.md` #28, P3 — 기존 추적 항목 독립 재확인).
  - 위치: `codebase/backend/src/modules/execution-engine/retry-turn.service.ts:138-142`(NodeExecution 미존재/executionId 불일치), `:144-148`(`nodeExec.status !== FAILED`). 근본 원인은 범위 밖 파일 `codebase/backend/src/modules/execution-engine/workflow-errors.ts:113-119`의 `InvalidExecutionStateError` 생성자(`super('Execution is not waiting for input.', detail)`).
  - 상세: `InvalidExecutionStateError`의 고정 client-safe 메시지("Execution is not waiting for input.")는 원래 4개 continuation 명령(`submit_form`/`click_button`/`submit_message`/`end_conversation`, `waiting_for_input` 기대)을 위해 설계됐다. `retryLastTurn`은 기대 상태가 `waiting_for_input`이 아니라 `failed`인데도 같은 클래스·같은 문구를 재사용해, 사용자가 실제로 받는 WS ack 메시지가 실제 실패 사유(노드를 찾을 수 없음 / 아직 FAILED가 아님)와 무관해진다. 같은 파일의 `RetryLastTurnError`는 정확히 이 문제를 피하려고 `notFound`/`notRetryable`/`tooEarly` 정적 팩토리로 상황별 고정 메시지를 분리해 뒀는데(`workflow-errors.ts:162-186`), `InvalidExecutionStateError` 재사용 2곳만 그 패턴을 따르지 않는 비대칭이다. `code`(`INVALID_EXECUTION_STATE`)는 spec(`spec/5-system/6-websocket-protocol.md` §4.2 에러 코드 표)과 정확히 일치하므로 프로토콜 계약 위반은 아니다 — `message` 문구만 부정확하다.
  - 제안: `InvalidExecutionStateError`에도 `RetryLastTurnError`와 동일한 정적 팩토리 패턴(예: `notFailed(detail)`)을 추가해 retry_last_turn 전용 문구를 분리하거나, 최소한 두 호출부에 메시지 부정확 가능성을 JSDoc으로 명시.

### 요약

`execution.retry_last_turn` 재진입의 짝 전이(`FAILED → RUNNING` / `FAILED → WAITING_FOR_INPUT`)가 DB 가드에 막혀 매 호출 결정적으로 실패하던 8R CRITICAL과 그 잔여(9R/10R)는 이번 검토 대상 3개 파일 기준으로 완전히 해소돼 있고, 11R 이후 소스 로직 변경도 없다(이번 라운드는 `engine-driver.interface.ts`의 JSDoc 2줄 추가뿐). 상태머신 opt-in과 DB 가드 양쪽 배선을 직접 계산으로 재검증한 결과 신규 추가된 JSDoc 주장(`opts.allowRetryReentry`가 두 계층 모두에 필요하다는 것, opt-in 시에도 COMPLETED/CANCELLED는 배제된다는 것)이 실제 구현과 정확히 일치했고, spec 3문서(websocket-protocol §4.2, execution-engine §1.1/§1.3, ai-agent §7.9/§12.8)와도 line-level로 어긋남이 없다. 남은 것은 이미 plan(`retry-turn-terminal-guard.md` #20/#28)에 P2/P3로 추적 중인 두 항목뿐이다 — (1) `retryLastTurn`이 `Execution.status===FAILED`를 검증하지 않아 좁은 동시-취소 레이스에서 spawn된 `NodeExecution`이 영구 RUNNING 고아로 남을 수 있는 엣지 케이스, (2) `InvalidExecutionStateError`의 고정 메시지가 다른 명령군을 위해 설계된 문구라 retry_last_turn 문맥에서 부정확한 실패 사유를 노출하는 문제. 둘 다 `code`/`Execution` 최종 상태 같은 프로그램적 계약은 정확히 유지되고 블라스트 반경이 좁아 기능 완전성에 근본적 위협은 아니다.
