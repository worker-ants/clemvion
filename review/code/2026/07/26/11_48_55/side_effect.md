# 부작용(Side Effect) 리뷰

대상: `codebase/backend/src/modules/execution-engine/execution-engine.service.ts` (+ spec) — §2.3/§5.1 "선형 경로 외부 cancel 전파" 가드(`assertExecutionNotCancelled`) 도입.

## 발견사항

- **[WARNING]** 새 가드의 docstring 주장("stop 이 쓴 finishedAt/durationMs 가 보존된다")이 실제 동작과 다르다 — 취소 시각이 뒤늦은 시각으로 조용히 덮어써진다
  - 위치: `codebase/backend/src/modules/execution-engine/execution-engine.service.ts:7792-7794` (신규 docstring, 주장) vs. 실제 처리부 `codebase/backend/src/modules/execution-engine/execution-engine.service.ts:4504-4517` (`runExecution` 의 기존 `err instanceof ExecutionCancelledError` catch — 이번 diff 가 건드리지 않았지만 `:4261` 의 신규 `await this.assertExecutionNotCancelled(executionId)` 로 인해 새로 도달 가능해짐)
  - 상세: `assertExecutionNotCancelled` 의 docstring(:7792-7794)은 "이미 terminal 인 행을 다시 마킹하지 않으므로 stop 이 쓴 `finishedAt`/`durationMs` 가 보존된다"고 명시한다. 그러나 이 에러를 실제로 잡는 `runExecution` 의 catch(:4504-4517)는 무조건적으로 `savedExecution.status = CANCELLED; savedExecution.finishedAt = new Date(); savedExecution.durationMs = ...; await this.executionRepository.save(savedExecution);` 를 수행한다 — "이미 terminal 이면 skip" 가드가 전혀 없다. `assertExecutionNotCancelled` 자신이 읽은 최신 row(`row`, :7799)도 `savedExecution` 에 되먹임되지 않는다. 결과: `POST /executions/:id/stop` 이 실제 취소 시점에 쓴 `finishedAt`/`durationMs`(`codebase/backend/src/modules/executions/executions.service.ts:774-792` 의 raw UPDATE)가, 엔진이 다음 node 경계에서 취소를 뒤늦게 감지한 시각으로 재차 덮어써진다. 노드 실행 자체(핸들러 I/O, LLM 호출 등)가 오래 걸릴수록 `durationMs` 가 사용자가 Stop 을 누른 시점보다 크게 부풀려져 기록된다. `finalizeResumedExecutionOutcome`(:2619-2631, 재개 세그먼트 쌍둥이 경로 — `runNodeDispatchLoop` 의 신규 체크 `:1638` 으로 마찬가지로 새로 도달 가능)도 동일 패턴이다. 이 catch 블록들은 이 파일의 다른 종결부(`updateExecutionStatus` 가드 UPDATE, M-3)와 달리 원자적 조건부 UPDATE 를 쓰지 않는 구식 패턴이며, 이번 diff 이전에는 (코멘트 :890-896 이 설명하는 옛 in-memory 코루틴 fast-path 제거 이후) 사실상 `runExecution` 초기 세그먼트에서는 도달 불가능했던 것으로 보인다 — 이번 diff 가 그 dead code 를 실질적으로 살려냈다.
  - 제안: `assertExecutionNotCancelled` 가 `findOneBy` 로 이미 읽은 최신 row(특히 `finishedAt`)를 caller 에 전달하거나, `runExecution`/`finalizeResumedExecutionOutcome` 의 catch 가 `updateExecutionStatus` 류 가드 UPDATE(이미 CANCELLED 면 no-op)로 전환해 stop() 이 쓴 타임스탬프를 실제로 보존하도록 고친다. 최소한 docstring 주장을 실제 동작에 맞게 수정.

- **[WARNING]** Background 노드 본문이 부모 execution 취소를 감지하면 "실패"로 오분류되어 admin 에게 허위 `background_failed` 알림이 발송될 수 있다
  - 위치: 신규 체크 `codebase/backend/src/modules/execution-engine/execution-engine.service.ts:3729`(`executeInline` 내부) → `executeBackgroundSubgraph` 의 catch `codebase/backend/src/modules/execution-engine/execution-engine.service.ts:6850-6852` (`ParkReleaseSignal` 만 특별 취급, 그 외는 `throw err`) → `codebase/backend/src/modules/execution-engine/queues/background-execution.processor.ts:71-84` (제네릭 catch)
  - 상세: Background 노드 본문(`executeBackgroundSubgraph`)은 부모와 **같은 `executionId`** 를 공유하며 별도 BullMQ job 으로 fire-and-forget 병행 실행된다(`executeInline` 호출부 `:6813-6820`). 부모 execution 이 `POST /stop` 으로 RUNNING 중 취소되면, 이 본문의 `executeInline` 루프도 동일 executionId 로 `assertExecutionNotCancelled` 를 통과하다 새로 `ExecutionCancelledError` 를 던진다. `executeBackgroundSubgraph`(:6840-6852)는 `ParkReleaseSignal` 만 별도 처리하고 그 외 모든 에러는 그대로 재throw 하므로, `BackgroundExecutionProcessor.process()` 의 catch(:71-84)가 이를 일반 실패로 취급한다: (1) `BACKGROUND_RUN_COMPLETED` 를 `status:'failed'` 로 emit(:78, 이전에는 취소 시 본문이 계속 돌다 자연 완료했으므로 이 이벤트 자체가 없었다), (2) `notifyOnFailure=true` 인 Background 노드는 workspace admin 에게 "Background 본문 실행이 실패했어요: Execution … cancelled externally" 라는 **오해를 부르는 실패 알림**을 인앱 발송한다(:79-81, `dispatchFailureNotification`), (3) `throw err` 로 BullMQ 가 job 을 실패 기록하고 재시도 정책에 따라 재시도한다(:83) — 재시도 시엔 즉시 다시 같은 취소를 감지해 동일 알림이 재시도 횟수만큼 중복 발송될 수 있다. `ExecutionCancelledError` 를 구분하지 않는 것이 원인이며, 이는 이번 PR 이 고치려던 "Stop 이 부수효과를 못 멈춘다" 문제와 정확히 같은 클래스의 문제(허위 통지)를 다른 표면(BullMQ/알림)에서 재생산한다.
  - 제안: `executeBackgroundSubgraph` catch 에서 `ParkReleaseSignal` 과 동일하게 `ExecutionCancelledError` 도 별도 분기해 graceful 종료(재throw 금지, `notifyOnFailure`/재시도 skip)하거나, `BackgroundExecutionProcessor` 가 `instanceof ExecutionCancelledError` 를 인지해 `background_failed` 알림·재시도를 억제하도록 한다.

- **[WARNING]** 새로 상시 도달하게 된 `EXECUTION_CANCELLED` emit 경로가 문서화된 payload 계약(`cancelledBy`)을 어긴다 — 프로젝트가 이미 4곳에서 지키던 `emitCancellationEvent` 헬퍼를 우회
  - 위치: `codebase/backend/src/modules/execution-engine/execution-engine.service.ts:4511-4515` (`runExecution` catch, `:4261` 의 신규 호출로 새로 도달), `codebase/backend/src/modules/execution-engine/execution-engine.service.ts:2626-2630` (`finalizeResumedExecutionOutcome`, `:1638` 의 신규 호출로 새로 도달)
  - 상세: `spec/5-system/6-websocket-protocol.md:179` 와 `spec/conventions/chat-channel-adapter.md:148`은 `execution.cancelled` 이벤트가 `{ executionId, cancelledBy: 'user'|'system'|'timeout', duration, error? }` 형태임을 명시한다. 실제로 이 프로젝트는 `cancelParkedExecution`(:941-944) · `markExecutionCancelled`(:2696-2700) · `markQueueWaitTimeout` 등 4개 취소 경로 모두 공용 헬퍼 `emitCancellationEvent`(:964-990, "cancelledBy 는 닫힌 3값 union(§6.5)에 고정" — :960)를 통해 이 계약을 지킨다. 그러나 이번 diff 가 새로 자주 도달시키는 `runExecution`/`finalizeResumedExecutionOutcome` 의 `ExecutionCancelledError` catch 는 그 헬퍼를 쓰지 않고 `emitExecution(id, EXECUTION_CANCELLED, { status: CANCELLED })` 를 직접 호출해 `cancelledBy` 가 아예 빠진다. `ChatChannelDispatcher`(`codebase/backend/src/modules/chat-channel/chat-channel.dispatcher.ts:576-584`)는 `result ?? {}` 로 방어적으로 흡수해 크래시는 나지 않지만, "누가 취소했는가" 속성이 이 경로에서만 유실된다 — 문서화된 계약을 위반하는 payload 형태 불일치이며, 향후 이 필드에 의존하는 소비자(FE/분석)가 새로 늘어나면 이 경로만 조용히 깨진다.
  - 제안: 두 catch 블록도 `emitCancellationEvent(executionId, { cancelledBy: 'user', logContext: ... })` 로 통일.

- **[INFO]** `ExecutionCancelledError` 생성자에 선택 `message` 인자 추가 — 하위 호환 확인됨, 그 자체는 안전
  - 위치: `codebase/backend/src/modules/execution-engine/workflow-errors.ts:314-325`
  - 상세: `constructor(message = 'Execution cancelled while waiting for input')` 로 기본값을 유지해 인자 없이 호출하는 기존 코드(`retry-turn.service.spec.ts:479` 의 `new ExecutionCancelledError()`)는 동일하게 동작한다. 전체 저장소에서 `new ExecutionCancelledError(...)` 호출부는 이 1건 + 이번에 추가된 `execution-engine.service.ts:7804-7806` 뿐이다. 분류 로직(`instanceof ExecutionCancelledError`, `retry-turn.service.ts:642`, `execution-engine.service.ts:1307/2619/4504` 등)은 전부 타입 기반이라 message 내용에 의존하지 않는다 — 시그니처 확장이 기존 호출부/분류 로직에 미치는 영향은 없다. (단, 이 생성자 확장 자체가 위 세 항목이 서술하는 "새로 자주 도달 가능해진 catch 경로들"을 가능하게 만든 **원인**이므로, 이 항목은 나머지 항목과 함께 읽어야 한다.)

- **[INFO]** 신규 이벤트의 "중복 emit" 여부 — 단일 세그먼트 내 중복은 없음, 다만 커버되지 않은 인접 루프(Parallel/Loop/ForEach 본문, `retry-turn.service.ts` 재개 루프)는 여전히 무가드
  - 위치: 신규 호출 3곳 — `:1638`(`runNodeDispatchLoop`, 재개 세그먼트 전용), `:3729`(`executeInline`), `:4261`(`runExecution` 자체 루프)
  - 상세: 이 세 진입점은 실행 생명주기 상 상호 배타적(초기 세그먼트 vs. 재개 세그먼트)이거나, 중첩 호출(Workflow 노드 → `executeInline`)이어도 예외가 단일 스택으로 unwind 되어 catch 는 정확히 한 번만 실행된다 — 같은 `execution:<id>` 채널에 동일 `EXECUTION_CANCELLED` 를 두 번 emit하는 경로는 발견되지 않았다. 다만 `ParallelExecutor`/`ForEachExecutor`/`LoopExecutor` 의 컨테이너 본문 dispatch 루프와 `retry-turn.service.ts` 의 자체 순회 루프에는 이번 diff 의 체크가 삽입되지 않았다 — 이는 이번 diff 로 인한 새로운 부작용이 아니라 기존에 존재하던 커버리지 갭의 연장이므로 CRITICAL 로 올리지 않았지만, "Stop 버튼이 부수효과까지 멈춘다"는 이번 PR 의 목표가 이 세 진입점 밖에서는 여전히 미달성이라는 점은 후속 커버리지 항목으로 남긴다.

- **[INFO]** 신규 회귀 테스트가 위 emit-shape/timestamp 이슈를 커버하지 않음
  - 위치: `codebase/backend/src/modules/execution-engine/execution-engine.service.spec.ts:4942-4969` (신규 describe/it)
  - 상세: 새 테스트는 `mockHandler.execute` 가 1회만 호출됐는지(=dispatch 중단)만 단언한다. `mockWebsocketService.emitExecutionEvent` 의 payload(`cancelledBy` 유무), `mockExecutionRepo.save` 에 넘어간 `finishedAt`/`durationMs`, Background 본문 상호작용은 어느 것도 단언하지 않는다 — 위 세 WARNING 이 회귀 가드 없이 남는다.
  - 제안: 최소한 `emitExecutionEvent` 가 `EXECUTION_CANCELLED` 로 몇 번 호출됐는지·payload 형태를 단언하는 케이스 추가 권장(별도 테스트 리뷰어 영역과 중복될 수 있으니 참고용).

## 요약

`ExecutionCancelledError` 생성자의 선택 `message` 인자 추가 자체는 기본값 보존으로 완전히 하위 호환이며 기존 호출부·`instanceof` 분류 로직에 영향이 없다. 진짜 위험은 그 확장이 가능하게 만든 **새 도달 경로**에 있다: `assertExecutionNotCancelled` 가 `runExecution`/`runNodeDispatchLoop`/`executeInline` 세 dispatch 루프에서 처음으로 `ExecutionCancelledError` 를 실전 트리거하면서, (1) 그동안 사실상 죽어있던 `runExecution`/`finalizeResumedExecutionOutcome` 의 구식 취소 종결 코드가 되살아나 stop() 이 기록한 `finishedAt`/`durationMs` 를 조용히 덮어쓰고(자신의 새 docstring 주장과 모순), (2) 같은 executionId 를 공유하는 Background 노드 본문이 취소를 "실패"로 오분류해 admin 에게 허위 알림을 보내고 BullMQ 가 무의미한 재시도를 하며, (3) 그 두 종결 코드가 프로젝트의 표준 취소-이벤트 헬퍼(`emitCancellationEvent`)를 우회해 문서화된 `cancelledBy` 계약을 깬다. 단일 세그먼트 내에서 같은 채널에 `EXECUTION_CANCELLED` 가 문자 그대로 중복 emit 되는 경로는 없었지만, 독립적으로 병행 실행되는 Background 본문 경로에서 별도 채널(`background:run:<id>`)로 의도치 않은 "실패" 이벤트·알림이 새로 발생하는 것은 실질적인 구독자 부작용이다. 셋 다 이번 diff 가 직접 작성한 코드는 아니고 기존 코드의 새로운 도달 가능성에서 기인하지만, 이번 PR 의 목적(Stop 이 부수효과를 확실히 멈추게 한다)과 정면으로 관련되므로 머지 전 처리를 권장한다.
