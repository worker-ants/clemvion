# 동시성(Concurrency) 코드 리뷰

## 발견사항

- **[WARNING]** `_retry_state.json` 의 read-modify-write 가 프로세스 간 잠금 없이 이뤄짐 — 동시 `--update` 호출 시 lost update
  - 위치: `.claude/_shared/retry_state.py:138-167`(`apply_status_update`), 관련 `:50-52`(`save_state`), `:41-47`(`load_state`), `:55-93`(`reconcile_state_with_disk`)
  - 상세: `apply_status_update` 는 `load_state` → 메모리에서 버킷 이동/카운터 갱신 → `save_state` 로 전체 JSON 을 통째로 덮어쓰는 고전적 read-modify-write 이며, 어떤 형태의 잠금(`fcntl.flock`)도 원자적 교체(temp+`os.replace`)도 없다. 이 CLI(`code_review_orchestrator.py --update`, `consistency_orchestrator.py --update`)는 reviewer/checker 가 종료될 때마다 **별도 OS 프로세스**로 호출되는데, `code-review-agents` SKILL 이 문서화한 "Workflow 불가 환경 fallback"(직접 `Agent` fan-out + `--update` CLI) 경로가 실제로 쓰이는 경로다 — 특히 CLAUDE.md 의 "구현 완료 후 자동 review" 트리거는 "Workflow 비동기 간극을 피하려 fallback 평문 Agent fan-out 을 선택할 수 있다"고 명시한다. 이 경로에서 main 이 여러 reviewer 의 상태를 한 턴에 "서로 의존성 없는 호출"로 배치해 병렬 실행하면(harness 자체가 그렇게 하길 권장), 예컨대 여러 reviewer 가 동시에 rate limit 에 걸려 각각 `--update --status rate_limit --reset-hint N` 을 병렬로 부르는 상황에서 두 프로세스가 같은 스냅샷을 읽고 각자 반영한 뒤 나중에 쓴 쪽이 앞선 쪽을 통째로 덮어써 갱신을 잃는다.
    - `agents_success`/`agents_pending` 은 `reconcile_state_with_disk` 가 디스크의 리포트 파일 존재 여부로 다시 도출하므로(다음 `--summary-state`/`--resume` 호출 시) 이 레이스가 있어도 결국 자가 치유된다 — 이 계약이 지키려는 핵심 안전 속성("리포트 파일 없는 자기신고 success 는 가짜")은 보호됨.
    - 그러나 **`agents_fatal` 은 대응하는 리포트 파일이 없어 디스크로 재도출할 수 없다.** 레이스로 어떤 agent 의 `fatal` 기록이 다른 프로세스의 stale write 에 덮여 사라지면, 다음 reconcile 은 그 agent 를 단순 "missing" 으로 보고 `agents_pending` 에 되돌린다(`reconcile_state_with_disk:82` 의 `fatal`-필터가 이미 사라진 항목을 보존할 수 없음) — 영구 실패한 reviewer 가 다시 재시도 대상이 된다.
    - `rate_limit_episodes` 증가(`:151`)와 `last_reset_hint_sec = max(prev, reset_hint)`(`:153-154`) 도 각자 stale `prev`/카운터 값을 기준으로 계산되므로, 동시 두 번의 rate_limit 이벤트 중 하나의 증가분·재시도 힌트가 조용히 유실될 수 있다. `agent_history`(`:159`) 항목도 마찬가지로 통째로 덮여 사라질 수 있어 `/loop` 의 재시도 판단·감사 로그가 실제보다 적게 보인다.
  - 참고: 동일 파일을 읽는 `.claude/hooks/_lib/review_guard.py:419-423`(`_forced_coverage_missing`)는 `json.load` 를 `except (OSError, ValueError)` 로 감싸 손상된/torn 파일에도 fail-open 하는데, 정작 훨씬 자주 쓰고 다시 읽는 오케스트레이터 쪽 `load_state`(`retry_state.py:41-47`)는 동일 예외를 잡지 않는다 — 레이스든 프로세스 kill 이든 쓰기 도중 잘린 JSON 이 남으면 다음 `--update`/`--resume`/`--summary-state`/`--apply-routing` 호출이 `json.JSONDecodeError` 로 그대로 죽는다(같은 파일의 두 소비자가 견고성 수준에서 어긋남).
  - 이 문제 자체는 이번 diff 가 새로 만든 것이 아니다 — `git diff origin/main...HEAD` 로 확인한 결과 `code_review_orchestrator.py`/`consistency_orchestrator.py` 에 있던 두 사본이 바이트 단위로 동일했고(모듈 docstring 의 AST 비교 주장과 일치), 이번 커밋은 그 로직을 `_shared/retry_state.py` 하나로 옮겼을 뿐 동작은 보존한다. 다만 이 프로젝트는 유사한 "잠금 없는 read-increment-write" 를 `.claude/hooks/_lib/failopen_state.py:106-110` 에서 이미 검토한 전례가 있고, 거기서는 "중요 신호(배너)를 racy 쓰기보다 먼저 내보내 카운터만 잃는다"는 설계로 리스크를 의도적으로 받아들였다 — retry_state.py 의 `agents_fatal`/`agent_history`/rate-limit 필드는 그런 "신호와 분리된 카운터" 구조가 아니라서 같은 수준의 사전 완화가 없다. 두 사본을 한 곳으로 모은 지금이 한 번에 고칠 자연스러운 시점이다.
  - 제안: (a) `load_state`→변경→`save_state` 임계구역을 advisory 파일 잠금(`fcntl.flock`)으로 감싸기 — 이 코드베이스가 이미 채택 이력이 있는 primitive(`손으로 짠 primitive` 대신 권장되는 3가지 중 하나)와 일치한다. 또는 최소한 (b) `save_state` 를 temp-file + `os.replace` 로 원자적 쓰기로 바꿔 torn-write 크래시만이라도 제거. (c) `load_state` 도 `review_guard.py` 와 동일하게 `(OSError, ValueError)` 를 잡아 CLI 가 손상 파일에 죽지 않게 함. (d) 두 개의 `--update` subprocess 를 실제로 동시에 실행해 갱신 유실이 없는지 보는 회귀 테스트 추가 — `test_bootstrap_mermaid_install.py` 의 `test_concurrent_cold_start_converges_and_then_stops_reinstalling` 이 이 프로젝트가 이미 쓰는 "mock 대신 진짜 동시 프로세스" 패턴의 선례다.

## 요약

이번 변경은 크게 (1) `block_integrity.py` 신설 — `consistency-summary` 의 `BLOCK: NO` 가 checker 의 `[CRITICAL]` 태그와 모순되는지 감지하는 순수 읽기 전용 검사(잠금·공유 상태 없음, 동시성 이슈 없음), (2) `code_review_orchestrator.py`/`consistency_orchestrator.py` 에 중복돼 있던 5개 상태 관리 함수를 `_shared/retry_state.py` 로 추출한 리팩터(동작 보존, `git diff` 로 바이트 단위 동일성 확인), (3) `review_guard.py` 에 13줄 추가해 `_block_integrity.contradiction_note()` 를 훅에 연결한 것으로 구성된다. 신규로 도입된 동시성 결함은 없다 — 유일하게 실질적인 발견은 `_shared/retry_state.py` 로 옮겨진 `_retry_state.json` read-modify-write 가 잠금 없이 이뤄진다는 점인데, 이는 리팩터 이전부터 양쪽 오케스트레이터에 동일하게 존재하던 사전 조건이며, 핵심 안전 속성(`agents_success`/`pending` 이 디스크의 실제 리포트 파일로 재도출됨)은 자가 치유된다. 다만 `agents_fatal`·`rate_limit_episodes`·`agent_history` 처럼 디스크로 재도출할 수 없는 필드는 실제 fan-out 병렬 호출 경로에서 갱신 유실(→ 이미 fatal 인 reviewer 의 불필요한 재시도, rate-limit 카운터/히스토리 과소집계)에 노출돼 있고, 같은 파일을 읽는 `review_guard.py` 쪽 리더보다 오케스트레이터 쪽 리더가 손상 파일에 더 취약하다. 두 사본이 한 곳으로 합쳐진 지금이 `fcntl.flock` 또는 원자적 쓰기로 고치기 좋은 시점이라 WARNING 으로 기록하며, 프로덕션 데이터가 아닌 harness 자체 도구 상태라 위험도는 제한적이다.
