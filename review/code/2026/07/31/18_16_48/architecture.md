# Architecture Review

## 발견사항

- **[WARNING]** `_shared/retry_state.py` 추출이 세 번째 소비자(`merge_coordinator_orchestrator.py`)를 빠뜨려, 이 리팩터링이 없애려던 바로 그 "N-copy, change-all" 패턴을 한 곳에 그대로 남겼다
  - 위치: `.claude/_shared/retry_state.py:1` (docstring: "shared by **both** orchestrators") / `.claude/skills/merge-coordinator/scripts/merge_coordinator_orchestrator.py:82-140` (`_load_state`/`_save_state`/`_apply_status_update`)
  - 상세: `retry_state.py`의 존재 이유는 "두 orchestrator 가 동일한 5개 함수를 `Mirrors X. Change both.` 주석으로만 동기화하다가 실제로 어긋난 전례(`report_paths.py`)를 반복하지 않기 위함"이다. 그런데 `.claude/skills/merge-coordinator/scripts/merge_coordinator_orchestrator.py` 는 `_retry_state.json` 을 다루는 **세 번째** orchestrator이고, 그 `_load_state`(82-88행)·`_save_state`(91-93행)·`_apply_status_update`(111-140행) 는 이번에 이관된 `_shared/retry_state.py` 버전과 **완전히 동일한 로직**이다(함수명 prefix `_` 유무만 다름). 이 파일 상단 주석("Mirror code_review_orchestrator so main never has to Read …")은 코드 리뷰 오케스트레이터가 이제 얇은 wrapper로 바뀐 뒤에도 그대로 남아 stale 하다. 더 심각한 것은 `_shared/retry_state.reconcile_state_with_disk` 로 이번에 나머지 두 orchestrator 에 적용된 "디스크 기준 자기치유" 수정(Agent tool 로 직접 fan-out 하면 `--update` 를 안 타서 상태가 prepare 시점에 얼어붙는 실제 프로덕션 버그의 수정)이 `merge_coordinator_orchestrator.py` 에는 전혀 반영되지 않았다는 점이다. `merge-coordinator/SKILL.md:67` 의 "3-fallback. 수동 Agent fan-out" 경로가 코드-리뷰/컨시스턴시와 동일하게 존재하므로, `/merge-coordinate` 세션도 정확히 같은 클래스의 버그(커밋된 두 산출물이 서로 모순)에 그대로 노출된 채로 남는다. `test_retry_state_shared.py` 도 CODE_REVIEW/CONSISTENCY 두 경로만 대조하므로 이 갭을 잡아내지 못한다.
  - 제안: `merge_coordinator_orchestrator.py` 의 네 함수도 동일하게 `_shared/retry_state.py` 로 위임하도록 이관하고(`_emit_summary_state` 는 `branches=`/`base=` 를 `extra_fields` 콜백으로 전달), reconcile-on-read 자기치유를 세 번째 소비자에도 적용할 것. 의도적으로 제외한 것이라면 그 이유를 `retry_state.py` docstring 에 명시해 "both" 라는 표현이 더 이상 사실과 다르지 않게 할 것.

- **[WARNING]** 신규 Critical-하향 백스톱이 시간 계산 함수 내부에 부수효과로 얹혀, 관련 없는 과거 세션에 대해 매 호출마다 전체 재스캔 + 반복 경고를 발생시킨다 (측정: 이 저장소에서 세션 323개 스캔, 그중 8개가 매번 재경고)
  - 위치: `.claude/hooks/_lib/review_guard.py:707-740` (`_newest_resolved_impl_done_mtime`), 특히 722-733행에 추가된 `_block_integrity.contradiction_note(...)` 호출 및 `print(..., file=sys.stderr)`
  - 상세: 이 함수의 계약은 "가장 최근에 통과한 --impl-done 세션의 timestamp 를 계산해 반환"이다. 이번 diff 는 그 루프 **내부**에 "이 세션이 checker CRITICAL 을 하향했는가"를 판정해 stderr 로 경고하는 완전히 다른 책임(진단/감사)을 끼워 넣었다 — 순수 질의 함수에 감사성 부수효과가 섞였다(SRP 위반). 이 함수는 `evaluate_review()` 의 Gate 2(spec-linked 변경이 있을 때)에서 push 시도·Stop 훅 종료마다 매번 새 프로세스로 호출되며, 매 호출마다 `review/consistency/**` 전체를 다시 순회한다 — 캐싱·메모이제이션이 전혀 없다. 실측: 이 저장소에는 현재 `--impl-done` 이면서 `BLOCK: NO` 인 세션이 323개 있고, 그중 8개가 실제로 `[CRITICAL]` 하향 모순을 갖고 있다 — 즉 spec-linked 코드를 건드리는 모든 push/turn-종료마다 (해당 8개 세션에 대해 매번 동일하게) 8줄의 경고가 stderr 에 다시 찍히고, `contradiction_note` 계산만으로 약 0.39초가 추가로 소요된다(순수 파이썬 측정치, `review/consistency` 트리 순회 자체의 0.13초는 별도). 이 8개·323개·0.39초는 이력이 쌓일수록 단조 증가만 하며 — 이미 처리된 과거 세션도 재확인·재경고를 영원히 반복한다는 점에서 감사 신호로서의 가치도 시간이 갈수록 희석된다.
  - 제안: 모순 탐지를 시간-계산 루프에서 분리해 별도 함수로 추출하고, ⓐ "이번 게이트 판정에 실제로 채택되는(best) 세션"에 대해서만 수행하거나 ⓑ 이미 경고한 세션 dir 을 지속 상태(예: `.claude/state/`)에 캐싱해 재경고를 억제할 것. 근본적으로는 이력 전체를 훑는 감사 성격이므로, hot-path 게이트가 아니라 `spec-coverage` 류의 standing-audit 스크립트 쪽 책임으로 옮기는 편이 SRP 에 맞는다.

- **[WARNING]** 체커 이름 목록(`CHECKER_REPORTS`)이 `_shared/block_integrity.py` 에 세 번째로 하드코딩되어 있고, 기존 4-place drift guard 의 감시 범위 밖에 있다
  - 위치: `.claude/_shared/block_integrity.py:44-50` (`CHECKER_REPORTS`), 사용처 `:83-84`
  - 상세: 체커 5종(`cross_spec`, `rationale_continuity`, `convention_compliance`, `plan_coherence`, `naming_collision`)의 목록은 이미 `consistency_orchestrator.ALL_CHECKERS` 와 `code-review-agents/lib/role_instructions.CHECKER_INSTRUCTIONS` 의 키(consistency_orchestrator 가 이걸 import 해서 쓴다) 두 곳에 SSOT 로 존재한다. 이번 diff 는 `downgraded_criticals()` 가 순회할 리포트 파일명을 `CHECKER_REPORTS` 라는 **세 번째** 하드코딩 튜플로 새로 만들었다. `.claude/tests/test_agent_consistency.py` 는 정확히 이런 "체커/리뷰어가 여러 곳에 따로 선언되어 drift 하는" 문제를 잡기 위한 기존 가드지만(`CHECKER_INSTRUCTIONS` 키 기준), `CHECKER_REPORTS` 는 그 대상에 포함되어 있지 않다. 지금은 세 목록이 우연히 일치하지만, 향후 6번째 체커가 추가되면 `CHECKER_REPORTS` 갱신을 잊는 순간 그 체커가 낸 CRITICAL 하향은 이 백스톱이 조용히 놓친다 — 정확히 이 커밋의 자매 변경(`retry_state.py` 추출)이 없애려던 것과 같은 실패 양식이다.
  - 제안: `CHECKER_REPORTS` 를 하드코딩하지 말고 `CHECKER_INSTRUCTIONS.keys()` (또는 `consistency_orchestrator.ALL_CHECKERS`) 에서 파생시키거나, 최소한 `test_agent_consistency.py` 의 drift guard에 이 다섯 번째 "체커가 선언되는 장소"로 등록할 것.

- **[WARNING]** `downgraded_criticals()` 가 리포트 경로를 직접 조합해, "리포트 위치는 한 곳에서만 결정한다"는 기존 `report_paths.py` 계약을 우회한다
  - 위치: `.claude/_shared/block_integrity.py:79,84` (`os.path.join(session_dir, "SUMMARY.md")` / `os.path.join(session_dir, name)`)
  - 상세: `.claude/_shared/report_paths.py` 는 정확히 "리포트가 어디 있는가"를 gate 와 CLI 가 다르게 답해서 실제로 어긋났던 사고(2026-07-17, `touch security.md` 가 한쪽만 통과) 이후 만들어진, `report_path()`/`has_report()` 로 그 판단을 한 곳에 모으는 shared 모듈이다. `review_guard.py` 와 두 orchestrator 는 모두 이걸 통해 리포트 유무를 판단하는데, 같은 `_shared/` 패키지 안에 나란히 있는 이번 신규 모듈만 `os.path.join(session_dir, name)` 로 경로를 직접 조합해 리포트를 읽는다. 지금은 checker 리포트 파일명이 항상 `f"{checker}.md"` 로 고정돼 있어 결과가 같지만(`consistency_orchestrator.prepare_session` 확인), `report_paths.report_path()` 가 존재하는 이유 자체가 "output_file 이 항상 그 규칙을 따른다고 가정하지 말라"는 것이므로, 이 신규 코드는 그 교훈이 적용되기 전 상태로 되돌아간 것에 가깝다.
  - 제안: `downgraded_criticals()` 의 체커 리포트 경로 계산을 `report_paths_lib.report_path(session_dir, name, state)` (또는 `has_report`) 로 위임할 것. `state` 가 필요하므로 `session_dir` 만 받는 현재 시그니처에 `state` 인자 추가가 필요하지만, 호출부(`review_guard._newest_resolved_impl_done_mtime`)는 이미 `meta.json`/`SUMMARY.md` 를 열어본 뒤라 `_retry_state.json` 도 같은 자리에서 읽을 수 있다.

- **[INFO]** `review_guard.py` 가 이번 diff 에서 `_block_integrity` 를 이미 import 했는데도, 자신의 기존 `_summary_block_is_no()` 는 여전히 별도의 동일한 정규식을 손으로 재구현하고 있다
  - 위치: `.claude/hooks/_lib/review_guard.py:141` (`_BLOCK_LINE = re.compile(r"BLOCK:\s*(YES|NO)", re.IGNORECASE)`, 기존 코드) 대 `.claude/_shared/block_integrity.py:42,66-69` (`summary_block_verdict`, 신규)
  - 상세: 두 정규식은 글자 그대로 동일하다. `review_guard._summary_block_is_no(summary_path)` 는 파일을 직접 읽어 `_BLOCK_LINE` 으로 매칭하는데, 이번 diff 로 새로 추가된 `block_integrity.summary_block_verdict(text)` 가 정확히 같은 일을 한다. `review_guard.py` 는 이 커밋에서 어차피 `_block_integrity` 를 새로 import 하므로, `_summary_block_is_no` 를 `_block_integrity.summary_block_verdict(text) == "NO"` 로 바꿔 끼우는 데 추가 의존성 비용이 없다. 지금 당장 동작 차이는 없지만, "BLOCK: 파싱 규칙"이 두 파일에 독립적으로 존재하는 상태가 남는다.
  - 제안: `_summary_block_is_no` 가 `_block_integrity.summary_block_verdict()` 를 재사용하도록 바꾸고 `review_guard.py` 자체의 `_BLOCK_LINE` 상수를 제거해, "BLOCK: 파싱"의 SSOT 를 `block_integrity.py` 하나로 좁힐 것.

## 요약

이번 diff 는 두 개의 독립된, 개별적으로는 잘 설계된 변경으로 구성된다: (1) `consistency-summary.md` 의 "Critical 하향 금지" 규약을 기계적으로 검증하는 `block_integrity.py` 신설과 `review_guard.py` 배선, (2) 두 orchestrator 가 "Mirrors X. Change both." 주석으로만 동기화하던 5개 상태-bookkeeping 함수를 `_shared/retry_state.py` 로 추출. `_shared/` 패키지 자체의 레이어링(양쪽 레이어가 소유하지 않는 중립 커널)은 견고하고 순환 의존성도 없으며, `retry_state.emit_summary_state` 의 `extra_fields` 콜백 설계는 OCP 를 잘 지킨다. 다만 두 변경 모두 이 프로젝트가 반복해서 대가를 치른 "동일 로직/목록의 여러 사본이 손으로만 동기화되다 어긋남" 패턴을 부분적으로만 해소했다: `retry_state.py` 추출은 세 번째 소비자(`merge_coordinator_orchestrator.py`)를 놓쳐 정확히 같은 패턴과 그로 인한 자기치유 미적용 버그 노출을 그대로 남겼고, `block_integrity.py` 는 체커 목록·리포트 경로 규칙을 각각 새로운 세 번째 하드코딩 사본으로 도입했으며, 하향 감지 로직은 순수 시간-계산 함수에 부수효과로 얹혀 이력 전체를 매 호출마다 재스캔·재경고한다(실측 323개 세션, 그중 8개가 매번 재경고, +0.39초). 이 중 어느 것도 현재 동작을 깨뜨리거나 fail-open 원칙을 위반하지 않으므로 병합을 막을 사안은 아니지만, 이 커밋의 서사 자체("mirrored copy 는 drift 한다")를 스스로 재현하고 있다는 점에서 후속 정리가 필요하다.
