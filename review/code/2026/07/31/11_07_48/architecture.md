# Architecture Review — harness-review-gate-fixes-1bd6aa

## 발견사항

- **[WARNING]** `_default_branch_ref()`만 파일 내 모든 자매 git 헬퍼와 다른 예외 처리 패턴을 쓰고, 그 결과 자신을 호출하는 함수의 "silent on any git failure" 계약을 어긴다.
  - 위치: `.claude/skills/code-review-agents/scripts/code_review_orchestrator.py:1092`-`1101` (`_default_branch_ref` 정의), 계약 서술은 `:1117`-`1118` (`warn_if_committed_work_is_missing` docstring)
  - 상세: 같은 파일 안의 다른 모든 git 호출 헬퍼(`get_git_diff_files`, `get_git_diff_content`, `get_git_commit_files`, `get_git_commit_diff`, `get_git_range_files`, `get_git_range_diff`, `get_git_branch_diff_files`, `get_git_branch_diff`, `get_file_at_commit` — 총 9곳, 각각 `except Exception as e:` 로 감싸고 실패 시 빈 값 반환)와 달리, 이번 diff 가 신설한 `_default_branch_ref()`는 두 번의 `_git(...)` 호출(`git symbolic-ref` / `git rev-parse --verify`)을 어떤 예외 처리도 없이 실행한다. `_git()` 자체는 `subprocess.run(...)`을 그대로 반환할 뿐 예외를 삼키지 않으므로(라인 817-818), `git` 바이너리 부재(`FileNotFoundError`) 또는 10초 기본 timeout 초과(`subprocess.TimeoutExpired`, 예: 동시에 실행 중인 다른 git 프로세스의 `.git/index.lock` 경합)가 발생하면 예외가 그대로 전파된다. 이 함수는 새로 추가된 `warn_if_committed_work_is_missing()`을 통해 **인자 없는 기본 `--prepare` 경로마다 무조건 호출**되므로(`collect_change_infos` 안, else 분기), 이번 PR 이 고치려던 "리뷰가 조용히 실패(빈 corpus 인데 Critical 0)"라는 결함 대신 "리뷰 준비 자체가 크래시"하는 새 실패 모드가 생긴다. 정작 `warn_if_committed_work_is_missing`의 docstring 은 "Advisory only … Silent on any git failure: a review must not fail because the warning could not be computed" 라고 명시적으로 약속하는데, 그 약속이 자신이 첫 줄에서 호출하는 `_default_branch_ref()` 내부에서 지켜지지 않는다. 흥미롭게도 같은 diff 의 자매 함수인 `consistency_orchestrator.py::_branch_changed_rels`(신규, 동일 책임 — "base ref 계산 실패시 안전하게 빈 값 반환")는 정확히 `try/except Exception`으로 이 패턴을 올바르게 구현했다 — 같은 PR 안에서 한쪽 orchestrator 는 맞고 다른 쪽은 틀렸다. 테스트 커버리지도 이 간극을 못 잡는다: `test_review_changeset_warning.py`의 유일한 `_default_branch_ref` 관련 테스트는 `orch._default_branch_ref = lambda: ARG["base"]` 로 함수 전체를 스텁 처리해 실제 subprocess 경로를 우회한다.
  - 제안: `_default_branch_ref()`의 두 `_git()` 호출을 파일 내 다른 9개 헬퍼와 동일하게 `try/except Exception`으로 감싸 실패 시 `None`을 반환하도록 통일한다. 최소 1개 테스트는 스텁이 아닌 실제 함수를 예외 유발 조건(예: `subprocess.run` 이 `TimeoutExpired`를 던지는 monkeypatch)에서 호출해 크래시 없이 `None`을 반환하는지 확인한다.

- **[WARNING]** "origin 기본 브랜치를 알아낸다"는 동일 책임의 독립 구현이 이제 세 곳에 존재하고, 서로 일치를 보장하는 자동 테스트가 없다.
  - 위치: `.claude/hooks/_lib/branch_guard.py:73` (`_origin_default_branch`), `.claude/hooks/_lib/review_guard.py:197` (`_default_branch`, 위 함수를 우선 재사용 후 로컬 `main`/`master` 로 폴백), `.claude/skills/code-review-agents/scripts/code_review_orchestrator.py:1092` (신규 `_default_branch_ref`)
  - 상세: 이번 diff 가 추가한 `_default_branch_ref()`는 기존에 두 벌 있던 "기본 브랜치 판정" 로직(하나는 `symbolic-ref`+네트워크 폴백, 다른 하나는 그걸 재사용 후 로컬 브랜치명 폴백)의 세 번째 독립 구현이다. 세 함수는 우선순위 전략과 반환 형식이 미묘하게 다르다(`review_guard._default_branch` 는 로컬 브랜치명 `"main"`을 반환하는 반면, 신규 `_default_branch_ref` 는 원격추적 참조 `"origin/main"`을 반환) — 각자의 소비처(merge-base 계산 vs. `git diff <ref>...HEAD`)에 맞춰 의도적으로 다르긴 하지만, 셋 다 "그 저장소의 기본 브랜치가 무엇인가"라는 같은 질문에 답하면서 서로 다른 결과를 낼 수 있는 알고리즘을 손으로 각각 유지한다. 이 저장소는 정확히 이 실패 유형 — 정책/로직이 여러 곳에 손으로 복제되고 자동 합치 테스트가 없어 조용히 갈라지는 것 — 을 이미 겪었고(`test_router_safety_policy_doc.py`가 두 문서의 "24 vs 44 extension" 표류를 잡기 위해 신설된 전례), 그 교훈은 이 코드베이스에서 반복 학습된 패턴이다. 다만 `.claude/hooks/_lib`(hooks 전용 패키지)과 skills 쪽 `_lib`이 동일 패키지명이라 같은 인터프리터에서 임포트가 충돌한다는 이미 문서화된 구조적 제약(`.claude/tests/README.md` 컨벤션 절, `test_review_changeset_warning.py` 상단 주석)이 있어, `code_review_orchestrator.py`가 `hooks/_lib/branch_guard.py`를 직접 재사용하기 어려웠을 정황은 감안할 만하다.
  - 제안: 세 함수 중 하나를 SoT로 명시하고 나머지 두 곳에 "로직이 바뀌면 함께 갱신" 상호 참조 주석을 남긴다. 여력이 되면 `_lib` 네임스페이스 충돌 자체를 해소해 실제 코드 공유로 전환하거나, 최소한 세 함수의 반환 계약(로컬명 vs `origin/`-prefixed, 폴백 순서)이 서로 다르다는 점을 각 정의부에 명시한다.

- **[INFO]** `evaluate_review`의 `in_flight_ok` 불리언 플래그가 두 호출자(push/stop)의 신뢰 수준 차이를 하나의 공유 함수 내부 분기로 인코딩한다 — 지금은 잘 봉인돼 있으나 향후 세 번째 호출자가 생기면 취약해지는 패턴이다.
  - 위치: `.claude/hooks/_lib/review_guard.py:858`-`859` (`evaluate_review(cwd=None, *, in_flight_ok: bool = False)` 시그니처), `:897` (`if in_flight_ok and _code_review_in_flight(repo_root):`)
  - 상세: 이번 수정 자체는 설계가 좋다 — 키워드 전용 파라미터를 기본값 `False`(기존 동작 유지)로 추가해 기존 호출자(`guard_review_before_push.py`, 위치 인자만 사용)의 계약을 전혀 건드리지 않은 채 새 호출자(`guard_review_before_stop.py:344`, `in_flight_ok=True`)에게만 관대한 동작을 열어준다 — OCP 를 지키는 하위호환 확장의 좋은 예다. 다만 "이 게이트가 얼마나 관대할지"를 불리언 플래그로 호출자에게 위임하는 구조 자체는, 이번에 고쳐진 결함(플래그가 아예 없어 억제가 무조건 적용됐던 것)과 같은 계열의 패턴이다. 지금은 호출자가 push/stop 두 곳뿐이고 양방향 모두 회귀 테스트(`EvaluateInFlightShortCircuitTest.test_push_path_still_blocks_while_in_flight` / `test_stop_path_opts_in_and_is_allowed`, `test_stop_guard_failopen.py::test_stop_passes_in_flight_opt_in`)로 고정돼 있어 당장의 위험은 낮지만, "관대함"이 함수 이름이 아니라 불리언 인자값으로만 드러나므로 세 번째 호출자가 추가될 때 올바른 값을 넘겼는지는 코드 리뷰/주석에만 의존한다(타입 시스템이 강제하지 않음).

## 요약

이번 변경은 세 개의 축 — (1) `evaluate_review`의 in-flight 억제를 Stop 전용으로 스코프 축소, (2) 기본 `--prepare` changeset 이 커밋된 브랜치 작업을 조용히 누락하는 것에 대한 경고, (3) consistency checker 번들의 4-계층 우선순위 재배열 — 를 다루며, 셋 다 반복 재발이 실측으로 기록된 실제 결함에 대한 최소-diff 교정이다. 아키텍처 관점에서 핵심 강점은 셋 다: `evaluate_review`의 API 확장이 키워드 전용 옵트인 파라미터로 하위호환을 지키고, `prioritize_bundle_files`(재배열 전용)와 `truncate_file_bundle`(절단+생략 고지)의 책임 분리가 명확하며, 카탈로그 강등 정규식이 경로 세그먼트 패턴 매칭이라 코드 변경 없이 향후 카탈로그 이동/추가를 흡수하는 등 확장성을 고려한 설계다. 순환 의존성이나 SOLID/레이어 경계의 실질적 위반은 발견되지 않았다. 다만 신규로 추가된 `code_review_orchestrator._default_branch_ref()`가 같은 파일의 다른 9개 git 헬퍼와 다른 예외 처리 패턴을 써서 자신이 지원하는 함수의 "무실패" 계약을 어기는 구체적 결함이 있고(테스트도 스텁으로 우회해 이 경로를 실제로 검증하지 않음), "기본 브랜치 판정" 로직이 이제 세 곳에 손으로 복제돼 있는 점은 이 저장소가 과거에 이미 대가를 치른 실패 유형(정책 중복 + 무동조 테스트)의 새로운 사례다. 두 사항 모두 차단급은 아니며 수정 비용도 낮다.
