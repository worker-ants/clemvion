# 유지보수성(Maintainability) Review

## 발견사항

- **[INFO]** 소스 텍스트를 정규식으로 파싱해 "호출이 실제로 있는지" 검증하는 테스트 패턴 — 동작 테스트가 아니라 텍스트 매칭 테스트라 포맷 변경에 취약
  - 위치: `codebase/backend/src/common/__test-utils__/workspace-id-fixtures.spec.ts:36-51` (`it('모듈이 로드 시점에 실제로 가드를 부른다 …')`), 특히 정규식 리터럴 `:47`
  - 상세: `readFileSync` 로 `workspace-id-fixtures.ts` 원본을 읽어 `/^[ \t]*assertAllUnique\s*\(\s*ALL_WS\s*\)\s*;/gm` 로 호출문을 찾는다. 목적(헬퍼 존재와 "실제 호출됨"을 구분)은 주석에서 명확히 근거를 대고 있고, 공백·개행에 관대하게 만들었다는 점도 인지하고 있다. 다만 호출부가 여러 줄로 개행되는 형태(`assertAllUnique(\n  ALL_WS,\n);`)로 리포맷되면 이 정규식은 매치하지 못해 **테스트가 깨진다** — 실패 자체는 fail-loud(조용한 통과가 아님)라 위험은 낮지만, 다음에 이 파일을 만지는 사람이 "왜 포맷 하나에 테스트가 깨지나"를 다시 추적해야 하는 비용이 있다.
  - 제안: 이미 주석으로 트레이드오프를 설명하고 있어 지금 형태로도 충분히 유지보수 가능하다. 다만 정규식을 조금 더 관대하게(`[\s\S]*?` 등으로 개행 허용) 만들거나, 최소한 정규식 옆에 "call-site 가 한 줄로 유지된다는 가정" 이라는 한 줄을 남겨두면 다음 사람이 원인을 더 빨리 찾을 수 있다.

- **[INFO]** 픽스처 파일명이 테스트 코드에 문자열 리터럴로 하드코딩됨
  - 위치: `codebase/backend/src/common/__test-utils__/workspace-id-fixtures.spec.ts:40-41` (`join(__dirname, 'workspace-id-fixtures.ts')`)
  - 상세: 대상 소스 파일이 리네임되면 `readFileSync` 가 `ENOENT` 로 즉시 실패하므로 은닉된 결함은 아니지만, spec 파일명과 대상 파일명이 문자열로만 연결돼 있어 IDE 리네임 리팩터링 시 자동으로 따라가지 않는다.
  - 제안: 현재 규모(파일 1개, 테스트 1케이스)에서는 문제 삼을 수준이 아니다. 참고용으로만 남긴다.

## 요약

이번 변경은 크게 두 갈래다. (1) `workspace-id-fixtures.ts` 에 `ALL_WS` 상수 배열과 `assertAllUnique` 로드 시점 유일성 가드를 추가하고, 그 가드 자체가 살아 있는지·비껴가지 않는지를 검증하는 신규 spec 파일을 붙였다. (2) `uuid.spec.ts` 와 `workspace-id-fixtures.ts` 에 중복돼 있던 nil-UUID 회귀 캐너리 관련 산문 설명을 `uuid.ts` 의 `isUuidShaped` docstring 한 곳(SoT)으로 모으고 나머지는 포인터로 축약했다. 두 변경 모두 이 저장소가 최근 반복해서 겪은 "같은 근거가 여러 파일에 복제돼 한쪽만 갱신되면 조용히 어긋난다" 는 결함 클래스를 정확히 겨냥해 줄였고(plan 문서에도 그 경위와 근거가 상세히 남아 있음), 신규 spec 은 "값이 우연히 유일해서 판정 로직이 뒤집혀도 무감지" · "하드코딩 목록 대조라 새 export 를 놓친다" · "Set 중복 제거로 유일성 위반 케이스가 스스로 지워진다" 는 세 가지 vacuous 함정을 각각 별도 테스트/주석으로 명시 방어하고 있어, 테스트 자체의 유지보수성도 높다. 네이밍(`ALL_WS`, `HEADER_WS`/`TOKEN_WS` 등)은 기존 컨벤션과 일관되고, 함수(`assertAllUnique`)는 단일 책임에 길이도 짧으며 중첩도 없다. 지적한 두 건은 모두 이미 주석으로 트레이드오프가 설명된 INFO 수준의 사소한 결합도 문제로, 전체적으로 이 PR 은 유지보수성을 개선하는 방향(중복 제거·SoT 통합·의도가 뚜렷한 방어적 테스트)이다.
