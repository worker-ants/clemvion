# 유지보수성(Maintainability) Review

## 발견사항

- **[WARNING]** `openStream` 의 반환값이 "성공적으로 열었다"와 "열 필요가 없어 그냥 통과시켰다"라는 서로 다른 의미를 같은 `true` 로 뭉갠다 — 같은 파일이 이미 한 번 고친 안티패턴의 재도입
  - 위치: `codebase/channel-web-chat/src/widget/use-widget.ts:367-393` (특히 `371 if (!client) return true;`, `373 if (streamRef.current !== null) return false;`, `390 return true;`)
  - 상세: `openStream` 은 이제 세 가지 서로 다른 상황에서 리턴한다 — (a) `client` 미확립: 아무것도 안 함, `true` (371) (b) 이미 다른 시도가 스트림을 소유: 아무것도 안 함, `false` (373) (c) 실제로 스트림을 염: `true` (390). (a)와 (c)는 동작이 전혀 다른데도 같은 `true` 로 합쳐진다. 이건 같은 파일의 `SeedOutcome` 타입 도입 배경(gate `78-83`)에서 이미 명문화한 바로 그 문제와 동형이다 — "boolean 이었을 때는 '정상 시드'와 'stale 폐기'가 같은 `false` 로 뭉개져 호출부가 구분할 수 없었다"(gate `81-82`)는 지적이 있어 `SeedOutcome`(gate `84-90`) 이라는 명명된 union 타입으로 승격시켰다. `openStream` 은 정확히 같은 클래스의 결정을 내리면서 그 교훈을 따르지 않고 다시 순수 `boolean` 을 택했다. 지금은 JSDoc(gate `344-366`)과 인라인 주석(gate `370`, `372`) 총 25줄 이상으로 의미를 상세히 방어 문서화해 두었고, plan 문서(§체크리스트)에 따르면 뮤테이션 테스트로 "client 없으면 true" 분기를 검증했다고 하므로 **현재는 안전**하다. 다만 함수 시그니처(`boolean`)만 보고 호출부를 작성하는 다음 사람은 `if (!openStream(...)) return;` 를 "열기 실패 시 중단"으로 오독하기 쉽고, 실제로 스트림이 열렸는지를 구분해야 하는 세 번째 요구(예: 텔레메트리, 테스트 단언)가 생기면 이 boolean 을 다시 쪼개야 한다 — 이 파일이 `SeedOutcome` 에서 이미 겪은 바로 그 리팩터가 반복될 자리다.
  - 제안: 문서화만으로 충분하다고 판단했다면 현행 유지도 가능하나, 만약 이 결정이 오래 유지될 것이라면 `SeedOutcome` 과 동일한 패턴으로 명명된 반환 타입(예: `"opened" | "no_client" | "already_owned"` 또는 최소한 `type StreamClaimResult = boolean` 에 의미를 붙인 타입 별칭)을 쓰는 편이 시그니처만으로 의도를 드러내고, 향후 세 번째 분기가 필요해질 때 컴파일러가 미처리 케이스를 잡아준다. 최소한 함수명을 `openStream` 대신 소유권 이전이 핵심임을 드러내는 이름(예: `claimStream`)으로 바꾸는 것도 고려할 만하다.

- **[INFO]** 동일한 설명이 JSDoc·인라인 주석·두 호출부 주석 네 곳에 걸쳐 거의 그대로 반복된다
  - 위치: `codebase/channel-web-chat/src/widget/use-widget.ts` — JSDoc `344-365`, 함수 내부 주석 `370`·`372`, 호출부 주석 `598-600`(`start()`), `946-949`(`applyConfig` 복원)
  - 상세: "게이트가 `openStream` 안으로 옮겨졌다", "이중 EventSource 를 막는다", "`01_44_21` 재현" 같은 동일 사실이 4곳에서 각자의 표현으로 반복 서술된다. 이 파일은 스스로 "JSDoc 인접성 취약성 — 선언 사이에 다른 코드가 끼면 주석이 유실되는 버그가 2회 재발했다"(plan 문서 §선행 판단, gate 미상이나 plan 파일 `46-48`행)는 교훈을 기록해 둔 바 있다. 설명이 네 곳에 흩어져 있으면, 훗날 의미가 바뀔 때 한 곳만 고치고 나머지가 stale 로 남을 위험이 구조적으로 존재한다(그 자체가 이 파일의 반복 결함 패턴과 같은 계열).
  - 제안: 지금 당장 리팩터할 정도는 아니지만, `openStream` JSDoc 을 단일 진실로 삼고 호출부 주석은 "자세한 설명은 `openStream` JSDoc 참조"로 축약하는 편이 drift 위험을 줄인다. (실제로 gate `598`·`946` 은 이미 이런 축약을 일부 시도했으나 — "겹친 두 seed 가...먼저 온 쪽만 소유한다" 등 — 여전히 핵심 서사를 재서술한다.)

- **[INFO]** `useWidget()` 자체의 함수 길이/응집도 문제는 이번 diff 로 해소되지 않으며 이미 별도 plan 에 정확히 추적되고 있음
  - 위치: `codebase/channel-web-chat/src/widget/use-widget.ts` 전체(`useWidget` 함수, gate `123-1024`)
  - 상세: 이번 변경은 함수 길이 자체를 늘리지 않고(중복 3줄 제거 + JSDoc 확장이 상쇄) 오히려 세 호출부의 손 복제 가드를 하나로 합쳐 **중복 코드를 줄이는 방향**이라 이 관점에서는 개선이다. `useWidget` 의 규모 문제는 `plan/in-progress/webchat-usewidget-extraction.md` 에 별도 항목(체크리스트 `52-55`행, "나머지 미착수")으로 이미 추적 중이므로 이번 리뷰에서 새로 지적할 필요는 없다.
  - 제안: 해당 plan 이 이미 커버하므로 별도 조치 불필요. 참고로만 남김.

## 요약

이번 변경은 `openStream` 진입부에서 소유권(스트림 게이트)을 재확인하도록 게이트를 함수 내부로 옮겨, 종전 `start()`·`applyConfig` 두 호출부가 각자 손으로 복제하던 `if (sessionEstablished()) return;` 3줄을 제거한 점에서 **중복 코드 축소·구조적 강제**라는 유지보수성 목표를 정확히 달성한다. 코드 자체의 중첩 깊이·순환 복잡도·네이밍 컨벤션은 이 파일의 기존 스타일과 일관되고 함수 길이도 과하지 않다. 다만 반환 타입을 `SeedOutcome` 같은 명명된 union 대신 순수 `boolean` 으로 택해 "성공적으로 열었다"와 "열 필요가 없어 통과시켰다"는 서로 다른 의미를 같은 `true` 값에 압축했는데, 이는 같은 파일이 이전에 동일한 문제로 `SeedOutcome` 타입을 도입했던 선례와 상충하는 결정이며, 현재는 방대한 JSDoc/인라인 주석과 뮤테이션 테스트로 안전을 담보하고 있지만 그 방대한 문서 자체가 네 곳에 분산 반복돼 있어 이 파일이 이미 겪은 "JSDoc 인접성/drift" 취약성 계열의 잠재 위험을 안고 있다. 둘 다 지금 당장 결함은 아니며, 향후 세 번째 분기 요구나 문서 갱신 누락 시 재발할 수 있는 종류의 리스크다.
