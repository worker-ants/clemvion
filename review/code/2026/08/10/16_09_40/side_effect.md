# 부작용(Side Effect) Review

## 발견사항

- **[CRITICAL]** `seedWaitingFromStatus` 의 401-refresh 성공 분기가 `sessionRef.current`/저장 세션을 새 토큰으로 갱신하지만, 호출부(`applyConfig`/`start`)는 **호출 이전에 캡처해 둔 로컬 변수**(`saved`/`session`, 즉 아직 401 을 유발한 옛 토큰)를 그대로 `openStream()` 에 넘긴다 — SSE 스트림이 **서버가 이미 거부한 옛 토큰**으로 재오픈된다.
  - 위치: `codebase/channel-web-chat/src/widget/use-widget.ts:499-521` (401 분기, 특히 510-512 의 `sessionRef.current = updated; saveSession(...)` 쓰기), 호출부 `codebase/channel-web-chat/src/widget/use-widget.ts:930-961`(`applyConfig` — `const saved = ...`(930) → `seedWaitingFromStatus(clientRef.current, saved)`(945) → `openStream(saved, "0")`(961)), `codebase/channel-web-chat/src/widget/use-widget.ts:587-611`(`start()` — `const session = persist(cfg, res)`(587) → `seedWaitingFromStatus(client, session)`(602) → `openStream(session, "0")`(611))
  - 상세: `client.openStream(endpoints, token, ...)` 은 `token` 인자를 그대로 `?token=` 쿼리로 써서 EventSource URL 을 만든다(`codebase/channel-web-chat/src/lib/eia-client.ts:121-133`). `applyConfig` 의 재로드 경로에서 `getStatus` 가 401 을 던진 건 곧 `saved.token` 이 서버에 의해 **이미 거부됐다**는 뜻인데, `seedWaitingFromStatus` 내부에서 refresh 가 성공해 `sessionRef.current` 는 새 토큰(`updated`)으로 바뀌어도, `applyConfig`/`start` 는 이 갱신을 알 방법이 없다 — `SeedOutcome` 이 `"ended"|"stale"|"continue"` 세 리터럴뿐이라 세션 교체 여부를 실어 나르지 않기 때문이다. 그 결과 `outcome === "continue"` 를 받은 호출부는 여전히 옛 `saved`/`session` 객체(옛 토큰 보유)로 `openStream(saved, "0")`/`openStream(session, "0")` 를 호출한다. 옛 토큰은 이미 서버가 401 로 거부한 값이므로 이 스트림 연결도 거의 확실히 다시 실패하며, 그 결과는 바로 이 PR 이 고치려던 증상("SSE 가 아무것도 안 줘 `streaming` 에 무기한 고착")을 §R4 낙관적 refresh 경로에서 **그대로 재현**한다. `worldGenRef` 기반 staleness 가드(`isStale(gen)`)는 "다른 시도가 세계를 교체했는가"만 보고 "같은 세션 안에서 토큰이 in-place 로 갱신됐는가"는 잡지 못하므로, 이 파일이 그동안 반복해서 잡아온 stale-세대 부류와는 **다른 축의 구멍**이다.
  - 근거(테스트 갭): 신규 테스트 `codebase/channel-web-chat/src/widget/use-widget-eager-start.test.ts` 의 `§R4: 재로드 getStatus 가 401 → 낙관적 refresh 1회 성공 시 복원(SSE 오픈)` (같은 파일 280번째 줄 부근 `it(...)`) 는 `getEs()).not.toBeNull()` 과 storage 내용만 단언하고, `ControllableEventSource` 스텁이 생성자 URL/토큰을 기록하지 않아 실제로 어떤 토큰으로 스트림이 열렸는지는 검증하지 못한다. 즉 이 버그는 신규 테스트로 걸러지지 않는다.
  - 제안: `seedWaitingFromStatus` 가 refresh 성공 시 갱신된 세션(`updated`)을 `SeedOutcome` 에 실어 반환하거나(예: `{ outcome: "continue"; session?: SessionRef }`), 호출부가 `openStream`/`scheduleRefresh` 직전에 `sessionRef.current` 를 다시 읽도록 고친다(`openStream(sessionRef.current ?? saved, "0")` 류). 아울러 EventSource 생성 시 넘어간 URL/토큰을 검증하는 테스트를 추가해 이 계열의 회귀를 잡을 것.

- **[WARNING]** `seedWaitingFromStatus` 의 401-refresh(opt-in `allowWhileStreaming`, 즉 `execution.replay_unavailable` 폴백 경로)와 `use-token-refresh` 의 주기 갱신 타이머가 **서로 모르는 채 동시에 `client.refreshToken()` 을 부를 수 있고**, 조율(mutex/in-flight 플래그) 이 없다.
  - 위치: `codebase/channel-web-chat/src/widget/use-widget.ts:499-521`(opportunistic refresh) 대 `codebase/channel-web-chat/src/widget/use-token-refresh.ts:79-102`(periodic refresh 콜백)
  - 상세: `execution.replay_unavailable` 은 **스트림이 이미 열린 뒤**(즉 `scheduleRefresh()` 가 이미 주기 타이머를 예약한 뒤)에만 `seedWaitingFromStatus(client, session, { allowWhileStreaming: true })` 를 fire-and-forget 으로 호출한다(`use-widget.ts:326-333`). 이 시점에 `getStatus` 가 401 을 반환하면 opportunistic refresh 가 트리거되는데, 마침 `use-token-refresh` 의 주기 타이머도 비슷한 창(만료 30분 전)에 발화할 수 있어 두 경로가 **동일 토큰으로 각각 독립적인 `refreshToken()` 요청**을 동시에 낼 수 있다. 두 쓰기 모두 `sessionRef.current`/`saveSession` 을 직접 갱신하므로 last-write-wins 로 끝나면 그나마 무해하지만, 백엔드가 refresh 토큰 1회성(rotation) 을 강제한다면 늦게 도착한 쪽은 실패한다. 두 실패 처리 정책이 비대칭이다: `use-token-refresh` 쪽은 실패 시 `console.warn` 만 하고 다음 재예약도 하지 않아(§설계상 "SSE 는 hard expiry 까지 유지") 상대적으로 안전하지만, `seedWaitingFromStatus` 쪽은 refresh 실패를 무조건 "재차 실패 → 복구 불가"로 해석해 `finalizeEnded("execution.token_revoked")` 를 호출한다(`use-widget.ts:516-520`) — **실제로는 건강한 세션인데 자신의 주기 갱신과 경합해서 진 것뿐**인 경우까지 종료로 오판할 수 있다. 이 파일의 다른 모든 staleness 가드는 "세계가 바뀌었는가"만 방어하고, "같은 세계 안에서 두 독립 refresh 트리거가 서로 부딪히는가"는 이번 401 분기가 새로 도입할 때까지 존재하지 않던 표면이다.
  - 제안: `seedWaitingFromStatus` 와 `use-token-refresh` 가 refresh 실행을 공유하는 단일 지점(예: `useTokenRefresh` 가 노출하는 `refreshNow()`/in-flight ref)을 쓰도록 통합하거나, 적어도 refresh 호출 전에 "이미 진행 중인 refresh 가 있으면 그 Promise 를 재사용"하는 가드를 추가할 것. 최소한 `seedWaitingFromStatus` 의 refresh 실패를 곧바로 `finalizeEnded` 로 보내기 전에 "직후 재조회(getStatus) 로 실제 종료 여부 재확인" 같은 완충을 고려.

- **[INFO]** `configRef.current` 부재 가드(`if (!cfg) return "stale";`)가 이 파일의 다른 동일 불변식 의존 지점(`teardownSession` 의 "**불변식 의존 주의**" 주석, `sessionEstablished` 의 동일 태그)과 달리 상호 참조 주석이 없다.
  - 위치: `codebase/channel-web-chat/src/widget/use-widget.ts:508-509`
  - 상세: 이 가드는 "`configRef.current` 는 확립 후 다시 null 이 되지 않는다"(같은 파일 `teardownSession` JSDoc, 250번째 줄 부근)는 불변식에 기대어 현재는 도달 불가능한 방어 코드다(`seedWaitingFromStatus` 는 언제나 `client`/`session` 이 존재하는 부팅-후 경로에서만 호출되고, 그 경로들은 이미 `configRef.current` 를 세팅한 뒤이기 때문). 문제라기보다, 이 파일은 같은 불변식이 깨질 경우("config 재설정" 류 기능이 `configRef.current = null` 을 도입) 를 이미 두 군데(`teardownSession`, `sessionEstablished`)에서 명시적으로 "같이 재검토할 것" 이라 태깅해 뒀는데, 이번에 새로 추가된 이 세 번째 의존 지점만 그 태그가 없다 — 향후 그 불변식이 재검토될 때 이 분기가 누락될 위험.
  - 제안: 다른 두 지점과 동일한 "불변식 의존 주의" 상호 참조 주석을 추가.

## 요약

이번 diff 는 `seedWaitingFromStatus` 에 §R4(401 재로드 낙관적 refresh)·§3.1-2(404 종료) 분기를 새로 얹으면서 `sessionRef.current`/저장 세션에 대한 새로운 쓰기 경로를 도입했다. 요청하신 세 축을 확인한 결과: (a) `worldGenRef` 세대 가드는 성공·실패 양쪽 서브패스 모두에서 쓰기 직전에 정확히 재검사되어 "다른 시도가 세계를 교체"하는 경합은 막는다. (b) 그러나 `use-token-refresh` 의 주기 갱신과는 조율 장치(mutex/in-flight 공유)가 전혀 없어, `execution.replay_unavailable` 경로를 통해 두 refresh 트리거가 동시에 발화하면 정상 세션이 `finalizeEnded("execution.token_revoked")` 로 오종료될 여지가 있다(WARNING). (c) `configRef` 부재 처리 자체는 안전하지만 이 파일의 기존 컨벤션(상호 참조 주석)이 누락됐다(INFO). 가장 심각한 것은 세 축 질문 바깥에서 발견한 CRITICAL 항목이다 — `seedWaitingFromStatus` 가 401→refresh 성공 시 `sessionRef.current`/storage 를 새 토큰으로 갱신해도 그 반환값(`SeedOutcome`)이 이를 실어 나르지 않아, 호출부(`applyConfig`/`start`)가 호출 이전에 캡처해 둔 **옛(이미 401 로 거부된) 토큰**으로 그대로 `openStream()` 을 호출한다. 이는 서버가 이미 거부를 확인한 토큰으로 스트림을 재오픈하는 것이라 사실상 실패가 예정되어 있고, 이 PR 이 고치려던 "SSE 무응답으로 `streaming` 고착" 증상을 §R4 성공 경로 자체에서 재현할 가능성이 높다. 신규 테스트는 EventSource 생성 시 넘어간 토큰/URL 을 검증하지 않아 이 회귀를 잡지 못한다.

## 위험도

CRITICAL
