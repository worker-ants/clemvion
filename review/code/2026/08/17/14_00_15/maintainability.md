# 유지보수성(Maintainability) 코드 리뷰

## 발견사항

- **[WARNING]** 새 주석 블록이 기존 JSDoc 블록과 스타일이 갈리고, "형제" 파일과도 문서화 패턴이 어긋난다
  - 위치: `codebase/backend/src/modules/websocket/websocket.service.ts:59-75` (특히 신규 추가된 67-73줄)
  - 상세: `CREDENTIAL_KEY_PATTERN` 선언 바로 위에 원래 `/** ... */`(JSDoc, `WARN #10` 설명) 블록이 있었는데, 이번 diff 가 그 **바로 아래에 별도의 `/* ... */`(plain block comment)** 를 추가했다(67-73줄). 같은 선언 하나를 설명하는 두 개의 인접한 주석 블록이 서로 다른 컨벤션(`/**` vs `/*`)을 쓰는 형태가 됐다. 반면 "의도된 미러"로 명시된 자매 상수 `sanitize-error-message.ts` 의 `CREDENTIAL_KEY_PATTERN` 에서는 같은 성격의 신규 설명을 **기존 JSDoc 블록 안에 문단으로 추가**해 하나의 블록으로 유지했다(`sanitize-error-message.ts:79-98`). 이 저장소는 이미 "미러 상수의 문서화가 어긋나면 다음 사람이 혼동한다"는 교훈을 코드 주석에 직접 남기고 있는데(바로 이 신규 주석 자체가 "함께 갱신한다"고 말함), 정작 그 갱신의 **형식**이 자매 파일과 갈렸다.
  - 제안: 새 `/* ... */` 블록을 기존 `/** ... */` JSDoc 블록에 병합해 `sanitize-error-message.ts` 와 동일한 "단일 도큐먼트 블록 + 문단 추가" 형태로 통일한다.

- **[INFO]** plan 문서의 "설계" 절이 제시한 정규식이 실제로 반영된 코드와 동치가 아니다 (문서-코드 drift)
  - 위치: `plan/in-progress/eia-secret-pattern-token-family.md:86` (`## 설계 — 접두 선택 형태` 블록의 `(?:[A-Za-z0-9]+[_-]?)?token`)
  - 상세: plan 이 "설계"로 제시한 형태는 `(?:[A-Za-z0-9]+[_-]?)?token` 인데, 실제로 세 소비처(`sanitize-error-message.ts:42,100`, `websocket.service.ts:75`)에 반영된 형태는 `[A-Za-z0-9_-]*token` / `[a-z0-9_-]*token` 이다. 두 형태는 동치가 아니다 — 예를 들어 `a_b_c_token`·`___token` 처럼 구분자가 연속·반복되는 키는 실제 코드 패턴에는 매칭되지만 plan 이 문서화한 설계 패턴에는 매칭되지 않는다(직접 실행 확인). plan 은 "왜 이 설계를 택했는가"의 근거 문서로 남는데, 그 문서에 적힌 정규식과 실제 shipped 코드가 문자 그대로 다르면 다음에 이 plan 을 근거로 정규식을 이해하려는 사람이 실제 매칭 범위를 오판할 수 있다.
  - 제안: plan 의 코드 블록을 실제 반영된 `[A-Za-z0-9_-]*token`(값 패턴)/`[a-z0-9_-]*token`(키 패턴)으로 정정하거나, "설계 초안이었고 구현 시 더 단순한 형태로 넓혔다"는 한 줄을 덧붙인다.

- **[INFO]** 이제 영구히 비게 된 배열을 순회하는 루프가 매 호출마다 no-op 으로 실행된다 (의도된 확장 지점이지만 정적 분석·차후 정리 시 혼동 소지)
  - 위치: `codebase/backend/src/modules/mcp/mcp-error-codes.ts:54`(`MCP_EXTRA_SECRET_PATTERNS` 빈 배열) 및 `redactMcpSecrets` 함수 내 `for (const [pattern, replacement] of MCP_EXTRA_SECRET_PATTERNS) { ... }` 루프
  - 상세: 배열 선언부 JSDoc(39-53줄)이 "훅을 남겨 두는 이유"를 상세히 설명하고 있어 **선언 지점에서는** 의도가 명확하다. 다만 실제로 매 호출마다 도는 소비 지점(`redactMcpSecrets` 함수 본문의 for 루프)에는 그 설명이 없어, 배열 선언부를 보지 않고 함수 구현만 보는 사람(혹은 "unreachable/dead code" 류 정적 분석 도구)에게는 이 루프가 죽은 코드로 보일 수 있다. 이미 이 저장소가 2026-07-10 에 같은 패턴(공용 흡수 후 MCP 전용 배열 비우기)을 한 번 겪었고 다음에 또 흡수·재확장이 반복될 가능성이 코드 자체가 명시한 시나리오이므로, 사소하지만 반복될 여지가 있다.
  - 제안: (선택) 함수 본문의 루프 옆에 "위 JSDoc 참조 — 현재는 no-op, 훅 유지" 한 줄만 추가해도 선언부까지 스크롤하지 않고 이해할 수 있다. 필수 아님.

## 확인했으나 문제 없다고 판단한 것

- `SECRET_LEAK_PATTERNS`(값-패턴, mcp/websocket 자매 3곳)의 `token` 계열 통합은 기존 3개 명시적 대안(`access[_-]token|refresh[_-]token|id[_-]token`)을 하나의 패턴으로 흡수하며, 코드 주석이 "중복 대안을 남기면 다음 사람이 어느 쪽을 고쳐야 할지 갈린다"는 근거를 명시해 통합 결정을 정당화한다 — 가독성·중복 제거 관점에서 개선.
- 새 테스트(`sanitize-error-message.spec.ts` `FAMILY` + `it.each`)는 값 축·키 축을 같은 표(`FAMILY` 배열)로 고정해 매직 리터럴 반복 없이 8+8건을 커버한다 — 좋은 패턴, 두 축이 갈리는 실수(자매 중 하나만 고치는 이 저장소의 반복 결함 클래스)를 구조적으로 방지.
- `mcp-error-codes.spec.ts` 의 테스트 이름 변경 + 그 이유를 설명하는 JSDoc 스타일 블록 주석은 "왜 오래된 이름이 거짓이 됐는지"를 명확히 남겨, 테스트만 보는 사람이 "MCP 전용"이라는 옛 이름과 지금 실제로 공용 패턴이 잡는다는 사실 사이의 괴리로 헷갈리지 않게 방지한다.
- 함수 길이·중첩 깊이·순환 복잡도는 이번 diff 로 늘어난 곳이 없다(모두 상수 값 확장 + JSDoc 갱신 + 배열 비우기 수준). 신규 매직 넘버 없음.
- 정규식 문자 클래스가 파일마다 `[A-Za-z0-9_-]*`(sanitize-error-message.ts 값-패턴) vs `[a-z0-9_-]*`(같은 파일의 키-패턴, websocket.service.ts 키-패턴) 로 갈리는 점을 확인했으나, 두 곳 모두 `/i` 플래그가 이미 있어 기능적으로 동일하고 각 파일 내 기존 로컬 컨벤션(값-패턴군은 대소문자 명시, 키-패턴군은 소문자만)을 그대로 따른 것이라 새로 도입된 비일관성은 아니다 — 등급 부여 보류.

## 요약

이번 변경은 세 곳의 자격증명 정규식 SoT(값-패턴 1곳 + 그 미러인 키-패턴 2곳)를 `token` 계열 단일 대안으로 통합하고, MCP 전용 보충 패턴을 공용으로 흡수해 비우는 저위험 확장이다. 회귀 테스트가 값 축/키 축을 동일 표로 고정하고 뮤테이션으로 두 축의 독립 관측을 확인했다는 점, 그리고 JSDoc·plan 문서 곳곳에 "왜 이 형태인가·왜 지금 비웠는가"를 상세히 남긴 점은 이 저장소가 반복 지적해 온 "자매 중 하나만 고쳐 SoT 가 갈리는" 결함 클래스를 구조적으로 예방하려는 시도로 보인다. 다만 그 설명 자체의 **형식**이 완전히 통일되지는 않았다 — `websocket.service.ts` 의 신규 주석이 기존 JSDoc 블록과 분리된 별도 스타일(`/*` vs `/**`)로 들어갔고, plan 문서의 "설계" 절 정규식이 실제 shipped 정규식과 문자 그대로 다르다. 둘 다 기능적 결함은 아니며 다음 사람이 문서만 보고 오판할 가능성을 낮추는 수준의 정리 여지다.
