# 보안(Security) Review

## 리뷰 대상

- `.claude/skills/consistency-checker/scripts/consistency_orchestrator.py` — `_named_in` 에 경계-고정 정규식(`_NAME_START`/`_NAME_END`) 도입
- `.claude/tests/test_consistency_bundle_priority.py` — 해당 변경의 양방향 뮤테이션 테스트
- `plan/complete/consistency-named-in-substring-match.md` — 결함 기록·근거 문서

## 점검 결과

### 1. ReDoS 가능성 — 직접 실측

패턴 구조:

```python
_NAME_START = r"(?<![A-Za-z0-9_.\-])"   # 고정폭(1글자) 부정 lookbehind
_NAME_END   = r"(?![A-Za-z0-9_\-])"     # 고정폭(1글자) 부정 lookahead
re.search(_NAME_START + re.escape(needle) + _NAME_END, plan_text)
```

`re.escape(needle)` 는 정량자(`*`,`+`,`{}`) 가 전혀 없는 **순수 리터럴 문자열**이고, 양쪽 경계는 모두
**고정폭 1글자** lookaround 다. 중첩 정량자·가변폭 lookaround 가 전혀 없으므로 이론적으로 파국적
backtracking(ReDoS) 이 발생할 수 있는 구조 자체가 아니다. 저장소 이력상 "정적 판단이 실측에 반증된
사례"(MULTILINE+`\s` 이차 성장)가 있으므로 이론에 기대지 않고 직접 4가지 입력 형태로 재측정했다(Python 3.11.9):

| 케이스 | 설명 | 배율(2배 입력당) |
| --- | --- | --- |
| A | 평범한 산문 텍스트, needle 부재(전체 스캔 최악 경로) | ~1.9–2.0x |
| B | needle basename 의 **near-miss 반복**(`storstorstorstore.md` 류) | ~1.8–1.9x |
| C | lookbehind 경계 후보가 매 위치에 있는 `"aaaa..."` 반복 | ~1.93–2.0x (128,000자까지) |
| D | needle 자체가 정규식 메타문자 다수 포함(`(`,`)`,`[`,`]`,`^`,`$`,`|`,`\`,`{`,`}` 등) | ~1.99–2.02x (197,632자까지) |
| E | 실제 규모 근사: needle 600개(파일 300 × 2 형태) × plan_text 104,000자 | 21.2ms (전체) |

모든 케이스에서 입력을 2배로 늘릴 때 소요 시간이 일관되게 **~2.0배**로 증가했다 — 이는 O(n) 선형 스케일링의
정의 그대로다. 저자가 보지 않았을 만한 입력 형태(정규식 메타문자 밀집 needle, lookbehind 경계 후보가 매
글자마다 있는 반복 문자열, near-miss 접두사 반복)까지 포함해 재현했고 전부 선형으로 확인했다.
`re.escape` 로 만들어진 순수 리터럴 + 고정폭 lookaround 조합은 CPython `sre` 가 리터럴 고속 스캔 경로를
탈 수 있는 형태라 이 결과는 이론과도 일치한다. **ReDoS 위험 없음.**

### 2. `re.escape(needle)` 의 메타문자 커버리지

`needle` 은 `rel`(저장소 상대경로) 또는 `os.path.basename(rel)` 이며, 둘 다 `collect_markdown_files` 가
실제 파일시스템에서 나열한 `.md` 파일 경로에서 파생된다(임의 외부 입력이 아니라 diskfs 상의 실재 경로).
Python 3.7+ 의 `re.escape` 는 영숫자·`_` 를 제외한 모든 문자를 이스케이프하도록 완전성이 보장된다. 직접
`.^$*+?{}[]\|()/-~`!@#%&_=:;'"<>,` 및 공백을 포함한 파일명으로 왕복 검증했고, 모든 문자에서
"의도한 리터럴만 매치, 다른 문자열은 매치하지 않음" 이 성립함을 확인했다. 경로에 정규식 메타문자가
들어가도(예: `weird(name).md`, `a+b.md`) 안전하게 리터럴로 처리되며 인젝션·오매치 경로가 없다.

### 3. 경계 도입으로 인한 과소-매치(정당한 언급 누락) 가능성

- 테스트(`test_mention_forms_that_must_still_count`)가 frontmatter·마크다운 링크·백틱 basename·문장 끝
  bare 4가지 형태를 각각 `subTest` 로 개별 단언하고, 양방향 뮤테이션(경계 제거 → 2건 RED, 과잉 조임 →
  4건 RED)으로 "덜 잡음"과 "더 잡음" 양쪽을 모두 검증한다 — 이 저장소가 이전에 반복해서 겪은 "한 방향만
  걸어 반대 방향 회귀를 놓치는" 패턴을 피한 설계다.
- 다만 `_NAME_END`(`[A-Za-z0-9_\-]` 부정 lookahead)가 트레일링 문자를 배제하는 범위상, `store.md_backup`
  이나 `store.md-variant` 처럼 확장자 뒤에 `_`/`-` 로 바로 이어지는 복합 토큰 형태는 (구 버전 `in` 방식이면
  매치했을) 새로 놓치게 된다. 이 저장소의 실제 plan/spec 산문에서 파일명 뒤에 `_`/`-` 가 공백 없이
  직접 붙는 표기 관례는 관측되지 않았고(마크다운 앵커 슬러그는 `.`을 `-`로 치환해 별도 토큰이 되므로
  해당 없음), Rationale 에서도 이 트레이드오프를 명시(`v2.store.md` 오매치 차단이 목적)하고 있어
  실질적인 회귀 가능성은 낮다.
- 문서화된 기존 한계(수정 전부터 존재, 이번 diff 로 새로 생긴 것은 아님): `rel` 전체경로 매칭은 `/` 가
  경계 문자 집합에 포함되지 않아 여전히 "suffix-vulnerable" 하다 — `rel="a/store.md"` 인 파일은
  `plan_text` 에 `"b/a/store.md"` 처럼 더 긴 경로가 등장해도 `/` 앞에서 lookbehind 가 통과해 오매치될
  수 있다. 코드 주석과 plan 문서(§원인·§Rationale) 모두 이를 인지하고 "드문 형태" 로 명시적으로 남겨둔
  기존 한계이며, 이번 PR 의 회귀가 아니라 `basename` 오매치(이번에 고친 실제 사고 원인)보다 발생 빈도가
  낮다고 판단해 의도적으로 범위 밖에 둔 것으로 보인다.

### 4. `plan_text` 크기의 메모리·시간 상한

`collect_context` 의 `_rank_plan_text = "\n".join(read_text_file(p) for p in _rank_plan_files)`
(`consistency_orchestrator.py:528`) 는 `plan/in-progress/` 의 전체 `.md` 파일을 상한 없이 통째로
연결한다. `_named_in` 의 정규식 자체는 (1번에서 확인했듯) 선형이므로 시간 측면에서는 문제가 되지
않지만, 이 문자열 자체에 명시적 크기 캡이 없는 것은 사실이다. 다만:
- 이는 이번 diff 로 새로 생긴 것이 아니라 기존 `collect_context` 설계이고, `_named_in` 경계 수정과는
  독립적인 차원의 이슈다.
- `plan_text` 는 저장소에 커밋(또는 워크트리에 존재)된 신뢰 문서이며 외부/네트워크 공격자가 임의로
  주입할 수 있는 입력이 아니다 — 이 스크립트는 harness 내부 CLI 로, 공격 표면이 "저장소 관리 권한을
  가진 사람이 매우 큰 plan 파일을 커밋한다" 정도로 제한된다.
- 실측(Case E, §1)으로도 파일 수백 개 × needle 수백 개 × 10만자 규모에서 21ms 수준이라, 저장소 규모가
  현재의 몇 배로 자라도 실질적 DoS 로 이어지긴 어렵다.
- 굳이 방어적으로 개선한다면 `_rank_plan_text` 조립 시 총 길이에 상한(예: 수 MB)을 두고 초과분을 잘라
  랭킹 신호로만 쓰는 정도가 안전선이지만, 현재 신뢰 경계상 필수는 아니다.

## 그 외 OWASP Top 10 관점

- 인젝션(SQL/XSS/커맨드/경로 탐색): 해당 diff 는 파일시스템에서 나열한 경로 문자열을 `re.escape` 로
  안전하게 리터럴화해 정규식에 삽입할 뿐, 셸 실행·SQL·HTML 렌더링 경로가 없다. 커맨드 인젝션 벡터 없음.
- 하드코딩된 시크릿: 없음.
- 인증/인가: 해당 없음(로컬 harness 스크립트, 인증 경계 밖).
- 암호화: 해당 없음.
- 에러 처리: `read_text_file` 의 예외는 `debug_log` 로만 기록되고 내용은 빈 문자열로 폴백 — 민감정보
  노출 없음.
- 의존성: 표준 라이브러리(`re`, `os`)만 사용, 신규 의존성 없음.

## 요약

`_named_in` 에 도입된 경계 고정 정규식은 순수 리터럴 + 고정폭 lookaround 조합으로, 4가지 서로 다른
적대적 입력 형태(근접 실패 반복·경계-후보 반복 문자·메타문자 밀집 needle·실사용 규모 근사)에 대해 실측
배율이 일관되게 ~2.0x(선형)임을 직접 확인했으며 ReDoS 위험은 없다. `re.escape` 는 경로에 포함될 수 있는
모든 정규식 메타문자를 완전히 리터럴화하므로 오매치·인젝션 경로가 없다. 경계 도입으로 인한 정당한 언급의
과소-매치 가능성은 존재하나(`.md_`/`.md-` 복합 토큰 형태, 그리고 사전부터 존재하던 `rel` suffix 취약성)
테스트 스위트가 양방향 뮤테이션으로 두 방향 회귀를 모두 감시하고 있고 실제 문서 관례상 영향은 제한적이다.
`plan_text` 조립에 명시적 크기 상한이 없는 점은 사실이나 입력이 저장소 신뢰 문서에 한정되고 실측상
성능 영향도 미미해 DoS 로 이어지기 어렵다. 전반적으로 이 변경은 기존 취약점(부분 문자열 오매치로 인한
번들 오염)을 보안·정합성 양쪽에서 건전하게 좁힌 수정이며, 새로 도입된 보안 취약점은 발견되지 않았다.
