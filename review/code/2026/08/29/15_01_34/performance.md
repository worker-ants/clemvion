# 성능(Performance) Review

## 발견사항

- **[INFO]** `MaskedDoc.srcLineOf` 배열이 항상 `index + 1` 과 같아 실질 정보량 없이 O(줄 수) 메모리를 낭비한다.
  - 위치: `codebase/frontend/src/lib/docs/__tests__/spec-links.ts` — `MaskedDoc` 인터페이스의 `srcLineOf` 필드(게이트 138), `buildMaskedDoc()` 안의 `srcLineOf.push(i + 1)`(게이트 159), `lineForOffset()` 의 `return doc.srcLineOf[lo]`(게이트 180).
  - 상세: `buildMaskedDoc` 의 for-loop 는 `lines` 의 모든 인덱스 `i` 에 대해 예외 없이 `masked.push(...)` 와 `srcLineOf.push(i + 1)` 를 한 쌍으로 실행한다(펜스 여부·인라인 코드 여부와 무관하게 매 반복 정확히 1개씩 push). 줄을 건너뛰거나 합치는 분기가 없으므로 `srcLineOf[k] === k + 1` 이 항상 성립한다 — 즉 이 배열은 인덱스에서 계산 가능한 값을 그대로 복제해 저장할 뿐이다. `lineForOffset` 이 이진 탐색으로 찾아낸 인덱스 `lo` 에 대해 `doc.srcLineOf[lo]` 대신 `lo + 1` 을 반환해도 결과는 동일하다. 스캔 대상 파일이 사전 필터(`cannotContainLink`)를 통과한 나머지(실측 11.9%)에 한해서만 만들어지는 배열이라 절대적 영향은 작지만, "값이 인덱스와 항상 같은 병렬 배열을 통째로 보유"하는 것은 목적 없는 할당이며, 파일이 커질수록(줄 수에 비례) 그대로 커진다.
  - 제안: `MaskedDoc` 에서 `srcLineOf` 필드를 제거하고 `lineForOffset` 이 이진 탐색 결과 인덱스에 `+ 1` 만 하도록 바꾼다. 배열 하나(`O(L)` 정수)와 그 채움 루프를 통째로 없앨 수 있다. (만약 향후 펜스/여러 원본 줄을 하나의 마스킹 줄로 합치는 변경이 생긴다면 그때 다시 명시적 지도가 필요해지므로, 그 시점에 되살리면 된다.)

- **[INFO]** (검증 결과 문제 없음) 파일당 O(줄 수) 배열/문자열 할당 증가는 허용 가능한 트레이드오프다.
  - 위치: `extractLinks()`(게이트 183~203) 및 `buildMaskedDoc()`(게이트 148~169).
  - 상세: 종전 구현은 줄마다 즉시 `LINK_RE.exec(noCode)` 를 돌려 별도 버퍼가 없었다. 새 구현은 사전 필터를 통과한 파일에 한해 `masked`·`srcLineOf`·`startOf` 세 배열과 `body = masked.join("\n")` 재조립 문자열을 추가로 만들어, 처리 구간의 피크 메모리가 대략 파일 크기의 2~3배로 늘어난다. 다만 (1) 스캔 대상(`spec/**.md`, 거버넌스 문서, 살아있는 plan, 코드 소스)이 통상 수 KB~수백 KB 수준이고, (2) `cannotContainLink` 사전 필터가 대상 파일의 88%를 걸러낸 뒤에만 이 경로를 타며, (3) 이 스캔은 사용자 요청 경로가 아니라 test/build 시점에 1회 실행되는 정적 가드라 지연시간에 영향이 없다. 실측(주석 기재): 전수 스캔 114ms → 56ms(사전 필터 도입 시점 실측이며, 이번 멀티라인 수정으로 그 필터가 무효화되지 않음을 별도로 확인·주석화했다). 별도 조치 불요.
  - 제안: 없음. 다만 향후 이 가드의 스캔 범위가 훨씬 큰 생성 파일(API 카탈로그 등)까지 넓어지면 `masked`/`body` 이중 보유를 재검토할 것 (현재는 `inGeneratedCatalog()` 로 이미 제외돼 해당 없음).

- **[INFO]** 매치 위치 → 원본 줄 번호 역산에 이진 탐색 도입 — 적절한 복잡도 개선.
  - 위치: `lineForOffset()`(게이트 172~181).
  - 상세: 정렬된 `startOf` 배열에서 "마지막으로 `startOf[mid] <= offset` 인 인덱스"를 찾는 upper-bound 이진 탐색을 정확히 구현했다(`(lo + hi + 1) >> 1` 편향으로 무한루프 없이 수렴). 매치당 O(log L)(L = 파일의 줄 수)로, 선형 탐색이었다면 매치가 많은 파일에서 O(M·L) 로 나빠졌을 지점을 O(M·log L) 로 눌러 놓았다.
  - 제안: 없음.

- **[INFO]** `regex.exec` 호출이 파일당 1회(전체 매칭)로 줄어 오히려 개선.
  - 위치: `extractLinks()`(게이트 192~201).
  - 상세: 종전에는 매치 가능한 줄마다 `LINK_RE.lastIndex = 0` 리셋 후 `exec` 루프를 새로 돌렸다(줄 수만큼 정규식 setup 비용 반복). 새 구현은 마스킹된 전문에 대해 단 한 번 `lastIndex = 0` 후 전역 매칭을 수행한다. 멀티라인 링크를 잡기 위한 정확성 수정의 부수 효과로 정규식 호출 오버헤드도 줄었다. 회귀 아님.
  - 제안: 없음.

- **[INFO]** 신규 `LINK_RE` (`[^\]]*` / `[^)\n]+`) 는 중첩 정량자가 없어 이차 백트래킹(ReDoS류 성능 저하) 위험이 없다.
  - 위치: `LINK_RE` 정의(게이트 82).
  - 상세: 목적지 그룹이 `[^)]+` → `[^)\n]+` 로 좁혀졌을 뿐 두 그룹 모두 "단일 부정 문자클래스 + 고정 리터럴" 형태라 파일 크기에 선형으로 스캔된다.
  - 제안: 없음.

- **[INFO]** `plan/in-progress/harness-review-gate-followups.md` 변경분과 `review/code/2026/08/29/14_36_39/*`(RESOLUTION.md·SUMMARY.md·`_retry_state.json`·각 reviewer `.md`·`meta.json`) 는 서술/기록용 문서·JSON 산출물이며, 런타임에 실행되는 알고리즘이 아니다. 성능 관점에서 검토할 코드가 없다(문서 갱신·이전 리뷰 세션 아카이빙).
  - 위치: 해당 파일 전체.
  - 제안: 없음.

## 요약

이번 diff 의 핵심(`extractLinks()` 를 "줄 단위 매칭"에서 "마스킹된 전문 단일 매칭 + 이진 탐색 역산"으로 교체)은 멀티라인 마크다운 링크 사각지대를 닫는 정확성 수정이며, 성능 관점에서는 중립~소폭 개선이다. 이 폴더가 과거 반복해 데었던 "성능 최적화가 가드를 조용히 멈추게 하는" 방향의 회귀는 없다 — 핵심 사전 필터(`cannotContainLink`)가 그대로 보존되고 멀티라인 케이스에서도 유효함이 주석·근거로 명시돼 있다. 파일당 부가 배열(`masked`/`srcLineOf`/`startOf`)과 재조립 문자열(`body`) 할당으로 피크 메모리가 늘지만, 스캔 대상 파일 크기와 사전 필터 통과율(11.9%)을 고려하면 무시할 수준이고, `regex.exec` 호출 횟수 감소·이진 탐색을 통한 매치→줄 역산은 오히려 개선이다. 유일한 신규 지적은 `srcLineOf` 배열이 인덱스와 항상 동일한 값만 담아 실질적으로 불필요한 할당이라는 점인데, 이는 코드 정리 수준의 사소한 사항이며 알고리즘 복잡도나 지연시간에는 영향이 없다. 이 스캔 자체가 test/build 시점의 정적 가드이지 요청 경로가 아니므로, N+1 호출·블로킹 I/O 병목·캐시 무효화·부적절한 자료구조 등 다른 관점에서도 CRITICAL/WARNING 급 결함은 발견되지 않았다. 문서/JSON 산출물(plan, review 세션 파일)은 알고리즘을 포함하지 않아 검토 대상 외다.
