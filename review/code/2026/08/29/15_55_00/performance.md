## 발견사항

- **[INFO]** 파일당 마스킹 버퍼(`body`/`masked`/`srcLineOf`/`startOf`) 추가 할당 — 허용 가능한 트레이드오프
  - 위치: `codebase/frontend/src/lib/docs/__tests__/spec-links.ts:125`–`154` (`buildMaskedDoc`)
  - 상세: 종전 구현(`text.split(/\r?\n/)` 뒤 줄마다 `LINK_RE.exec`)은 원문 외 별도 버퍼가
    거의 없었다. 새 구현은 원문(`text`) · 줄 배열(`lines`) · 마스킹 배열(`masked`) ·
    두 개의 병렬 인덱스 배열(`srcLineOf`, `startOf`) · 재조립 문자열(`doc.body`,
    `:154` `masked.join("\n")`)을 동시에 메모리에 올린다. `extractLinks`(`:204`)가 이를
    호출하는 지점(`:211`)은 `cannotContainLink` 사전 필터(`:103`, `:209`)를 통과한 파일만
    타므로, 실측된 통과율(주석에 명시된 11.9%, codebase 소스 기준)을 고려하면 실질 영향은
    작다. 개별 파일 크기도 이 가드가 스캔하는 대상(`spec/**.md`, 거버넌스 문서, plan,
    `.ts`/`.tsx` 소스)이 통상 수 KB~수백 KB 수준이라 O(파일 크기)의 2~4배 피크 메모리는
    무시할 수준이다.
  - 제안: 조치 불요. 이 가드가 훨씬 큰 생성 파일(예: API 카탈로그)까지 스캔 범위에
    들어가는 방향으로 확장될 경우에만 재검토 대상 — 현재는 `inGeneratedCatalog`
    (`:246` 부근)로 그런 파일을 이미 배제하고 있어 해당 없음.

- **[INFO]** `lineForOffset` 의 이진 탐색은 정확하지만, 호출 패턴상 상각 O(1) 전진 포인터로 대체 가능
  - 위치: `codebase/frontend/src/lib/docs/__tests__/spec-links.ts:157`–`166`
    (`function lineForOffset`), 호출부 `:213`–`220` (`extractLinks` 의 `while` 루프)
  - 상세: `LINK_RE.exec(doc.body)`(`:215`)는 `g` 플래그 정규식이므로 매 호출마다 이전보다
    큰 `m.index`를 순차적으로 반환한다. 즉 매치를 순회하는 동안 `doc.startOf`에 대한
    탐색 위치는 단조 증가한다 — `lo` 포인터 하나를 유지하며 앞으로만 전진시켜도 매치
    전체를 상각 O(M)(M=매치 수)으로 처리할 수 있는데, 현재는 매치마다 독립적으로
    O(log L)(L=파일의 줄 수) 이진 탐색을 처음부터 다시 수행한다(`:157`–`166`). 다만 이
    함수가 처리하는 L·M 은 파일 하나의 줄 수·링크 수 규모(수십~수백)로 매우 작고, 이
    가드는 CI/테스트 시점에만 도는 개발 도구이지 요청 경로의 hot path 가 아니다. 실질
    성능 영향은 측정 불가 수준으로 작다 — 앞선 두 라운드의 maintainability 리뷰
    (`review/code/2026/08/29/15_01_34/maintainability.md`, `15_30_59/maintainability.md`)가
    같은 지점을 "성능 문제라기보다 더 단순하게 쓸 수 있었다" 수준으로 이미 트리아지했고,
    이 판단에 동의한다.
  - 제안: 조치 불요. `lineForOffset`이 호출 순서에 의존하지 않는 독립 유틸로 남아 있는
    편이(임의 오프셋 질의에도 안전) 현재 규모에서는 견고성 이점이 크다. 이 가드가
    대용량 파일(수만 줄)을 스캔하는 방향으로 스코프가 넓어지면 그때 전진 포인터로
    바꾸는 것을 고려.

- **[INFO]** `regex.exec` 호출 패턴이 "파일당 1회 전체 매칭"으로 줄어 오히려 개선
  - 위치: `codebase/frontend/src/lib/docs/__tests__/spec-links.ts:213`–`220`
  - 상세: 종전에는 매치 불가능하지 않은 줄마다 `LINK_RE.lastIndex = 0` 리셋 후 `exec` 루프를
    새로 돌렸다(줄 수만큼 정규식 엔진 setup 비용 반복). 새 구현은 마스킹된 전문에 대해
    단 한 번(`:212`) 리셋 후 전역 매칭을 수행한다. 멀티라인 링크를 잡기 위한 정확성
    수정이면서 동시에 호출 오버헤드를 줄이는 부수 효과가 있다 — 회귀 아님, 개선 사항.
  - 제안: 조치 불요.

- **[INFO]** 정규식 `[^\]]*` / `[^)\n]+` 는 중첩 정량자가 없어 이차 백트래킹(ReDoS) 위험 없음
  - 위치: `codebase/frontend/src/lib/docs/__tests__/spec-links.ts:82` (`LINK_RE` 정의)
  - 상세: 목적지 부분이 `[^)]+`에서 `[^)\n]+`로 좁아졌을 뿐 두 그룹 모두 단일 부정

  - 제안: 조치 불요.

## 요약

이번 diff 의 핵심은 `extractLinks()` 를 "줄 단위 매칭"에서 "마스킹된 전문 단일 매칭 + 이진
탐색 역산"으로 바꿔 멀티라인 마크다운 링크 사각지대를 닫는 정확성 수정이며, 세 라운드에
걸친 review-fix 반복(빈 줄/문단 경계 마스킹 추가, 펜스 분기 병합, 함수 분리, plan 문서
동기화 등) 동안에도 알고리즘의 점근 복잡도나 I/O 패턴은 바뀌지 않았다. 성능 관점에서는
중립~소폭 개선이다: 핵심 성능 가드(`cannotContainLink` 사전 필터)는 그대로 보존됐고 새
구현에서도 유효함이 주석·근거로 명시돼 있으며, `regex.exec` 호출 횟수는 줄당 반복에서
파일당 1회로 줄었다. 파일당 부가 배열(`masked`/`srcLineOf`/`startOf`)과 재조립 문자열
(`body`) 할당이 늘었지만 사전 필터 통과율(11.9%)과 대상 파일 크기를 고려하면 무시할
수준이다. `lineForOffset`의 매치당 이진 탐색은 호출 패턴(단조 증가 오프셋)을 고려하면
상각 O(1) 전진 포인터로 대체 가능한 자리이지만, 이 가드가 처리하는 규모(파일당 수십~수백
줄·링크)와 호출 빈도(CI/테스트 시점 devtool, hot path 아님)에서는 측정 가능한 영향이
없다 — 앞선 두 라운드가 같은 결론에 도달했고 동의한다. N+1 호출, 블로킹 I/O 병목, 캐시
무효화 문제, 부적절한 자료구조 사용 등 다른 관점에서 CRITICAL/WARNING 급 결함은 발견되지
않았다.
