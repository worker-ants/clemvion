## 발견사항

- **[WARNING]** "코드펜스를 사이에 둔 `[` 와 `](` 는 링크가 아니다" 테스트가 **펜스 마스킹을
  실제로 격리해서 검증하지 못한다** — 같은 입력에 섞여 있는 **빈 줄 마스킹**이 이미 링크를
  차단하므로, 펜스 마스킹 로직을 통째로 제거해도 이 테스트는 계속 GREEN 이다.
  - 위치: `codebase/frontend/src/lib/docs/__tests__/spec-links.test.ts:374` (`it("코드펜스를
    사이에 둔 ...")`, 바디는 `:376`). 원인이 되는 프로덕션 로직은
    `codebase/frontend/src/lib/docs/__tests__/spec-links.ts:139-142` (`buildMaskedDoc` 의
    `isFenceBoundary || inFence || isBlank ? "]" : ...` 3항 마스킹 병합).
  - 상세: 테스트 바디는 `"# T\n\n[열린 텍스트\n\n\`\`\`\ncode\n\`\`\`\n\n](./a.md)\n"` 다.
    줄로 쪼개면 3번째 줄(`[열린 텍스트`)과 5번째 줄(펜스 시작) 사이에 **빈 줄(4번째 줄)이
    끼어 있다.** `buildMaskedDoc` 는 펜스 줄과 빈 줄을 **똑같이** `"]"` 로 마스킹하므로,
    4번째 줄의 빈 줄 마스킹만으로 이미 `[` 텍스트가 조기 종료되어 `](` 로 이어지지 못한다 —
    5~7번째 줄의 펜스가 마스킹되든 안 되든 결과는 바뀌지 않는다.
    저장소 밖 scratch 에서 `buildMaskedDoc`/`lineForOffset`/`LINK_RE` 로직을 그대로 복제해
    직접 확인했다(저장소 파일은 건드리지 않음, `git status --short` 로 clean 확인):
    - 이 테스트의 바디를 그대로 두고 **펜스 마스킹 조건만 제거**(빈 줄 마스킹은 유지)한
      뮤턴트를 돌리면 → 결과가 여전히 `[]` (**GREEN 유지 — 관측 실패**).
    - 반면 빈 줄을 없애 펜스에 바로 붙인 격리된 입력(`"# T\n[열린 텍스트\n\`\`\`\ncode\n\`\`\`\n](./a.md)\n"`)으로
      같은 뮤턴트를 돌리면 → `[{"line":2,"target":"./a.md"}]` (**RED — 이번엔 관측됨**).
    즉 "펜스가 있어서 링크가 아니다" 라고 이름 붙인 테스트가 실제로는 "빈 줄이 있어서
    링크가 아니다" 를 재확인하고 있을 뿐이다. `buildMaskedDoc` JSDoc(`:117-122`)이 스스로
    "펜스를 그냥 지우면 앞뒤 줄이 붙어 없던 링크가 생긴다" 고 설명하는 바로 그 시나리오
    (펜스 앞뒤에 **빈 줄 없이** 텍스트가 바로 붙는 경우, 예: 목록 안 펜스나 인용문 안 펜스처럼
    빈 줄이 끼지 않는 마크다운 관용구)는 이 스위트 어디에도 격리된 회귀 테스트가 없다.
    이 저장소가 같은 PR 문서(`plan/in-progress/harness-review-gate-followups.md`)에서 이미
    "양방향" 이라고 썼다가 실측으로 두 번 반증된 것과 동일 계열의 함정 — **분기를 못 가르는
    fixture** — 이며, 프로덕션 코드 자체는 (격리 입력으로 확인한 대로) 옳게 동작하므로 지금
    당장의 라이브 버그는 아니지만, 향후 펜스 마스킹 조건이 실수로 삭제/축소돼도 이 테스트
    스위트가 침묵으로 통과시킨다.
  - 제안: 이 테스트의 바디에서 펜스 앞뒤 빈 줄을 없애(또는 목록/인용문처럼 빈 줄이 끼지
    않는 실제 마크다운 관용구로 교체해) 펜스 마스킹 단독으로 결과가 갈리게 만든다. 예:
    `"# T\n[열린 텍스트\n\`\`\`\ncode\n\`\`\`\n](./a.md)\n"` (본 리뷰가 프로브에 쓴 것과 동일)
    처럼 빈 줄 없이 펜스가 바로 이어지는 입력을 쓰면, 펜스 마스킹 조건을 빼는 뮤테이션에
    대해 RED 로 반응한다 — 실측 확인 완료.

## 테스트 설계 품질 (긍정 관찰, 회귀 테스트 유효성 포함)

- 위 한 건을 제외하면 9개 신규 케이스(멀티라인 텍스트·줄 번호·목적지 개행 금지·멀티라인
  2개 이상(off-by-one 방지)·단일+멀티 혼재·3줄 스팬·빈 줄 경계·DEAD 통합 경로)가 과거
  실측 결함(2026-08-11, `spec/**.md` 6건 + 거버넌스 2건)과 그 반대 방향 오류(넓히기 과다)
  양쪽을 정확히 겨냥한다. 특히 "링크가 하나뿐이면 이진 탐색이 우연히 맞아 off-by-one 이
  숨는다" 는 사각지대를 두 개 이상의 멀티라인 링크로 명시적으로 겨냥한 점은 이 저장소가
  이미 겪은 실패 형태(`feedback_mutation_coverage_multiarm_operators` 계열)를 정확히
  선반영한 것으로 판단된다.
- Mock 사용 없음 — `fs.mkdtempSync` 로 describe 마다 격리된 임시 디렉터리를 만들고
  `afterAll` 에서 `fs.rmSync` 로 정리한다. 스캐너가 실제 파일을 읽는 로직이므로 mock 을
  안 쓰는 편이 실제 동작과의 괴리를 없앤다 — 적절하다.
- 테스트 격리: 각 describe 가 고유 prefix(`extract-links-ml-`, `ml-broken-`)의 tmp
  디렉터리를 쓰므로 블록 간 상태 공유가 없다. `beforeAll`/`afterAll` 짝이 맞고 병렬 실행 시
  경합 소지도 없다(별도 유일 경로).
- 가독성: 모든 `it` 제목과 인접 주석이 "무엇을 겨냥한 테스트인지" 와 "이게 빨개지면
  무엇이 깨진 것인지" 를 명시한다(예: ":323-325" 의 off-by-one 설명). 한국어 서술체가
  일관되고 의도 전달이 명확하다.
- 회귀 테스트 유효성: 기존 4개 describe 블록(사전 필터 3건, `findBrokenLinksInFiles core`,
  `findBrokenPlanLinks (living plans)`)은 이번 diff 로 직접 수정되지 않았고, 구현이
  "줄 단위 매칭 → 마스킹된 전문 매칭" 으로 바뀌었어도 공개 함수 시그니처·산출 계약
  (`fingerprint` 배열 형태)이 그대로라 여전히 유효하다 — RESOLUTION 의 실측 로그(unit
  6,213/6,214 passed)와 일치한다.
- 인터페이스 문서화(`MdLink.line`/`raw`, `LinkViolation.line`)는 직전 라운드 WARNING 이
  지적한 뒤 이번 커밋에서 이미 해소되어 있음을 `spec-links.ts:74-76,263` 에서 직접
  확인했다 — 재지적 불필요.

## 커버리지 갭 (우선순위 낮음, INFO 성격 — 과거 라운드가 이미 지적하고 우선순위를 낮춘 항목)

- `findBrokenPlanLinks`/`findBrokenSpecLinksInSources` 두 진입점은 멀티라인 DEAD 픽스처로
  통합 검증되지 않는다(`findBrokenLinks` 만 `:399` 에서 검증). 세 진입점이 같은
  `findBrokenLinksInFiles` 코어를 공유해 판별력은 낮지만, 이번 PR 의 실제 Critical
  사고(§1 참조)가 하필 `findBrokenPlanLinks` 스코프에서 터졌다는 점을 감안하면 대칭성
  차원에서 낮은 우선순위로 남겨 둘 만하다.
- CRLF(`\r\n`) 줄바꿈을 쓰는 멀티라인 링크는 테스트되지 않는다. `buildMaskedDoc` 이
  `text.split(/\r?\n/)` 로 CRLF 를 정규화하므로 동작상 문제는 없을 것으로 보이나, 이
  저장소가 CRLF 파일을 다룰 가능성이 낮지 않다면(윈도우 편집기로 만든 문서 등) 회귀
  테스트 한 건으로 고정해 둘 가치는 있다.

## 요약

멀티라인 링크 사각지대 수정에 대한 테스트는 전반적으로 탄탄하고, 과거 두 라운드가 잡은
문서화·off-by-one 이슈는 이미 해소되어 있다. 다만 이번 라운드에서 독립적으로 뮤테이션
프로브를 재수행한 결과, "코드펜스를 사이에 둔 링크는 아니다" 를 검증한다고 주장하는 테스트가
실제로는 같은 입력에 섞인 **빈 줄 마스킹**에 의해 우연히 통과하고 있으며, 펜스 마스킹
로직만 제거해도 GREEN 을 유지한다는 것을 격리 입력 대조로 확인했다(프로덕션 코드 자체는
격리 입력에서 정상 동작함도 함께 확인 — 지금 당장의 라이브 버그는 아니다). 이는 이 PR 이
스스로 여러 차례 문서화한 "분기를 못 가르는 fixture" 패턴의 재발이며, 향후 펜스 마스킹
조건이 실수로 손상돼도 이 테스트 스위트가 침묵으로 통과시킬 수 있다는 뜻이라 WARNING 으로
분류한다. 그 외 테스트 설계(mock 미사용, 격리, 가독성, 회귀 유효성)는 우수하다.
