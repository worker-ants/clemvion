# 문서화(Documentation) 리뷰 결과

## 발견사항

- **[WARNING]** `buildMaskedDoc()` 상단 JSDoc 의 "§1~§3 을 담당한다" 는 참조가 실제 구현 범위보다
  좁다 — 이 함수는 §4(빈 줄/문단 경계)도 담당한다.
  - 위치: `codebase/frontend/src/lib/docs/__tests__/spec-links.ts:118`
    (`* 원문을 링크 매칭용으로 마스킹한다 — `extractLinks` 의 §1~§3 을 이 함수가 담당한다.`)
  - 상세: `extractLinks()` JSDoc(`:180-192`)은 마스킹이 지켜야 할 불변식을 **네 가지**로
    번호 매긴다 — 1.인라인 코드 제거, 2.줄 번호 원본 기준, 3.펜스 사이 링크 미생성,
    4.**빈 줄(문단 경계)도 끊는다**. 그런데 `buildMaskedDoc()` 은 실제로 이 네 항목을 전부
    구현한다 — `isBlank` 분기(`:139-142`)와 그 바로 위 인라인 주석(`:135-138`, "CommonMark
    에서 링크 텍스트는 문단 경계를 넘지 못한다... 끊지 않으면 문단을 건너뛰어 없는 링크를
    만들어 낸다")은 §4 의 설명과 사실상 동일한 내용이다. 그런데도 함수 상단 JSDoc 은
    "§1~§3" 이라고만 적어 §4 를 언급하지 않는다. plan 문서(`harness-review-gate-followups.md`)
    의 서술을 보면 이 §4(빈 줄) 불변식은 이번 PR 진행 도중(2라운드, `15_01_34`)에 뒤늦게
    추가된 것으로 보인다 — `extractLinks` 의 "네 가지" 목록은 그때 갱신됐지만, 먼저 쓰인
    `buildMaskedDoc` 의 "§1~§3" 교차 참조는 갱신에서 빠졌다. 전형적인 "일부만 갱신된 교차
    참조" 형태의 오래된 주석이다 — 다음 사람이 "§4 로직은 어디 있지, `buildMaskedDoc` 이
    아니라면?" 하고 헤맬 수 있다.
  - 제안: `§1~§3` 을 `§1~§4` 로 바꾸거나, 아예 번호 대신 "인라인 코드 제거·펜스 마스킹·빈 줄
    마스킹을 전부 이 함수가 담당하고, 줄 번호 원본 환산은 `lineForOffset` 과 나눠 담당한다"
    처럼 항목명을 직접 나열해 향후 항목 추가/삭제 시 번호가 다시 어긋나지 않게 한다.

- **[WARNING]** 새로 추가된 plan 문단에 마크다운 인라인 코드 스팬이 백틱 개수 불일치로
  깨져, 렌더링 시 다음 문장 일부를 스팬 안으로 삼켜 버린다 — 바로 이 문단이 경고하는
  "백틱 인용이 함정이 된다" 는 주제를 스스로 재현한 사례다.
  - 위치: `plan/in-progress/harness-review-gate-followups.md:155`
    (`> **펜스로 감싸는 것은 여기서 안 통한다** — `FENCE_RE` 가 `^\s*```' 를 요구하는데`)
  - 상세: `` `^\s*```' `` 부분은 여는 백틱 1개 뒤에 백틱 3개(```)가 연달아 나오고 이어서
    작은따옴표(`'`)가 온다 — 닫는 백틱(길이 1)이 그 줄 안에 없다. CommonMark 규칙상 코드
    스팬은 **같은 길이의 백틱 런**으로만 닫히므로, 이 스팬은 닫히지 않은 채 다음 줄로
    이어지다 `:156` 의 `` `>` `` 앞 백틱에서야 닫힌다. 실제로 이 저장소가 이미 사용 중인
    `mdast-util-from-markdown`(이 파일이 헤딩 슬러그에 쓰는 그 파서)으로 직접 파싱해
    확인했다 — 렌더 결과 "^\s*```' 를 요구하는데\n인용문 안에서는 줄이 " 전체가 **하나의
    코드 스팬**이 되고, 그 뒤 원래 별도 인라인 코드였어야 할 `` `>` `` 의 여는 백틱이
    스팬을 닫아 버려 남은 텍스트가 `>` 로 시작하는 문장 조각이 어색하게 이어진다(">` 로
    시작한다..." 형태로 스팬 종료 표시가 문장 중간에 노출됨). 이 문단 바로 위(`:150-153`)가
    "이 문장을 쓰는 방식 자체가 함정이다 — **세 번째로 밟았다**" 며 정확히 이런 백틱 인용
    실수를 경계하는 내용이라, 그 경계문 바로 다음 문장에서 네 번째로 같은 종류의 실수가
    난 셈이다. 다행히 대괄호/괄호 문자가 없어 `spec-link-integrity` 가드(빌드 차단)를
    새로 건드리지는 않는다 — 순수 렌더링/가독성 결함이다.
  - 제안: `` `^\s*` `` 처럼 백틱 3개를 아예 언급하지 않거나(펜스 마커는 "3개 백틱" 이라고
    말로 풀어 쓰거나), 이 문장 전체를 코드펜스(` ``` `)로 옮길 수 없다면(인용문 안이라
    `FENCE_RE` 가 안 먹는다는 게 바로 이 단락의 요지) 이중 백틱 구분자(`` `` … `` ``)를 써서
    `` ``^\s*``` `` `` 처럼 내부 백틱 런과 구분자 길이를 다르게 만든다. 수정 후
    `mdast-util-from-markdown` 또는 실제 렌더러(GitHub 미리보기 등)로 한 번 더 확인 권장.

## 요약

핵심 코드 변경(`extractLinks()` 의 멀티라인 링크 매칭 수정)은 JSDoc·인라인 주석·plan
뮤테이션 근거표가 매우 충실하고, 직전 두 라운드가 지적한 documentation WARNING들도 이번
diff 시점엔 모두 실제로 반영돼 있음을 확인했다. 다만 반복적인 수정 과정에서 문서 자체의
자기 정합성이 두 군데 새로 어긋났다 — (1) `buildMaskedDoc` 의 "§1~§3" 교차 참조가 나중에
추가된 4번째 불변식(빈 줄/문단 경계)을 반영하지 못한 오래된 주석, (2) plan 문서에 새로
추가된 문단이 "백틱 인용 함정을 세 번째로 밟았다" 고 적으면서 바로 그 옆 문장에서 백틱
개수 불일치로 네 번째 함정에 빠져 렌더링이 깨진다(빌드는 깨지지 않음, 대괄호 없음). 둘 다
동작에는 영향이 없는 문서 정확성/가독성 결함으로 WARNING 수준이며, Critical은 없다.
