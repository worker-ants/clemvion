## 발견사항

- **[WARNING]** 한 문서 안에 **멀티라인 링크가 2개 이상**인 경우를 고정하는 테스트가 없다.
  - 위치: `codebase/frontend/src/lib/docs/__tests__/spec-links.test.ts:274` (`describe("extractLinks — 링크 텍스트가 줄을 넘어도 본다", ...)`) 이하 5개 `it` 전부 문서당 링크 1개뿐.
  - 상세: 이번 PR 이 새로 도입한 것은 "줄 단위 매칭"에서 "마스킹된 전문 + 이진탐색으로 원본 줄 복원"으로의 구조 변경이다(`spec-links.ts:159-185`, `startOf`/이진탐색). 이 알고리즘은 매치가 **여러 개**일 때 각 매치가 올바른 `startOf` 구간에 귀속되는지가 핵심 불변식인데, 새로 추가된 테스트는 전부 "문서당 링크 1개"만 검증한다. 기존(변경 전) `describe("extractLinks — 사전 필터가...")` 블록도 마찬가지로 문서당 1개다. 즉 "두 번째 이후 매치의 이진탐색이 올바른 줄을 찾는가"를 실제로 실행하는 테스트가 저장소에 전혀 없다.
  - 리뷰어가 직접 로직을 스크립트로 옮겨 프로브한 결과 **현재는 정확**하지만(위 프로브1·2·3), 이는 "지금 버그가 없다"는 증거일 뿐 "회귀를 막는다"는 증거가 아니다 — 이 계열 사각지대(멀티라인 링크 자체)가 실측으로 두 번(spec 6건 + 거버넌스 2건) 드러난 이력이 있는 파일이라, 두 번째 매치의 offset 계산이 깨지는 회귀(off-by-one 등)가 들어와도 지금 테스트 스위트는 잡지 못한다.
  - 제안: `describe("extractLinks — 링크 텍스트가 줄을 넘어도 본다", ...)`에 "한 문서에 멀티라인 링크가 2개 있을 때 각각 올바른 시작 줄을 보고한다" 케이스 1개, 그리고 "단일라인 링크 뒤에 멀티라인 링크가 이어질 때도 둘 다 정확하다" 케이스 1개를 추가할 것을 권장.

- **[INFO]** 멀티라인 링크가 `ANCHOR` 위반(자기참조 앵커 또는 교차파일 앵커 불일치)으로 잡히는 통합 경로는 테스트되지 않았다.
  - 위치: `codebase/frontend/src/lib/docs/__tests__/spec-links.test.ts:334` (`describe("멀티라인 링크의 깨진 타깃도 잡힌다", ...)`), `it` 블록(줄 348) — `fingerprint(findBrokenLinks(root))` 단언이 `"DEAD ./nope.md"` 한 종류뿐.
  - 상세: `findBrokenLinksInFiles` (`spec-links.ts:251` 이하)는 `target.startsWith("#")` 분기(ANCHOR, 자기참조)와 DEAD/교차파일 ANCHOR 분기로 나뉘는데, 새 통합 테스트는 DEAD 경로만 고정한다. `extractLinks` 가 반환하는 `target` 문자열 자체는 멀티라인 여부와 무관하게 동일한 형식이라 위험도는 낮지만(리뷰어 프로브4로 확인), 이 PR 의 다른 테스트들이 보여주는 "양방향으로 고정한다"는 엄격한 기준에 비추면 이 조합만 비어 있다.
  - 제안: 같은 `describe` 블록에 "멀티라인 링크의 깨진 자기참조 앵커도 잡힌다" 케이스를 추가해 `ANCHOR` kind 경로도 멀티라인 입력으로 한 번은 통과시킬 것.

- **[INFO]** `mkMultiLink` 헬퍼가 **2줄** 스팬만 만든다 — 3줄 이상 스팬(줄 번호 계산이 세 번째 줄 이상으로 넘어가는 경우)은 테스트되지 않는다.
  - 위치: `codebase/frontend/src/lib/docs/__tests__/spec-links.test.ts:288-290` (`mkMultiLink`).
  - 상세: 리뷰어 프로브3 으로 3줄 스팬도 현재 정확함을 확인했으나, 이 역시 회귀 방지 테스트로 고정돼 있지 않다. 우선순위는 낮음(2줄 케이스가 이미 알고리즘의 핵심 분기를 충분히 노출한다).

- **[INFO]** `writeDoc` 헬퍼가 새 `describe` 블록 두 곳(줄 282, 340 인근)에 이미 있던 패턴대로 각각 인라인 재정의된다.
  - 상세: 기존 파일의 다른 `describe` 블록들(예: 줄 229 `extractLinks — 사전 필터가...`)도 동일한 패턴을 쓰고 있어 이 PR 이 새로 만든 중복은 아니다(기존 컨벤션을 따른 것). 기능적 결함은 아니며 참고용으로만 남긴다.

## 회귀·격리·Mock 평가 (문제 없음, 근거만 기록)
- **회귀**: 기존 line-by-line 케이스(단일라인 링크, 인라인 코드 제거, self-anchor, DEAD/ANCHOR 판정)는 새 구현에서도 동일 코드 경로(각 줄을 `noCode` 치환 후 결합)를 거치므로 의미상 그대로 유효하며 실행 결과도 18/18 GREEN 으로 확인됨.
- **격리**: 모든 새 `describe` 블록이 `beforeAll`/`afterAll` 에서 `fs.mkdtempSync`/`fs.rmSync` 로 각자 고유한 임시 디렉터리를 만들고 정리한다. 블록 간 공유 상태 없음.
- **Mock 적절성**: mock/stub 을 전혀 쓰지 않고 실제 파일시스템에 실제 마크다운 파일을 써서 검증한다 — 이 함수의 성격(파일 I/O + 정규식 파싱)에 적절한 선택이며 실제 동작과의 괴리 없음.
- **가독성**: 각 `it` 제목과 인접 주석이 "왜 이 케이스가 필요한가"(양방향 고정, 실제 저장소에서 발견된 형태 재현)를 명시해 의도가 분명하다.
- **테스트 용이성**: `extractLinks` 는 순수 함수(파일 경로 → 배열)로 export 되어 있어 DI 없이도 테스트하기 쉬운 구조. 구조적 개선 불필요.

## 요약
`extractLinks()` 를 줄 단위 매칭에서 마스킹된 전문 + 이진탐색 방식으로 바꾼 리팩터링에 대해, 새로 추가된 테스트는 핵심 사각지대(멀티라인 링크 텍스트, 목적지 개행 금지, 코드펜스 경계)를 실제 저장소에서 발견된 형태까지 반영해 양방향으로 꼼꼼히 고정했고, 격리·mock 사용·가독성 모두 양호하며 vitest 실행으로 18/18 통과를 확인했다. 다만 이번 PR 이 새로 도입한 "여러 매치를 원본 줄로 되돌리는 이진탐색" 로직 자체는 지금까지 "문서당 링크 1개" 조건에서만 검증됐다 — 리뷰어가 로직을 저장소 밖에서 그대로 복제해 2개 이상 매치·3줄 스팬·ANCHOR 경로를 프로브한 결과 현재는 정확했지만, 이를 고정하는 회귀 테스트가 없어 향후 이 계열(멀티라인 링크) 회귀가 다시 침묵으로 통과할 잔여 위험이 남는다.
