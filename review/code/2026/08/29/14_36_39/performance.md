# 성능(Performance) Review

## 발견사항

- **[INFO]** 파일당 O(라인 수) 만큼 배열/문자열 할당이 늘었다 (허용 가능한 트레이드오프)
  - 위치: `codebase/frontend/src/lib/docs/__tests__/spec-links.ts:131`–`187` (`extractLinks`)
  - 상세: 종전 구현은 줄마다 `LINK_RE.exec(noCode)` 를 즉시 돌려 별도 버퍼가 없었다. 새
    구현은 사전 필터(`cannotContainLink`, 132–136행)를 통과한 파일에 한해 `masked`·
    `srcLineOf`(139–157행)·`startOf`(159–165행) 세 배열과 `body = masked.join("\n")`
    문자열(166행)을 추가로 만든다. 즉 파일 원문(`text`)·줄 배열(`lines`)에 더해 재조립된
    전문(`body`)까지 동시에 메모리에 떠 있어, 처리 구간의 피크 메모리가 대략 파일 크기의
    2~3배로 늘어난다. 다만 이 가드가 스캔하는 대상은 `spec/**.md`·거버넌스 문서·plan·
    `.ts`/`.tsx` 소스로 개별 파일 크기가 통상 수 KB~수백 KB 수준이고, 사전 필터가 `"]("`
    또는 `"]\`"` 를 가진 파일(실측 11.9%, 88% 컷)만 이 경로를 타므로 실질 영향은 미미하다.
    핵심 성능 가드(사전 필터로 라인 스캔 자체를 건너뛰는 것)는 그대로 보존됐고, 주석에도
    "멀티라인 링크에서도 `](` 는 붙어 있어 사전 필터가 유효하다"는 근거가 명시돼 있다.
  - 제안: 별도 조치 불필요. 다만 이 가드가 향후 훨씬 큰 생성 파일(예: API 카탈로그)까지
    스캔 범위에 넣는 방향으로 확장될 경우, `masked`/`body` 이중 보유가 문제가 될 수 있으니
    그때 재검토할 것(현재는 `inGeneratedCatalog` 로 카탈로그를 이미 제외하고 있어 해당 없음).

- **[INFO]** 매치 위치 → 원본 줄 번호 역산에 이진 탐색을 도입 — 적절한 복잡도
  - 위치: `codebase/frontend/src/lib/docs/__tests__/spec-links.ts:176`–`183`
  - 상세: 정렬된 `startOf` 배열에 대해 "마지막으로 `startOf[mid] <= m.index` 인 인덱스"를
    찾는 upper-bound 이진 탐색(`(lo + hi + 1) >> 1` 편향)을 정확히 구현했다. 매치당
    O(log L)(L = 파일의 줄 수)로, 선형 탐색이었다면 매치 수가 많은 파일에서 O(M·L) 로
    나빠졌을 지점을 O(M·log L) 로 눌러 놓았다. 별도 개선 불필요.

- **[INFO]** `regex.exec` 호출 횟수가 "파일당 1회(전체 매칭)"로 줄어 오히려 개선
  - 위치: `codebase/frontend/src/lib/docs/__tests__/spec-links.ts:168`–`185`
  - 상세: 종전에는 파일의 매치 불가능하지 않은 줄마다 `LINK_RE.lastIndex = 0` 리셋 후
    `exec` 루프를 새로 돌렸다(줄 수만큼 정규식 엔진 setup 비용 반복). 새 구현은 마스킹된
    전문에 대해 단 한 번 `lastIndex = 0` 후 전역 매칭을 수행한다. 이는 멀티라인 링크를
    잡기 위한 정확성 수정이면서 동시에 정규식 호출 오버헤드를 줄이는 부수 효과가 있다.
    회귀 아님, 개선 사항으로 기록.

- **[INFO]** 정규식 `[^\]]*` / `[^)\n]+` 는 중첩 정량자가 없어 ReDoS/이차 백트래킹 위험 없음
  - 위치: `codebase/frontend/src/lib/docs/__tests__/spec-links.ts:82` (`LINK_RE` 정의)
  - 상세: 목적지 부분이 `[^)]+` 에서 `[^)\n]+` 로 좁아졌을 뿐 두 그룹 모두 단일 부정
    문자클래스 뒤에 고정 리터럴이 오는 형태라 선형 시간이다(겹치는 정량자·backreference
    없음). 파일 크기에 비례해 선형으로 스캔되므로 대용량 입력에서도 안전하다.

## 요약

이번 diff 의 핵심은 `extractLinks()` 를 "줄 단위 매칭"에서 "마스킹된 전문 단일 매칭 + 이진
탐색 역산"으로 바꿔 멀티라인 마크다운 링크 사각지대를 닫는 정확성 수정이며, 성능 관점에서는
중립~소폭 개선이다. 기존에 이 폴더가 반복해서 데었던 "성능 최적화(줄 단위 사전 필터
`cannotContainLink`)가 가드를 조용히 멈추게 하는" 회귀는 발생하지 않았다 — 사전 필터는 그대로
보존됐고 새 구현에서도 유효함이 주석·리즈닝으로 명시돼 있다(`](` 는 멀티라인 케이스에서도
인접하다는 불변식). 파일당 부가 배열(`masked`/`srcLineOf`/`startOf`)과 재조립 문자열(`body`)
할당이 늘었지만 스캔 대상 파일 크기와 사전 필터 통과율(11.9%)을 고려하면 무시할 수준이고,
regex.exec 호출 횟수 감소·이진 탐색을 통한 매치→줄 역산은 오히려 개선이다. 테스트 파일
(`spec-links.test.ts`)과 plan 문서(`harness-review-gate-followups.md`) 변경분은 런타임 성능에
영향을 주는 코드가 아니다(테스트는 임시 디렉터리 기반의 소규모 fixture, plan 문서는 서술
갱신). N+1 호출, 블로킹 I/O 병목, 캐시 무효화, 부적절한 자료구조 사용 등 다른 관점에서
CRITICAL/WARNING 급 결함은 발견되지 않았다.
