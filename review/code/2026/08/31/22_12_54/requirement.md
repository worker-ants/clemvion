# 요구사항(Requirement) 리뷰 — 아바타 이미지 업로드 (공개 버킷 + 공개 URL)

## 발견사항

- **[CRITICAL]** 옛 아바타 정리 시 `decodeURIComponent` 가 try/catch **밖**에 있어, 이미 성공한 업로드 요청이 500 으로 응답한다 — "실패는 삼킨다" JSDoc 약속을 어긴다.
  - 위치: `codebase/backend/src/modules/users/users.service.ts:125` (`deletePreviousAvatarObject` 내부 `const key = decodeURIComponent(previousUrl.slice(at));`) — try 블록은 128행에서 시작하므로 125행은 가드 밖.
  - 상세: `updateAvatar()`는 새 파일 업로드 + `userRepository.save(user)`(:96, 이미 성공)까지 마친 뒤 `deletePreviousAvatarObject(userId, previousUrl)`(:100)를 호출한다. 이 함수는 `try { await this.s3Service.delete(cleanKey); } catch { … 삼킴 }`으로 S3 삭제 실패만 삼키도록 문서화돼 있는데(":112~113 실패는 삼킨다"), 그 앞의 `decodeURIComponent(previousUrl.slice(at))`(:125)는 어떤 보호도 없다. `previousUrl`은 이 함수 호출 시점에 `user.avatarUrl`(교체 전 값)이고, 이는 기존 `PATCH /api/users/me`(`UpdateMeDto.avatarUrl`, `@IsUrl({ require_tld: false })`)로 사용자가 자유롭게 설정할 수 있는 값이다. `validator.isURL`은 경로 안의 불완전한 percent-encoding(`%zz`, `%%` 등)을 문법 오류로 거부하지 않는다(실측: `validator.isURL('http://localhost:9000/bucket/avatars/<uuid>/%zz.png', {require_tld:false})` → `true`). 사용자가 `avatarUrl`을 `.../avatars/{자신의 userId}/%zz.png`처럼 설정한 뒤(자신의 `userId`는 본인이 알고 있음) `POST /api/users/me/avatar`로 새 아바타를 올리면: (1) 새 파일 업로드 성공, (2) DB에 새 `avatarUrl` 저장 성공, (3) `deletePreviousAvatarObject`가 옛(malformed) URL을 디코딩하려다 `URIError: URI malformed`를 던짐(실측: `decodeURIComponent('avatars/x/%zz.png')`가 즉시 throw), (4) 이 예외는 어디서도 잡히지 않아 `updateAvatar` 밖으로, 컨트롤러 밖으로 전파돼 Nest 기본 예외 처리가 500을 반환한다. 결과적으로 **아바타 교체는 실제로 성공했는데 클라이언트는 500(실패)을 받는다** — 이 기능 자체가 명시적으로 경계하는 "동작은 하는데 잘못된 채로 동작"의 정반대 실패 모드(제대로 동작했는데 실패로 보고)이며, 회귀 테스트(`users-avatar.service.spec.ts`)의 "정리 실패가 업로드를 깨뜨리지 않는다" 케이스는 `s3.delete` 거부만 검증해 이 경로를 못 잡는다.
  - 제안: `decodeURIComponent(...)`와 `key.split(/[?#]/)[0]`까지 포함해 `try` 블록 안으로 옮기거나, 함수 전체를 `try { … } catch { warn 만 }`으로 감싼다. 회귀 테스트에 malformed `%` 시퀀스를 포함한 `previousUrl` 케이스를 추가해 고정한다.

- **[WARNING]** 이번 diff가 신설한 `S3Service.getPublicUrl()`의 실제 구현이 어떤 테스트에서도 직접 실행되지 않는다.
  - 위치: `codebase/backend/src/common/services/s3.service.ts:80` (`getPublicUrl` 정의) / `codebase/backend/src/common/services/s3.service.spec.ts` (diff 대상 아님, `getPublicUrl` 관련 `it`/`describe` 0건).
  - 상세: `getPublicUrl`은 base URL 트레일링 슬래시 제거, 키를 `/`로 split 후 세그먼트별 `encodeURIComponent`, `${base}/${bucket}/${encoded}` 조립까지 이 기능 전체의 "공개 URL" 요구사항을 구현하는 핵심 로직이다. 그런데 `codebase/backend/src/common/services/s3.service.spec.ts`는 이번 diff에 포함되지 않았고(파일 목록에 없음) 실제로 `getPublicUrl`을 다루는 테스트가 0건이다(`grep -n "getPublicUrl\|describe(\|it(" s3.service.spec.ts` → `deleteMany` 관련 6건만). 소비하는 `users-avatar.service.spec.ts`/`users.service.spec.ts`에서도 `S3Service`를 통째로 mock해 `getPublicUrl: jest.fn((key) => \`https://cdn.example/bucket/${key}\`)`로 대체하므로, 실제 구현 코드는 리포지토리 전체에서 어떤 테스트에도 실행되지 않는다. 슬래시 이중 인코딩(`encodeURIComponent`를 키 전체에 적용했다면 `/`가 `%2F`가 됐을 버그류)을 정확히 우려하며 방어 코드를 짜 놓고 정작 그 로직을 검증할 테스트가 빠졌다.
  - 제안: `s3.service.spec.ts`에 `getPublicUrl` 단위 테스트(트레일링 슬래시 제거, 경로 세그먼트 인코딩 보존, 키에 특수문자 포함 시 동작)를 추가한다.

- **[WARNING] [SPEC-DRIFT]** 구현된 아바타 S3 키 패턴이 `spec/0-overview.md §2.7`과 `spec/data-flow/4-file-storage.md`의 (여전히 "계획/미구현"으로 남아 있는) 서술과 어긋나고, developer가 만든 정정 plan의 스코프에서 이 두 문서가 빠져 있다.
  - 위치: `spec/0-overview.md:269`(버킷 다이어그램 `avatars/ {userId}.{ext}`), `spec/0-overview.md:276`(표 행 "Form 노드 업로드 / Avatar | `{workspaceId}/forms/...`, `{workspaceId}/avatars/...` | 계획 (코드 미구현)"), `spec/data-flow/4-file-storage.md:55`(`### 1.2 (Spec 상 정의되지만 미구현) Form 첨부 / Avatar`), `:71`(표 행 "`<workspaceId>/avatars/<userId>.<ext>` | 프로필 이미지 | spec 정의, 미구현"), `:78`("S3 직접 업로드 도입 시 prefix 정의 필요") — 대응 코드: `codebase/backend/src/modules/users/users.service.ts:92`(`const key = \`avatars/${userId}/${randomUUID()}.${ext}\`;`).
  - 상세: spec은 아바타 키를 `{workspaceId}/avatars/{userId}.{ext}`로 "계획"했지만, 실제 구현은 `avatars/{userId}/{uuid}.{ext}` — `workspaceId` 접두가 전혀 없고, 파일명도 `{userId}.{ext}`가 아니라 `{uuid}.{ext}`다. 이 diff의 나머지 부분(CHANGELOG, `users-avatar.service.spec.ts` 테스트 1축)은 uuid를 넣은 이유(공개 버킷에서 키=접근 통제, `avatars/{userId}`만이면 워크스페이스 멤버 목록을 아는 사람이 열거 가능)를 명확히 설명하고 있고, User 엔티티는 `PATCH/POST /api/users/me/*` 계열 전부에서 `workspaceId` 컨텍스트 없이 JWT `sub`만으로 다뤄지는 워크스페이스-비종속 리소스이므로(사이드바에는 워크스페이스와 무관하게 같은 아바타가 표시됨) `workspaceId` 접두를 넣을 자연스러운 지점 자체가 없다. 즉 코드 쪽이 의도적이고 합리적인 설계이고, 두 spec 문서의 "계획" 서술이 구현 전 초안인 채로 낡아 있는 쪽으로 보인다(SPEC-DRIFT 판정). 문제는 developer가 직접 만든 `plan/in-progress/spec-update-avatar-upload-implemented.md`가 `9-user-profile.md`의 세 지점(`:334`, `:136`, `§5.1`)만 planner 트랙으로 위임했고, `0-overview.md §2.7`과 `data-flow/4-file-storage.md`(§1.1 제목의 "KB 문서 업로드 (현재 유일한 production 사용처)"도 이제 사실이 아님·§1.2·§2.1·§2.2)는 이 plan의 스코프에 전혀 언급되지 않았다는 점이다 — planner가 `9-user-profile.md`만 고치고 나면 두 문서는 계속 "avatar 미구현"이라고 말하는 채로 남는다.
  - 제안: 코드는 유지하고, `plan/in-progress/spec-update-avatar-upload-implemented.md`의 "## 할 일" 목록에 `spec/0-overview.md §2.7`(버킷 다이어그램·표 행을 실제 키 패턴 `avatars/{userId}/{uuid}.{ext}`로 정정 + workspaceId 미포함 근거)과 `spec/data-flow/4-file-storage.md`(§1.1 제목·§1.2 avatar 섹션·§2.1 표·§2.2 `user.avatar_url` 각주)를 planner 반영 대상으로 추가한다.

- **[INFO]** `S3Service` 생성자의 `?? endpoint` 폴백은 도달 불가능한 죽은 분기이며, 바로 위 주석의 취지("폴백 규칙은 한 곳(`s3.config.ts`)에만 둔다")와 모순된다.
  - 위치: `codebase/backend/src/common/services/s3.service.ts:34-35` (`this.publicBaseUrl = this.configService.get<string>('s3.publicBaseUrl') ?? endpoint;`).
  - 상세: `s3.config.ts`의 `publicBaseUrl`은 `process.env.S3_PUBLIC_BASE_URL || process.env.S3_ENDPOINT || 'http://localhost:9000'`로 항상 truthy 문자열을 반환하도록 이미 폴백 체인을 완결해 뒀으므로(`s3.config.ts:19-22`), `configService.get<string>('s3.publicBaseUrl')`이 `null`/`undefined`가 되는 경우는 없다 — `?? endpoint`는 실행되지 않는다. 기능 결함은 아니지만(무해), 인접 주석이 "여기서 다시 폴백하면 폴백 규칙이 두 곳이 되어 갈라진다"고 경고하면서 정작 코드에 (죽은) 두 번째 폴백을 남겨 다음 사람이 오독할 여지가 있다.
  - 제안: `?? endpoint`를 제거하거나(단언 처리), 유지한다면 "방어적 코드이며 s3.config.ts 계약이 깨질 때만 발동"이라고 주석을 정정한다.

## 요약

핵심 업로드 플로우(확장자 화이트리스트→서버측 Content-Type 강제, UUID 기반 추측 불가능 키, DB 저장 후 옛 객체 정리라는 순서)는 CHANGELOG·plan이 서술한 세 가지 "조용히 잘못 동작하는" 위험을 실제로 코드와 13건의 회귀 테스트로 정확히 막고 있고, `spec/` 쓰기 경계(developer는 `9-user-profile.md` 배지 flip을 planner 트랙으로 올바르게 위임)도 잘 지켰다. 다만 옛 아바타 정리 경로의 `decodeURIComponent`가 try/catch 밖에 있어 (기존에 이미 허용되던) malformed URL을 가진 사용자가 새 아바타를 올리면 실제로는 성공한 요청이 500으로 응답하는 CRITICAL 결함이 있고, 신설한 `S3Service.getPublicUrl`은 직접 테스트가 전혀 없다. 또한 구현된 S3 키 패턴(`avatars/{userId}/{uuid}.{ext}`)이 `spec/0-overview.md §2.7`·`spec/data-flow/4-file-storage.md`의 낡은 "계획" 서술과 어긋나는데, developer가 만든 spec 정정 plan은 이 두 문서를 스코프에서 빠뜨렸다.
