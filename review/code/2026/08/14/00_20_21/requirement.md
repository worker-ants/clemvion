# 요구사항(Requirement) 리뷰

## 발견사항

- **[CRITICAL]** `handleCallback` 이 튜플 shape 을 고친 뒤에도 `record.rememberMe` 는 여전히 `undefined` — 소셜 로그인마다 "로그인 유지" 선택이 조용히 무시된다.
  - 위치: `codebase/backend/src/modules/auth/auth-oauth.service.ts:159-175` (`const record = consumed[0]`, `record.rememberMe` 사용처 `:172`, `:175`)
  - 상세: `updateReturningRows<AuthOAuthState>(...)` 로 튜플에서 꺼낸 `record` 는 `DELETE … RETURNING *` 의 **raw pg row** 다. `auth_oauth_state` 테이블의 실제 컬럼은 `remember_me`(`codebase/backend/migrations/V013__auth_oauth_state.sql:9`, snake_case)이고, TypeORM `dataSource.query()` 의 raw 경로는 naming strategy 를 적용하지 않는다 — QueryBuilder/Repository 를 거치지 않은 리터럴 SQL 이기 때문이다. 그래서 `record.rememberMe` 는 항상 `undefined` 다(반면 `record.provider` 는 컬럼명이 우연히 camelCase 와 같은 문자열이라 동작한다 — 이 우연이 버그를 가렸다). `undefined` 는 `AuthService.issueTokensForOauthUser(user, rememberMe, ctx)` → `generateTokens(user, rememberMe = false, …)` 의 파라미터 기본값에 걸려 항상 `false` 로 떨어지고, `refreshExpDays = rememberMe ? 30 : 7`(`auth.service.ts:1086`) 및 `setRefreshTokenCookie(res, …, { rememberMe: result.rememberMe })`(`auth.controller.ts:586-589`, `refresh-cookie.ts:48-50`)가 각각 refresh token DB 만료일과 쿠키 `maxAge` 를 **항상 7일(DEFAULT_MAX_AGE_MS)** 로 고정한다. 사용자가 OAuth 시작 시 `rememberMe=true` 를 보내(`GET /api/auth/oauth/:provider?rememberMe=true`, `spec/data-flow/2-auth.md:121`) `auth_oauth_state.remember_me=true` 로 정확히 INSERT 됐어도, 콜백에서 그 값을 되읽는 순간 소실된다.
    이 결함 자체는 이번 diff 가 새로 만든 줄이 아니지만(`git log -p` 확인, `ae8f9cfd9` 이전부터 존재), **이번 PR 이 처음으로 이 줄을 프로덕션에서 실행 가능하게 만든다** — 수정 전에는 `consumed.length === 0` 이 항상 거짓이라 이 함수가 100% `OAUTH_STATE_MISMATCH` 로 throw 하고 `record.rememberMe` 줄에 도달한 적이 없었다(죽은 코드였다). 즉 이 PR 은 "정상 콜백이 성공해야 한다" 는 요구사항을 부분적으로만 충족한다 — 토큰 발급 자체는 성공하지만 그 안의 `rememberMe` 시맨틱은 배포 즉시 매 소셜 로그인에서 깨진다.
    같은 저장소의 자매 지점 `integration-oauth.service.ts` 는 정확히 이 컬럼명 문제를 이미 알고 `normalizeRawStateRow()`(`integration-oauth.service.ts:220-259`)로 snake_case → camelCase 정규화를 거친다("TypeORM `dataSource.query()` 는 raw SQL 결과를 column 이름 그대로 반환한다 … entity property 와 불일치" 라고 그 자리에 명시). 이번 PR 이 추가한 `update-returning-rows.ts` JSDoc 의 관용구 비교표(`:27-31`)는 `integration-oauth` 를 "(선제 대응)" 으로 인용하면서 **튜플 shape 문제만** 언급하고, 같은 파일이 이미 풀어 둔 **필드명 shape 문제**는 언급하지 않는다 — `auth-oauth.service.ts` 는 그 두 번째 교훈을 놓쳤다.
    새로 추가된 회귀 테스트도 이 값을 검증하지 않는다: 단위 테스트(`auth-oauth.service.spec.ts:188-192,235`)의 `validState` mock 은 처음부터 camelCase `rememberMe: false` 필드를 쓰므로 raw-row 문제를 재현하지 않고, 신설 e2e(`test/auth-oauth-callback.e2e-spec.ts:71-78`)는 리다이렉트 URL 의 `success=true` 문자열만 확인할 뿐 응답 쿠키의 `Max-Age`/DB 의 `refresh_tokens.expires_at` 값은 단언하지 않는다 — 이 PR 이 스스로 진단한 "mock 이 틀린 현실을 인코딩한다" 는 결함 클래스가 같은 함수의 다른 필드에서 미검출로 남아 있다.
  - 제안: `integration-oauth.service.ts` 의 `normalizeRawStateRow` 와 같은 방식으로 `record.remember_me` (또는 raw row 를 `{ ...raw, rememberMe: raw.remember_me }` 로 정규화)를 읽도록 고친다. 회귀 테스트는 e2e 에서 `rememberMe=true` 로 시작한 플로우가 실제로 30일 쿠키를 받는지(`res.headers['set-cookie']` 의 `Max-Age` 파싱) 또는 최소한 단위 테스트에서 raw 컬럼명(`remember_me`)으로 mock 한 뒤 `issueTokensForOauthUser` 가 `true` 를 받는지 검증해야 한다.

## 요약

핵심 결함(`UPDATE/DELETE RETURNING` 이 `[rows, rowCount]` 튜플인데 행 배열로 다뤄 admission·KB CAS 락·소셜 로그인이 상시 실패/무력화되던 문제)에 대한 처방은 정확하다 — `updateReturningRows` 헬퍼, 7개 소비 지점 전수 적용, 구조적 회귀 가드(`assert-row-array.spec.ts`/`update-returning-rows.spec.ts` 개수 일치), 그리고 실제 shape 을 반영한 단위·e2e 테스트까지 로컬에서 전부 통과(`update-returning-rows.spec.ts`/`assert-row-array.spec.ts`/`auth-oauth.service.spec.ts` 35 passed, `execution-engine.service.spec.ts`+`knowledge-base.service.spec.ts` 505 passed, 관련 lint 0 경고)를 직접 재현 확인했다. spec(`spec/data-flow/2-auth.md` §3.3·§Rationale)이 서술하는 "단일 원자 `DELETE … RETURNING`, 동시 콜백 중 한쪽만 소비" 행동도 코드와 일치한다. 다만 이 수정이 처음으로 "실행 가능"하게 만든 `handleCallback` 의 성공 경로 안에서, `record.rememberMe` 가 raw pg row 의 snake_case 컬럼(`remember_me`)과 어긋나 항상 `undefined`→`false` 로 떨어지는 별개의 shape 결함이 그대로 남아 있다 — 이번 PR 이 스스로 "지식이 지점에 갇히면 같은 실수가 재발한다" 며 인용한 `integration-oauth.service.ts` 가 이미 정확히 이 문제(필드명 shape)를 풀어 뒀는데도 `auth-oauth.service.ts` 는 그 처방을 적용하지 않았다. 결과적으로 "정상 콜백이 성공해야 한다" 는 이번 PR의 핵심 요구사항은 인증 성공 자체는 충족하지만, 그 안에 실려야 할 `rememberMe` 값은 배포 즉시 매 소셜 로그인에서 침묵 소실된다 — 새로 추가된 테스트(단위·e2e 모두)가 이 필드를 단언하지 않아 그린 상태로 넘어간다. 나머지 항목(엣지 케이스·에러 시나리오·반환값·TODO 부재 등)은 검토한 범위에서 문제가 없다.
