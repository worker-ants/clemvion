# Security Review — `nodeOutput` fail-closed allowlist (EIA §R17 잔여)

## 발견사항

- **[WARNING]** SSE/WebSocket fanout 경로는 여전히 fail-open deny-list — 동일 `_retryState`류 필드가 그 채널로는 계속 샌다
  - 위치: `codebase/backend/src/modules/websocket/websocket.service.ts` (`toFanoutEnvelope`, `attachRoutingContext` 인근 — 함수 정의부. 게이트 라인 번호 미부여 구간이라 함수명으로 기재), `codebase/backend/src/modules/execution-engine/form-interaction.service.ts` (`waitForFormSubmission`), `codebase/backend/src/modules/execution-engine/button-interaction.service.ts` (`waitForButtonInteraction`)
  - 상세: 이번 PR 은 `allowlistNodeOutputKeys`(fail-closed)를 `InteractionService.getStatus` 의 waiting `nodeOutput` 출구(`codebase/backend/src/modules/external-interaction/interaction.service.ts:392`) 한 곳에만 배선했다. 그러나 같은 `NodeHandlerOutput` shape 의 `nodeOutput` 이 WebSocket `EXECUTION_WAITING_FOR_INPUT` 이벤트로도 동일하게 나간다 — 직접 확인 결과 `FormInteractionService.waitForFormSubmission` 은 `context.structuredOutputCache?.[node.id] ?? context.nodeOutputCache[node.id]` 를 **아무 필터 없이** payload 의 `nodeOutput` 필드에 그대로 싣고(`form-interaction.service.ts`), `ButtonInteractionService.waitForButtonInteraction`/`processButtonResumeTurn` 도 `structured ?? flatNodeOutput` 을 그대로 `buttonConfig.nodeOutput` 에 싣는다(`cleanNodeOutput` 은 `status`/`interactionType` 두 키만 수동 delete). 이 envelope 은 이후 `WebsocketService.toFanoutEnvelope()` → `stripExternalOnlyFields(..., MAX_SANITIZE_DEPTH)` 를 지나는데, 이 함수의 deny-list 는 여전히 `EXTERNAL_STRIPPED_FIELDS = ['llmCalls']` 한 칸뿐이다(`strip-external-only-fields.ts:93`) — `allowlistNodeOutputKeys` 는 여기에 배선돼 있지 않다. 즉 REST `getStatus` 로는 막힌 `_retryState`(그리고 향후 신설될 미지 핸들러 키)가 WS `execution:<executionId>` 채널 구독자에게는 그대로 나간다. `websocket.service.ts` 자신의 JSDoc(`maskWireEnvelope`)이 이미 "그 구독 인가는 `verifyOwnership(executionId, workspaceId)` 만 보고 role 을 안 받는다 — REST 와 동일 인구" 라고 명시하므로, 이 두 출구는 **동일한 수신 인구**를 갖는 병렬 표면이며 한쪽만 닫힌 상태다. `ai-turn-orchestrator.service.ts` 의 `emitAiWaitingForInput` 은 대조적으로 `nodeOutput` 을 수동으로 재조립(`interactionType`/`config`/`conversationConfig`/`meta` 만 선별)해 이 클래스의 문제에서 원천적으로 자유롭다 — 즉 3개 park 진입 경로 중 2개(form/buttons)만 이 패턴에 노출된다.
  - 이 갭은 **이번 PR 이 새로 만든 회귀가 아니다** — 착수 전부터 있었고, 개발자가 impl-prep consistency 리뷰(`review/consistency/2026/08/23/18_30_40/`)에서 W2 로 지적받아 (a) `spec/5-system/14-external-interaction-api.md` §R17 에 "REST 와 SSE 의 `nodeOutput` 방어 강도가 이 시점부터 다르다" 라고 명시하고, (b) `plan/in-progress/spec-sync-external-interaction-api-gaps.md` 에 후속 항목으로 등재했다. 즉 투명하게 문서화·추적된 알려진 잔여 갭이며, 의도적 스코프 축소(REST 우선, chat-channel 렌더 파손 위험 때문에 SSE 는 별건)다. 다만 **보안 리뷰 관점에서 "현재 실서비스 상태"는 여전히 이 필드가 WS 경로로 노출된다**는 사실 자체는 변하지 않으므로, fix 우선순위 판단을 위해 별도 항목으로 재확인해 둔다. 현재 알려진 핸들러(ai_agent/information_extractor) 는 `_retryState`/`_resumeState` 설정 시 항상 `handleAiConversation` 경로(안전)로 라우팅되므로 **오늘 시점에 실제로 활성 도달 가능한 인스턴스는 확인되지 않는다** — 그러나 그 불변식이 `waitForFormSubmission`/`waitForButtonInteraction` 코드 자체에 구조적으로 강제돼 있지 않아(라우팅 registry 에 의존), 향후 어떤 폼/버튼류 핸들러가 이 필드를 채우면 조용히 재발한다.
  - 제안: 두 옵션 중 하나를 실제 코드 변경으로 확정. (a) `WebsocketService.toFanoutEnvelope()` 에 `allowlistNodeOutputKeys` 를 envelope 내부 `nodeOutput`/`buttonConfig.nodeOutput` 위치에 대칭 적용(단, `attachRoutingContext` 가 붙이는 `triggerId`/`workflowId`/`chatChannel` 등 envelope 최상위 키는 이 allowlist 대상이 아니므로 nodeOutput 서브트리에만 국한). 또는 (b) `FormInteractionService.waitForFormSubmission`/`ButtonInteractionService.waitForButtonInteraction`(및 `processButtonResumeTurn`) 이 WS emit 직전에 `allowlistNodeOutputKeys(nodeOutputForEvent)` 를 명시적으로 호출하도록 REST 와 동일 헬퍼를 재사용. 이미 tracker 에 등재돼 있으므로 이번 PR 의 blocking 사유는 아니지만, 후속 PR 착수 전 이 WARNING 을 그대로 인계할 것.

- **[INFO]** `NODE_OUTPUT_ALLOWED_KEYS` 컴파일타임 결속과 fail-closed 구현은 견고함 — 확인된 방어 특성
  - 위치: `codebase/backend/src/shared/utils/strip-external-only-fields.ts:138-192` (`NODE_OUTPUT_ALLOWED_KEYS`, `assertAllowlistCoversHandlerContract`, `allowlistNodeOutputKeys`)
  - 상세: `allowlistNodeOutputKeys` 는 오직 `delete out[k]` 만 수행하고 bracket 대입으로 새 키를 쓰지 않으므로, 스프레드 기반 own-property `"__proto__"` 케이스에서도 프로토타입 오염 벡터가 되지 않는다(자매 `stripDeep` 의 CWE-1321 방어 패턴과 별개로 이 함수 자체는 애초에 그 벡터가 없음). `PublicHandlerOutputKey extends (typeof NODE_OUTPUT_ALLOWED_KEYS)[number] ? true : never` 컴파일타임 assertion 이 `NodeHandlerOutput` 공개 키(`config`/`output`/`meta`/`port`/`status`) 전량을 실제로 덮는지 검증했고(직접 `node-handler.interface.ts:304-336` 대조 완료), `_resumeState`/`_retryState` 는 명시적으로 `Exclude` 되어 fail-closed 로 차단된다. `getStatus` 의 나머지 두 출구(terminal `result`/`error`)에 이 allowlist 를 걸지 않은 것은 `Execution.outputData` 가 워크플로 작성자 정의 데이터라 셰이프가 다르기 때문이며, JSDoc·spec(§R17 표) 양쪽에 정확히 근거가 남아 위 WARNING 과 달리 이 부분은 스코프·근거가 이미 잘 문서화돼 있다. 조치 불요, 참고용 기록.

## 요약

이번 변경은 `InteractionService.getStatus` 의 waiting `nodeOutput` REST 출구에서 기존 fail-open deny-list(`llmCalls` 한 칸)를 fail-closed allowlist(`NodeHandlerOutput` 공개 키 + 위젯 wire 전용 키)로 교체해, 실제로 새고 있던 엔진 내부 필드 `_retryState`(및 향후 미지 핸들러 키)의 REST 노출을 차단하는 정당한 보안 강화다. 구현은 컴파일타임 타입 결속·프로토타입 오염 안전·수동 나열 함정(폼 폴백 `formConfig ?? nodeOutput`) 회피 등 방어적으로 잘 설계됐고, 스코프 축소(terminal 출구 제외, SSE/fanout 제외)는 spec·plan 양쪽에 명시적으로 근거·추적되어 있어 은폐된 축소가 아니다. 다만 동일한 `_retryState`류 필드가 여전히 노출 가능한 두 번째 병렬 표면 — WebSocket `EXECUTION_WAITING_FOR_INPUT` 이벤트(`waitForFormSubmission`/`waitForButtonInteraction` 경유, `toFanoutEnvelope` 는 여전히 deny-list 만 적용) — 는 이미 문서화·추적됐을 뿐 아직 코드로 닫히지 않았다는 사실은 이 변경 세트만으로는 완결되지 않은 방어라는 점에서 보안 리뷰 결과에 반영해 둔다. 새 코드 자체에서 인젝션·하드코딩 시크릿·인증 우회·안전하지 않은 암호화·에러 메시지 정보노출 등 다른 OWASP 축의 문제는 발견되지 않았다.
