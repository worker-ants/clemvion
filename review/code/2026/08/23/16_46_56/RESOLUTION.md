## WARNING #1 (side_effect, MEDIUM) — `DEFAULT_SENSITIVE_KEYS` 확장의 blast radius 미측정

**타당한 지적이고, 내 plan 이 틀린 지점이었다.** plan 에 자매 표면의 키 축을 *"위험 없는
절반"* 이라 적었는데 **그건 측정이 아니라 단정**이었다. 이 저장소에서 내가 반복해 온
"유예·안전 판단의 근거가 프록시인" 형태다.

**실측했다** — 이 상수를 공유하는 `handler-output.adapter.ts` 는 노드 `config` echo 를
DB·WS·표현식으로 내보내므로, 비-자격증명 config 필드명이 신규 8개와 겹치면 **멀쩡한 값이
가려진다**(과잉 마스킹 = 기능 회귀).

| 대상 | 결과 |
| --- | --- |
| `codebase/backend/src/nodes/**` config 필드명 | **충돌 0건** |
| 전체 코드베이스 정확 일치 | `http-request.handler.ts:58` 의 `auth_token` **1건** |

그 1건은 **URL 쿼리파라미터 블랙리스트**(`QUERY_PARAM_BLACKLIST`)라 목적이 다르고 이 상수와
무관하다. `oauth_token_exchange_failed` 류는 **부분 문자열**일 뿐이고 이 목록은 **완전 일치**
(`sensitiveKeys.has(k.toLowerCase())`)라 안 걸린다.

**목록을 분리하지 않았다.** 리뷰어의 대안(`ASSISTANT_SENSITIVE_KEYS` 분리)은 blast radius 를
좁히지만 **같은 규칙을 두 목록에 손으로 동기화**하는 상태를 만든다 — 이 세션이 #1202 부터
계속 없애 온 바로 그 형태다. 충돌이 0건으로 측정됐으므로 분리 비용이 이득을 넘는다.

**실측을 코드 옆에 남겼다** — 다음에 이 목록을 넓히는 사람이 *"목록 자체가 아니라 자매
표면의 config 필드명과 겹치는지"* 를 다시 재도록 적었다.

**판별력 확인**: 목록에서 8개를 뺀 상태로 **이 spec 만** 돌리니 **5건 RED**. 이제 자매
표면이 자기 테스트만으로 회귀를 잡는다.
