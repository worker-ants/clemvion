# 동시성(Concurrency) Review

## 발견사항

- **[WARNING]** `_retry_state.json` 동시 갱신 시 `agents_fatal` 버킷 손실이 `agents_success` 와 달리 self-heal 되지 않음 — 독스트링의 "convergence" 서술이 실제 보장 범위보다 넓게 읽힘
  - 위치: `.claude/_shared/retry_state.py:59-71`(accepted-risk 독스트링), `:101-114`(`reconcile_state_with_disk`, 특히 103행·110-114행), `:166-190`(`apply_status_update`)
  - 상세: `apply_status_update` 는 `load_state`(읽기) → 메모리 mutate → `save_state`(전체 state 오버라이트)의 read-modify-write 이며 파일 잠금이 없다. `save_state` 자체의 독스트링(59-71행)은 "Lost updates between concurrent writers are a separate matter, left to the project's existing convergence approach (`reconcile_state_with_disk` derives the agent buckets from disk on every read)... `agent_history` and the rate-limit fields have no such convergence and can still be lost" 라고 서술해, 마치 손실 위험이 `agent_history`/rate-limit 필드에 한정되고 나머지 버킷들은 disk 로부터 재도출되어 안전한 것처럼 읽힌다. 그러나 실제 `reconcile_state_with_disk`(103행)의 `fatal = [n for n in state.get("agents_fatal", []) if n in missing]` 는 파일시스템의 독립적 증거로 재도출하는 게 아니라 **이미 로드된 state 의 기존 `agents_fatal` 리스트를 그대로 필터링**할 뿐이다(반면 바로 위 `agents_success` 는 101행 `has_report()` 로 실제 report 파일 존재 여부에서 새로 도출된다 — 비대칭). 따라서 같은 세션의 서로 다른 두 checker 에 대한 `--update` 호출이 겹치면(CLAUDE.md 자체가 "독립 호출은 배치 병렬 실행" 을 지시하고, 독스트링 63-64행도 "concurrent `--update` is a real path, not a thought experiment" 라고 인정) 한쪽 프로세스가 이미 커밋한 `status=fatal` 전이가 다른 프로세스의 stale 스냅샷 전체 덮어쓰기로 조용히 `pending` 으로 되돌아갈 수 있고, 그 뒤로는 어떤 `reconcile_state_with_disk` 호출도 이를 복구하지 못한다(디스크에 "한때 fatal 이었다"는 흔적이 없기 때문). 결과적으로 `/loop` 는 영구 실패로 판정됐던 checker 를 pending 으로 잘못 재시도하고, `agent_history`/`rate_limit_episodes` 감사 기록도 함께 유실된다. 실제 피해는 낭비성 재시도·감사 로그 누락 수준으로 데이터 손상이나 차단 오동작은 아니지만, 서술된 "convergence" 보장 범위가 부정확하다는 점은 정정할 가치가 있다.
  - 제안: 최소 조치로 독스트링을 정정해 disk-derived 인 것은 `agents_success` 뿐이고 `agents_fatal` 은 (이미 그 값이 메모리에 남아있을 때만) 보존될 뿐 독립 재도출은 안 된다는 점, 그래서 손실 가능 필드가 `agent_history`/rate-limit 뿐 아니라 `agents_fatal` 전이 자체도 포함한다는 점을 명시한다. 원한다면 `reconcile_state_with_disk` 가 report 파일과 무관한 별도의 fatal sentinel(예: `<name>.fatal` 마커 파일)로 `agents_fatal` 도 디스크에서 재도출하도록 확장할 수 있으나, 이는 새 설계라 이 브랜치가 이미 지켜온 관행대로("다른 skill 의 동작 변경이라 별도 PR 로 분리한다", `merge_coordinator_orchestrator.py` 주석 참고) 별도 후속으로 분리하는 편이 안전하다.

- **[INFO]** 하향(downgrade) 감지 백스톱이 `SUMMARY.md` 와 5개 checker 리포트를 개별 `_read()` 호출로 non-atomic 하게 읽어, 세션이 디스크에 쓰이는 도중이면 이론상 불완전한 조합을 볼 수 있음
  - 위치: `.claude/_shared/block_integrity.py:117-125`(`downgraded_criticals` — 117행 SUMMARY 읽기, 122행 각 checker 개별 읽기), 호출부 `.claude/hooks/_lib/review_guard.py:756-759`(`_newest_resolved_impl_done_mtime`)
  - 상세: `downgraded_criticals` 는 `SUMMARY.md` 를 먼저 읽고(117행) 이어서 `CHECKER_REPORTS` 를 순회하며 각 checker 파일을 서로 다른 시점에 읽는다(122행 루프). 이 여러 읽기가 하나의 원자적 스냅샷을 이루지 않으므로, 만약 이 게이트가 아직 완료되지 않은(체커가 파일을 쓰는 중인) 세션 디렉터리를 대상으로 실행되면 일부 checker 리포트가 비어있거나 부분 기록 상태로 읽혀, 실제로는 존재하는 `[CRITICAL]` 태그를 놓칠 수 있다(false negative — 경고가 조용히 안 뜸). 다만 실측 영향은 작다: `_newest_resolved_impl_done_mtime` 은 `_summary_block_is_no`(SUMMARY.md 가 존재하고 BLOCK 파싱에 성공)를 통과한 세션만 `best_dir` 후보로 삼고, 문서화된 워크플로 상 SUMMARY.md 는 5개 checker 완료 후 마지막에 쓰이므로 레이스 윈도우가 좁다. 이 백스톱 자체도 경고(warn)일 뿐 차단(block)이 아니므로 실패해도 영향은 제한적이다.
  - 제안: 필수 수정은 아니나, checker 리포트 mtime 이 SUMMARY.md mtime 보다 늦는(즉 SUMMARY 작성 이후 재기록된) 경우 경고를 보류하는 방어를 고려할 수 있다.

- **[INFO]** Stop 훅의 신규 note 중복 억제 로직이 기존 marker 패턴을 그대로 재사용해 check-then-act 레이스가 있음 — 기존에 이미 수용돼 있던 패턴과 동일 성격이고 최악의 경우도 중복 출력에 그침
  - 위치: `.claude/hooks/guard_review_before_stop.py:371-377`(신규 note 순회 루프), `:213-223`(`_already_nudged`/`_mark_nudged` 정의, 이 파일에 기존재)
  - 상세: `_already_nudged` 의 `os.path.exists(marker)` 확인과 `_mark_nudged` 의 `open(marker, "w")` 생성 사이에 원자성이 없다. 동일 `session_id`+`token`+`note{idx}` 조합으로 두 Stop 훅 프로세스가 근접 시점에 실행되면 둘 다 `_already_nudged` 를 False 로 보고 동일 경고를 중복 출력할 수 있다. 다만 (1) 이 파일에 이미 있던 review/plan-complete nudge 와 동일한 마커 패턴을 그대로 재사용한 것이며("Throttled like the nudge below" 주석이 명시), (2) 최악의 결과가 "동일 경고가 한 번 더 출력"에 그쳐 `BLOCK` 판정이나 디스크 상태에는 영향이 없고, (3) Stop 훅은 한 대화 세션에서 통상 순차 실행되어 실제 동시 실행 빈도는 낮다.
  - 제안: 별도 조치 불필요. 유사 마커 기반 dedup 이 앞으로 늘어난다면 `os.open(marker, os.O_CREAT | os.O_EXCL)` 로 "생성 자체"를 원자적 판정 신호로 바꾸는 것을 고려할 수 있으나, 현재는 관찰용 dedup 이라 우선순위 낮음.

## 요약

이번 diff 는 대부분 (1) 세 orchestrator(`code_review_orchestrator.py` / `consistency_orchestrator.py` / `merge_coordinator_orchestrator.py`)에 중복돼 있던 `_retry_state.json` 헬퍼 5종을 `.claude/_shared/retry_state.py` 로 추출하는 동작-보존 리팩터(AST 비교로 사전 검증)와, (2) checker `[CRITICAL]` 하향을 감지해 게이트 결정에 `notes` 로 실어 나르는 신규 경고 백스톱(`block_integrity.py` + 훅 3곳)으로 구성된다. 새 스레드/프로세스 풀·asyncio·명시적 락은 전혀 도입되지 않았고, `save_state` 는 temp-file + `os.replace()` 로 단일 라이터의 torn-write(부분 기록) 문제를 원자적으로 막아 신규 테스트(`test_a_failed_write_leaves_the_original_intact`)로도 고정돼 있다. 훅(`guard_review_before_push.py`/`guard_review_before_stop.py`)은 스레드 없이 순차 실행되는 단일 프로세스 구조라 프로세스 내부의 새 `notes` 필드 자체는 동시성 문제가 없다. 남아있는 위험은 전부 "여러 독립 프로세스가 같은 JSON/마크다운 파일을 잠금 없이 read-modify-write" 하는 기존 하네스 패턴에서 비롯되며, 저자가 이미 명시적으로 "lock 대신 accept, follow-up 등록"으로 트레이드오프를 문서화해 두었다(`failopen_state.py` 의 스트릭 카운터에도 동일 철학이 선례로 있음) — 다만 그 문서의 self-healing 범위 서술이 `agents_success`(disk-derived)와 `agents_fatal`(state 유지뿐, 미도출)의 비대칭을 놓치고 있어 이를 WARNING 으로 정정 요청했다. 나머지 두 건(체커 리포트 non-atomic 다중 읽기, Stop 훅 마커 dedup 레이스)은 경고 전용·저빈도·저영향이라 INFO 로 남긴다. `merge_coordinator_orchestrator.py` 가 `_reconcile_state_with_disk` 자기치유 없이 동일한 공유 `apply_status_update` 를 쓰게 된 점은 이미 저자 본인이 `plan/in-progress/harness-review-gate-ci-backstop.md` 항목 #9 로 별도 follow-up 등록해 두어 추가 지적을 요하지 않는다.
