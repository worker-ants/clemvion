# 아키텍처(Architecture) 리뷰 — masked-marker-shared-package

## 발견사항

- **[WARNING]** 재발 방지용 "미러 소멸 캐너리" 가드가, 이 PR이 없애려던 것과 **동일한 형태의 CI 경로 게이팅 사각지대**를 그대로 재도입한다
  - 위치: `codebase/frontend/src/lib/repo-guards/__tests__/masked-marker-mirror-guard.ts:32-36` (`SCAN_DIRS` 가 `codebase/backend/src`·`codebase/frontend/src`·`codebase/channel-web-chat/src` 셋을 스캔) + `codebase/frontend/src/lib/repo-guards/__tests__/masked-marker-mirror.test.ts:30-33` (배치 정당화 코멘트) / 실제 CI 트리거: `.github/workflows/frontend-checks.yml:43-44`, `.github/workflows/backend-checks.yml:61-62` (둘 다 diff에 없는 기존 파일이라 `Read`/`grep` 으로 직접 열어 확인한 실제 줄 번호)
  - 상세: 이 PR의 핵심 근거는 "가드를 한쪽 스택에만 두면 반대쪽이 그 값을 바꾸는 방향에 무력하다 — `frontend-checks` 는 `codebase/backend/**` 변경 시, `backend-checks` 는 `codebase/frontend/**` 변경 시 검사를 생략(그리고 skip=통과 보고)한다"이고, 이 원칙에 따라 마커 **값**은 `@workflow/masked-markers` 로 옮겨 양쪽 워크플로가 공통으로 `relevant` 로 잡는 `codebase/packages/**` 아래 두었다(정확한 해법). 그런데 이관 후 잔존 위험("미러가 되살아났는가")을 감시하는 **새 캐너리 가드**(`findMirrorRedeclarations`)는 정작 `codebase/frontend/src/lib/repo-guards/__tests__/` 안에 배치되어, `frontend-checks.yml`(`codebase/frontend/**`/`codebase/packages/**` 만 relevant)이 트리거될 때만 vitest 로 실행된다. 실측: `backend-checks.yml:61-62` 의 pathspec 은 `codebase/backend/**`/`codebase/packages/**` 뿐이라 `codebase/frontend/**` 를 포함하지 않는다. 즉 누군가 `codebase/backend/src/**` 안에서(예: 새 노드 핸들러) `const MASKED_MARKERS = [...]` 형태로 재선언하는 **backend-only PR** 을 낸다면, 그 PR 은 `codebase/frontend/**`/`codebase/packages/**` 어느 것도 건드리지 않으므로 `frontend-checks` 는 "무관한 변경 — 검사 생략" 패스트패스로 통과 보고되고, 이 가드가 도는 vitest 스위트(`pnpm --filter frontend test`) 자체가 CI 에서 한 번도 실행되지 않는다. `packages-checks.yml`(매트릭스 대상은 `codebase/packages/*` 각 패키지 자신의 lint/test/build) 도 이 가드를 커버하지 않는다. 남는 유일한 백스톱은 로컬 `TEST WORKFLOW 4단계`(`cmd_unit` → `pnpm --filter frontend test`, `.claude/test-stages.sh`)를 push 전에 수행하라는 **개발자 워크플로 관행**뿐이며, 이를 강제하는 pre-push 훅은 없음을 `.claude/hooks/` 전수 확인으로 검증했다(`guard_review_before_push.py` 는 `/ai-review` 실행만 강제하지 테스트 스위트 실행은 강제하지 않는다). 즉 "재선언은 그 파일을 바꾼 PR 에서만 생기므로 문제 없다"는 테스트 파일 자체의 방어 논리(`masked-marker-mirror.test.ts:30-33`)는, 그 PR 이 **backend 전용**일 때 정확히 깨진다 — 이는 값의 완전 대칭(타입 컴파일로 강제)이 아니라 "재선언 여부"라는 이 가드 고유의 불변식에 대한 것이고, 컴파일러는 로컬 `const MASKED_MARKERS = [...]` 재선언을 문법 오류로 잡지 않으므로 조용히 통과한다. 이 저장소에는 정확히 이런 "스택 무관하게 항상 돌아야 하는 가드"를 위한 선례 패턴이 이미 있다 — `deps-security-checks.yml` 헤더가 "`paths:` 필터가 없다 — 의도적이다(required status check 등록을 위해)"라고 명시하는 형태.
  - 제안: 이 캐너리를 `frontend-checks.yml` pathspec 게이팅 밖으로 옮긴다 — (a) `packages-checks.yml` 워크플로(공유 패키지 변경 시 항상 relevant)의 별도 스텝으로 실행하거나, (b) `deps-security-checks.yml` 처럼 `paths:` 필터 없는 별도 job 으로 분리해 모든 PR 에서 무조건 실행한다. 최소한 backend/frontend 어느 한쪽만 바뀌어도 트리거되도록 `frontend-checks.yml`/`backend-checks.yml` 양쪽 pathspec 모두에 이 특정 vitest 파일(또는 그 디렉터리)을 명시적으로 추가하는 방법도 있으나, 그 경우 "왜 이 가드만 예외적으로 양쪽에 걸리는지"를 주석으로 남겨야 후속 유지보수자가 다시 걷어내지 않는다.

- **[INFO]** 공유 패키지가 "마커 리터럴 집합"과 "마스커/스캐너가 공유해야 하는 재귀 깊이 상한"이라는 두 개의 별개 불변식을 한 이름(`masked-markers`) 아래 묶는다
  - 위치: `codebase/packages/masked-markers/src/index.ts` (`VALUE_MASK_MARKER`/`KEY_MASK_MARKER`/`DEPTH_MASK_MARKER`/`MASKED_MARKERS`/`isMaskedMarker` 와 `MAX_MASK_DEPTH` 가 같은 파일에 공존)
  - 상세: 두 불변식 모두 "backend 가 만들고 frontend 가 판정한다"는 같은 소비 패턴을 공유하므로 병합 자체는 실용적으로 타당하고 README 가 그 근거를 명확히 문서화한다(`codebase/packages/masked-markers/README.md`). 다만 패키지명이 "markers" 만을 시사해, 향후 제3의 개발자가 `MAX_MASK_DEPTH` 를 별도 상수로 오인해 재복제할 여지가 약간 있다 — 실제로는 미러 소멸 캐너리(`SOT_SYMBOLS`)가 `MAX_MASK_DEPTH` 도 감시 대상에 포함시켜 두어(위 WARNING 이 해소되면) 이 리스크는 낮다. 조치 불요, 참고용.

## 요약

이번 변경의 핵심 설계 — 손으로 복제되던 마커 상수·깊이 상한을 `@workflow/masked-markers` 공유 패키지로 추출하고, backend/frontend 는 재export shim 으로 소비처 import 경로를 보존한 것 — 은 SOLID/결합도 관점에서 견고하다. 순환 의존 없이 두 스택이 중립 패키지에 단방향으로 의존하는 "공유 커널" 구조이고(개방-폐쇄 원칙: 마커 추가는 소비처 코드 변경 없이 전파됨), 패키지 자체는 프레임워크 의존 없는 순수 값 도메인이라 추상화 수준도 적절하며, 명명(`@workflow/*` 스코프)·등록 표면(`test-stages.sh`/`packages-checks.yml`/Dockerfile ×3/두 `package.json`/`pnpm-lock.yaml`)도 기존 `@workflow/ai-end-reason` 선례를 정확히 따른다. 다만 이 PR의 존재 이유 자체가 "가드를 한쪽 스택에만 두면 반대쪽 변경 방향에 무력해지는 CI 경로 게이팅"이라는 실측 원칙인데, 그 원칙을 지키기 위해 새로 만든 재발 방지 캐너리(`masked-marker-mirror-guard`/`masked-marker-mirror.test.ts`)는 정작 `frontend-checks.yml` 파이프라인 안에서만 실행되어, backend-only PR 이 마커 심볼을 재선언해도 CI 상에서 이 가드가 아예 트리거되지 않는다 — 값 자체의 발산(핵심 위험)은 공유 패키지 추출로 구조적으로 닫혔지만, "미러가 되살아났는가"를 감시하는 이차 방어선은 같은 종류의 비대칭 커버리지 문제를 물려받았다. 그 외 발견은 명명/문서 수준의 경미한 사항이다.
