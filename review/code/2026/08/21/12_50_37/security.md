# 보안(Security) Review — masked-marker-contract-7d2e14

## 발견사항

- **[WARNING]** frontend 미러 소멸 가드의 `SOT_DIR` 접두 경계가, 같은 라운드에서 backend 형제 파일에 적용된 경계 수정(prefix-overlap fix)을 받지 못한 채 옛 취약 형태로 남아 있다 — 이 가드는 자격증명 마스킹 마커(`MASKED_MARKERS`)의 손-복제(미러) 재발을 잡는 보안 회귀 방지 컨트롤이므로, 이 gap 은 그 컨트롤 자체의 fail-open 표면이다.
  - 위치: `codebase/frontend/src/lib/repo-guards/__tests__/masked-marker-mirror-guard.ts:143` (`findMirrorRedeclarations` 내부 `if (relPath.startsWith(SOT_DIR.split(path.sep).join("/"))) continue;`). 대조: `codebase/backend/src/repo-guards/__tests__/masked-marker-mirror-guard.ts:141` 은 같은 커밋(`811a40f48`)에서 `if (relPath === SOT_DIR || relPath.startsWith(\`${SOT_DIR}/\`)) continue;` 로 이미 경계가 수정됨.
  - 상세: `SOT_DIR`(=`codebase/packages/masked-markers`)로 시작하는 스캔 대상 파일은 "SoT 패키지 자신"으로 간주돼 재선언 탐지에서 **제외**된다. `relPath.startsWith(SOT_DIR)` 형태는 문자열 접두사 비교라 슬래시 경계를 확인하지 않으므로, 예를 들어 `codebase/packages/masked-markers-legacy/src/foo.ts` 처럼 **이름이 `masked-markers` 로 시작하되 실제로는 다른 패키지**인 파일도 `startsWith` 조건을 만족해 스캔에서 조용히 제외된다. `resolveScanDirs` 가 이번 PR(round3, `811a40f48`)에서 `codebase/packages/<pkg>/src` 전체를 훑도록 2단계 확장되면서, 그 확장된 스캔 범위 안에서 이 접두 겹침이 실제로 도달 가능해졌다(파일이 스캔 목록에는 들어오지만 `findMirrorRedeclarations` 의 제외 분기에서 걸러짐).
    `git show 811a40f48` 로 직접 대조한 결과, 커밋 메시지·`RESOLUTION.md`(`review/code/2026/08/21/12_25_15/RESOLUTION.md`)는 "`startsWith(SOT_DIR)` 만 쓰면 `masked-markers-extra` 같은 형제를 오배제하므로 경계를 명시했다"고 **이 정확한 시나리오를 인지하고 수정했다고 서술**하지만, 실제 diff 는 그 수정을 backend 파일에만 적용했고 frontend 파일(`findMirrorRedeclarations`, 143행)은 손대지 않았다 — `resolveScanDirs` 확장 부분만 두 파일에 동일하게 반영되고, 경계 조건 수정은 backend 로만 갔다. 두 테스트 스위트(`masked-marker-mirror.test.ts`/`masked-marker-mirror.spec.ts`)에도 이 정확한 경계(형제 디렉터리 이름이 `SOT_DIR` 을 접두사로 갖는 경우)를 검증하는 케이스가 없다 — `it.each` 의 "접두가 겹치는 다른 식별자"(`MAX_MASK_DEPTH_OLD`) 캐너리는 **심볼 이름** 접두 겹침만 다루지 **디렉터리 경로** 접두 겹침은 다루지 않는다. 이 가드의 목적이 "마스킹 마커 값이 두 스택에 손으로 복제돼 어긋나면, 한쪽이 이미 마스킹된 자격증명을 다시 프리필/재제출해도 조용히 넘어간다"는 실제 발생 이력이 있는 결함 클래스를 잡는 것이므로, 탐지 로직 자체의 이런 사각지대는 (값이 아니라 로직의 중복이라 위험도는 낮다고 설계 문서가 명시하지만) 정확히 이 회귀가 frontend 트리거 경로에서만 재발할 경우 두 번째 방어선이 없다는 뜻이 된다. 다만 `codebase/packages/**` 변경은 `backend-checks.yml`/`frontend-checks.yml` 양쪽 모두에 relevant 로 잡히므로(리뷰 산출물 `dependency.md`/`architecture.md` 교차 확인), 이런 형제 패키지가 실제로 추가되는 PR 은 통상 backend 가드(수정됨)도 함께 트리거되어 실전에서는 상당 부분 완화된다 — 그래서 CRITICAL 이 아니라 WARNING 으로 판정한다.
  - 제안: frontend `masked-marker-mirror-guard.ts:143` 을 backend 와 동일하게 `relPath === SOT_DIR || relPath.startsWith(\`${SOT_DIR}/\`)` 형태로 맞춘다. 동시에 두 테스트 스위트에 "`codebase/packages/masked-markers-extra/src/x.ts` 같은 형제 디렉터리는 재선언 탐지 대상에 **포함**되어야 한다"는 경계 캐너리를 추가해 이 접두 겹침 클래스가 향후에도 회귀하지 않도록 고정한다(이 PR 은 이미 심볼 접두 겹침엔 캐너리를 뒀지만 경로 접두 겹침엔 두지 않았다).

## 요약

이 PR 은 backend/frontend 에 손으로 복제되던 자격증명 마스킹 마커 상수(`'***'`/`'[REDACTED]'`/`'[REDACTED_DEPTH]'`)와 깊이 상한을 `@workflow/masked-markers` 공유 패키지로 추출하는 리팩터이며, 마스킹 로직·정규식 패턴(`SECRET_LEAK_PATTERNS` 등)·시그니처·마커 값 자체는 diff 전후로 완전히 동일함을 확인했다 — 새로운 인젝션·인증/인가 우회·하드코딩 시크릿·평문 전송·안전하지 않은 암호화·민감정보 에러 노출 표면은 발견되지 않았다(마스킹 정규식 자체는 이번 diff 의 변경 대상이 아니다). 유일한 발견은 이번 PR 이 재발 방지용으로 신설한 "미러 소멸 가드"(값이 아니라 마커 재선언 심볼을 탐지하는 보안 회귀 방지 컨트롤) 자신의 결함이다 — 같은 세션의 직전 라운드에서 backend 형제 파일에 적용한 경로 접두-겹침(prefix overlap) 경계 수정이 frontend 형제 파일에는 누락되어, 커밋 메시지·RESOLUTION 문서가 "수정했다"고 서술한 것과 실제 코드 상태가 어긋난다. `codebase/packages/**` 변경이 양쪽 CI 워크플로 모두를 트리거하므로 실전 위험은 상당히 완화되지만, 가드 로직 자체의 비대칭 하드닝은 이 시리즈가 반복해 겪어 온 "자매 함수에 하드닝 미적용" 패턴의 재발이라 WARNING 으로 판정한다. 이 외 나머지 34개 이상의 변경 파일(CI 배선·Dockerfile·package.json·plan/review 문서)은 보안 관점에서 중립적 기계적 등록 변경이다.
