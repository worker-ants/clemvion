이 PR 의 핵심 설계 — backend/frontend 에 손으로 복제되던 마스킹 마커 상수·판정 로직·깊이 상한을 `@workflow/masked-markers` 공유 패키지로 추출하고, 두 스택은 재export shim 으로 소비처 import 경로를 보존한 것 — 은 SOLID/결합도 관점에서 견고하고, 이미 두 차례의 코드 리뷰 라운드(`11_27_29`, `11_53_49`)를 거치며 "가드를 한쪽 스택에만 두면 CI 경로 게이팅에 걸려 반대쪽 변경 방향에 무력해진다"는 이 PR 고유의 핵심 실패 클래스를 두 번 실측·수정했다(backend 전용 PR 우회 → backend 사본 신설, `channel-web-chat` 누락 → `frontend-checks.yml` pathspec 확장). 이번 최종 누적 diff 를 다시 실측 검증한 결과, 그 실패 클래스가 **세 번째로**, 이번엔 "top-level 스택 vs 2단계 중첩 패키지 컨테이너" 라는 다른 축에서 조용히 재발했다 — `resolveScanDirs` 가 `codebase/` 직속 하위마다 `src` 를 찾는 1단계 순회만 수행해 `codebase/packages/` 자체(그 밑에 `src` 없음)를 필터링해 버리는 바람에, `masked-markers` 를 제외한 **7개 shared workspace 패키지의 `src` 전체가 두 미러 가드 어느 쪽에서도 한 번도 스캔되지 않는다.** 이는 아직 라이브 미탐(실제 재선언)으로 이어지지는 않았지만, 이 가드의 존재 이유(SoT 밖 재선언을 "스택이 늘어도" 자동으로 잡는다) 자체를 부분적으로 무력화하는 구조적 사각지대이고, 캐너리 테스트도 이 갭을 검증하지 않는다. 그 외 발견은 두 스택에 걸친 근 동일 로직 복제(의도적·문서화된 트레이드오프, INFO)뿐이며, 패키지 경계·의존 방향(단방향, 순환 없음)·재export shim 을 통한 API 안정성 유지 등 나머지 아키텍처 축은 모두 견고하다.
