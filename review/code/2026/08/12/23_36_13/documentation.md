# 문서화(Documentation) 리뷰

## 발견사항

- **[WARNING]** 테스트 파일의 인라인 주석이 이번 PR 에서 바뀐 클래스 docstring 문구를 그대로 인용하고 있어, 그 인용이 더 이상 사실과 맞지 않는다.
  - 위치: `codebase/backend/src/modules/external-interaction/idempotency.interceptor.spec.ts:819`
  - 상세: 819번 줄 주석은 `// 클래스 docstring 이 "세 경로 모두 fail-open" 이라 주장하는데 적재 경로만 검증이 없었다` 라고 적혀 있다. 그런데 이번 PR(같은 브랜치의 `docs(eia)` 커밋, `idempotency.interceptor.ts:65-71`)이 바로 그 클래스 docstring 을 "세 경로" 산문에서 **다섯 경로 표**로 갈아엎었다 — 지금 docstring 은 "세 경로 모두 fail-open" 이라는 문자열을 더 이상 담고 있지 않다. 즉 이 주석이 인용하는 문구는 이번 PR 로 인해 존재하지 않게 된 옛 표현이다. 더 얄궂은 점은, 이번 PR 자체가 정확히 이 클래스의 "경로 개수 드리프트"(세 경로→실제 다섯 경로)를 고치는 작업이었고, `idempotency.interceptor.ts:76-78` 에 "표를 함께 갱신하지 않으면 다음 사람이 방어의 범위를 실제보다 좁게 읽는다" 라는 자기 성찰적 경고까지 새로 추가했다는 것이다 — 그런데 그 성찰이 미치지 못한 자리가 바로 이 테스트 주석이다. 기능·테스트 정확성에는 영향 없음(이 테스트 자체는 SET 실패 fail-open 을 정상적으로 검증한다), 순수하게 "주석이 가리키는 근거 문서가 바뀌었는데 주석은 안 바뀐" 문서 드리프트다.
  - 제안: 819번 줄 주석을 현재 docstring 표현("다섯 경로 모두 fail-open", 또는 아예 구체 문구 인용을 빼고 "클래스 docstring 이 전 경로 fail-open 을 보장한다고 주장하는데 적재 경로만 검증이 없었다" 식으로 인용을 느슨하게)에 맞게 갱신. 향후 재발 방지를 위해 이런 "docstring 문구를 그대로 따온 주석"은 되도록 피하고 도메인 사실만 서술하는 편이 유지비용이 낮다.

## 문서화 우수 사례 (참고, 감점 아님)

이번 diff는 문서화 관점에서 전반적으로 매우 높은 품질을 보인다:

- `CHANGELOG.md`: 새 Unreleased 항목이 근본 원인·클라이언트 영향(500→정상 처리)·새로 계약이 된 파싱 순서·바깥 엔트리 손상에도 warn 이 추가됐다는 점을 정확하고 구체적으로 서술한다. 기존 항목들과 문체·구조가 일관된다.
- `idempotency.interceptor.ts` 클래스 docstring: fail-open 경로를 "세 경로"→"다섯 경로" 표로 재구성하면서 `{@link storeEntry}`/`{@link discardCorruptEntry}` 로 각 경로가 실제로 어느 메서드에 사는지 앵커링했고, "이 목록은 개수를 세어 두는 것이 요점" 이라는 메타 주석으로 향후 드리프트를 예방하려는 의도까지 명시했다(다만 위 WARNING 처럼 파급 범위가 테스트 파일까지 못 미쳤다).
- 새 `discardCorruptEntry` private 메서드의 JSDoc은 두 호출부(엔트리/payload)의 **종전 동작이 서로 달랐다**는 사실(하나는 조용한 강등, 하나는 방어 자체가 없어 500)까지 구분해 설명 — 리뷰어가 "왜 두 자리를 하나로 모았는가"를 바로 이해할 수 있다.
- `idempotency.interceptor.spec.ts` 모듈 docstring이 신규 테스트 4건의 의도(이중 손상 fallback·각각 warn·에러 재현 분기도 동일 방어·파싱 순서 캐너리)를 정확히 요약하고 있으며 실제 추가된 `it` 블록과 1:1로 대응한다.
- 각 신규 테스트의 인라인 주석이 "왜 이 단언이 필요한가"(예: "응답만 단언하면 이 자리를 반만 지킨다", "단언은 형제 테스트와 동형이어야 한다")를 뮤테이션 관점에서 설명해, 향후 이 자리를 손대는 사람이 실수로 단언을 약화시키는 것을 막는다.
- `plan/in-progress/backend-lint-gate-broken-on-main.md` 체크박스가 실제 완료 상태(`[ ]`→`[x]`)로 갱신되고, 완료 근거·순서 뮤턴트가 처음엔 무효였다는 실패담까지 기록되어 있어 프로젝트 관례("plan 체크박스 = 실제 상태", "뮤턴트 유효성 선검증")를 잘 따른다.
