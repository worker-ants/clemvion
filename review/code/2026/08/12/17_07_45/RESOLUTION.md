## WARNING #1 (side_effect) — 내가 쓴 불변식이 깨질 수 있었다 → 조치

`storeEntry` 의 `JSON.stringify(payload ?? null)` 가 throw 하면, 그건 `catchError` **셀렉터
안**이라 그 새 에러가 **원래 409/410 예외를 대체**한다. 클라이언트가 500 을 받고
`return throwError(() => err)` 는 실행조차 되지 못한다 — 바로 위 주석에 내가 적어 둔
**"응답을 기록할 뿐 삼키지 않는다"** 는 불변식이 깨지는 것이다.

현재 서비스의 4개 throw 지점이 전부 plain object 라 즉시 터지지는 않지만 **그건 계약이 아니다**.
게다가 이 PR 이 바로 옆에서 고친 결함(부수 경로 실패가 본 응답을 왜곡)과 **같은 클래스**를
새 표면에 열어 둔 셈이다.

**조치**: 직렬화를 `try/catch` 로 감싸 실패 시 **적재만 skip** 하고 원 예외는 그대로 흐르게 했다.

## WARNING #2 (testing) — 5xx 가 우회 경로로 통과하고 있었다 → 조치

5xx 테스트가 순수 `Error` 를 던져 구현의 `instanceof HttpException` 가드에 **먼저 막혔다.**
즉 `isErrorStatusCacheable` 이 **호출조차 되지 않았고**, 판정 함수를 `>= 500` 도 캐시하도록
오염시켜도 아무도 잡지 못했다(리뷰어 실측). `isErrorStatusCacheable` docstring 의 "네 경우
모두 회귀 테스트가 있다" 는 5xx 방향에서 **거짓**이었다.

**조치**: `InternalServerErrorException` 으로 교체해 가드 **뒤**를 행사하고, 가드 **앞**을
보는 별도 테스트(`HttpException` 이 아닌 예외)를 신설해 두 층을 분리했다.
