# 아키텍처(Architecture) 코드 리뷰

## 범위

프로덕션 코드 변경 0. 아홉 개 e2e 동시성 테스트 파일(11 블록)에 손으로 복제돼 있던
`BEGIN → 락 쿼리 → 요청 발사 → 1.5초 공허성 가드(Promise.race) → COMMIT → 결과 반환,
finally: ROLLBACK + pending 흡수` 블록을 `codebase/backend/test/helpers/concurrency.ts` 의
`raceUnderHeldLock()` 단일 함수로 추출한 순수 리팩터다. `PROJECT.md` 에 이 헬퍼 사용을
의무화하는 가이드 한 절이 추가됐고, `plan/in-progress/e2e-race-helper.md` 가 착수 근거·
실측·판별 실험을 기록한다. 나머지 diff 항목(`review/code/**`, `review/consistency/**`)은
이전 리뷰/일관성 검토 라운드의 산출물이 커밋에 포함된 것으로, 프로덕션·테스트 아키텍처와
무관하다.

## 발견사항

- **[INFO]** 공유 상수 레지스트리(`KNOWN_LOCK_TIMEOUTS_MS`)가 개방-폐쇄 원칙상 "닫혀"
  있지 않고, 새 호출부 추가마다 이 파일을 손으로 갱신해야 검사가 유효하다
  - 위치: `codebase/backend/test/helpers/concurrency.ts:12-14` (`KNOWN_LOCK_TIMEOUTS_MS`
    선언), 검사 루프는 같은 파일 `:29-36`
  - 상세: `raceUnderHeldLock()` 은 "락 전용 커넥션 + 락 SQL + 발사 thunk 배열"이라는
    좁고 명확한 인터페이스로 설계돼 있어 그 자체는 확장에 열려 있다(새 호출부는 함수
    시그니처를 바꾸지 않고 그대로 쓸 수 있다). 다만 "가드 대기시간이 프로덕션 락
    타임아웃보다 짧아야 한다"는 불변식은 `VACUITY_GUARD_MS` 하나를 모든 호출부가 공유하는
    구조라, 이 불변식을 지키려면 새 호출부가 생길 때마다 이 파일의 배열에 항목을 **추가**해야
    한다 — 즉 확장 지점이 함수 시그니처가 아니라 이 내부 배열이다. JSDoc(`:7-10`, `:23-25`)이
    "추가하지 않으면 검사는 통과하지만 그 호출부의 가드는 오탐한다"고 이 한계를 스스로
    명시하고 있어 설계자가 트레이드오프를 인지하고 있음은 확인된다. 현재 유일한 등록
    항목(`TRIGGER_DELETE_LOCK_TIMEOUT_MS = 5_000`)은 실제 최소 타임아웃과 일치하므로
    지금 당장 오탐 위험은 없다.
  - 제안: 이미 문서화된 한계이므로 즉시 조치는 불필요하다. 다만 열 번째 호출부를
    추가하는 사람이 이 등록을 빠뜨리는 것 자체를 막고 싶다면, 장기적으로는 "호출부가
    자신의 타임아웃을 함께 넘기고 헬퍼가 그 자리에서 비교"하는 방향(선택적 `expectedMaxMs`
    파라미터)으로 옮겨 레지스트리를 호출 시점 계약으로 대체하는 편이 OCP 에 더 가깝다 —
    다른 reviewer(concurrency.md INFO)도 같은 방향을 제안했다.

- **[INFO]** 모듈 로드 시점에 부수효과(불변식 검증 + 조건부 throw)가 있어, 이 헬퍼를
  import 하는 어떤 테스트 파일이든 이 검사에 암묵적으로 결합된다
  - 위치: `codebase/backend/test/helpers/concurrency.ts:29-36` (top-level `for` 루프)
  - 상세: 이 검사는 특정 테스트 케이스 안이 아니라 모듈 평가 시점에 실행된다. 설계
    의도(락 타임아웃 회귀를 "그 값을 실제로 쓰는 테스트가 실패"가 아니라 "이 헬퍼를 쓰는
    아무 스위트나 즉시 실패"로 조기 발견)는 합리적이고, 부수효과가 순수하며(외부 IO 없음)
    결정적이라 테스트 격리를 깨지 않는다. 다만 아키텍처 관점에서는 "이 파일을 import 하면
    무조건 실행되는 검증 로직"이 함수 API 표면 밖에 숨어 있다는 뜻이라, 향후 이 파일에
    등록 항목이 늘어나고 검증 로직도 복잡해지면 "왜 이 테스트가 죽었는지"를 함수 본문이
    아니라 모듈 최상단에서 찾아야 하는 디버깅 비용이 생긴다.
  - 제안: 현재 규모(항목 1개, 비교 1줄)에서는 blocking 할 이유가 없다. 등록 항목이
    여러 개로 늘어나면 이 검증을 별도의 `it('불변식: 공허성 가드는 모든 등록된 락
    타임아웃보다 짧다', ...)` 형태의 명시적 테스트로 옮겨 실패 지점을 테스트 러너 결과에
    드러내는 편이 추적성이 좋아진다.

## 확인했으나 결함 아닌 것 (근거만 기록)

- **단일 책임·응집도**: `raceUnderHeldLock()` 의 책임은 "겹침을 강제로 만들고, 만들어졌음을
  관측(공허성 가드)한 뒤, 트랜잭션을 안전하게 정리한다" 하나로 좁다. 정렬 로직·도메인
  단언(`expect(results...).toEqual(...)`)은 명시적으로 헬퍼 밖(`@returns` 주석,
  `codebase/backend/test/helpers/concurrency.ts:61`)에 남겨 헬퍼가 도메인 지식을
  흡수하지 않는다 — 인터페이스 분리 원칙에도 부합한다(호출부는 필요한 것만 준다:
  `locker`/`lock`/`fires`).
- **과도한 일반화(anti-pattern) 회피**: `plan/in-progress/e2e-race-helper.md` §B 는
  `integration-rotate-concurrency.e2e-spec.ts`(삭제 경합이 아니라 갱신 경합 — 발사 수 1개,
  락과 가드 사이에 도메인 IO 개입, 가드 반환 형태도 다름)를 이 헬퍼에 욱여넣지 않고
  **의도적으로 제외**했다. "몇 개 발사할지·락 쥔 채 실행할 훅·COMMIT 전 읽을 훅" 같은
  파라미터를 추가해 억지로 통합했다면 파라미터 수가 늘고 각 파라미터의 유효 조합이
  좁아지는 전형적인 "god parameter" 안티패턴이 됐을 것이다. 구조가 다른 것을 구조가
  다르다고 인정하고 별도로 둔 것은 좋은 판단이다.
- **레이어 경계**: 테스트 헬퍼가 프로덕션 상수 `TRIGGER_DELETE_LOCK_TIMEOUT_MS` 를
  `../../src/modules/triggers/trigger-config-lock` 에서 직접 import 한다
  (`codebase/backend/test/helpers/concurrency.ts:4`). 이는 테스트→프로덕션 방향의
  단방향 의존이며, 그 반대 방향(`src/**` 가 `test/**` 를 참조)은 diff 전체에서 발생하지
  않는다 — 순환 의존 없음. 프로덕션 값과 테스트 가드의 관계를 하드코딩된 복제 숫자가
  아니라 실제 상수 참조로 고정한 것은 오히려 두 값의 drift 를 구조적으로 막는 바람직한
  선택이다(값이 바뀌면 이 파일이 재컴파일되며 불변식 검사가 즉시 반응한다).
- **확장성 판단**: 9 파일 11 블록 전체가 "한 락 문장 + 2개 이상 thunk"라는 동일한 형태였음을
  `plan/in-progress/e2e-race-helper.md` §B 표로 실측한 뒤 그 형태에 맞춘 시그니처를
  설계했다 — 추상화 수준이 관찰된 사례 수와 일치하며, 사례보다 넓게 앞서 나가는 과잉
  추상화(예: 임의 개수의 락, 임의 단계의 훅)를 시도하지 않았다.
- **디자인 패턴**: 클래스 계층이나 전략 패턴 없이 순수 함수 하나로 구현한 것은 이 문제
  규모(단일 오케스트레이션 절차)에 적절하다 — 불필요한 추상화 계층을 추가하지 않았다.

## 요약

프로덕션 코드에는 영향이 없는 테스트 전용 리팩터로, 아키텍처 관점에서 뚜렷한 문제는
발견되지 않았다. `raceUnderHeldLock()` 은 단일 책임(겹침 오케스트레이션 + 공허성 가드)에
집중하고 도메인 단언·정렬은 호출부에 남겨 인터페이스를 좁게 유지했으며, 구조가 다른
`integration-rotate-concurrency` 를 억지로 통합하지 않고 배제한 판단은 과잉 추상화를
피한 좋은 사례다. 유일하게 주목할 점은 프로덕션 락 타임아웃과의 정합성 검사가 함수
시그니처가 아니라 이 파일 내부의 수동 레지스트리(`KNOWN_LOCK_TIMEOUTS_MS`)에 의존한다는
점인데, 현재 규모(등록 1건)에서는 실질적 위험이 없고 설계자가 이미 JSDoc 으로 한계를
명시했다 — 둘 다 INFO 수준이며 즉시 조치가 필요한 사안은 아니다.
