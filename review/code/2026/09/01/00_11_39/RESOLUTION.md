# RESOLUTION — 아바타 업로드 리뷰 5라운드 반영

대상 SUMMARY: 위험도 **MEDIUM** · Critical **0** · Warning **6** · SPEC-DRIFT 4 · INFO 9

Critical 0 이 두 라운드 연속이다. 이번 라운드의 WARNING 중 **한 건은 사실이 아니어서 반박**
했고, 두 건은 실재 결함(내 테스트의 vacuity·문서 수치)이며, 두 라운드 연속 지적된 한 건은
유예를 접고 **구현**했다.

## W1 — 반박한다. 캐너리는 존재하고 물린다

리뷰는 이렇게 적었다:

> 이 우회를 지키는 캐너리 테스트는 실제로 존재하지 않는다(grep 0건) — plan 문서의
> "캐너리로 감지 중" 서술은 자동 가드가 아니라 서술적 표현이다.

**사실이 아니다.** 캐너리는 `users-avatar.service.spec.ts:472` 의
`describe('OAuth 연동 경로가 아바타 정리를 우회한다 — 캐너리')` 다. 지적을 액면가로 받지
않고 뮤턴트를 다시 넣어 확인했다:

```
$ # auth-oauth.service.ts: byEmail.avatarUrl ?? profile.avatarUrl
$ #                     → profile.avatarUrl ?? byEmail.avatarUrl
$ npx jest --silent src/modules/users/users-avatar.service.spec.ts
● OAuth 연동 경로가 아바타 정리를 우회한다 — 캐너리 › resolveUser 는 기존 avatarUrl 을 …
Tests: 1 failed, 34 passed, 35 total
```

원복 후 35/35 GREEN. 리뷰어의 grep 이 `auth-oauth` 쪽 파일만 봤거나 검색어가 좁았던 것으로
보인다 — 캐너리는 우회당하는 쪽이 아니라 **불변식을 세운 쪽**(users) 스펙에 있다.

문서 서술은 그대로 둔다. 다만 이 지적이 나온 이유 자체는 유효하다 — 캐너리가 지키는 대상과
그 파일 위치가 멀어서 찾기 어렵다. 그건 W8/W9(정리 불변식 통합) 항목에서 함께 볼 일이다.

## W3 — 내가 다른 곳마다 경계하던 결함이 정작 이 가드에 있었다

`'빈 파일을 거부한다'` 테스트가 이름과 달리 **파일 부재**(`undefined`)만 넘겼다. 가드는
`!file?.buffer?.length` 라 두 조건을 보는데, `!file` 로 뮤테이션해 **빈-버퍼 방어를 통째로
없애도 GREEN** 이었다.

이 PR 은 다른 자리에서 "분기를 못 가르는 fixture" 를 실측 주석까지 달아 가며 경계했다.
같은 기준을 이 가드에는 적용하지 않았다. `Buffer.alloc(0)` 케이스를 더해
`it.each(['파일 부재', '파일은 있으나 buffer 가 빈 것'])` 로 갈랐다.
뮤턴트 R1(`!file?.buffer?.length` → `!file`) → **RED 1**.

## W2 — 유예를 접고 구현했다

버킷 정책 e2e 부재는 4·5라운드가 **두 번** 지적했고, 나는 3라운드 RESOLUTION 에
"선행 조건은 이 PR 에서 해소했다" 고 적어 두었다. 세 번째로 미루는 대신 썼다:
`codebase/backend/test/users-avatar-upload.e2e-spec.ts`.

**유닛이 원리적으로 닿을 수 없는 것을 문다.** 이 기능의 접근 통제는 코드가 아니라 버킷
정책이 정하는데, 유닛은 `S3Service` 를 통째로 mock 하므로 정책이 되돌아가도 전부 GREEN 이다.
실 MinIO 상대로 고정한 것:

| 단언 | 왜 |
|---|---|
| 익명 GET **200** | 정책이 닫히면 업로드는 성공하고 이미지만 403 — 증상이 원인에서 멀다 |
| 익명 목록 **403** | 열리면 키 UUID 의 추측 불가능성이 통째로 무의미해진다 (`set download` 를 쓰면 실제로 열린다) |
| 교체 후 옛 객체 **404** | 고아가 쌓이지 않는다는 계약 |
| 응답 **200** · 키에 UUID | 자매 POST 와 같은 상태코드, 키가 예측 불가능 |
| SVG **400** | 스크립트를 품는 유일한 이미지 포맷이라 의도적 제외 |

**응답의 `avatarUrl` 을 그대로 fetch 하지 않는다.** `S3_PUBLIC_BASE_URL` 은 브라우저가
도달할 주소라 컨테이너 안에서 도는 이 테스트의 도달 주소와 다르다(e2e 는 `localhost:9000`,
컨테이너 망은 `minio:9000`). base 를 따라가면 **환경 설정을 시험하게 되고 정책은 못 본다.**
그래서 키만 떼어 컨테이너 망 주소로 직접 친다 — 시험 대상을 버킷 정책 하나로 좁혔다.
base URL 자체의 정확성은 유닛(`s3.service.spec.ts`)과 부팅 경고(`main.ts`)가 맡는다.

첫 실행에서 5건 중 1건이 실패했다 — 에러 봉투가 `{ code }` 가 아니라 `{ error: { code } }`
였다(`auth.e2e-spec.ts` 등 기존 관례). **정책 단언 4건은 첫 판부터 통과했다.**

### W6 — 같은 숫자가 세 번째로 stale 해졌다

plan 두 곳의 회귀 테스트 건수가 **13 → 30 → (실제) 35** 로 두 번 정정됐고, 그때마다 다음
라운드가 테스트를 더해 곧바로 다시 틀렸다. 3라운드에서 "문서에 수치를 쓰는 그 시점에 다시
재라" 고 적었는데, **그 습관으로도 못 막는다** — 커밋 시점에 맞는 숫자도 다음 커밋이 틀리게
만든다.

그래서 이번엔 재는 대신 **숫자를 뺐다.** 두 문서 모두 "건수는 적지 않는다, 필요하면
`jest --silent <file>` 로 그 시점에 센다" 로 바꿨다. 리뷰어가 제안한 방향이고, 반복해서
틀리는 항목은 고치는 것보다 **없애는 것**이 맞다.
