# RESOLUTION — 아바타 업로드 리뷰 8라운드 반영

대상 SUMMARY: 위험도 **MEDIUM** · Critical **0** · Warning **3** · INFO 26

7라운드 CRITICAL(로그인 카운터의 스냅샷 저장)이 해소됐음을 **13개 reviewer 가 소스 직접
확인으로 재검증**했고, 신규 CRITICAL 은 없다. WARNING 3건 중 하나는 이미 유예 등재된 항목의
재확인이고, 둘은 실질이 있어 둘 다 처리했다.

**이 라운드를 마지막 코드 수정으로 잡는다.** 근거는 아래 §수렴 판단.

## W1 — 내가 7라운드에 만든 비대칭을 disclose 했다

7라운드에서 `locked_until` 을 DB `NOW()` 로 잡도록 바꿨는데, 그 값을 **읽어 비교하는**
`isLocked()` 는 여전히 앱 서버 시계를 쓴다. 쓰기와 읽기의 시계가 갈렸고 어디에도 적혀
있지 않았다.

**의도적으로 남기되 이유를 코드에 적었다:**

- 영향은 시계 드리프트만큼 잠금이 길거나 짧아지는 것뿐이다. NTP 동기 환경에서 초 단위이고
  잠금은 10분이다.
- 없애려면 판정마다 `SELECT NOW()` 를 한 번 더 쳐야 한다 — **모든 로그인 시도**가 치르는
  비용이고 막는 것은 초 단위 오차다.

`isLocked()` JSDoc 에 재개 조건까지 적었다("시계가 크게 어긋난 배포에서 잠금 시간이 눈에
띄게 달라지면 DB 기준 판정으로 바꾼다").

한 가지는 분명히 해 둔다 — 내 7라운드 주석·테스트는 **쓰기**에 대해서만 "DB `NOW()` 로
잡는다" 고 말했고 그건 참이다. 읽기까지 DB 기준이라고 주장한 적은 없다. 이번 건은 거짓
주장이 아니라 **미기재**이고, 그래서 정정이 아니라 disclose 로 처리했다.

## W2 — 업로드 자체의 실패 축이 비어 있었다

이 스위트는 정리 실패·DB 갱신 실패는 촘촘히 잠갔는데 **`S3Service.upload()` 실패만**
비어 있었다. S3/MinIO 장애 시 부분 상태가 남지 않는지는 별개 축이다.

`upload.mockRejectedValue` 케이스를 더해 **예외 전파 + `update` 미호출 + `delete` 미호출**
을 단언했다. 뮤턴트 U1(업로드 실패를 `.catch(() => {})` 로 삼킴) → **RED 1**.

## W3 — 이미 유예 등재된 항목의 재확인

`updateAvatar`/`update()` 끼리의 `avatarUrl` 경합(패자의 객체가 고아로 남음). 리뷰 스스로
"DB 정합성 훼손은 없고 순수 스토리지 누수, plan 에 **측정 가능한 재개 신호**와 함께 명시적
유예 등재됨, 현행 유예 유지는 근거 있음" 으로 판정했다. 새 조치 불요.

7라운드에서 이 유예 근거가 한 번 반증됐던 이력과, 다시 성립함을 보인 실측 표(기존 `User` 를
스냅샷 전체로 저장하는 곳이 없음)는 그 plan 항목에 이미 들어 있다.
