# RESOLUTION — 감사 로깅 잔여 리뷰 3라운드 반영

대상 SUMMARY: 위험도 **MEDIUM** · Critical **0** · Warning **2** · INFO 13

Critical 은 없다. WARNING 2건은 **둘 다 내 것**이고, 하나는 개별 결함을 넘어선다 — 내가
**거짓 문장을 조치하지 않을 근거로 썼다**.

## W2 — 나는 존재하지 않는 문서를 근거로 댔다

1·2라운드 RESOLUTION 에 가드의 화살표 함수 필드 미인식을 두고 **"가드 헤더에 트레이드오프로
이미 문서화됨"** 이라고 적었다. 그 문장으로 "의도적으로 닫지 않은 경계" 라 분류하고 넘어갔다.

**거짓이었다.** 리뷰가 세 파일을 grep 해 0건임을 보였고, 나도 같은 grep 으로 확인했다:

```
$ grep -c "화살표\|arrow\|트레이드오프\|한계\|제약" audit-action-binding-guard.ts
0
```

그런 문서화는 **존재한 적이 없다.** 1라운드에 쓰고, 2라운드에서 확인 없이 되풀이했다.

### 그리고 갭은 실재했다

"문서화된 트레이드오프" 가 아니라 **그냥 놓친 구멍**이었다. 직접 프로브했다:

```
class S { private recordAudit = (params: { action: AuditAction; … }) => … }
→ 발견된 helper 수: 0
→ 묶이지 않음으로 잡힌 수: 0
```

화살표 함수 클래스 필드는 NestJS 서비스에서 `this` 바인딩용으로 **흔한 문법**인데, 가드가
그 형태를 **존재하지 않는 것처럼** 통과시켰다. 즉 이 PR 이 막으려는 결함(리소스에 안 묶인
`action`)이 **문법만 바꾸면 그대로 재도입**된다.

`auditHelperParams()` 로 메서드/화살표 필드를 같은 형태로 정규화해 닫았다 — 판정 로직이
선언 문법에 따라 갈리면 새 문법이 등장할 때마다 사각지대가 생긴다. fixture 2종(맨 union
화살표 · 묶인 화살표)과 "실제로 수집하는지" 단언을 함께 넣었다(그게 없으면 "안 잡는다" 와
"잡았는데 묶여 있다" 가 구분되지 않는다). 뮤턴트 Y1 → **RED 2**.

**두 RESOLUTION 의 거짓 문장도 정정했다.** 거짓 근거를 남겨 두면 다음 사람이 그걸 믿고
같은 판단을 반복한다 — 실제로 내가 2라운드에서 그렇게 했다.

## W1 — 이름은 `@Optional` 회귀인데 그걸 안 물었다

`'metrics 없이 조립해도 감사 기록은 동작한다 (@Optional)'` 테스트가 `new AuditLogsService(repo)`
로 **생성자를 직접 불러** DI 를 타지 않았다. `@Optional()` 이 있든 없든 항상 통과한다.

리뷰가 뮤테이션으로 확인한 것이 결정적이다 — `@Optional()` 을 지우면 RED 가 나긴 하는데,
**실패하는 것은 이 테스트가 아니라 무관한 `findAll` DI 스위트**였다. 그 스위트가 리팩터되면
이 계약은 아무도 안 지키게 된다.

`Test.createTestingModule` 로 `BusinessMetricsService` provider **없이** 조립해 성공을 단언하는
테스트로 바꿨다. 뮤턴트 Y2 → **RED 3**.

이건 이 세션에서 반복된 vacuity 클래스다 — 이름이 계약을 말하는데 단언은 그 계약을 안 무는 것.

## 정정 (2026-09-01, 5라운드 실측)

위에서 **"컴파일러의 `_NoCrossDomain` 가드가 다른 도메인 오귀속을 이미 정적으로 막는다"**
고 적은 근거는 **틀렸다.** 원문은 기록이라 지우지 않고 여기에 정정을 남긴다.

5라운드 리뷰어 둘이 이 문장을 지적했고, 뮤테이션으로 확정했다:

| 뮤턴트 | 결과 |
|---|---|
| `auth-configs` helper 를 `AuditActionFor<'workflow'>` 로 오귀속 | `tsc` **에러 5건** |
| 위 + `_NoCrossDomain` 캐너리까지 제거 | `tsc` **에러 5건 (변화 없음)** |

두 번째 줄이 결정적이다 — 캐너리를 지워도 검출이 그대로면 **잡는 주체는 캐너리가 아니다.**
에러 5건은 전부 helper 선언부가 아니라 **액션 리터럴을 넘기는 호출부**에 찍힌다. 즉 오늘
오귀속이 잡히는 이유는 호출부가 그 리소스의 액션을 넘기기 때문이고, `_NoCrossDomain` 은
`AuditActionFor` 유틸리티가 좁히기는 하는지를 하드코딩된 조합 하나로 확인할 뿐이다.

**리뷰어의 반증도 함께 틀렸다.** 두 리뷰어는 "뮤턴트가 `tsc` 에서 0 에러로 통과한다" 를
근거로 살아있는 구멍이라 했는데, 그 프로브는 **호출부가 없는 스크래치 재현**이었다. 실제
저장소에서는 5건이 난다. 표면은 실재하되 이유가 다르다 — 남는 갭은 "호출부가 아직 없는
helper" 와 "호출부의 액션이 두 리소스 모두에 유효해 갈리지 않는 경우" 다.

그 갭은 5라운드에서 `findMisboundHelpers` 로 **닫았다**(선언 단계 검사, 호출부 유무와 무관).
