# 성능(Performance) 리뷰

## 발견사항

- **[INFO]** `make_temp_repo_copy` 가 프로브마다 전체 서브트리 복사 + git 커밋 2회를 반복한다
  - 위치: `.claude/tests/_harness.py:138` (`make_temp_repo_copy` 정의, `shutil.copytree` + `git add -A` + `git commit`)
    호출부: `.claude/tests/test_consistency_bundle_priority.py:641`, `:679`, `:717`, `:771`, `:876` (5곳, `spec/5-system` 서브트리 — 실측 18개 파일 · 1.4MB)
  - 상세: 기존에는 프로브 격리를 `shutil.copy`(파일 1개 백업) + 원복으로 처리했지만, 이번 변경은 병렬 실행 트램플을 막기 위해 각 프로브 호출마다 `make_temp_git_repo`(git init + 2개 config + 초기 commit) → 대상 서브트리 전체 `shutil.copytree` → `git add -A` → 두 번째 `git commit` 을 새로 수행한다. 이는 이미 `run_in_orchestrator` 가 프로브마다 새 파이썬 인터프리터를 fork 하는 기존 오버헤드(`_lib` 충돌 회피 목적, 기존 설계) 위에 추가되는 것이라, 파일 I/O(디렉터리 트리 복사)와 git 해싱/압축 비용이 테스트 파일당 최대 5회 반복된다. 클래스 단위로 서브트리 복사본을 한 번만 만들어 공유(`setUpClass`)하지 않고 테스트 메서드/헬퍼 호출마다 매번 새로 복사·커밋한다.
  - 제안: 현재 규모(18개 파일, 1.4MB)에서는 실행 시간 영향이 서브초 단위로 미미하고, 이 코드는 `.claude/tests/` 하위의 테스트 하네스 전용이라 프로덕션 런타임에는 전혀 영향이 없다. 다만 대상 서브트리가 커지거나 이 패턴이 다른 대형 디렉터리에 복제될 경우 테스트 스위트 전체 소요 시간이 선형으로 늘어날 수 있으니, 같은 서브트리를 여러 테스트가 반복해서 복사하는 경우 `setUpClass`/모듈 스코프 fixture 로 사본을 1회만 만들고 테스트마다 파일시스템 레벨 스냅샷(예: 하드링크 복제)만 뜨는 방식을 고려할 수 있다. 현재 크기 기준으로는 정정을 요구할 정도는 아니다.

- **[INFO]** 격리를 위한 트레이드오프이며 실제 회귀는 아님
  - 위치: `.claude/tests/test_router_decision_trust.py:376-390` (`tmp_src = tempfile.mkdtemp(dir=str(REPO_ROOT))` → `tempfile.mkdtemp()`)
  - 상세: 임시 소스 디렉터리를 워크트리 안이 아니라 시스템 임시 경로로 옮겼다. 파일을 만들고 subprocess cwd 로 넘겨 읽기만 하므로 파일시스템이 달라져도(디스크 간 이동이 아니라 생성 위치만 바뀜) 성능에 미치는 영향은 없다. 정보 제공 목적으로만 기재.

## 요약

이번 변경은 `.claude/tests/` 하네스 전용 코드로, 프로덕션 코드 경로(`codebase/**`)에는 영향이 없다. 핵심 변화는 병렬 pytest 실행이 서로의 프로브를 밟는 문제(단일 파일 `cp` 백업/복원 방식)를 프로브별 임시 git 저장소 사본(`make_temp_repo_copy`)으로 교체한 것으로, 정합성(격리) 확보를 위해 테스트당 디렉터리 복사 + git commit 비용을 소폭 추가로 지불하는 트레이드오프다. 대상 서브트리(`spec/5-system`, 18개 파일·1.4MB) 규모에서는 이 오버헤드가 무시할 수준이며, 알고리즘 복잡도·N+1 호출·메모리 누수·블로킹 I/O 등 심각한 성능 문제는 발견되지 않았다. 유일하게 짚을 만한 점은 동일 서브트리를 여러 테스트가 매번 새로 복사·커밋한다는 것으로, 서브트리가 커지면 테스트 스위트 실행 시간에 누적 영향을 줄 수 있으니 향후 확장 시 공유 fixture 화를 검토할 만하다.
