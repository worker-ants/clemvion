## 발견사항

- **[INFO]** 판정표 일부 행이 "취소선(원 판정) + 굵게(정정 판정) + 반증 근거"를 한 셀에 중첩해 담아 스캔하기 어렵다
  - 위치: `plan/in-progress/changelog-backfill-12.md` — `## A. 판정` 표의 `#1364` 행, `#1238` 행 (`Read` 로 확인한 원본 줄 번호 기준 각각 23행·34행)
  - 상세: `#1364` 행은 `~~**항목**~~ **안 낸다**` 로 최종 판정을 뒤집은 뒤, 근거 칸 안에서 다시 `~~오늘 관측되는 것: …~~` 으로
    한 번 더 취소선을 걸고 `**반증(diff 대조)**: …` 으로 새 근거를 붙인다. `#1238` 행도 같은 구조로 `~~spec 0~~ — \`--plan\` W1: …` 을
    담는다. markdown 표는 셀 하나가 렌더링·raw 양쪽에서 줄바꿈 없는 한 단위이므로, 이렇게 취소선이 두 겹으로 중첩되면 "지금
    유효한 판정이 무엇인지" 를 재구성하려면 그 긴 줄 전체를 순서대로 읽어야 한다. 같은 표의 다른 10행은 단문 하나로 끝나
    정보 밀도 편차가 크다.
  - 제안: 이 plan 문서가 감사 추적(자기반증 정정 이력)을 남기는 것 자체는 프로젝트 관례(정정 시 원문에 취소선 유지)와
    맞다. 다만 개정 이력이 길어지는 행은 표 셀 안에 전부 넣기보다, 표에는 **최종 판정만** 남기고 개정 서사는 표 아래
    각주나 기존에 이미 쓰고 있는 인용 블록(예: 문서 하단의 "처음 판정은 11·1 이었다" 콜아웃)으로 빼는 편이 다음에 이
    표를 훑는 사람에게 더 읽기 쉽다. (blocking 은 아님 — 이미 커밋되어 CHANGELOG 에는 반영되지 않는 감사용 문서이므로
    가독성 개선 권고에 그친다.)

- **[INFO]** CHANGELOG 신규 항목 제목이 나열하는 항목 수와 본문이 실제로 매핑하는 PR 번호 수가 어긋난다
  - 위치: `CHANGELOG.md` — `## Unreleased — 가드가 안 보던 자리 넷 — lint 글롭 · frontend 테스트 타입체크 · 도구 태그 잔재 · 인용문 안 체크박스 (#1261 · #1262 · #1263 CHANGELOG 누락 backfill)` 헤더 (파일 컨텍스트 게이트 54행)
  - 상세: 제목은 "넷"(4개 결함)을 나열하지만 괄호 안 PR 은 세 개(`#1261`·`#1262`·`#1263`)뿐이다. 본문을 보면 "도구 태그 잔재
    가드"와 "plan 체크박스 정규식" 두 항목이 모두 `#1262` 하나에 묶여 있어 수가 안 맞는 게 아니라 표기 방식(항목 수 vs
    PR 수)이 섞인 것인데, 제목만 보면 "4 항목 = 4 PR" 로 오독하기 쉽다. 파일의 다른 항목들(예: `V110~V130` 항목)은
    제목에 "인덱스 마이그레이션 21개"처럼 항목이 세는 대상(마이그레이션)과 PR 목록을 분리해 명시하는 관례를 따르는데,
    이 항목만 "넷" 이 무엇을 세는 수인지(결함 종류 수 vs PR 수) 제목만으로는 모호하다.
  - 제안: 제목을 "가드가 안 보던 자리 넷(PR 3건)" 처럼 두 수를 분리해 적거나, 본문 첫 문장에서 "네 결함 중 뒤 둘은 같은
    PR(`#1262`)" 이라고 한 번 밝히면 다음에 이 항목을 인용하는 사람이 항목 수와 PR 수를 혼동하지 않는다.

- **[INFO]** 판정표 행의 정보 밀도가 균일하지 않다

## 긍정적 관찰 (참고)

- `CHANGELOG.md` 에 새로 추가된 6개 항목은 모두 기존 파일의 `## Unreleased — <무엇이 바뀌었나> (#PR CHANGELOG 누락 backfill)`
  헤더 포맷, 코드 식별자 백틱 표기, PR 번호 백틱+`#` 표기를 정확히 재사용한다 — 새 스타일을 도입하지 않아 파일 전체의
  일관성이 유지된다.
- `plan/in-progress/changelog-backfill-12.md` 의 frontmatter(`title`/`status`/`owner`/`worktree`/`spec_impact`/`started`)는
  `.claude/docs/plan-lifecycle.md §4` 스키마를 그대로 따르고, `spec_impact: none` 은 Gate C 가 요구하는 bare 리터럴이다
  (naming/포맷 일관성 양호 — consistency-checker 의 `convention_compliance.md` 도 동일하게 확인함).
- `review/consistency/2026/09/25/13_31_14/*` 산출물은 프로젝트 컨벤션이 규정한 표준 구조(발견사항/요약/위험도, WARNING·INFO
  표, checker별 위험도 표)를 그대로 따르는 생성물이라 별도의 유지보수성 이슈가 없다.

## 요약

이번 diff는 애플리케이션 코드를 포함하지 않는 순수 문서 변경(CHANGELOG 백필 6항목 + plan 신설/체크박스 갱신 + consistency
리뷰 산출물)이라 함수 길이·중첩·순환 복잡도 같은 통상 유지보수성 지표는 적용되지 않는다. `CHANGELOG.md` 신규 항목은 기존
파일의 헤더·인용 포맷을 정확히 재사용해 일관성이 높다. 유일하게 눈에 띄는 것은 `plan/in-progress/changelog-backfill-12.md`
판정표에서 취소선 기반 정정 이력을 표 셀 안에 중첩해 담은 행(`#1364`·`#1238`)의 가독성 저하와, 한 CHANGELOG 항목 제목에서
"결함 항목 수"와 "PR 수" 표기가 섞여 읽는 사람이 오독할 여지인데, 둘 다 내용의 정확성 자체는 다른 리뷰(consistency-checker)가
이미 대조·확인했고 차단 사유가 아니라 스타일 개선 권고 수준이다.
