# 유지보수성(Maintainability) 리뷰

## 검토 범위 메모

- 파일 1~8 (엔티티 8개): 각각 한 속성(`type: 'uuid'` · `enumName` · `default`)만 추가하는 1~5줄짜리 diff. 같은 파일 안 다른 컬럼들이 이미 쓰는 표기(예: `node.entity.ts` 의 다른 `type: 'uuid'` 컬럼, `edge.entity.ts` 자신의 `enumName` 관례)를 그대로 따라가는 정정이라 네이밍·스타일 일관성 문제 없음.
- 파일 9 (`entity-schema-declarations.e2e-spec.ts`): 이번 diff 의 실질적인 코드 본체. 아래 발견사항은 전부 이 파일 기준.
- 파일 10~11 (plan 문서): 코드가 아닌 작업 기록이라 가독성/네이밍/함수길이 등 코드 기준이 적용되지 않음 — 별도 findings 없음.
- 파일 12~27 (`review/consistency/**` 산출물 — SUMMARY/체커별 결과/`_retry_state.json`/`meta.json`): 다른 sub-agent 가 생성한 리뷰 산출물이며 harness 관례상 매 세션 새 타임스탬프 디렉터리에 뜨는 구조적 보일러플레이트(두 세션분 `_retry_state.json` 이 거의 동일한 구조인 것 등)다. 이 프로젝트의 review 산출물 저장 관례이지 이 작업이 짠 로직이 아니므로 유지보수성 관점 코드 리뷰 대상에서 제외.

## 발견사항

- **[INFO]** `.log()` 호출 결과를 담는 변수명 `log` 가 메서드명과 겹쳐 읽을 때 "로거"로 오독될 여지
  - 위치: `codebase/backend/test/entity-schema-declarations.e2e-spec.ts:552` (`let log: SqlInMemory;`, 555줄 `log = await readOnly.driver.createSchemaBuilder().log();`)
  - 상세: `SqlInMemory` 는 비교기가 기록한 DDL 묶음이지 로거가 아니다. 변수명이 직전 호출한 메서드 이름과 동일해 코드를 처음 보는 사람이 "무엇을 담은 값인지"를 파악하는 데 한 박자 걸린다. 파일의 다른 이름들(`FK_ACTION`, `UNDECLARED_COLUMNS`, `COLUMN_LEVEL`, `dataSourceOptions`)은 모두 내용을 설명하는 이름이라 이 변수만 상대적으로 불투명하다.
  - 제안: `sqlMemory` 또는 `schemaLog` 등 내용을 드러내는 이름으로 변경.

- **[INFO]** 새 테스트 하나가 서로 다른 성격의 검증 세 가지를 한 `it` 블록에 묶어 실패 시 원인 판별에 한 단계가 더 필요
  - 위치: `codebase/backend/test/entity-schema-declarations.e2e-spec.ts:527-569` (`it('컬럼 — TypeORM 스키마 비교기가 컬럼 정의 변경을 내지 않는다 (선언을 생략한 컬럼만 예외)', ...)`)
  - 상세: 이 테스트는 (1) 호출 전후 카탈로그 불변 확인(부작용 없음 탐지), (2) 컬럼 층 문이 예외 목록 밖에서 나오지 않는지, (3) 예외 목록이 낡지 않았는지(목록의 문이 실제로 나오는지) — 세 가지를 순서대로 단언한다. 각 단언 자체는 짧지만 테스트 하나의 실패 메시지만으로는 "어느 성격의 회귀인지"(부작용 발생 vs 새 컬럼 drift vs 예외 목록 stale)를 즉시 구분하기 어렵고, 주석(528-533줄)이 그 구조를 설명해야 할 만큼 테스트가 여러 역할을 겸한다.
  - 제안: 다만 `readOnly` `DataSource.initialize()` + `log()` 호출 자체가 비용이 있어 세 `it` 로 쪼개면 셋업을 반복하거나 `beforeAll` 레벨 상태 공유가 필요해진다는 트레이드오프가 있다 — 지금 구조가 "잘못"은 아니고, 실패 메시지에 어떤 `expect` 가 깨졌는지 jest 가 보여주므로 심각한 문제는 아니다. 진단 편의를 더 높이고 싶다면 `describe.each`/module-level 캐시로 `log()` 결과를 한 번만 계산해 세 `it` 로 분리하는 정도를 고려할 수 있다.

- **[INFO]** `COLUMN_LEVEL_SAMPLES.caught` 배열의 일부 항목이 길고 밀도 높은 리터럴 DDL 문자열(예: 86번째 줄 `CREATE TYPE ... AS ENUM(...)`)이라 한눈에 어떤 패턴을 검증하려는 표본인지 바로 대응이 안 됨
  - 위치: `codebase/backend/test/entity-schema-declarations.e2e-spec.ts:80-90` (`COLUMN_LEVEL_SAMPLES.caught` 배열)
  - 상세: 다섯 정규식(`COLUMN_LEVEL`, 63-69줄)과 아홉 개 표본 문자열이 순서·주석 없이 나열돼 있어, 어느 표본이 어느 정규식을 겨냥한 것인지는 코드를 두 번 오가며 대조해야 안다. 실측 채집값을 그대로 고정한다는 의도(72-75번째 줄 주석)는 명확하지만, 표본과 패턴의 대응 관계는 암묵적이다.
  - 제안: 배열 옆에 정규식 인덱스나 짧은 인라인 주석(`// ADD`, `// DROP COLUMN` 등)을 달면 향후 패턴이 늘거나 표본이 깨졌을 때 대응 관계를 더 빠르게 짚을 수 있다. 다만 526줄의 판별력 테스트가 "각 패턴이 최소 한 표본을 잡는다"를 이미 자동으로 검증하므로 실질적 위험은 낮다.

## 요약

이번 diff 는 엔티티 8개의 1~5줄짜리 속성 추가(각 파일의 기존 표기 관례를 그대로 따름)와, e2e 가드 파일 한 곳에 컬럼 층 검증 로직(상수 3개·함수 2개·테스트 2개, 약 130줄)을 추가한 것이 전부다. 새로 추가된 코드는 기존 파일의 네이밍 컨벤션(대문자 상수, `is*` 불리언 함수, 모듈 레벨 순수 헬퍼 vs `describe` 스코프 헬퍼 분리)을 그대로 따르고, 왜 이런 구조가 필요한지(읽기 전용 세션 이중 방어, 표본을 실측으로 고정한 이유, 예외 목록의 신선도 검증 이유)를 각 지점에 상세한 한국어 주석으로 남겨 의도가 매우 명확하다. 함수 길이·중첩 깊이·매직 넘버·중복은 모두 양호한 수준이며, 지적한 세 건은 전부 INFO 수준의 가독성 미세 개선 여지(변수명 하나, 테스트 응집도 하나, 표본-패턴 대응 표기 하나)로 병합을 막을 사유가 아니다.
