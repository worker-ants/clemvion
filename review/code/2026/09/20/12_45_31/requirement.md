# 요구사항(Requirement) 리뷰 — schedule-trigger e2e 「D. PATCH cron」 flake (3라운드 / 최종 상태)

## 컨텍스트

이번 라운드는 origin/main 대비 브랜치 전체 diff(1·2라운드 리뷰 산출물 포함)를 대상으로 한다. 실 코드 변경은
`codebase/backend/test/schedule-trigger.e2e-spec.ts` 「D. PATCH cron → nextRunAt 재계산」 한 케이스뿐이며,
`schedules.service.ts` 등 서비스 로직은 변경되지 않았다(직접 확인, `update()` 259~275행 — recompute 후 `save()` 로
실제 영속화까지 확인됨).

1·2라운드가 지적한 핵심 결함 — "옛 값(생성 cron 이 만드는 값)과의 비교는 형태가 무엇이든(«다르다»·«창 밖») 두 cron 의
다음 실행이 같아지는 순간에 거짓 실패한다" — 은 최종 커밋(`b40b5b98f`)에서 비교 자체를 통째로 제거해 해소됐다.
현재 코드(298~322행)는 `originalNext`/생성 cron 값과 어떤 비교도 하지 않고, 오직 "PATCH 시점부터 새 cron(`*/1 * * * *`)이
만드는 값인가"(1분 이내 + 초 자리 0)만으로 판정한다. 뮤턴트(서비스 재계산 블록 삭제) RED 재확인도 두 라운드 모두
거쳤다(`RESOLUTION.md` 기록). 연말 경계 등 두 cron 이 같아지는 어떤 순간에도 이 판정 방식 자체는 창을 만들지 않으므로,
1·2라운드가 발견한 결함 클래스는 구조적으로 재발하지 않는다 — Critical 없음.

## 발견사항

- **[WARNING]** plan 문서 「## 할 것」 항목 2가 이미 폐기된(2라운드에서 되돌린) 접근을 여전히 최종 지시로 서술한다 — 의도(plan) 와 구현 간 괴리.
  - 위치: `plan/in-progress/schedule-cron-flake.md:33-34` (「## 할 것」 2번 항목)
  - 상세: 해당 항목은 "PATCH 응답의 `nextRunAt` 이 요청 시점부터 1분 안이고 초 자리가 0이며, **생성 cron 의 값은 그 창 밖임을 함께 단언한다**" 고 적고 있다. 이는 1라운드에서 채택했던 접근(`originalNext`/생성 cron 값이 `patchedAt + 90_000` 밖임을 별도 단언)을 그대로 서술한 것인데, 바로 그 접근이 2라운드 리뷰에서 "형태만 다를 뿐 같은 종류의 연말 겹침 창(12/31 23:58:30~23:59:59.999 KST, ~90초/년)을 재도입한다"는 지적을 받아 최종 커밋 `b40b5b98f` 에서 **완전히 제거**됐다(`originalNext` 선언 포함). 최종 코드(`schedule-trigger.e2e-spec.ts:296-322`)는 생성 cron 값과의 비교를 전혀 하지 않는데, plan 의 이 지시 문장만 업데이트되지 않고 남아 이미 폐기된, 결함이 있던 접근을 재구현 지침처럼 보이게 한다. 같은 파일의 JSDoc(283~295행)과 인라인 주석(315~317행)은 "옛 값과 비교하지 않는다" 로 정확히 갱신됐고, 체크리스트("옛 «다르다» 단언 제거")도 1라운드 조치까지만 반영해 2라운드의 추가 제거를 언급하지 않는다 — 세 서술(JSDoc·주석·checklist) 중 「## 할 것」 절만 유일하게 최신 구현과 어긋난다. 2라운드 documentation 리뷰(`review/code/2026/09/20/12_17_18/documentation.md:24`)는 "본문이 diff 내용과 정확히 대응한다" 고 판단했지만, 이는 2라운드 diff(수정 전 상태) 기준 평가였고 `b40b5b98f` 적용 후 재검증되지 않았다.
  - 제안: 「## 할 것」 2번 항목의 "생성 cron 의 값은 그 창 밖임을 함께 단언한다" 절을 삭제하거나, "(1라운드 초안 — 2라운드에서 같은 결함 클래스 재발로 폐기, 최종 구현은 생성 cron 값과 비교하지 않는다)" 로 취소선/각주 처리해 다음 사람이 폐기된 접근을 다시 구현하지 않도록 한다.

- **[INFO]** spec fidelity — `spec/2-navigation/3-schedule.md`(§2.1, §4), `spec/5-system/4-execution-engine.md`, `spec/data-flow/10-triggers.md` 어디에도 PATCH 후 `nextRunAt` 재계산의 정확한 타이밍 허용 오차(1분 이내·초 자리 0 등)를 규정하는 문장이 없다 — "재계산이 일어난다" 는 원칙만 있고 세부 타이밍은 침묵한다. spec 위반이 아니라 회색지대이며, 1·2라운드 리뷰에서도 동일하게 결론 내린 항목으로 이번 라운드에서도 재확인만 한다.
  - 위치: `spec/2-navigation/3-schedule.md` §4 API 표 (PATCH 행)

## 뮤테이션 검증 관련

저장소 파일을 뮤테이션하지 않았다 — 기존 라운드의 뮤턴트 검증 결과(`RESOLUTION.md`, `plan/in-progress/schedule-cron-flake.md` 「## 테스트」)를 근거로 코드·서비스 로직만 정독해 재확인했다. `git status --short` 로 저장소가 조사 시작 시점과 동일함을 확인함(untracked 는 본 세션 산출물 디렉터리뿐).

## 요약

실 코드(e2e 테스트 1케이스)는 1·2라운드가 지적한 "두 cron 이 같은 시각을 가리키는 순간의 거짓 실패" 결함 클래스를 최종적으로 (생성 cron 값과의 비교를 완전히 제거하는 방식으로) 구조적으로 해소했고, 서비스 로직·비즈니스 규칙(cron/timezone 변경 시 재계산, DB 영속화까지)과도 일치하며 뮤턴트 검증으로 판별력이 확인됐다. 다만 plan 문서의 「## 할 것」 지시가 2라운드에서 폐기된 접근을 그대로 남겨 두어, 구현(코드)과 계획(plan) 서술이 어긋난다 — 기능적 결함은 아니지만 다음 작업자를 잘못된 방향(이미 결함 있는 것으로 판명된 접근)으로 이끌 수 있는 문서 정합성 문제다. Critical 없음.
