# 테스트(Testing) 리뷰

## 발견사항

- **[CRITICAL]** 신설된 §5.4 금지-조합 래칫 가드의 "positive control" 테스트가 **존재하지 않는 픽스처 파일**을 참조하며, 그 결과 실제로는 아무것도 검증하지 않는데도 항상 GREEN이다.
  - 위치: `codebase/backend/src/repo-guards/__tests__/swagger-dto-contract.spec.ts:467-475` (`it('[대조군] 술어가 실제로 그 조합을 집는다', ...)` — `path.join(__dirname, 'optional-nullable-ratchet-fixture.ts')`)
  - 상세: 이 테스트가 참조하는 `codebase/backend/src/repo-guards/__tests__/optional-nullable-ratchet-fixture.ts` 파일은 저장소에 **존재하지 않는다**(`find`/`git diff --stat` 로 확인 — 이번 diff 는 `swagger-dto-contract-guard.ts`/`swagger-dto-contract.spec.ts` 두 파일만 바꿨고 새 픽스처 파일은 추가되지 않았다). `findOptionalNullableResponseFields()` 는 `if (!isResponseDtoFile(file)) continue;` 를 파일을 열기(`fs.readFileSync`) **전에** 먼저 평가하는데, 이 픽스처 경로(`.../__tests__/optional-nullable-ratchet-fixture.ts`)는 `/dto/responses/` 를 포함하지 않으므로 이 시점에서 곧바로 `continue` 된다 — 즉 파일이 없어도 `ENOENT` 조차 던지지 않고 조용히 스킵된다. 실제로 `npx jest ... -t "술어가 실제로 그 조합을 집는다"` 를 돌려 확인했다 — **1 passed**(파일이 없는데도 그린). 테스트 이름과 인접 주석은 "픽스처 경로가 dto/responses 를 포함하지 않아 스킵된다 — 그것 자체가 응답-DTO 한정 판정의 증거" 라고 스스로 설명하고 있어, 사실상 이 테스트는 바로 위 `it('[대조군] 요청 DTO 는 대상이 아니다 ...')` 와 **똑같은 것**(경로 필터링)만 재확인할 뿐, 테스트 이름이 약속하는 "술어가 실제로 (문법적으로) 그 조합을 집어내는가" 는 전혀 검증하지 않는다. `findOptionalNullableResponseFields` 의 핵심 판정 로직(`effectiveRequired`/`nullable` 조합 감지) 자체는 `EXPECTED_OPTIONAL_NULLABLE_DRIFT` 목록과 실제 78개 응답 DTO 전수 대조 테스트(같은 파일 458행 부근)로 간접 검증되긴 하지만, 그 목록이 잘못 편집되거나(예: 오프너를 몰래 목록에서만 빼는 방식으로 회귀) 판정 함수 자체가 깨지는 것을 잡아 줄 **격리된 unit-level positive control 은 이 저장소에 없다** — 이번에 추가하려 한 시도가 이 형태로 무효화됐다.
  - 제안: `optional-nullable-ratchet-fixture.ts` 를 `dto/responses/` 를 실제로 포함하는 경로(예: `__tests__/fixtures/dto/responses/optional-nullable-fixture.dto.ts`)에 생성하고, `@ApiPropertyOptional({ nullable: true })` + `field?: T | null` 조합 필드 최소 1개를 넣어, `found` 가 정확히 그 필드를 담은 배열이 되는지(빈 배열이 아님을) 단언하도록 고칠 것. 지금 상태로는 이 테스트를 삭제해도 안전성에 아무 변화가 없다(그 자체가 vacuous 하다는 증거).

- **[WARNING]** `Schedule.trigger` 가 **완전히 생략되는 분기**(키 자체가 없는 응답)가 어떤 테스트에도 도달하지 않는다.
  - 위치: `codebase/backend/src/modules/schedules/schedules.controller.ts:67-83` (`private toResponse<T extends Schedule>(schedule: T)` — `return t ? {...} : rest;` 의 `: rest` 분기). 정합 확인: `codebase/backend/src/modules/schedules/entities/schedule.entity.ts` 의 `triggerId`(non-nullable FK)로 보아 DB 상 스케줄은 항상 트리거를 갖지만, `codebase/backend/src/modules/schedules/schedules.service.ts` 의 `create()` 는 `isActive` 가 false 일 때만 `saved.trigger = savedTrigger;` 를 **건너뛴다**(해당 대입이 `if (isActive) { ... }` 블록 안에만 있음) — 즉 `POST /api/schedules`(`isActive:false`)에서 `schedule.trigger` 가 undefined 로 남아 `toResponse` 의 `rest`(트리거 키 생략) 분기가 실제로 실행되는 유일한 재현 경로다.
  - 상세: `ScheduleDto.trigger?: ScheduleTriggerRefDto`(`schedule-response.dto.ts:90-91`, `@ApiPropertyOptional`)는 §5.4 상 "키 생략형"이고, JSDoc·컨트롤러 주석 모두 "조회 경로에 따라 없을 수 있다"고 명시한다. 그런데 `codebase/backend/test/schedule-trigger.e2e-spec.ts` 를 전수 확인한 결과 `isActive: false` 로 스케줄을 **생성**하는 테스트가 없다(`grep -n "isActive: false"` → G/H 케이스뿐이고, 둘 다 트리거 쪽 PATCH 로 기존 활성 스케줄을 비활성화하는 시나리오라 `schedule.trigger` 가 이미 채워진 이후의 update 경로다). 즉 "키가 아예 없어야 한다"는 계약의 절반(present 케이스는 test C 가 `Object.keys(...).sort()` 로 양성 고정)만 고정돼 있고, 나머지 절반(absent 케이스)은 회귀 방지 장치가 없다 — 누군가 `: rest` 를 `: { ...rest, trigger: null }` 로 바꿔도(§5.4 가 명시적으로 금지하는 "키 생략형에 null" 형태) 어떤 테스트도 실패하지 않는다.
  - 제안: `POST /api/schedules` 를 `isActive: false` 로 호출하는 케이스를 추가하고, 응답에 `trigger` **키 자체가 없음**(`expect(res.body.data).not.toHaveProperty('trigger')` 또는 `expect('trigger' in res.body.data).toBe(false)`)을 양성으로 단언할 것 — `null` 이 아니라 키 생략임을 구분하는 단언이어야 한다(`toBeUndefined()` 만으로는 `{trigger: undefined}` 와 키 생략을 구분 못 함).

- **[WARNING]** `sanitizeForResponse` 가 새로 지우는 `config.notification.signing` 두 키(`secretRef`, `secret`) 중, 회귀 테스트는 `secretRef` 만 실제로 입력에 채우고 `secret` 은 채우지 않은 채로 두 키 모두에 대해 `not.toHaveProperty` 를 단언한다 — `secret` 쪽 단언은 **입력에 그 키가 아예 없으므로 vacuous 하게 항상 참**이다.
  - 위치: `codebase/backend/src/modules/triggers/triggers.service.spec.ts:196-229` — 픽스처(`:207-210`, `signing: { secretRef: '...' }` 만 있고 `secret` 없음)와 단언(`:224` `not.toHaveProperty('secretRef')`, `:225` `not.toHaveProperty('secret')`).
  - 상세: 프로덕션 코드(`triggers.service.ts` 의 `NOTIFICATION_SIGNING_STRIP_KEYS = new Set(['secret', 'secretRef'])`, `sanitizeForResponse` 안 `for (const [key, value] of Object.entries(signing)) { if (NOTIFICATION_SIGNING_STRIP_KEYS.has(key)) continue; ... }`)는 순수하게 **입력 객체에 존재하는 키**만 순회해서 걸러낸다. 픽스처에 `secret` 키가 없으므로 이 스트립 로직은 그 키에 대해서는 애초에 아무 것도 안 지운 것과 같고, `expect(signing).not.toHaveProperty('secret')` 는 스트립 로직의 정확성과 무관하게 항상 통과한다. 예컨대 `NOTIFICATION_SIGNING_STRIP_KEYS` 에서 `'secret'` 을 실수로 빼는 뮤턴트를 넣어도 이 테스트는 여전히 GREEN 이다 — "정규화 전 평문이 스쳐 가는 자리"(코드 주석이 스스로 명시하는, 레거시 row 등 정규화를 우회한 평문이 남아 있는 방어적 케이스)를 실제로 방어하는지는 이 회귀로 전혀 확인되지 않는다. 이 필드는 `outbound notification` 서명에 쓰이는 secret 이라 §5.4 스윕이 이번에 고친 것과 같은 등급의 민감 정보다.
  - 제안: 픽스처에 `signing: { secretRef: '...', secret: 'plaintext-should-be-stripped' }` 처럼 두 키를 모두 채우고, 두 단언 모두 실제로 입력에 있던 값이 사라졌는지 검증하도록 고칠 것.

- **[WARNING]** `SchedulesController.update`(`PATCH /api/schedules/:id`)도 이번 PR 에서 새로 `toResponse()` 를 타도록 배선됐지만, 그 응답에 대해서는 계약 대조도 형태 단언도 없다 — 4개 배선 지점(`findAll`/`findOne`/`create`/`update`) 중 **`update` 만 미검증**이다.

  - 상세: `findAll`/`findOne`/`create` 세 경로는 이번 diff(`schedule-trigger.e2e-spec.ts` test C, 실측 gate 136·144·160)에서 `assertMatchesContract(..., ScheduleDto)` 로 새로 덮였지만, `update` 는 이번 diff 가 손댄 4번째 배선 지점인데도 어떤 e2e 도 그 응답 바디에 계약 대조나 `trigger` 키 형태 단언을 하지 않는다. `toResponse` 가 공유 헬퍼라 로직 자체가 findOne 등에서 이미 검증된다는 점에서 위험도는 낮지만, `update()` 서비스 경로는 `saved.trigger = trigger ?? schedule.trigger;` 처럼 findOne 과 다른 대입 로직을 갖고 있어(코드 경로 자체가 다르다), 공유 헬퍼 재사용만으로 "이 경로도 안전하다" 를 자동으로 보장하지 않는다.

## 요약

이번 diff 는 §5.4 응답-계약 스윕을 14→27개(e2e 신규 배선 포함) 자리로 넓히면서, 직전 라운드 리뷰가 지적한 두 개의 실질 갭(트리거 시크릿 유출에 대한 unit 회귀 부재, `GET /api/schedules/:id` 무테스트)을 정확히 메웠고 뮤턴트로 재확인까지 남겼다는 점에서 전반적인 테스트 태도는 견고하다. `allowMissing`/`contractForDto` 메모이제이션 신설 코드에도 각각 대응하는 단위 테스트가 붙어 회귀 안전망을 갖췄다. 다만 이번에 **새로 추가된** 테스트 중 하나(§5.4 금지-조합 래칫의 positive-control 유닛 테스트)는 존재하지 않는 픽스처 파일을 참조해 실질적으로 아무것도 검증하지 못하는 vacuous 테스트였고(실행으로 확인), 이는 이 저장소가 반복적으로 겪어 온 "GREEN 이 증거가 아니다" 패턴의 재발이다. 그 외에 `Schedule.trigger` 완전 생략(키 부재) 분기, `notification.signing.secret` 평문 스트립, `PATCH /api/schedules/:id` 응답 계약 세 자리가 새로 도입된 코드 경로임에도 회귀 테스트 사각지대로 남아 있다.
