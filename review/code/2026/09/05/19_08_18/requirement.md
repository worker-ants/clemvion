# 요구사항(Requirement) 리뷰

## 발견사항

- **[WARNING]** `swagger-dto-contract.spec.ts` 의 "술어가 실제로 그 조합을 집는다" 대조군 테스트가 존재하지 않는 fixture 를 참조하며, 이름이 주장하는 것과 반대되는 경로를 검증한다.
  - 위치: `codebase/backend/src/repo-guards/__tests__/swagger-dto-contract.spec.ts:467-476` (`it('[대조군] 술어가 실제로 그 조합을 집는다', ...)`, `path.join(__dirname, 'optional-nullable-ratchet-fixture.ts')`)
  - 상세: 이 테스트가 참조하는 `codebase/backend/src/repo-guards/__tests__/optional-nullable-ratchet-fixture.ts` 는 저장소 어디에도 존재하지 않는다(`find`/`grep -rn` 로 실측 확인 — 참조는 이 한 줄뿐). 그런데 테스트는 실패하지 않는다: `findOptionalNullableResponseFields()` 는 `isResponseDtoFile(file)` 검사를 **`fs.readFileSync` 보다 먼저** 수행하고(`swagger-dto-contract-guard.ts` 의 `for (const file of files) { if (!isResponseDtoFile(file)) continue; ... fs.readFileSync(file, ...) }`), 이 fixture 경로(`__tests__/optional-nullable-ratchet-fixture.ts`)는 `/dto/responses/` 를 포함하지 않으므로 파일을 열어보기도 전에 `continue` 된다. 즉 `expect(found).toEqual([])` 는 **파일이 없어서** 도 아니고 **금지 조합을 못 찾아서** 도 아니라, `isResponseDtoFile` 이 그 경로 자체를 스킵하기 때문에 항상 통과한다 — 테스트 자신의 주석("픽스처 경로가 `dto/responses/` 를 포함하지 않으므로 스킵된다")이 이를 스스로 인정하면서도, 그 사실이 테스트 **이름**("술어가 실제로 그 조합을 집는다")과 정반대라는 점은 짚지 않는다. 이 이름이 약속하는 것 — "`@ApiPropertyOptional({nullable:true})` + `field?: T | null` 조합을 담은 실제 응답 DTO 파일을 술어에 먹였을 때 그 필드를 실제로 검출한다" — 은 이 테스트가 검증하지 않는다. (바로 위 "알려진 목록과 정확히 일치한다" 테스트가 프로덕션 코드 78건을 통해 간접적으로 탐지 능력을 담보하긴 하지만, 그것은 이 "[대조군]" 테스트의 존재 이유와 무관하다 — 이름이 명시적으로 "술어 자체"의 양성 탐지를 약속하고 있다.)
  - 제안: (a) 실제로 `dto/responses/` 아래에 금지 조합 필드를 가진 fixture 파일을 만들어 `findOptionalNullableResponseFields([fixture], SRC_ROOT)` 가 그 필드를 `key` 로 정확히 지목하는지 단언하거나, (b) 지금처럼 "응답-DTO 스코프 밖은 스킵된다"만 확인하고 싶다면 테스트 이름을 그 사실에 맞게(`'응답 DTO 스코프 밖 파일은 스킵한다'` 등) 바꿀 것. 현재 이름과 구현이 어긋나 있어, 다음에 `findOptionalNullableResponseFields`/`isResponseDtoFile` 를 리팩터링하는 사람이 "이 테스트가 통과하니 탐지 로직은 안전하다"고 오판할 위험이 있다.

- **[WARNING]** `POST /api/schedules` 에 `isActive: false` 를 명시하면, 이번 PR 이 도입한 `ScheduleDto.trigger`(참조 4필드) 가 **응답에서 통째로 빠진다** — 트리거 행은 실제로 생성·연결됐는데도.
  - 위치: `codebase/backend/src/modules/schedules/schedules.controller.ts:67-83` (`toResponse` — `t = schedule.trigger` 가 falsy 면 `trigger` 키 자체를 생략), 원인은 `codebase/backend/src/modules/schedules/schedules.service.ts:159-205` (`create()` — `saved.trigger = savedTrigger` 대입이 `if (isActive) { ... }` 블록 **안에서만** 일어난다. `isActive` 가 `false` 면 `scheduleRepository.create({...})` 가 애초에 `trigger` 속성을 설정하지 않으므로 `saved.trigger` 는 `undefined` 로 남는다)
  - 상세: `schedules.service.ts` 는 이 diff 범위 밖(git log 로 최근 변경 없음 확인)이라 이 데이터 공백 자체는 기존 결함이지만, 그것을 **응답 계약의 공식 필드**로 노출·문서화한 것은 이번 PR 이다 — `toResponse()` 는 `t`(=`schedule.trigger`) 의 진위만으로 "키 생략" 여부를 정하는데, 이 값이 비는 이유가 §5.4 가 말하는 "조회 경로에 따라 다르다"(GET vs POST 같은 엔드포인트 성격 차이)가 아니라 **같은 POST 엔드포인트 안에서 요청 바디의 `isActive` 값에 따라** 갈린다. `CreateScheduleDto.isActive` 는 공개 optional 필드(기본 `true`)라 이 경로는 실제로 도달 가능하다. `schedule-trigger.e2e-spec.ts` 의 신규 계약 단언(`assertMatchesContract` + `Object.keys(trigger).sort()` 양성 단언)은 전부 기본값(`isActive` 미지정 → true) 경로만 때리므로 이 조합은 이번 PR 의 신규 테스트로도 회귀 방지되지 않는다. 다행히 프런트엔드는 생성 성공 시 `queryClient.invalidateQueries({queryKey:['schedules']})` 로 재조회하고 create 응답을 직접 렌더링하지 않으므로(실측: `schedules/page.tsx` mutation 핸들러) 알려진 소비처엔 영향이 없지만, 문서화된 계약("trigger 는 참조 4필드, 조회 경로에 따라 없을 수 있다")과 실제 원인이 어긋나 있고 향후 다른 소비처(제3자 API 클라이언트·낙관적 UI)가 "POST 직후 응답에는 방금 만든 trigger 참조가 있다"고 가정하면 깨진다.
  - 제안: `SchedulesService.create()` 에서 `isActive` 값과 무관하게 `saved.trigger = savedTrigger`(+ 필요 시 `workflow`)를 대입해 응답 관점에서 GET/POST 가 일관되게 트리거를 포함하도록 정정하거나, 정 지금 형태를 유지한다면 `isActive: false` 로 생성하는 e2e 케이스를 추가해 "trigger 키 생략"이 의도된 것임을 회귀 테스트로 고정할 것.

## 요약

이 PR 의 핵심 목적(§5.4 응답-계약 검증자를 14개 엔드포인트로 배선하고, 그 과정에서 실측으로 드러난 트리거 회전 secret 이중 유출을 응답 경계에서 차단하며, 24개 DTO 필드 선언을 실제 wire 에 맞추는 것)은 코드로 정확히 구현돼 있다. 직접 확인한 결과: `TriggersService.sanitizeForResponse` 는 JSONB 키(`config.chatChannel`, `config.notification.signing`)와 엔티티 컬럼(`notificationSecretV2`/`chatChannelTokenV2`) 두 축을 조기 return 없이 모두 덮고(이전 라운드 W1/W3 수정이 반영돼 있음을 소스에서 직접 확인), `SchedulesController.toResponse`/`ScheduleTriggerRefDto` 는 조인을 타고 새던 Trigger 엔티티 전체 노출을 참조 4필드로 정확히 좁힌다. 이전 라운드의 consistency-check Critical(§5.4 응답 바디 금지 조합 `@ApiPropertyOptional({nullable:true})`+`T|null` 재도입)도 `TriggerDto`/`IntegrationDto`/`KnowledgeBaseDto`/`AlertRuleDto`/`ScheduleDto` 전부에서 spec §5.4 표(190~213행)와 line-level 로 일치하는 형태(`@ApiProperty({nullable:true})`+`T|null` 또는 순수 키 생략형)로 정정돼 있음을 spec 원문과 대조해 확인했다. `response-contract.ts` 의 `allowMissing` 옵션은 경로 매칭이 정확하고 `ExportWorkflowDto.formatVersion` 인용도 `spec/2-navigation/1-workflow-list.md:153` 의 실제 Planned 문구와 일치한다. 다만 두 가지 흠을 확인했다 — (1) 이번 PR 이 신설한 §5.4 금지-조합 래칫 가드의 "대조군" 테스트가 존재하지 않는 fixture 를 가리키며 이름이 약속하는 양성 탐지 검증을 실제로는 하지 않는 vacuous 테스트이고, (2) 새로 도입한 `ScheduleDto.trigger` 참조 필드가 `POST /api/schedules`(`isActive:false`) 경로에서 (기존 서비스 코드의 데이터 공백 때문에) 의도와 다른 이유로 키 생략되는 엣지 케이스가 이번 PR 의 신규 e2e 로도 방지되지 않는다. 둘 다 보안·계약 위반은 아니며(테스트는 여전히 GREEN, 필드는 여전히 optional 이라 계약 위반 아님) 기능적 회귀는 아니지만, 각각 "테스트가 검증한다고 주장하는 것"과 "새로 공식화한 필드가 실제로 일관되게 채워지는 조건" 사이의 괴리라 WARNING 으로 기록한다.
