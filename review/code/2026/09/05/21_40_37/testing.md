- **[WARNING]** `contractForDto` 캐시의 격리 범위에 대한 설계 근거("Jest worker 마다 모듈 레지스트리가 갈리므로 캐시도 worker 단위로 격리된다")를 실측으로 재현해 보니 **틀렸다** — 실제로는 파일 단위로 격리된다.

  - 상세: 저장소 밖 scratch 디렉터리에 `jest-e2e.json` 과 동일 설정(`maxWorkers: 1`, `testEnvironment: 'node'`, `ts-jest`)의 독립 jest 프로젝트를 만들고, 모듈 스코프 `Map` 카운터를 두 개 e2e-spec 파일에서 공유 import 해 `bump('x')` 를 호출하도록 구성해 `codebase/backend` 의 실제 jest 바이너리로 실행했다(저장소 파일은 건드리지 않음 — scratch 안에서만 작성·실행). 결과: 두 파일 모두 `1` 을 출력했다(`FILE_A_VALUE=1`, `FILE_B_VALUE=1`) — 두 번째 파일이 `2` 를 봤다면 worker 단위 공유가 맞겠지만, 둘 다 `1` 이라는 것은 **Jest 가 `maxWorkers:1` 이어도 테스트 파일마다 모듈 레지스트리를 새로 만든다**(파일 단위 격리, 워커 단위 아님)는 뜻이다. 즉 `contractForDto` 캐시는 **같은 파일 안에서 같은 DTO 를 여러 번 부를 때만** 재사용되고, 서로 다른 e2e-spec 파일이 같은 DTO(예: 여러 파일이 각각 `ScheduleDto`/`TriggerDto` 를 참조)를 부르면 매번 새로 부트스트랩한다 — JSDoc 이 내세우는 "호출부가 매번 반복해야 하는 보일러플레이트 회피" 혜택은 **파일 간에는 발생하지 않는다**. 기능 자체(캐시가 파일 내에서 올바르게 동작하는지)는 `response-contract.spec.ts` 의 신규 `describe('contractForDto 메모이제이션', ...)` 가 잘 잠그고 있어 버그는 아니지만, 근거 서술이 실측과 어긋나 있고 그 서술을 검증하는 테스트도 없다(파일 단위 vs 워커 단위 격리를 구분하는 테스트는 이 diff 에 없다) — 이 저장소가 반복해서 지적해 온 "설계 근거는 쓰기 전에 반증해 보라" 패턴의 재발이다.

## 요약

이 PR 은 §5.4 응답-계약 검증자를 14→18개 DTO 로 넓히면서 실측으로 드러난 트리거 회전 secret 유출(엔티티 컬럼 미스트립 + 스케줄 조인 2차 유출)을 서비스·컨트롤러 경계에서 고쳤다. 이미 3라운드의 자체 리뷰를 거치며 unit 회귀(비밀 fixture + 뮤턴트 검증), 스케줄 쪽 e2e 계약 대조(생성·조회·목록·PATCH·isActive 변형), 래칫 가드의 자기-vacuity 정정(존재하지 않는 fixture 참조 → 실제 양성/대조군 fixture) 등 이례적으로 성숙한 테스트 태도를 보였다. 다만 이번 라운드에서 좁혀 보니 대칭이 다시 한 번 깨지는 지점을 찾았다 — 스케줄 쪽(`ScheduleDto`)은 계약 대조가 촘촘한데, CHANGELOG 가 **똑같이** 유출 경로로 지목한 트리거 쪽(`TriggerDto`)은 `POST` 생성의 단일 케이스에만 배선돼 있고 `GET /api/triggers`(목록)·`PATCH /api/triggers/:id` 는 wire 레벨 검증이 전혀 없다. 근본 스트립 로직(`sanitizeForResponse`)은 unit 이 잘 지키므로 실질 유출 위험은 낮지만, 이 PR 자신의 목적(계약을 실제 HTTP 응답으로 대조)이 정작 자신이 고친 보안 결함의 절반(트리거 쪽 목록/PATCH)에는 적용되지 않은 비대칭이다. 아울러 새 `contractForDto` 캐시의 격리 범위 주장("worker 단위")을 scratch 환경에서 실측했더니 실제로는 파일 단위였다 — 동작 결함은 아니지만 문서 정확성 이슈이자 이 저장소가 여러 차례 지적해 온 "근거는 검증 없이 쓰지 말라" 패턴의 재발이다.
