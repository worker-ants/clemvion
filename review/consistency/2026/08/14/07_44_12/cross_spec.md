### 발견사항

- **[WARNING]** `Execution.error` 의 `nodeId` nullable 계약이 `spec/1-data-model.md` 에는 반영되지 않았다 — 이번 작업(종결 payload 정리)이 정확히 이 컬럼에 쓰기 시작하는 지점
  - target 위치: `spec/5-system/14-external-interaction-api.md` §6 "종결 이벤트의 필드 집합" (`error` 행, "목표는 `{code, message, nodeId, details?}`") + §6.4 `execution.failed` payload 예시 (`"nodeId": "uuid" | null`)
  - 충돌 대상: `spec/1-data-model.md` §2.14 NodeExecution 절 말미 "Execution.error ↔ NodeExecution.error 관계" 표의 "구조" 행 — `{ nodeId: "uuid", code: "ERROR_CODE", message: "에러 설명" }` (null 변형 없음, `details` 미언급). 같은 문서 §2.13 Execution 의 `error` 필드 설명(엔진 인프라 코드 `SERVER_INTERRUPTED`/`WORKER_HEARTBEAT_TIMEOUT`/`EXECUTION_TIME_LIMIT_EXCEEDED`/`RESUME_*` 목록)과, `spec/5-system/4-execution-engine.md` §7.1 (`onFailed → finalizeStalledExhausted` 가 `error.code='WORKER_HEARTBEAT_TIMEOUT'` 를 세팅하는 경로 — 이 경로는 특정 실패 노드가 없어 "최초 failed NodeExecution 의 에러 정보를 복사" 메커니즘을 타지 않는다)
  - 상세: `spec/1-data-model.md` 의 "구조" 행은 "워크플로우 실행이 `failed` 상태로 전이될 때, **최초 failed NodeExecution** 의 에러 정보를 복사" 하는 경로 한정으로 `nodeId` 를 항상 존재하는 UUID 로 문서화한다. 그런데 EIA §6.4 는 `nodeId: "uuid" | null` 로 명시적으로 null 변형을 이미 허용하며, `spec/conventions/chat-channel-adapter.md:150` 의 `EiaEvent` 유니언도 `nodeId: string | null` 로 동일하게 타입화했다. 이번 plan(`eia-terminal-payload.md`)이 채우려는 4개 emit 지점 중 하나(`execution-engine.service.ts:3301`, stalled-job 재배달 attempts 소진)는 계획서 자신도 "노드가 아예 없다" 고 적었다 — 즉 정확히 data-model.md 의 "구조" 행이 문서화하지 못한 non-null 전제가 깨지는 지점이다. `SERVER_INTERRUPTED`/`EXECUTION_TIME_LIMIT_EXCEEDED`/`RESUME_*` 등 다른 "엔진 인프라 차원의 코드"도 NodeExecution-copy 경로를 타지 않으므로 같은 사각지대에 있다. 요컨대 EIA 쪽 계약(target)은 이미 nullable 로 정합되어 있는데, 데이터 모델 쪽 문서만 뒤처져 있다.
  - 제안: `spec/1-data-model.md` §2.14 의 "구조" 행을 `{ nodeId: "uuid" | null, code: "ERROR_CODE", message: "에러 설명", details?: {...} }` 로 갱신하고, "복사" 설명을 "최초 failed NodeExecution 이 있는 경우 그 정보를 복사, 없는 경우(엔진 인프라 레벨 실패) `nodeId: null`" 로 넓힐 것. 이는 developer(구현자) 권한 밖(spec 변경)이므로 planner 위임 필요 — `eia-terminal-payload.md` 의 "nodeId 처분(planner 위임)" 항목에 이 구체 파일·행을 추가해 반영 권고.

- **[INFO]** (참고, 발견사항 아님 — 확인 결과 문제 없음) `durationMs`(EIA) ↔ `duration`(WS/3-execution 계열) 표기 차이, §6 SoT 포인터 원칙(3-execution.md §8.1 / chat-channel-adapter.md §1.2 의 `EiaEvent` union), `result.outputs` 소스(`Execution.output_data`), `Idempotency-Key` 캐시 키 스코프(`interaction:idempotency:<executionId>:<route>:<key>`)는 모두 `spec/data-flow/15-external-interaction.md`, `spec/conventions/redis-keys.md`, `spec/5-system/6-websocket-protocol.md:205`, `spec/3-workflow-editor/3-execution.md:283-287` 와 정확히 일치함을 직접 대조로 확인했다. `plan/in-progress/eia-terminal-payload.md` 가 언급한 "outbound 계약 위반 아님(#1166 이 이미 Planned 로 표시)" 판단도 target §6 실물과 일치한다.

### 요약
이번 검토 대상은 `spec/5-system/14-external-interaction-api.md` §6(종결 이벤트 payload) 정리 작업의 impl-prep 이다. §6 SoT 원칙(단일 소유 + 타 문서 포인터화)은 최근 커밋(#1166)으로 이미 `3-execution.md §8.1`·`chat-channel-adapter.md`·`data-flow/15-external-interaction.md` 전반에 잘 반영돼 있어 새 모순은 없었다. 다만 이번에 실제로 채워 넣을 `error` 객체의 `nodeId` 필드는 EIA 자신(§6.4)과 `chat-channel-adapter.md` 는 이미 `nodeId: string | null` 로 nullable 계약을 확립한 반면, 그 값의 저장처인 `spec/1-data-model.md` 의 `Execution.error` 구조 문서는 여전히 `nodeId` 를 항상 존재하는 UUID 로만 기술하고 있어 — 노드가 아예 없는 엔진 인프라 실패 경로(이번 plan 이 채우려는 지점 중 하나)를 커버하지 못한다. 그 외 범위(요구사항 ID·상태 전이·RBAC·계층 책임)에서는 이번 변경과 충돌하는 사항을 찾지 못했다.
