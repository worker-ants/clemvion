# Rationale 연속성 검토 — Personal 통합 소유자 강제 (--impl-prep)

## 발견사항

- **[WARNING] Personal 소유자 판정을 컨트롤러별 수동 호출로 배치 — 이 코드베이스가 두 번 겪은 "opt-in 누락" 패턴과 형태가 같다**
  - target 위치: `plan/in-progress/integration-personal-owner.md` `## 설계` — "컨트롤러 — 해당 핸들러에 `@CurrentUser()` · `resolveRole` 를 붙여 서비스로 넘긴다."
  - 과거 결정 출처: `spec/data-flow/12-workspace.md` Rationale "멤버십 검증은 가드 1곳에서 — `@Roles()` 와 무관 (2026-08-08)" 의 **기각된 대안** — "73개 라우트에 `@Roles('viewer')` 부착" (사유: "opt-in 모델의 연장이라 74번째 라우트에서 같은 누락이 재발한다(이미 최소 2회 발생)"). 같은 문서의 "경로 파라미터 워크스페이스도 가드가 본다 (2026-09-25)" 항목이 **또 다른 15개 라우트**에서 정확히 같은 구멍(서비스 계층 `assertMembership`/`assertAdmin` 에만 의존, 가드 미적용)이 재발했음을 기록한다.
  - 상세: 이번 plan 은 남의 personal 통합 은닉·Organization 변경 Admin 강제를 `IntegrationsController`(그리고 `integration-oauth.service.ts` 의 `oauth/begin`)의 **각 핸들러가 개별적으로 `requireVisible`/`assertCanModify`/`requireModifiable` 를 호출**하는 형태로 구현한다. 요구 목록 자체가 이미 10개 이상의 개별 경로(`:id` 상세·사용처·활동·연결테스트·별칭수정·삭제·rotate·reauthorize·request-scopes·scope전환·`oauth/begin` 의 두 모드)를 손으로 열거하고 있다 — 이는 과거 기각된 "라우트마다 수동으로 붙인다" 모델과 구조적으로 동일하고, 이 프로젝트가 그 모델을 **두 차례** 겪은 뒤 "가드에서 무조건 수행" + "부트 캐너리(`assertWorkspaceIdReflectionWorks`)로 fail-closed" 로 옮겨간 것과 반대 방향이다. 이 도메인은 role/membership 이 아니라 row 단위 `created_by` 비교라 범용 `RolesGuard` 로 표현할 수는 없지만(그 점에서 `WorkspacesService.assertAdmin()` 과 같은 "서비스 계층 2차 방어선" 유으로 정당화는 되지만), 이번 plan 의 검증 계획("뮤턴트 — 각 경로의 판정 제거가 테스트에 잡히는지")은 **이미 배선된 호출이 제거되는 회귀**만 잡을 뿐, "새 `:id` 경로/새 통합 관련 핸들러가 추가됐는데 판정을 안 붙였다" 는 **정확히 재발했던 그 실패 모드**는 구조적으로 잡지 못한다.
  - 제안: `spec-draft-integration-personal-owner.md`/`integration-personal-owner.md` 에 완결성 안전망을 명시한다 — 예를 들어 (a) `IntegrationsController`·`IntegrationOAuthService` 의 `:id` 또는 `integrationId` 를 소비하는 핸들러 전수를 열거하고 각각이 공유 판정 함수를 거치는지 검증하는 전수 테스트(부트 캐너리 또는 static reflection 캐너리, `assertWorkspaceIdReflectionWorks` 선례와 같은 형태), 또는 (b) 인터셉터/데코레이터로 판정을 강제해 새 핸들러 추가 시 fail-closed 되도록 하는 설계로 전환. 최소한 plan 체크리스트에 "신규 `:id` 경로 추가 시 이 판정이 자동으로 걸리는가" 를 명시적 완료 조건으로 추가.

- **[WARNING] `spec/3-workflow-editor/4-ai-assistant.md` 의 candidate-lookup 계약("워크스페이스 스코프로 쿼리")을 좁히면서 그 문서의 Rationale·spec_impact 를 갱신하지 않는다**
  - target 위치: `plan/in-progress/integration-personal-owner.md` §요구 1 — "워크플로우 어시스턴트 — `list_integrations` 도구 · 노드 후보(integration-selector · mcp-server-selector)"; frontmatter `spec_impact`(두 plan 모두) 는 `spec/2-navigation/4-integration.md` 하나뿐.
  - 과거 결정 출처: `spec/3-workflow-editor/4-ai-assistant.md` Rationale "Workflow Assistant — Candidate Picker 정책 결정 (ED-AI-39)" §"구현자가 기억해야 할 계약" 1번 — "`collectPendingUserConfig` 는 ... widget 별 저장소(integrationRepo …) 를 **워크스페이스 스코프로 쿼리**해 `candidates` 를 채운다." 같은 문서 §4.3.1 표(라인 371-372)도 `integration-selector`/`mcp-server-selector` 의 판정 조건을 "`workspace_id` 일치 + `status='connected'`" 로만 명시하고, §4.1 표(라인 201)도 `list_integrations` 를 "현재 워크스페이스에 등록된 Integration 목록" 으로 적는다 — 셋 다 personal 소유자 축을 언급하지 않는다.
  - 상세: 실제 구현 대상 코드(`codebase/backend/src/modules/workflow-assistant/tools/candidate-lookup.service.ts`)는 `this.integrations.findAll(workspaceId, query)` 를 그대로 호출하므로, `IntegrationsService.findAll` 에 owner 가시성 절을 추가하면 이 도구의 후보 목록도 자동으로 좁아진다 — 즉 코드 변경이 `ai-assistant.md` 가 명시적으로 서술한 필터 계약을 사실과 다르게 만든다("워크스페이스 스코프"만이 아니라 "워크스페이스 + 본인 소유" 가 됨). 그런데 이 plan 의 spec_impact 에는 그 파일이 없고, `spec-draft-integration-personal-owner.md` 의 "## 영향 — 다른 spec" 절에도 언급이 없다(§8 규칙 자체는 "워크플로우 어시스턴트의 통합 목록 도구와 노드 후보 제시" 를 "조회" 행에 귀속시켜 SoT 를 `4-integration.md` 로 삼겠다는 의도로 읽히지만, 그 사실이 `ai-assistant.md` 쪽에서 교차 참조되지 않는다). 이 문서는 §4.3.1 표를 "판정 조건의 전수 목록"으로 서술해 온 만큼, 이 서술이 이제 불완전해진다.
  - 제안: `spec-draft-integration-personal-owner.md` "## 영향 — 다른 spec" 에 `spec/3-workflow-editor/4-ai-assistant.md` 항목을 추가하고, §4.3.1 표의 `integration-selector`/`mcp-server-selector` 행과 §4.1 의 `list_integrations` 행에 "본인 personal 만(§8 판정 규칙)" 한 구절 + 링크를 보태거나, 최소한 ED-AI-39 Rationale 에 "2026-09-25: 워크스페이스 스코프 쿼리는 이제 `4-integration.md §8` 의 소유자 판정을 얹는다" 각주를 추가한다. `integration-personal-owner.md`/`spec-draft-integration-personal-owner.md` 의 spec_impact 리스트에도 반영.

## 요약

핵심 판정 규칙(«본인» = `created_by`, 역할 우위 없음, 404 존재 은닉, Organization 변경 Admin 이상)은 실제 사용자 결정·기각 대안이 함께 기록돼 있고(날짜·선택지 셋 인용이 구체적), 기존 RBAC 표(§3.2 "Integration (Personal) | 자기 것")·§9.1 의 기존 `RESOURCE_NOT_FOUND` 선례·rotate 의 락-재확인 이중 판정 패턴과 정합적이며, precheck 의 "받아들인 잔여"(유일성 제약이 존재를 드러내는 트레이드오프)도 §9.2 유일성 제약의 실제 근거로 뒷받침된다 — 코드 주석(`assertCanRotate` 부근)이 과거 기각된 advisory-lock 대안과의 차이를 스스로 명시하는 등, 전반적으로 Rationale 연속성에 대한 주의는 확인된다. 다만 두 지점에서 과거 결정과의 정합이 약하다: (1) 이 프로젝트가 두 차례의 실측(73개·15개 라우트 누락)을 거쳐 "가드 무조건 + fail-closed 캐너리" 로 옮겨간 원칙과 달리, 이번 소유자 판정은 다시 라우트/핸들러별 수동 호출로 설계돼 있어 신규 경로 추가 시 같은 누락이 재발할 구조적 위험이 있고 완결성 안전망이 계획에 없다; (2) `ai-assistant.md` 의 candidate-lookup 계약("워크스페이스 스코프")이 이번 구현으로 사실상 좁혀지는데 그 문서의 spec_impact·Rationale 갱신이 계획에 없다. 두 건 모두 CRITICAL 수준의 명시적 기각 대안 재도입은 아니지만(도메인이 다르고, 의도적 기각이라기보다 누락 가능성), 구현 착수 전에 보강할 가치가 있는 WARNING이다.
